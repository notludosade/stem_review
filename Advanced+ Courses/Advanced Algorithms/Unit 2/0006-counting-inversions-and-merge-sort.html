Counting Inversions & Merge Sort

A classic divide-and-conquer trick: piggyback a second computation on top of merge sort's existing structure, for free, because the merge step already does the comparisons you need.

← Lesson 5 Lesson 7 → Contents Glossary →

An inversion in an array is a pair of indices i < j where arr[i] > arr[j] — a pair that's "out of order" relative to each other. Counting inversions measures how far an array is from sorted (a sorted array has zero; a reverse-sorted array has the maximum, n(n−1)/2). The brute-force approach checks every pair in Θ(n²). This lesson derives an O(n log n) algorithm by noticing that merge sort's merge step already discovers every inversion that crosses the midpoint, as a side effect of the comparisons it does anyway.

The key observation

Observation Split the array into a left half L and right half R. Every inversion is one of three kinds: both indices in L, both in R, or one in each. The first two kinds are exactly the inversions counted by recursively solving the subproblems on L and R. The third kind — cross-inversions — are exactly what the merge step can detect, because merging L and R together requires comparing elements across the two halves in the first place.
How merge detects a cross-inversion During the merge of two already-sorted halves L and R, maintain pointers i (into L) and j (into R). At each step, if L[i] ≤ R[j], output L[i] and advance i — no inversion, since L[i] is correctly placed before R[j]. But if R[j] < L[i], output R[j] and advance j — and here's the count: since L is sorted, every remaining element from L[i] onward is also > R[j], meaning R[j] forms a cross-inversion with all of L[i], L[i+1], ..., L[end] at once. Add (length of L − i) to the inversion count right at that moment, and move on. Every cross-inversion gets counted exactly once, with no extra comparisons beyond what merge was already doing.
Algorithm — count-and-sort 
// Returns (sorted array, inversion count) for arr
function countInversions(arr):
    if length(arr) <= 1:
        return (arr, 0)
    mid = length(arr) / 2
    (L, countL) = countInversions(arr[0:mid])
    (R, countR) = countInversions(arr[mid:end])
    (merged, crossCount) = mergeAndCount(L, R)
    return (merged, countL + countR + crossCount)

// Merges two sorted arrays, counting cross-inversions
function mergeAndCount(L, R):
    result = [], i = 0, j = 0, crossCount = 0
    while i < length(L) and j < length(R):
        if L[i] <= R[j]:
            append L[i] to result; i += 1
        else:
            append R[j] to result; j += 1
            crossCount += (length(L) - i)   // R[j] inverts with all remaining L[i..]
    append remaining elements of L and R to result
    return (result, crossCount)
Why this is correct — reusing Lesson 5's proof shape Base case (length ≤ 1): zero inversions, trivially correct. Inductive hypothesis: countInversions correctly counts inversions for any array shorter than n. Inductive step: the recursive calls on L and R correctly count all within-L and within-R inversions by hypothesis; the separate direct argument above shows mergeAndCount correctly counts every cross-inversion exactly once. Since every inversion is within-L, within-R, or cross, and all three are accounted for, countL + countR + crossCount is the total. This is exactly Lesson 5's two-part shape: induction for the recursive calls, a direct proof for the combine step.
Runtime — Unit 1's tools, reapplied mergeAndCount does O(1) extra work per comparison beyond ordinary merge, so it's still Θ(n) at each level. The recurrence is T(n) = 2T(n/2) + Θ(n) — identical to merge sort's own recurrence from Unit 1. By the Master Theorem (Case 2, a=2, b=2, n^(log_b a)=n=f(n)), T(n) = Θ(n log n) — an exponential improvement over the Θ(n²) brute force, obtained by noticing a computation was already implicit in a comparison the algorithm was doing anyway.

Check your recall

No peeking back up — answer from memory first, then check.

1. Why are cross-inversions the only kind not already handled by the recursive calls on L and R?

Recursion on L only ever compares indices inside L, and likewise for R, so any pair straddling both halves is structurally outside what either recursive call could ever detect.

2. When R[j] < L[i] during the merge step, why does it form an inversion with every remaining element of L from index i onward?

Sortedness of L guarantees every element from L[i] onward is at least as large as L[i], which is already larger than R[j] — and since R[j]'s original index is to the right of the whole R-half but its value is smaller, each such pair is a genuine inversion.

3. Why does the inversion-counting algorithm have the same Θ(n log n) runtime as ordinary merge sort?

Adding a constant-time increment per merge comparison doesn't change the recurrence's asymptotic shape, so the Master Theorem gives the identical Θ(n log n) result as plain merge sort.

4. Fill in the blank: every inversion is within-L, within-R, or ___ — and the merge step is exactly what detects the third kind.

This three-way partition of all possible inversions is exactly what makes the recursive-plus-merge structure complete: nothing falls outside these three categories.

5. Fill in the blank: the cross-inversion counting trick only works because L is already ___ by the time the merge step runs on it, letting one comparison stand in for many.

Sortedness is what licenses jumping straight to "all remaining elements of L are also greater than R[j]" instead of checking each one individually.
