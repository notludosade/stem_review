Correctness by Strong Induction

Unit 1 built the tools to analyze how fast a recursive algorithm runs. This lesson builds the tool to prove it's actually correct — every divide-and-conquer proof in this unit is the same three-step induction argument wearing a different problem.

← Lesson 4 Lesson 6 → Contents Glossary →

CP2 taught recursion by tracing call stacks until the pattern felt intuitive — trust that the recursive call does its job, and build the current level's answer on top of it. That "trust the recursive call" move is not a leap of faith; it's an application of strong induction, and making it explicit is what turns "this seems to work on my test cases" into "this is provably correct on every input." Every divide-and-conquer algorithm in this unit gets the same treatment: a base case, an inductive hypothesis, and an inductive step that combines subproblem solutions correctly.

The three-part structure

Method — proving a recursive algorithm correct 1. Base case: show the algorithm is correct on the smallest input(s) it handles directly (no recursive call). 2. Inductive hypothesis: assume the algorithm is correct on every input strictly smaller than n (this is strong induction — you get to assume correctness for all smaller sizes, not just n−1). 3. Inductive step: show that, given correct answers to the subproblems (by the hypothesis), the algorithm's combine step produces a correct answer for size n.
Why strong induction, not ordinary induction Ordinary induction assumes correctness only for n−1 to prove n. Divide-and-conquer algorithms typically split n into pieces like n/2, which is not n−1 for any n > 2 — so the inductive hypothesis needs to cover every smaller size at once, which is exactly what strong induction (also called complete induction) provides. Every recursive algorithm whose recursive calls aren't on "one less" needs this stronger form.
Worked proof — binary search is correct Claim: binary search on a sorted array correctly finds target t, or correctly reports it's absent. Base case: array of size 0 — correctly reports absent (nothing to find). Array of size 1 — correctly compares the single element to t. Inductive hypothesis: binary search is correct on every array of size < n. Inductive step: on an array of size n, compare t to the middle element m. If t = m, done correctly. If t < m, the recursive call searches the left half — a strictly smaller array — and by the hypothesis returns a correct answer for it; sortedness guarantees t cannot be in the right half, so the left half's correct answer is the whole answer. Symmetric for t > m. Every case is covered, so by strong induction, binary search is correct for all n.
Worked proof — merge sort is correct (correctness only; runtime is Unit 1's Master Theorem) Base case: array of size 0 or 1 is trivially already sorted. Inductive hypothesis: merge sort correctly sorts every array of size < n. Inductive step: on size n, split into two halves, each of size < n; by the hypothesis, the recursive calls return each half correctly sorted. The remaining question is whether the merge step correctly combines two sorted arrays into one sorted array — a separate, non-recursive claim, proved directly: merge repeatedly takes the smaller of the two current front elements, so at every step the output so far is sorted and no smaller remaining element is skipped over. Since both the recursive calls (by hypothesis) and the merge step (by direct proof) are correct, size n is correct.
Why the "combine step" needs its own separate proof Strong induction only discharges the recursive calls — it says nothing about whether the non-recursive glue code is correct. Merge sort's proof above needed a second, ordinary (non-inductive) argument that the merge step itself is correct. This is the recurring shape of every divide-and-conquer correctness proof in this unit: induction handles "trust the subproblems," and a separate direct argument handles "the combine step is correct given trustworthy subproblem answers." Skipping the second part is the most common gap in an otherwise induction-shaped proof.

Check your recall

No peeking back up — answer from memory first, then check.

1. Why does proving a divide-and-conquer algorithm correct typically require strong induction rather than ordinary induction?

Ordinary induction's single "assume n−1" step doesn't cover a jump straight to n/2, so the hypothesis needs to hold for all smaller sizes simultaneously — exactly what strong induction provides.

2. In the merge sort correctness proof, what does the inductive hypothesis get to assume, and what does it leave unproven?

Strong induction only discharges the recursive calls; the merge step is non-recursive glue code that needs its own separate, direct correctness argument.

3. What is the most common gap in an otherwise induction-shaped correctness proof for a divide-and-conquer algorithm?

Induction covers "trust the subproblems"; it says nothing about whether the code that stitches subproblem answers together is itself correct, which needs a separate direct proof.

4. Fill in the blank: every correctness induction needs a ___ case proven directly, with no recursive call to lean on.

Without a directly-proven base case, the whole induction has nothing to anchor to, no matter how correct the inductive step is.

5. Fill in the blank: strong induction proves the recursive calls trustworthy, but the ___ step that stitches subproblem answers together always needs its own direct argument.

The non-recursive glue code — merging two sorted halves, for instance — sits outside what the inductive hypothesis covers and must be proven correct on its own terms.
