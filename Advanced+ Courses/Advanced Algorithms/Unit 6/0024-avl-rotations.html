AVL Rotations

An ordinary binary search tree's Θ(log n) search only holds if the tree stays balanced — a bad insertion order can degrade it to a Θ(n) linked list. AVL trees fix this by rebalancing automatically after every insertion and deletion.

← Lesson 23 Lesson 25 → Contents Glossary →

CP2+ Lesson 13 ("Binary Search Trees: Properties and Validation") established the BST invariant — every left subtree's keys are smaller, every right subtree's keys are larger — and relied on this to make search, insert, and delete all Θ(h), where h is the tree's height. That analysis quietly assumed h = Θ(log n). It isn't automatic: inserting keys 1, 2, 3, 4, 5 in increasing order into a plain BST produces a tree that's really a linked list, with h = Θ(n) and every operation degraded to Θ(n). An AVL tree (named for inventors Adelson-Velsky and Landis) is a BST that maintains h = Θ(log n) automatically, by rebalancing itself after every insertion and deletion.

The balance invariant

Definition For every node v in an AVL tree, define balance(v) = height(left subtree of v) − height(right subtree of v) (treating an empty subtree as height −1). The AVL invariant requires balance(v) ∈ {−1, 0, 1} for every node v, at all times. Whenever an insertion or deletion would violate this at some node, one or two rotations restore it before the operation is considered complete.
Why this invariant forces Θ(log n) height Let N(h) be the minimum number of nodes possible in an AVL tree of height h. A tree of height h has a root with two subtrees of height at least h−1 and h−2 (the most unbalanced the invariant allows), so N(h) ≥ 1 + N(h−1) + N(h−2) — the same recurrence shape as Fibonacci (Lesson 21), which grows exponentially in h. Since N(h) grows exponentially in h, h itself can grow no faster than logarithmically in n (inverting the exponential relationship) — so the balance invariant provably bounds height at Θ(log n), which is exactly what search, insert, and delete need to stay Θ(log n).

Rotations — restoring balance in O(1)

Right rotation (fixes a left-heavy imbalance) 
function rotateRight(y):
    x = y.left
    y.left = x.right
    x.right = y
    updateHeight(y)             // update child before parent — order matters
    updateHeight(x)
    return x                    // x is the new root of this subtree
A left rotation is the mirror image (swap left/right throughout). Both run in O(1): only a constant number of pointers and heights change, no matter how large the subtrees involved are.
The four imbalance cases After an insertion, walk back up from the inserted node to the root, checking balance(v) at each ancestor. If some node v has balance(v) = 2 (left-heavy) or −2 (right-heavy), one of four cases applies: Left-Left (balance(v.left) ≥ 0) — a single right rotation at v fixes it. Right-Right (mirror) — a single left rotation. Left-Right (balance(v.left) < 0) — a left rotation at v.left first, converting it to the Left-Left case, then a right rotation at v. Right-Left (mirror) — a right rotation at v.right first, then a left rotation at v. At most one of these (single or double) rotation is ever needed per insertion, since fixing the lowest unbalanced ancestor always restores the subtree to its pre-insertion height.
Why insertion only ever needs one rebalancing step After a single insertion, at most one node's subtree height actually increases along the path back to the root — once a rotation restores that subtree to its original height, every ancestor above it sees no height change at all, so no further rotations are triggered. This is why AVL insertion is O(log n) overall: O(log n) to walk down and insert, plus O(1) work (at most one rotation, single or double) to rebalance, not O(log n) rotations. (Deletion is a similar walk back up, but can require rebalancing at multiple ancestors in the worst case — still O(log n) total, since there are only O(log n) ancestors to check.)
Runtime summary Search, insert, and delete are all Θ(log n) worst case — a guarantee an ordinary unbalanced BST cannot make, since its worst case (a degenerate, linked-list-shaped tree) is Θ(n).

Check your recall

No peeking back up — answer from memory first, then check.

1. Why can an ordinary (non-self-balancing) binary search tree degrade to Θ(n) search time?

Search cost is proportional to tree height, and an unlucky insertion order can make that height linear rather than logarithmic.

2. Why does the AVL balance invariant (balance factor in {−1, 0, 1} at every node) guarantee Θ(log n) height?

Inverting an exponential lower bound on node count as a function of height is exactly what produces a logarithmic upper bound on height as a function of node count.

3. Why does a single AVL insertion only ever require rebalancing at most one subtree (a single or double rotation), rather than rotations all the way up the tree?

Restoring the original height at the lowest imbalance point means every ancestor's own height calculation is unaffected, stopping propagation immediately.

4. Fill in the blank: an AVL tree restores its balance invariant after an insertion or deletion using one or two ___ , each of which runs in O(1) time.

Rotations are the sole mechanism AVL trees use to restore balance, and each touches only a constant number of pointers.

5. Fill in the blank: by keeping every node's balance factor within {−1, 0, 1}, an AVL tree guarantees height Θ(___), which keeps search, insert, and delete all worst-case efficient.

This is the entire payoff of maintaining the invariant — logarithmic height under any sequence of insertions and deletions, not just favorable ones.
