Fenwick Trees (Binary Indexed Trees)

Segment trees solve range-sum-with-updates in general. When the only aggregate needed is sum, a Fenwick tree solves the same problem with a smaller, simpler structure — built entirely from a bit trick on the index itself.

← Lesson 22 Lesson 24 → Contents Glossary →

Lesson 22's segment tree solves prefix-sum-with-updates (and range-min, range-max, and more) using an explicit binary tree with 2n−1 nodes. A Fenwick tree (also called a binary indexed tree, or BIT) solves the narrower but extremely common case — prefix sums with point updates — using only an n-element array and no explicit tree structure at all. The "tree" is implicit, encoded entirely in how array indices relate to each other via their binary representations.

The key idea — indices encode implicit ranges

Setup A Fenwick tree over an array of size n is itself just an array tree[1..n] (1-indexed — this matters for the bit trick below). Each tree[i] stores the sum of a specific range of the original array, ending at index i, whose length is determined by the lowest set bit of i: tree[i] covers the range (i − lowbit(i), i], where lowbit(i) = i & (−i) extracts the lowest set bit of i as a number (e.g. lowbit(12) = lowbit(0b1100) = 0b0100 = 4, so tree[12] covers indices 9 through 12).
Why lowbit(i) = i & (−i) works In two's-complement representation, −i is the bitwise NOT of i plus 1. Flipping every bit and adding 1 turns every trailing zero of i into a trailing zero of −i too, but flips the lowest set bit and everything above it — so i & (−i) cancels every bit except that lowest set bit, leaving exactly it. This single expression is what lets both prefix-sum queries and point updates be implemented as simple loops that repeatedly add or subtract lowbit(i), with no recursion and no explicit child/parent pointers to store or follow.
Prefix sum query — O(log n) 
function prefixSum(i):                 // sum of arr[1..i]
    sum = 0
    while i > 0:
        sum += tree[i]
        i -= lowbit(i)                 // jump to the range just before this one
    return sum
Range sum query(l, r) = prefixSum(r) − prefixSum(l − 1), same as with ordinary prefix sums — the only difference from a plain array of prefix sums is that updates no longer cost Θ(n).
Point update — O(log n) 
function update(i, delta):             // add delta to arr[i]
    while i <= n:
        tree[i] += delta
        i += lowbit(i)                 // advance to the next range that includes i
Why both loops terminate in Θ(log n) steps Each step of the query loop strips the lowest set bit of i entirely (i −= lowbit(i) always clears that bit), so after at most log₂(n) steps i reaches 0 — the number of set bits in i's binary representation bounds the loop. Each step of the update loop adds lowbit(i), which increases i's value but is also bounded by log₂(n) iterations before exceeding n, by a similar bit-level argument. Both bounds trace directly back to the same lowbit trick, which is why a Fenwick tree needs no explicit tree traversal to hit the same Θ(log n) bound a segment tree gets from tree depth.
Why "Fenwick" beats "segment tree" here — and when it doesn't For pure prefix-sum-with-point-update problems, a Fenwick tree is preferred over a segment tree: roughly half the memory (n integers instead of ~2n tree nodes), a handful of lines of iterative code instead of recursive build/query/update functions, and in practice a smaller constant factor. But a Fenwick tree only naturally handles associative, invertible operations like sum (subtraction undoes addition) — it does not extend to range-min or range-max the way a segment tree does, since there's no way to "undo" a min. When the aggregate is min or max, or the problem needs range updates (not just point updates), reach for the segment tree from Lesson 22 instead.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does tree[i] store in a Fenwick tree?

Each tree[i]'s range length is exactly lowbit(i), which is what lets the query and update loops navigate without any explicit tree pointers.

2. Why does the expression i & (−i) isolate the lowest set bit of i?

The two's-complement negation mechanism is exactly what makes i & (-i) a reliable lowest-set-bit extractor for any positive integer.

3. When should a segment tree be preferred over a Fenwick tree, even though the Fenwick tree is smaller and simpler?

The Fenwick tree's simplicity comes at the cost of only supporting invertible, associative operations like sum — min and max don't fit that requirement.
