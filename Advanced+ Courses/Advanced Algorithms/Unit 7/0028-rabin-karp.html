Rabin-Karp & Rolling Hashes

KMP avoids redundant comparisons by exploiting the pattern's own structure. Rabin-Karp takes a completely different approach: hash every window of the text, and only bother comparing characters when hashes collide.

← Lesson 27 Lesson 29 → Contents Glossary →

KMP (Lesson 27) solves substring search by never re-examining a text character, using structural information from the pattern itself. Rabin-Karp solves the same problem with an entirely different idea: compute a hash of the pattern, compute a hash of every length-m window of the text, and only fall back to an actual character comparison when two hashes match. The technique hinges on a rolling hash — a hash function that can be updated from one window to the next in O(1), rather than recomputed from scratch.

The rolling hash

Definition Treat a string s[0..m−1] as a number in some base b (typically a prime near the alphabet size), where hash(s) = (s[0]·bᵐ⁻¹ + s[1]·bᵐ⁻² + ... + s[m−1]·b⁰) mod q, for some large prime modulus q (to keep values bounded and reduce collisions). This is exactly a polynomial evaluated at b, treating each character's code as a coefficient.
Why this specific formula supports O(1) updates Sliding the window one position to the right — dropping s[0] and adding a new character c at the end — can be expressed algebraically: newHash = ((hash − s[0]·bᵐ⁻¹)·b + c) mod q. Subtracting s[0]·bᵐ⁻¹ removes the departing character's contribution (it was the highest-order term); multiplying by b shifts every remaining term up one power of b, matching their new positions in the window; adding c inserts the new character at the lowest-order position. Every step is O(1) arithmetic (modular subtraction, multiplication, addition), so the hash for the next window is computed directly from the previous one — no re-scanning of the window's characters at all.
Algorithm 
function rabinKarp(text, pattern):
    n, m = |text|, |pattern|
    patternHash = hash(pattern)
    windowHash = hash(text[0..m-1])
    bM = b^(m-1) mod q                      // precomputed once
    for i in 0..n-m:
        if windowHash == patternHash:
            if text[i..i+m-1] == pattern:   // verify: hashes can collide
                report match at position i
        if i < n - m:
            windowHash = ((windowHash - text[i]*bM) * b + text[i+m]) mod q
Why the verification step is non-negotiable Two different strings can hash to the same value — a collision — since the hash compresses an m-character string into a single number modulo q, an inherently lossy operation. Skipping verification and trusting a hash match alone would silently produce false positives. With q chosen large enough (and ideally randomized per run, to defend against an adversarial input crafted to force collisions), collisions are rare in practice, so verification is cheap on average — but it is still required for correctness, not merely a defensive nicety.
Runtime Average case Θ(n+m): each window's hash update is O(1), and verification (O(m)) is only triggered on a hash match, which is rare with a good modulus. Worst case (many or adversarial collisions) degrades to Θ(nm), identical to the naive approach — a real risk that motivates KMP's guaranteed-linear alternative whenever worst-case time matters, not just average case.
Where rolling hashes go beyond single-pattern search The same rolling-hash idea generalizes past "find one pattern": comparing rolling hashes of many substrings supports finding the longest common substring between two strings, checking whether two large chunks of text are identical without a full character comparison, or (combined with binary search on substring length) efficiently finding the longest repeated substring within a single text — problems where KMP's pattern-specific failure function doesn't directly apply, but a hash-based comparison does.

Check your recall

No peeking back up — answer from memory first, then check.

1. What makes a hash function "rolling" in the Rabin-Karp sense?

The O(1) incremental update — dropping the outgoing character's contribution and shifting in the incoming one — is exactly what "rolling" refers to.

2. Why must Rabin-Karp verify a match with an actual character comparison even after a hash match?

Hashing is a lossy compression of the string, so collisions are always possible in principle, making direct verification necessary for correctness.

3. Why can Rabin-Karp degrade to Θ(nm) in the worst case, matching the naive algorithm?

Frequent collisions force frequent full verifications, which is exactly what erases the average-case speed advantage over the naive approach.
