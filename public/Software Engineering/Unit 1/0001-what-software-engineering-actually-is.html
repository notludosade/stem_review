What Software Engineering Actually Is

Why writing correct code and engineering a system that stays correct for years are two different skills.

← Course Contents Lesson 2 → Contents Glossary →

Computer Programming 1 and 2 taught you to write correct code — code that produces the right output for a given input, in Python, JavaScript, Java, or C++. This course starts from a different question: what happens to that code after you write it? Who else has to read it? What happens when the requirements change six months later? What happens when it breaks at 2 a.m. and someone who didn't write it has to fix it? Software engineering is the set of practices, tools, and judgment calls that answer those questions.

Programming versus engineering

Why "it works" isn't the finish line A script that solves a problem once, on one machine, for one person, only needs to be correct. A system that a team builds, that runs in production, that other engineers will modify long after you've moved to a different project, needs to be correct and maintainable, and understandable to someone who didn't write it, and resilient to the requirements changing. Programming is about the first property. Software engineering is about all of them at once, over time.
Example A weekend script that renames a folder of files only has to work today, on your laptop, for this one batch of files — if it's ugly or undocumented, the cost is nearly zero. A billing system at a company has to keep working correctly for years, survive being read and modified by dozens of engineers who never met each other, and handle requirement changes (new tax rules, new currencies, new payment providers) without being rewritten from scratch. The same programming skill produces both — but only one of them additionally demands engineering.

The dimensions that change everything

Scale A program one person writes and only that person reads has no coordination cost. The moment a second engineer touches the same codebase, you need conventions, shared understanding, and a way to combine each person's changes without one silently overwriting the other's — which is exactly the problem version control (Unit 2) exists to solve.
Lifetime Code that will be deleted next week can tolerate shortcuts that code expected to run for ten years cannot. Most professional software has a lifetime measured in years, and the total cost of a system is dominated by the years engineers spend reading, fixing, and extending it after it first shipped — not by the time spent writing the first version.
Changing requirements A program built for a fixed, known problem can be optimized entirely around that problem. Real software rarely stays still — the business adds a feature, a regulation changes, a competitor forces a pivot — so an engineer has to design systems that can absorb change without collapsing, which is a genuinely different design goal than just solving today's problem well.

Non-functional requirements: the properties "does it work" doesn't capture

Why correctness alone isn't a complete spec A login() function that returns the right answer for every test case can still be a serious engineering failure if it takes eight seconds under real traffic, if a single crash takes down the whole application, or if the only person who understands it just quit. These properties — performance, reliability, maintainability, security — are called non-functional requirements, and professional software engineering treats them as first-class design goals, not afterthoughts.

What this course actually covers

Each unit ahead targets one piece of the gap between "I can write correct code" and "I can build software professionally": version control (Unit 2), automated testing (Unit 3), design patterns (Unit 4), architecture and technical debt (Unit 5), code review (Unit 6), and the agile process teams use to coordinate all of it (Unit 7). None of it replaces the programming skill from CP1 and CP2 — it's what turns that skill into something a team can build on.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the key difference between programming and software engineering, as this lesson defines them?

Programming targets correctness for a given input; engineering additionally targets correctness that survives time, teams, and changing requirements.

2. Why does a one-off personal script tolerate shortcuts that a production billing system cannot?

Scale (other engineers) and lifetime (years of use) are exactly the two dimensions that turn shortcuts into real costs.

3. What is a non-functional requirement?

Non-functional requirements describe how well a system behaves — speed, uptime, security — separately from whether a given input produces the right output.

4. Fill in the blank: most of the total cost of professional software comes from its ___, since engineers spend years reading, fixing, and extending a system after it first ships.

The years a system spends in maintenance dwarf the time spent writing its first version.

5. Fill in the blank: real software has to be designed to absorb requirement ___, since businesses and regulations rarely stay fixed for a system's whole lifetime.

Designing only for today's fixed problem is a programming mindset; designing to absorb future change is an engineering one.
