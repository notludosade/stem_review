Redundancy, Failover, and Designing for Failure

Every piece of hardware in every cloud provider's data center will eventually fail — a disk, a power supply, an entire building's cooling system. The goal was never to prevent that. It's to make sure no single failure takes the whole system down with it.

← Lesson 17 Unit 7, Lesson 19 → Contents Glossary →

Lesson 8 measured availability in fractions of a percent. This lesson is about the actual architectural technique that earns those numbers: never letting any one failure — a crashed server, a dead disk, an entire building losing power — be the thing standing between your application and staying online.

Regions and availability zones

Definition A cloud provider's global footprint is organized into regions (broad geographic areas, like "US East" or "Southeast Asia"), and each region contains multiple availability zones (AZs) — physically separate data center facilities within that region, each with its own independent power, cooling, and networking, but connected to each other by low-latency links. The physical separation matters: a fire, a power grid failure, or a cooling system malfunction in one AZ's building has no way to reach a different AZ's building.

Redundancy: never just one

Definition Redundancy means running more than one independent copy of anything critical, so that one copy failing doesn't take down the whole system. This is a generalization of an idea already in this course: Lesson 8's durability came from storing multiple copies of data across separate hardware; Lesson 11's load balancer only works because there's more than one server behind it; Lesson 13's managed database failover depends on a standby copy existing in the first place.
Definition Failover is the automatic process of switching from a failed component to a healthy redundant one — with the emphasis on automatic. A failover process that requires a human to notice the outage and manually intervene is much slower, and much less reliable, than one a system performs on its own within seconds.
Worked example: surviving a whole availability zone going down An application deploys its web server fleet (Lesson 16's auto scaling group) across three separate availability zones instead of one, all behind a single load balancer (Lesson 11). If one entire AZ loses power, every server in it fails its health check simultaneously — and the load balancer, already built to route around any unhealthy server, simply stops sending traffic to that AZ and continues serving all users from the remaining two. Users experience, at most, a few seconds of elevated latency while the load balancer detects the failure — not an outage. Nothing about this required an engineer to be paged, let alone to intervene.

The mindset: no single point of failure

Why "design for failure" beats "try to prevent failure" At the scale a cloud provider operates, hardware failures aren't rare edge cases — they're a routine, expected, daily occurrence somewhere across a provider's global footprint. Trying to build a system that never experiences a single failed disk or server is not a realistic goal. The realistic goal is ensuring no single point of failure — no one component whose failure, alone, is capable of taking the whole system down — exists anywhere in the architecture. Every reliability technique in this course, from Lesson 8's storage durability through this lesson's multi-AZ redundancy, is really the same idea applied at a different layer: assume failure will happen, and make sure it's never fatal on its own.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the relationship between a region and an availability zone?

A region is the broader area; AZs are the physically independent facilities within it that avoid sharing critical infrastructure.

2. Why does physical separation between availability zones matter?

Independent physical infrastructure is exactly what prevents one AZ's failure from cascading into another's.

3. Why does automatic failover matter more than a failover process that requires manual intervention?

Speed and reliability are exactly why automatic failover is preferred — human response time is a real bottleneck.

4. Fill in the blank: a single component whose failure alone is capable of taking down an entire system is called a ___.

Eliminating single points of failure, not preventing every possible failure, is the realistic goal of resilient design.

5. Fill in the blank: running more than one independent copy of a critical component, so that one copy failing doesn't take down the whole system, is called ___.

Redundancy is the general principle behind storage durability, load balancing, and database failover alike.
