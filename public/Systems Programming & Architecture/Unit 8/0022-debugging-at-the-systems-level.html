Debugging at the Systems Level

Lesson 9 mentioned that a segfault is often the visible symptom of a dangling pointer. This lesson finally explains exactly what a segfault is, who kills the program and why, and the debugger's basic mental model for finding the line responsible instead of guessing.

← Unit 7, Lesson 21 Lesson 23 → Contents Glossary →

Every unit so far named a way C code can go wrong: a stack address returned past its frame's lifetime (Lesson 5), a use-after-free (Lesson 9), an out-of-bounds array write (Lesson 8). This lesson is about what actually happens when one of those bugs is triggered, and how to find exactly which line caused it.

Segmentation fault: the kernel refusing an illegal access

Definition A segmentation fault ("segfault") happens when a process tries to access memory outside its own valid address space (Lesson 4) — dereferencing a wild or dangling pointer, or writing far past an array's bounds into unmapped memory. The kernel (Unit 5), which enforces every process's address-space isolation, detects the illegal access and immediately terminates the process, rather than letting it silently corrupt memory it has no right to touch. A core dump is an optional file the OS can write at that exact moment, capturing the crashed process's full memory and register state for later inspection — a snapshot of exactly what everything looked like the instant it died.
Worked example Lesson 9's use-after-free — free(p); printf("%d", *p); — dereferences p after its memory has been returned to the allocator. Most of the time this doesn't segfault at all: the freed memory is still mapped, just logically invalid, so the program reads garbage and keeps running. It segfaults specifically when that address happens to fall in memory the process no longer has mapped at all — which is exactly why the same buggy line can run fine a thousand times and then suddenly crash on the thousand-and-first, depending entirely on what the allocator happened to do with that memory in between.

The debugger's mental model

Definition A breakpoint pauses a running program at a specific line, handing control to the programmer instead of letting it run to completion or to a crash. Once paused, a backtrace (or stack trace) lists every currently active stack frame — literally Lesson 5's stack, made visible — showing the exact chain of function calls that led to this exact point, innermost call first. Reading a backtrace after a crash means starting at the top (where it actually died) and reading downward through who called whom, rather than guessing from the symptom alone.
Why "add print statements everywhere" doesn't scale Print-statement debugging works for small, easily reproducible bugs, but it breaks down exactly where it matters most: a bug that only shows up rarely (like Lesson 17's race conditions), or a crash whose cause is several function calls removed from where the symptom appears. A debugger's actual advantage isn't that it's smarter — it's that it lets you pause at the exact moment something is wrong and inspect every variable, every register, and the entire call chain as it genuinely was, instead of only the handful of values you thought in advance to print. That "pause and inspect real state, don't guess" habit is the same instinct this unit's remaining lessons build on directly.
