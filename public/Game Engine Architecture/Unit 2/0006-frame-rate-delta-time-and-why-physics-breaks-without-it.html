Frame Rate, Delta Time, and Why Physics Breaks Without It

Lesson 5 assumed update() gets some notion of elapsed time. This lesson makes that concrete — and shows the single most common bug new engine programmers write, in one line of code.

← Lesson 5 Unit 3, Lesson 7 → Contents Glossary →

Imagine a character that should walk at 5 meters per second. The tempting first line of code is position += 5; inside update(). It looks correct, and it even runs — but it silently ties the character's actual speed to how fast the game happens to be rendering, which is exactly the bug this lesson exists to name and fix.

Delta time: the missing multiplier

Definition Frame rate (frames per second, FPS) is how many times per second the loop completes. Delta time (often written dt) is the amount of real time, in seconds, that elapsed since the last frame — roughly 1 / FPS when frame rate is steady. Any quantity that should change at a rate per second — movement, rotation, a timer counting down — must be multiplied by delta time inside update(), so that the actual amount it changes each frame scales with how much real time that frame represents. 
// WRONG: moves 5 units every *frame*, not every *second*
position += 5;

// RIGHT: moves 5 units every *second*, regardless of frame rate
position += 5 * delta_time;

Worked example Without delta time, position += 5 adds exactly 5 units every frame. At 30 FPS that's 150 units per second; at 120 FPS it's 600 units per second — the same character moves four times faster purely because a player's GPU is faster, which is obviously wrong. With delta time, position += 5 * dt adds 5/30 ≈ 0.167 units per frame at 30 FPS, or 5/120 ≈ 0.042 units per frame at 120 FPS — thirty and one-twenty tiny steps respectively, but both add up to exactly 5 units after one real second, on any hardware.
Why this bug is so easy to miss Code that forgets delta time still runs, still moves something, and looks completely fine to the one person testing it on their own machine at a fairly consistent frame rate. The bug only becomes obvious on a different machine, under a different load, or during a frame-rate dip — exactly the conditions a developer's test environment often doesn't reproduce. This is why "multiply movement by delta time" isn't a style preference; it's the difference between a simulation that's correct by construction and one that happens to look right on one machine, one time.

1. What does multiplying a movement value by delta time actually accomplish?

Delta time converts a per-frame change into a true per-second rate.

2. What happens to position += 5; (no delta time) if frame rate doubles from 30 to 60 FPS?

Without delta time, more frames per second directly means more per-frame additions per second — faster movement.

3. Why can this bug survive testing on a developer's own machine without ever being noticed?

The bug is silent — it produces plausible-looking motion, just at the wrong rate under different conditions.

Delta time is exactly the elapsed-seconds value defined at the top of this lesson.
