The Core Game Loop

Every subsystem from Unit 1 has to run over and over, dozens of times a second, for the entire lifetime of the program. There's exactly one piece of code responsible for making that happen — and it's a lot simpler than it sounds.

← Unit 1, Lesson 3 Lesson 5 → Contents Glossary →

A word processor waits for you to type, then reacts. A web server waits for a request, then responds. A game can't just sit and wait — the world has to keep moving even if the player does nothing at all, an enemy needs to keep walking, gravity needs to keep pulling. That requires something running continuously, all on its own.

Three steps, repeated forever

Definition The game loop is the top-level loop that runs for the entire life of a game, repeatedly executing three phases in order: process input (read what the player did since last time), update (advance the game world — physics, AI, animation, game logic), and render (draw the current state of the world to the screen). It runs this cycle continuously, typically dozens of times per second, until the player quits. 
// the shape of nearly every game loop ever written
while (game_is_running) {
    process_input();   // read keyboard/controller/mouse
    update(delta_time); // advance the world by one step
    render();           // draw the current state
}

Worked example Say the player holds the "move right" key with nothing else happening. Every single frame, process_input() notices the key is still down, update() moves the character's position a little further right and advances any walk animation, and render() draws the character in its new spot. Sixty times in one second, that's sixty tiny position changes — which is exactly what makes "holding a direction" look like smooth, continuous motion instead of a single jump.
Why render always comes last Rendering has to come after update, every single frame, because the screen should always show the world after this frame's changes — never a half-updated or stale state. If a loop rendered before updating, the screen would always be showing last frame's world one step late. This ordering constraint seems obvious in isolation, but it becomes one of the trickiest things to get right once physics and animation both need to affect what gets drawn, which Unit 4 and Unit 5 come back to.

Check your recall

No peeking back up — answer from memory first, then check.

1. What are the three phases of a basic game loop, in order?

Input is read first, the world is advanced next, and the result is drawn last.

2. Why does a game need a continuously running loop, unlike a word processor that just waits for input?

A game world must keep moving on its own, unlike an application that's purely reactive.

3. Why must render always run after update in the loop, not before?

Rendering must reflect the freshest state, which only exists after update has run.

4. Fill in the blank: the top-level loop that repeatedly processes input, updates the world, and renders it for the entire life of a game is the ___.

This is the term defined at the top of the lesson.

5. Fill in the blank: the phase of the loop responsible for advancing physics, AI, and animation is called ___.

Update is the phase that advances the state of the game world.
