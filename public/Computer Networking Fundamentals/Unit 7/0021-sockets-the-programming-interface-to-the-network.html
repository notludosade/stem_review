Every protocol this course has covered — TCP, UDP, HTTP — is ultimately just a set of rules. Somewhere, actual code has to open a connection, send bytes, and receive bytes, obeying those rules. That code talks to the operating system through a socket — and once you understand what a socket actually is, writing a simple networked program is a lot closer to the functions and loops you already know from Computer Programming 1 than it might sound.

What a socket is

Definition A socket is the operating system's programming interface for network communication — an object your code creates and uses to send and receive data over a network, hiding the actual packet-building, addressing, and Transport-layer bookkeeping from Units 2 through 5 behind a much simpler set of function calls. Creating a socket is conceptually similar to opening a file: you get a handle back, you read from and write to it, and you close it when you're done — except a socket's other end is a network connection instead of a location on disk.

The basic socket operations

Definitions Bind associates a socket with a specific local port number (Lesson 14), telling the operating system "traffic addressed to this port belongs to this program." Listen puts a socket into a state where it's waiting for incoming connection attempts, used only by a server. Connect is what a client calls to actually initiate a connection to a specific address and port — for a TCP socket, this is the call that triggers Lesson 15's three-way handshake to happen, entirely behind the scenes.
A Minimal TCP Server and Client, Side by Side
Python 
# create a TCP socket
sock = socket(AF_INET, SOCK_STREAM)

# bind to a local port, then listen for connections
sock.bind(("0.0.0.0", 5050))
sock.listen()

# accept() blocks until a client connects
conn, addr = sock.accept()
data = conn.recv(1024)
conn.send(b"Hello, " + data)
conn.close()
Python 
# create a TCP socket
sock = socket(AF_INET, SOCK_STREAM)

# connect() triggers the three-way handshake
sock.connect(("127.0.0.1", 5050))

sock.send(b"World")
reply = sock.recv(1024)
print(reply)  # prints: Hello, World
sock.close()
Reading the example against what you already know sock.bind(("0.0.0.0", 5050)) is Lesson 14's port concept, made literal in code — this program is now the one listening on port 5050 for this device. sock.listen() and sock.accept() are the server side of Lesson 15's handshake: accept() blocks (pauses execution) until a client's connect() call completes the three-way handshake, then returns a new connection object to actually use. send() and recv() are just writing to and reading from that connection — and because this is TCP, everything Lesson 15 covered (ordering, reliability, retransmission) is happening underneath these two calls automatically, without a single extra line of code from you.
Why the socket API hides so much Every concept from Units 2 through 5 — encapsulation, IP addresses, TCP's handshake and retransmission — is still happening every time this code runs. The socket API's entire value is that none of it needs to be written by hand: connect() alone triggers packet construction, routing, and a full three-way handshake, and send()/recv() alone handle sequencing and retransmission. This is layering (Lesson 5) paying off directly for you as a programmer — your code only has to think at the Application layer, in terms of "send these bytes, receive those bytes," while the operating system's networking stack handles every layer underneath.

TCP sockets vs. UDP sockets

Everything above used SOCK_STREAM, which creates a TCP socket — connection-oriented, reliable, exactly matching Lesson 15. A UDP socket (SOCK_DGRAM) skips connect(), listen(), and accept() entirely, since UDP is connectionless (Lesson 16): a UDP socket just sends and receives individual datagrams, each one addressed independently, with no handshake and no guarantee any particular one arrives.

1. What is a socket, at a high level?

A socket is the software handle a program uses for network I/O, similar in spirit to a file handle.

2. What actually happens, in terms of earlier lessons, when a client's code calls connect() on a TCP socket?

connect() is the client-side trigger for TCP's full three-way handshake, hidden behind one function call.

3. Why does a UDP socket skip listen(), accept(), and connect() entirely?

UDP's connectionless nature (Lesson 16) means there's no handshake step for those socket calls to perform.

4. Fill in the blank: the socket operation that associates a socket with a specific local port number, telling the OS which program owns that port, is ___.

Bind is what a server calls to claim a specific port before listening on it.
