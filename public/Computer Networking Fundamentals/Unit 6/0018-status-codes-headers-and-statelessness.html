Status Codes, Headers, and Statelessness

The three-digit number at the top of every response, the metadata riding alongside it, and the surprising fact that HTTP forgets you the instant a response is sent.

← Lesson 17 Lesson 19 → Contents Glossary →

Lesson 17 showed a response starting with HTTP/1.1 200 OK. This lesson is what that number actually communicates, what the headers alongside it typically carry, and a property of HTTP that surprises almost everyone the first time they learn it: the protocol has no memory at all.

Status codes

Definition A status code is the three-digit number in a response's status line, summarizing what happened to the request, grouped by its first digit: 2xx means success; 3xx means redirection (the resource has moved, follow a different URL); 4xx means a client error (the request itself was wrong somehow); and 5xx means a server error (the request was fine, but the server failed to handle it).
CodeMeaningCategory
200 OKThe request succeeded2xx success
301 Moved PermanentlyResource moved to a new URL — follow it3xx redirection
404 Not FoundNo resource exists at this URL4xx client error
403 ForbiddenThe server understood, but refuses to allow it4xx client error
500 Internal Server ErrorSomething went wrong on the server's own side5xx server error
Why the first-digit grouping matters more than memorizing every code There are dozens of specific status codes, but a program (or a person) doesn't need to memorize all of them to react sensibly — the first digit alone tells you the general category of what happened, which is often enough to decide the next move. A well-written program checking a response can reasonably say "if it's in the 2xx range, proceed; if it's 4xx, my request was wrong somehow and retrying identically won't help; if it's 5xx, the problem is on the server's end and retrying later might work" — useful logic derived entirely from one digit, without needing to look up the exact meaning of, say, 418 versus 429.

Headers, revisited

Lesson 17 introduced headers as key-value metadata. A few show up constantly enough to be worth naming directly: Content-Type tells the receiver what kind of data the body contains (like text/html or application/json), so it knows how to interpret it; Content-Length tells the receiver exactly how many bytes the body contains, so it knows when the message ends; and Cookie — the mechanism this lesson's next section leans on — lets a client send back a small piece of data the server previously asked it to store.

Statelessness

Definition HTTP is stateless: the server does not automatically remember anything about a previous request when handling a new one, even from the exact same client. Each request is processed as a completely independent event, with no built-in memory linking it to any request that came before it.
Why this is genuinely surprising, and how sites "remember" you anyway If HTTP has no memory, how does a website keep you logged in as you click from page to page? The answer is a workaround, not a built-in HTTP feature: after you log in, the server sends back a cookie — a small piece of data, via the Set-Cookie header — that your browser then automatically re-sends with every subsequent request to that same site, via the Cookie header. The server isn't remembering you between requests at all; instead, you (via your browser) are re-presenting proof of who you are on every single request, and the server checks that proof fresh, every single time. What feels like a continuous, remembered session is actually hundreds of individually stateless requests, each one carrying its own repeated evidence.
Worked example: logging in, request by request You submit a login form: a POST request with your username and password. The server verifies them and responds with Set-Cookie: session=abc123. Every later request your browser makes to that site — clicking a link, loading an image — automatically includes Cookie: session=abc123, and the server checks that value fresh on every single one of those independent, stateless requests to confirm you're still logged in. Delete that cookie, and the very next request arrives with no proof of anything — the server has no separate memory of you to fall back on.

Check your recall

No peeking back up — answer from memory first, then check.

1. A response comes back with status code 404. What general category does this fall into, and what does that mean?

404 (Not Found) is a 4xx client error — the requested resource simply doesn't exist at that URL.

2. What does HTTP being "stateless" mean?

Each HTTP request is processed as an independent event with no built-in memory of prior requests.

3. Given that HTTP has no built-in memory, how does a website actually keep you "logged in" across many page loads?

Cookies are a workaround built on top of stateless HTTP, not a violation of statelessness — the server still checks fresh proof on every request.

4. Fill in the blank: the header telling the receiver what kind of data the body contains (like text/html or application/json) is ___.

Content-Type tells the receiver how to interpret the bytes in the body.
