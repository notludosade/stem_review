TCP — Reliable, Ordered Delivery and the Three-Way Handshake

Lesson 4 pointed out that packet switching means packets can arrive late, out of order, or not at all. TCP is the protocol that quietly fixes all three problems before your program ever sees the data.

← Lesson 14 Lesson 16 → Contents Glossary →

TCP (Transmission Control Protocol) is one of the two Transport-layer protocols this course covers (UDP, its opposite in almost every way, is Lesson 16). TCP's entire reason for existing is turning an unreliable, packet-switched network into something that behaves, from a program's point of view, like a reliable, ordered stream of bytes — even though nothing about the underlying network actually guarantees that on its own.

What "reliable" and "ordered" actually mean here

Definition TCP is connection-oriented: before any data is exchanged, both sides perform a setup process (the handshake, below) to establish a shared connection. Every byte TCP sends is tracked using a sequence number, which lets the receiving side reassemble data in the correct order even if segments arrive out of order, and detect if any segment never arrived at all. When the receiver successfully gets data, it sends back an acknowledgment (ACK) confirming what it received; if the sender doesn't get an acknowledgment within an expected time, it assumes the segment was lost and performs a retransmission — sending it again.
Why this matters to you as a programmer, even though you never write this code yourself When you write code that opens a TCP connection and reads data from it, you get to assume — correctly — that the bytes you read arrive in the exact order they were sent, with nothing missing and nothing duplicated. That guarantee is not free; it's TCP doing real, continuous work underneath your program: numbering, acknowledging, and retransmitting as needed, entirely invisibly. Lesson 16's UDP deliberately skips all of this — understanding what TCP is actually doing for you here is what makes it possible to understand why a program would ever choose to give that guarantee up.

The three-way handshake

Definition The three-way handshake is the fixed three-message exchange TCP uses to establish a connection before any actual data is sent, confirming both sides are ready and synchronizing their starting sequence numbers: the client sends a SYN (synchronize) message; the server responds with a combined SYN-ACK (acknowledging the client's SYN while sending its own SYN back); and the client responds with a final ACK, at which point the connection is considered established and either side may begin sending actual data.

Why three messages, not two A connection is between two independent programs, and each side needs to both propose and confirm its own starting sequence number. Two messages (SYN, then ACK) would only let the client confirm the server's number — the server would never get confirmation that its own SYN was received. The middle message is deliberately combined (SYN-ACK) purely as an efficiency shortcut — the server's own SYN and its acknowledgment of the client's SYN are sent together in a single message instead of two separate ones — but conceptually, both sides are still proposing and confirming a starting number each, which is why it's routinely described as three-way even though only three messages, not four, are needed.

Closing a connection

Ending a TCP connection is a comparable, similarly deliberate exchange (commonly a four-message sequence, since either side might have more data to finish sending before it's ready to close), rather than either side just silently going quiet. That deliberateness is the same theme running through this whole lesson: TCP treats "did we actually agree this happened" as something worth spending a few extra messages on, at both the start and the end of a connection, in exchange for the reliability guarantee described above.

1. What does TCP's sequence number let the receiving side do?

Sequence numbers are what make reordering and loss detection possible, both essential to TCP's reliability guarantee.

2. What triggers a TCP retransmission?

Missing acknowledgment within the expected window is what triggers TCP to assume loss and retransmit.

3. Why is the three-way handshake called "three-way" even though both sides are proposing and confirming a sequence number, which sounds like it should need four messages?

Combining the server's SYN and ACK into one SYN-ACK message is an efficiency shortcut that reduces the exchange to three actual messages.

4. Fill in the blank: a protocol like TCP that requires a setup process (like a handshake) before any data is exchanged is described as ___.

Connection-oriented protocols establish a shared connection state before exchanging data — the opposite of Lesson 16's connectionless UDP.
