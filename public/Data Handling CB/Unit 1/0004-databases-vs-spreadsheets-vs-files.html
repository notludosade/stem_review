Databases vs. Spreadsheets vs. Files

Three different tools all store data in rows and columns — but they're built for different jobs, and picking the wrong one causes real pain later. This lesson gives you the mental model for choosing correctly.

← Lesson 3 Lesson 5 → Contents Glossary →

Units 2 and 3 of this course teach spreadsheets and SQL databases in depth. Before diving into either, it's worth understanding what each tool is actually for — and what a plain data file (like CSV or JSON) is, since it's the format that usually moves data between the two.

The row-and-column mental model

Shared structure Spreadsheets, database tables, and CSV files all share the same basic shape: rows (individual records — one customer, one order, one measurement) and columns (fields — the same attribute recorded for every row, like "email" or "order date"). If you understand this shape, you already understand 80% of what all three tools are organizing.

Spreadsheets

What they're built for A spreadsheet (Excel, Google Sheets) is built for small-to-medium datasets a single person or small team edits directly, interactively, with formulas recalculating live as data changes. Strengths: fast to start, visual, no setup required, great for one-off analysis and quick calculations. Weaknesses: struggles past roughly hundreds of thousands of rows, has no built-in way to enforce that data stays consistent across multiple people editing at once, and formulas referencing the wrong cell fail silently rather than raising an error.

Databases

What they're built for A database (the subject of Unit 3) stores data in formally defined tables with enforced rules — a "quantity" column can be forced to always be a number, never blank. Strengths: handles millions or billions of rows, supports many people and programs reading and writing at once safely, and lets you ask precise questions (via SQL) without manually scrolling. Weaknesses: more setup and technical overhead than a spreadsheet, and not built for the highly visual, drag-and-drop interactivity a spreadsheet offers.

Plain data files: CSV and JSON

What they're built for A CSV (comma-separated values) file is the simplest possible structured-data format: plain text, one row per line, values separated by commas. It's the universal export/import format — nearly every spreadsheet and database can read and write CSV, which is exactly why it's used to move data between them. JSON (JavaScript Object Notation) is a semi-structured text format built from key-value pairs and nested lists, common in exports from web services and APIs (recall Lesson 1's semi-structured data category) — more flexible than CSV's strict rows-and-columns shape, at the cost of not opening cleanly in a spreadsheet without some conversion.
Why the choice actually matters Picking a spreadsheet for a dataset that's really a multi-person, constantly-updated, million-row operational system leads to broken formulas, version-conflict chaos ("final_v3_ACTUAL.xlsx"), and silent data corruption. Picking a full database for a one-time analysis of 200 rows is needless overhead. The right default: use a spreadsheet for small, single-analyst, interactive work; use a database when multiple people or programs need reliable, simultaneous access to larger data; use CSV/JSON as the transfer format connecting the two, or as a lightweight way to store a small dataset without either tool's overhead.

Check your recall

No peeking back up — answer from memory first, then check.

1. What structural feature do spreadsheets, database tables, and CSV files all share?

The rows-and-columns shape is the one structural idea shared across all three tools, even though their capabilities differ sharply.

2. Why would a database generally be a better choice than a spreadsheet for a million-row dataset edited simultaneously by many people?

Scale and safe concurrent access are exactly where spreadsheets start to break down and databases are specifically designed to hold up.

3. Why is CSV commonly used to move data between a spreadsheet and a database?

CSV's simplicity is exactly what makes it universally importable and exportable, which is why it works as a lowest-common-denominator transfer format.

4. Fill in the blank: the semi-structured, key-value-based text format common in web service and API exports, more flexible than CSV's strict rows-and-columns shape, is called ___.

JSON's nested key-value structure gives it more flexibility than CSV, at the cost of not opening cleanly as a simple table.

5. Fill in the blank: in the shared row-and-column mental model, a row is an individual record, and a ___ is an attribute recorded consistently for every row.

Rows are individual records; columns are the fields recorded the same way across every one of those records.
