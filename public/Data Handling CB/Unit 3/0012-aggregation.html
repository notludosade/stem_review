Aggregation

GROUP BY is SQL's pivot table: it collapses many rows into one summary row per group, and pairs with aggregate functions to answer "total by category" questions directly in the database.

← Lesson 11 Lesson 13 → Contents Glossary →

Unit 2's Lesson 7 built a pivot table to answer "total sales by region" without writing per-region formulas. SQL answers the same class of question with GROUP BY.

Aggregate functions

Functions COUNT(column) counts non-null values (or COUNT(*) counts rows regardless of nulls). SUM(column), AVG(column), MIN(column), MAX(column) — the same operations as Unit 2's spreadsheet functions, applied to a query result instead of a spreadsheet range.

GROUP BY

Syntax SELECT region, SUM(order_total) FROM orders GROUP BY region; collapses the orders table into one row per distinct region, with SUM(order_total) computed within each group. Every column in SELECT that isn't itself an aggregate function must appear in GROUP BY — SQL needs to know which column defines the groups, since it can't display an individual order_id next to a summed total that spans many orders.

HAVING: filtering groups, not rows

Syntax SELECT region, SUM(order_total) AS total FROM orders GROUP BY region HAVING SUM(order_total) > 10000; — HAVING filters after grouping, on the aggregated value itself, e.g. "only show regions whose total exceeds $10,000." WHERE can't do this, because WHERE filters individual rows before grouping happens — it has no access to a group's summed total, since that total doesn't exist yet at the point WHERE is applied.
Why WHERE and HAVING aren't interchangeable This follows directly from Lesson 10's query execution order: WHERE filters raw rows before grouping; GROUP BY then collapses the surviving rows into groups and computes aggregates; HAVING filters those already-computed group results. Trying to write WHERE SUM(order_total) > 10000 fails, because at the point WHERE runs, no sum has been computed yet — there's nothing to compare.
Worked example combining JOIN, GROUP BY, and HAVING SELECT customers.region, COUNT(*) AS order_count, SUM(orders.order_total) AS total_revenue FROM orders INNER JOIN customers ON orders.customer_id = customers.customer_id WHERE orders.order_total > 0 GROUP BY customers.region HAVING COUNT(*) > 5; — join orders to customers to get each order's region, keep only orders with a positive total, group by region, count orders and sum revenue per region, then keep only regions with more than 5 qualifying orders.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does GROUP BY region do to a query's results?

GROUP BY's defining behavior is collapsing many rows into one row per distinct group value.

2. Why can't WHERE be used to filter on a condition like "SUM(order_total) > 10000"?

WHERE runs before grouping/aggregation, so it has nothing to compare an aggregate value against yet — that's exactly what HAVING is for.

3. What is the rule for which columns can appear in SELECT alongside a GROUP BY clause?

Non-aggregate columns must be part of the grouping, or SQL has no consistent single value to display for that column within a collapsed group.

4. Fill in the blank: the clause used to filter grouped results based on an aggregate value, applied after GROUP BY, is ___.

HAVING is specifically for filtering on aggregate results, unlike WHERE which filters raw rows before grouping.

5. Fill in the blank: the SQL clause that collapses rows into one summary row per distinct value of a chosen column is ___.

GROUP BY is the clause responsible for defining the groups that aggregate functions then compute over.
