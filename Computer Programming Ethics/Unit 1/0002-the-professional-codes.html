The Professional Codes

Two documents turn "be a good programmer" into something you can actually check a pull request against.

Lesson 3 → Contents Glossary →

Lesson 1 showed a function that lied about what it did. This lesson gives you the actual reference documents the software field uses to name and judge that kind of failure — not company-specific policy, but two widely-recognized professional codes you can point to regardless of where you work.

The ACM Code of Ethics and Professional Conduct

The ACM Code of Ethics, most recently revised in 2018, is organized as a short list of general principles, each phrased as an imperative. In summary, a computing professional should:

  • Contribute to society and to human well-being, acknowledging that all people are stakeholders in computing.
  • Avoid harm — the one from Lesson 1. Harm includes unjustified physical, financial, or psychological injury, and unauthorized destruction or disclosure of information.
  • Be honest and trustworthy — don't misrepresent what a system does, including through omission.
  • Be fair and take action not to discriminate.
  • Respect the work required to produce new ideas, inventions, creative works, and computing artifacts — credit and licensing matter.
  • Respect privacy.
  • Honor confidentiality.

These aren't laws with penalties attached — they're a professional's own definition of "good work," the same way a doctor has one. Reading them side by side with actual code decisions is the point of this course.

Definition A principle (as used here) is a general commitment — "avoid harm" — that has to be interpreted for a specific decision. It's not a rule with a single correct mechanical answer; it's a lens you apply.

The Software Engineering Code

A second, older, more specific document exists: the ACM/IEEE-CS Software Engineering Code of Ethics and Professional Practice (1999). Where the general ACM Code applies to anyone in computing, this one is written specifically for people who build software, organized around eight areas of obligation: the public, client and employer, the product itself, judgment, management, the profession, colleagues, and self (ongoing learning). Its "Product" principle is the most directly relevant to code you write today: engineers should strive for high quality, acceptable cost, and a reasonable schedule, while making sure significant risks are disclosed, not buried.

Honesty shows up in error handling, too

"Be honest and trustworthy" isn't only about big decisions like the delete-account example. It shows up in small, everyday code — like what happens when something goes wrong.

Silently swallowing the problem 
try:
    charge_card(amount)
except Exception:
    pass  # nothing logged, nothing surfaced
print("Payment successful!")
Honest about failure 
try:
    charge_card(amount)
    print("Payment successful!")
except PaymentError as e:
    logger.error("Payment failed for order %s: %s", order_id, e)
    raise

The first version tells the user "Payment successful!" even when the payment failed — it's not lying on purpose in the way a dark pattern is, but the effect on the user is the same: the code claims something happened that didn't. The second version does the harder, more honest thing: it only claims success when success actually occurred, and it makes the failure visible instead of hiding it.

Why it matters here A silent except: pass is one of the most common ways ordinary, well-intentioned code becomes dishonest by accident. Nobody set out to lie to the user — but that's what the program does.

Check your recall

1. How many general principles does the 2018 ACM Code of Ethics list?

Contribute to society, avoid harm, be honest and trustworthy, be fair, respect the work behind new ideas, respect privacy, honor confidentiality — seven in total.

2. What is the Software Engineering Code's relationship to the general ACM Code of Ethics?

Published in 1999 by ACM and IEEE-CS jointly, it's a distinct document narrowed to software engineering practice, organized around eight areas of obligation.

3. What specifically makes the first charge_card example on this page dishonest?

The bare except: pass discards the failure entirely, so the unconditional "Payment successful!" print statement runs regardless of what actually happened.

The "Product" principle calls for high quality and disclosure of significant risks — not burying problems to hit a schedule.
