Reading Code for Ethical Red Flags

The syntax changes from language to language. The red flags don't.

Lesson 4 → Contents Glossary →

This lesson turns Lessons 1 and 2 into a scanning habit: a short list of patterns that should make you slow down and look closer, no matter which of the four languages this course covers you're reading. Five to know, to start:

  • Hardcoded secrets — API keys, passwords, or tokens written directly into source code instead of loaded from a secure config.
  • Unsanitized input reaching a query or command — user-typed text pasted directly into SQL, a shell command, or eval.
  • Silent exception handling — an empty catch/except block that hides a failure instead of surfacing it (Lesson 2).
  • Plaintext sensitive data — passwords or personal data stored or logged without hashing/encryption.
  • Missing authorization checks — a sensitive action (delete, refund, admin action) with no check that the caller is actually allowed to do it.

The second one — unsanitized input reaching a query — is worth seeing in all four languages side by side, because it's the same vulnerability wearing four different outfits.

Definition An injection vulnerability is a flaw where untrusted input is inserted directly into a command, query, or expression, letting an attacker change what that command does. It's been on the OWASP Top 10 list of critical web risks for over a decade.
Python — login query 
query = ("SELECT * FROM users WHERE username = '" + username +
         "' AND password = '" + password + "'")
cursor.execute(query)
Java — login query 
String query = "SELECT * FROM users WHERE username = '" + username +
    "' AND password = '" + password + "'";
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(query);
JavaScript — login query 
const query = "SELECT * FROM users WHERE username = '" + username +
  "' AND password = '" + password + "'";
db.query(query);
C++ — login query 
std::string query = "SELECT * FROM users WHERE username = '" + username +
    "' AND password = '" + password + "'";
sqlite3_exec(db, query.c_str(), callback, 0, &errMsg);

Four languages, four syntaxes, one mistake: the username and password are stitched straight into the query text. Someone typing ' OR '1'='1 as a username can rewrite what the query does — no password required. The fix isn't language-specific either: send the input separately from the query, and let the database driver keep the two apart.

Python — fixed with a parameterized query 
query = "SELECT * FROM users WHERE username = ? AND password = ?"
cursor.execute(query, (username, password))

Java, JavaScript, and C++ each have their own equivalent — a PreparedStatement, a parameterized query builder, a bound-parameter API — but the shape of the fix is identical everywhere: never let user input become part of the query text itself.

Why it matters here This is the payoff of learning to scan for patterns instead of memorizing per-language rules. Once you can spot "input glued into a command string" in one language, you can spot it in all four — and in languages this course never covers.

Check your recall

1. What do all four login-query examples above have in common?

Different syntax, same mistake: username and password are pasted directly into the query string in every version.

2. What is the general name for this class of vulnerability?

It's been on the OWASP Top 10 for over a decade precisely because it's this common and this language-independent.

3. What does the fixed, parameterized version of the query do differently?

The ? placeholders keep the query's structure fixed; the database driver binds the values without letting them change what the query means.

4. Fill in the blank: pasting untrusted input directly into a query or command is called an ___ vulnerability.

See the definition box above — this exact term is what you'll see it called in OWASP and most security literature.

Every mainstream database driver in all four languages this course covers supports parameterized (or "prepared") queries.
