Collect Only What You Need

The easiest way to protect data you didn't collect: don't collect it.

Lesson 8 → Contents Glossary →

Units 1 and 2 were about protecting data that's already in your system — hashing passwords, validating input, keeping secrets out of source code. Unit 3 starts one step earlier: deciding what data your program collects in the first place. Every field you ask for is something you now have to secure, store correctly, and eventually be responsible for if it leaks.

The signup form that asks too much

Collecting everything "just in case" 
signup_form_fields = [
    "email", "password", "full_name",
    "date_of_birth", "home_address",
    "phone_number", "gender"
]
Collecting what the product actually needs 
signup_form_fields = ["email", "password"]
# date_of_birth only requested later, if the feature
# that actually needs it (age-restricted content) is used

A newsletter signup doesn't need a home address. A to-do list app doesn't need a phone number. Each unused field in the first version is pure downside: it doesn't make the product better, but it's one more thing a breach can expose, one more thing a user has to trust you with, one more line in a privacy policy nobody reads. This isn't a hypothetical concern — it's a named principle in data protection law: the EU's GDPR, Article 5(1)(c), requires personal data to be "adequate, relevant and limited to what is necessary" for the purpose it's collected for, a rule referred to as data minimization.

Definition Data minimization is the practice of collecting only the data a system actually needs to do its job — not data that might be useful someday, might help with a future feature, or is simply easy to ask for on the same form.

"We might need it later" is not a reason

It's tempting to add a field because a future feature might use it. But data sitting unused is a liability that starts accumulating the moment it's collected, while the feature that would justify it may never ship. The better order is: build the feature, then add the field it actually needs — collected with a clear, specific reason a user could be told if they asked.

Why it matters here This connects directly to "avoid harm" and "respect privacy" from Lesson 2. A field you never collected can never leak, can never be subpoenaed, can never be sold to a data broker after a company changes hands — it's the one privacy protection that requires no ongoing effort to maintain.

Check your recall

1. According to this lesson, what's the main downside of collecting an unused field?

An unused field doesn't improve the product, but it does add something a breach can expose and something the user has to trust you with.

2. What does GDPR Article 5(1)(c) require of personal data collection?

This is the "data minimization" principle — data collected must be adequate, relevant, and limited to what's necessary for its stated purpose.

3. What does this lesson recommend instead of collecting a field for a possible future feature?

Data sitting unused is a liability from the moment it's collected — better to add the field when there's a specific, shippable reason for it.

4. Fill in the blank: collecting only the data a system actually needs to do its job is called ___ ___.

See the definition box above — GDPR Article 5(1)(c) is the best-known legal statement of this principle.

5. Fill in the blank: the EU regulation cited on this page, whose Article 5(1)(c) requires data to be limited to what's necessary, is called the ___.

The General Data Protection Regulation — its influence extends well beyond the EU, since many companies apply its rules globally rather than maintaining separate systems.
