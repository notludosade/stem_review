Validating Input Before You Trust It

The injection fix from Unit 1 was one example of a much bigger rule.

Lesson 6 → Contents Glossary →

Lesson 3 fixed one specific problem — user input glued into a SQL query. The general principle behind that fix is bigger than SQL: anything that enters your program from outside it is untrusted until it's checked. That includes form fields, URL parameters, uploaded files, API responses, even data read back out of your own database if another program could have written to it.

What "checked" actually means

Validation isn't one thing — it's a small set of questions asked of every piece of external input before it's used:

  • Type — is this actually a number, if a number is expected?
  • Range — is this number, or string length, within a sane bound?
  • Format — does this look like a real email address, date, or ID?
  • Allowed values — if only three options are valid, is this one of them?
Trusting the input as-is 
def set_age(age):
    user.age = age  # could be -5, "banana", or 9999999
Checking before using it 
def set_age(age):
    if not isinstance(age, int) or not (0 <= age <= 130):
        raise ValueError(f"Invalid age: {age!r}")
    user.age = age

The fixed version doesn't just avoid a crash — it refuses to let obviously-wrong data ever reach the rest of the program. That matters even when nobody is attacking anything: bad input arrives from bugs, from other systems, from users who mistype a field, just as often as it arrives from someone probing for a weakness.

Definition Input validation is the practice of checking that external data meets expected type, range, format, and value constraints before it's used — rejecting or correcting it if it doesn't, rather than trusting it by default.

Validate at the boundary, trust inside

A useful mental model, drawn from the OWASP Input Validation Cheat Sheet: draw a line around your program. Outside that line — anything from a user, a network request, a file — is untrusted. Validate right at the boundary, the moment data crosses in. Once it's validated, the rest of the program can trust it, instead of every function re-checking everything defensively forever.

Why it matters here Skipping validation is rarely a deliberate ethical failure the way a dark pattern is — it's usually just skipped for speed. But the OWASP Top 10's "Injection" category, and a long list of real breaches, trace back to exactly this: input that should have been checked at the boundary and wasn't.

Check your recall

1. According to this lesson, when should external input be treated as untrusted?

The rule applies to any external source — form fields, files, API responses — not just user-typed text, and applies by default, not after a failure.

2. What does the fixed set_age example check, beyond just "is this a number"?

Type alone isn't enough — an age of 9999999 is a valid integer but not a valid age, so the range check 0 <= age <= 130 catches it.

3. In the "boundary" mental model, where should validation happen?

Validating at the boundary means the rest of the program can trust the data without re-checking it everywhere — the check happens once, at the point of entry.
