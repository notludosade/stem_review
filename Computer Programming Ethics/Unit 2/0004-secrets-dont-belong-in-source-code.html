Secrets Don't Belong in Source Code

The first red flag from Lesson 3, in depth: why a hardcoded key is worse than it looks.

Lesson 5 → Contents Glossary →

Unit 1 ended with a list of five red flags to scan for. This unit takes each one further, starting with the first: secrets — API keys, database passwords, signing keys — written directly into source code instead of loaded from somewhere secure.

Python — hardcoded key 
STRIPE_API_KEY = "sk_live_51H8x9K2eZvKYlo2C..."

client = StripeClient(STRIPE_API_KEY)
Java — hardcoded key 
String stripeApiKey = "sk_live_51H8x9K2eZvKYlo2C...";

StripeClient client = new StripeClient(stripeApiKey);
JavaScript — hardcoded key 
const STRIPE_API_KEY = "sk_live_51H8x9K2eZvKYlo2C...";

const client = new StripeClient(STRIPE_API_KEY);
C++ — hardcoded key 
const std::string stripeApiKey = "sk_live_51H8x9K2eZvKYlo2C...";

StripeClient client(stripeApiKey);

This doesn't look dangerous — it compiles, it works in testing, and it's tempting because it's the fastest way to get something running. The danger shows up the moment this file reaches version control. GitHub's own secret scanning documentation exists specifically because committed keys are found and abused so often — automated scanners watch public repositories for exactly this pattern. And even a private repo isn't safe forever: deleting the line in a later commit doesn't remove it from git history, where it stays fully readable to anyone with repo access, indefinitely.

Definition A secret is any credential — API key, password, signing key, access token — that grants access to something and must not be readable by people who shouldn't have that access. An environment variable is a value set outside the program (by the operating system or a hosting platform), read at startup instead of written into the source.
Python — loaded from the environment 
import os

STRIPE_API_KEY = os.environ["STRIPE_API_KEY"]
client = StripeClient(STRIPE_API_KEY)

The key itself now lives outside the source file entirely — set in the hosting platform's configuration, a local .env file that's excluded from version control, or a dedicated secrets manager. Java's System.getenv("STRIPE_API_KEY"), JavaScript's process.env.STRIPE_API_KEY, and C++'s std::getenv("STRIPE_API_KEY") all do the same job: read the secret at runtime instead of storing it in code that gets committed, copied, and shared.

Why it matters here This connects straight back to Lesson 1's "avoid harm" and "respect confidentiality": a leaked payment API key isn't a hypothetical, it's a direct path to real financial harm for whoever's account it belongs to — and it happens through code that "worked fine" for the person who wrote it.

Check your recall

1. Why isn't deleting a hardcoded key in a later commit enough to fix the problem?

Version control keeps every prior version of every file by design — the key remains fully readable in history unless the repo's history itself is rewritten and force-pushed, which is disruptive and easy to skip.

2. What does the fixed version of the example load the API key from?

os.environ[...] in Python, System.getenv(...) in Java, process.env... in JavaScript, and std::getenv(...) in C++ all read the same kind of value: one set outside the program.

3. Why does GitHub run secret scanning on public repositories?

Automated scanners exist on both sides — GitHub scans to warn maintainers, and attackers run their own scanners hoping to find a key first.

4. Fill in the blank: any credential that grants access and must stay unreadable to unauthorized people is called a ___ (as defined on this page).

API keys, passwords, signing keys, and access tokens are all examples of secrets.

5. Fill in the blank: a value set outside the program and read at startup, instead of written into the source, is called an ___ ___.

Every language in this course reads them slightly differently, but the concept — configuration kept outside committed code — is identical.
