Error Messages That Tell the Truth

Two different audiences see an error message, and they need two different amounts of detail.

Lesson 11 → Contents Glossary →

Lesson 2 covered the basic honesty problem: don't silently swallow an error and claim success anyway. This lesson goes one level deeper — once you've decided to surface a failure, what you show depends entirely on who's looking at it, and getting this wrong is a mistake in both directions.

Too vague to be useful 
except Exception:
    return {"error": "Something went wrong."}
Too detailed to be safe 
except Exception as e:
    return {"error": str(e), "traceback": traceback.format_exc(),
            "query": failed_query, "db_host": DB_HOST}
Honest to the user, detailed to the developer 
except Exception as e:
    error_id = log_error_with_details(e, traceback.format_exc())
    return {"error": "We couldn't process that request.",
            "reference_id": error_id}

The first version is honest that something failed, but useless for a user trying to figure out what to fix — did they mistype a field, or is the server down? The second version is useful for debugging but hands an attacker a database hostname, a raw SQL query, and internals they were never supposed to see. The third version splits the difference correctly: the user gets an honest, actionable message and a reference number; the full technical detail goes somewhere only the development team can see it.

Definition Information disclosure is a security weakness where a system reveals internal details — stack traces, file paths, database structure, software versions — that help an attacker understand and exploit it. It's listed among the OWASP Top 10's broader "Security Misconfiguration" category.

Honest doesn't mean unfiltered

It's worth being precise about what "honest error messages" from Lesson 2 actually means. It does not mean showing the user everything the system knows about the failure. It means never claiming something succeeded when it didn't, and never hiding that a failure happened at all. Within those two boundaries, there's a real design decision about how much detail belongs in front of the user versus in a log only the team can see.

Why it matters here Getting this wrong in either direction causes real harm: a too-vague error frustrates and confuses a genuine user trying to get help, while a too-detailed one hands an attacker a map of your system. A reference ID pattern like the good example gives support staff enough to look up the real error without exposing it publicly.

Check your recall

1. What's the problem with the "Something went wrong" error message on its own?

It's honest that something failed, but a user has no way to tell whether it was their mistake or a server problem.

2. What's the risk of returning a full traceback and database host directly to the user?

This is information disclosure — internal details that help someone understand and exploit the system, not information the user asked for.

3. What does the fixed version give the user instead of the full error detail?

The full technical detail is logged separately (Lesson 11 covers logging it safely), and only the reference ID connects the user's report to it.
