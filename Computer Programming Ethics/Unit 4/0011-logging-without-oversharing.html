Logging Without Oversharing

Lesson 10 pushed the detail into a log. This lesson is about what belongs in that log — and what still doesn't.

Lesson 12 → Contents Glossary →

It's tempting to think of the internal log as a safe place to put everything, since the user never sees it. That's true relative to the user — but Lesson 8 already established that logs are a second copy of your data with their own access list, retention period, and export paths, often less carefully controlled than the primary database. A full stack trace including live request data can put exactly the sensitive fields Unit 3 spent three lessons protecting right back into an unprotected file.

Logging the exception object directly 
except Exception as e:
    logger.error(f"Payment failed: {e}")
    # str(e) on a database error can include the full failed query,
    # which may contain the customer's card number and billing address
Logging a structured, scrubbed summary 
except Exception as e:
    logger.error("Payment failed", extra={
        "error_type": type(e).__name__,
        "order_id": order.id,
        "amount": order.amount,
    })
    # the exception's own message/args are deliberately left out

The difference isn't "log less" — the second version is arguably more useful, because error_type and order_id are exactly what you'd search logs for later. The difference is choosing what goes in, field by field, instead of dumping whatever an exception object happens to contain and hoping it's nothing sensitive.

Definition Log scrubbing is the practice of removing or masking sensitive fields — passwords, tokens, card numbers, full request bodies — before a message is written to a log, rather than trusting that sensitive data will never end up in a log statement by accident.

Structured beats freeform

Notice the good example doesn't build a sentence with an f-string — it passes a dictionary of named fields. This is structured logging, and it has a security benefit beyond being easier to search: a developer writing logger.error("Payment failed", extra={...}) has to consciously list each field, which makes it much harder to accidentally interpolate an entire object — and everything nested inside it — into a log line without noticing.

Why it matters here Every field logged is a field someone with log access can see — which, at most companies, is a much larger group than the people with production database access. Deciding what goes into a log is the same "collect only what you need" discipline from Lesson 7, applied to a second, easy-to-forget data store.

Check your recall

1. Why is logging the raw exception object risky, even though users never see logs directly?

Lesson 8's "log leak" idea applies directly here — the log is a second copy of data with its own, often weaker, protections.

2. What does the good example log instead of the raw exception message?

error_type, order_id, and amount are useful for debugging without carrying whatever an exception's own message happened to contain.

3. What security benefit does structured logging (named fields) have over an f-string sentence?

An f-string can silently absorb an entire object's contents; a dictionary of named fields makes each piece of included data explicit.
