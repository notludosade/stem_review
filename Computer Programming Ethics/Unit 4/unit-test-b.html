1. A login form shows only "Error." when a submission fails, with no other detail anywhere. What's wrong with stopping there?

Being truthful that a failure happened isn't the same as being useful — the user still can't tell what to do next.

2. Fill in the blank: an error response that hands back a full traceback, a database hostname, and a raw failed query is an example of ___ ___ — exposing internal details useful to an attacker.

This falls under OWASP's broader "Security Misconfiguration" category — internals that help an attacker understand and exploit the system.

3. A file-upload endpoint throws an unexpected exception. Answer both parts:

(a) Fill in the blank: instead of the raw exception, the response the user sees should include a short, honest message plus a ___ ___ that support staff can use to look up the real error.

(b) Where should the full traceback and internal details actually go?

(a) The reference ID is what connects a user's honest-but-vague error to the full detail without exposing it publicly. (b) The full technical detail belongs in a log only the team can see, searchable via that reference ID.

4. A developer says, "It's fine to log anything, users can't read our logs anyway." What's the flaw in that reasoning?

"Users can't see it" doesn't mean the log is safe — it's a second copy of data with its own, often less carefully controlled, access list.

5. Answer both parts about what belongs in a log entry for a failed payment:

(a) Which field should most likely be left out of the log entirely?

(b) Fill in the blank: the general practice of removing or masking sensitive fields before anything is written to a log is called log ___.

(a) A raw exception's message can carry far more than intended, including a failed query with sensitive data embedded in it. (b) That deliberate removal of sensitive fields before logging is log scrubbing.

6. A developer writes logger.error(f"Failed: {e}") instead of passing named fields in a dictionary. What risk does the f-string version specifically introduce?

An f-string interpolates whatever an object's string form happens to contain; naming fields explicitly avoids that silent overshare.

7. Answer both parts about a payment-authorization check that can't reach its verification service:

(a) Which behavior is fail-closed?

(b) Fill in the blank: a system that defaults to letting a request through when it hits an unresolved error is described as ___.

(a) Denying on error keeps the check enforced instead of silently letting an unverified transaction through. (b) Letting things proceed by default on an unresolved error is the definition of fail-open.

8. What's the specific danger in choosing fail-open for a security check purely to avoid annoying users during downtime?

A convenience-driven fail-open default removes a safety check exactly when it's most likely to be needed — during an outage or attack.

9. Answer both parts about deciding between fail-open and fail-closed for a specific system:

(a) Fill in the blank: fail-closed is correct for a locked door, but a ___ ___ is the classic example designed to fail open during a power outage instead.

(b) What is the right way to decide which failure mode a given system should use?

(a) A fire exit trades a security gap for safety during an emergency — the counterexample to "fail-closed is always right." (b) Neither default is universally correct; the choice has to be reasoned through for what's actually being protected.

10. Answer both parts about what "honest" error handling actually requires:

(a) Which of these actually breaks the honesty requirement, regardless of how little detail is shown?

(b) Fill in the blank: honest error handling means never claiming success falsely and never hiding that a ___ happened at all — everything else is a design choice about how much detail to show.

(a) Faking a success response is dishonest no matter how the rest of the message is worded. (b) Those two boundaries — no false success, no hidden failure — are the actual honesty requirement.
