When Code Should Refuse to Run

Sometimes the most honest thing a program can do is stop.

Lesson 13 → Contents Glossary →

Every lesson in this unit assumed the program keeps running after something goes wrong — it just needs to fail honestly. But some failures are serious enough that continuing at all is the actual mistake. A permissions check that can't reach its database, a payment system that can't confirm a charge went through, an access-control library that fails to load: in each case, "keep going anyway" quietly removes a safety check the rest of the system was relying on.

Fail-open: errors let the request through 
def is_authorized(user, resource):
    try:
        return permissions_service.check(user, resource)
    except ServiceUnavailable:
        return True  # don't block the user if the check fails
Fail-closed: errors deny by default 
def is_authorized(user, resource):
    try:
        return permissions_service.check(user, resource)
    except ServiceUnavailable:
        logger.error("Permission check unavailable", extra={"user_id": user.id})
        return False  # deny access when the check itself can't run

The fail-open version was probably written to avoid annoying users during a permissions-service outage — a reasonable-sounding goal. But it means the permission check silently stops enforcing anything the moment it's needed most: during an actual outage or attack, when the service might be unavailable precisely because something is already wrong. The fail-closed version denies access on error, which is inconvenient during an outage but never silently grants access it shouldn't.

Definition Fail-closed (or "fail-secure") means a system defaults to the safer, more restrictive state when it encounters an error it can't resolve. Fail-open means it defaults to letting things proceed. Which one is correct depends entirely on what's guarded — a locked door should fail closed; a fire exit should fail open.

This isn't a universal rule

Fail-closed isn't automatically "more ethical" than fail-open — that's exactly why the fire-exit example exists. A building's electronic door locks are deliberately designed to fail open during a power outage, because trapping people inside during an emergency is worse than a security gap during a blackout. The judgment call is about which failure mode does less harm for this specific system, and that has to be reasoned through deliberately — not defaulted to out of convenience, in either direction.

Why it matters here A fail-open default chosen to avoid a support ticket, without thinking through what's actually being protected, is a decision made for the developer's convenience at the expense of whoever the check exists to protect. Making the choice explicit — and logging when it happens, as the fixed example does — turns an invisible default into a decision someone can review.
