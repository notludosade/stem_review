Unit 7 Test — Version B

Code as a Professional Artifact. 10 points across every lesson in this unit — 5 questions worth 1 point, 5 worth 1 point split across two parts. Score 90% or higher to clear this unit.

1. A new hire says, "Once the CI pipeline is green, human code review is just a formality we keep out of habit." Based on this lesson, how would you respond?

The lesson's argument is that nearly every mistake in this course was made by one developer alone — a second reviewer applying these patterns is cheap and effective, not a formality CI can replace.

2. Two reviewers on a team have a habit of approving any pull request within a minute of it opening, commenting only "tests green, approved." A pull request that silently begins logging full request bodies passes through this way. What is this lesson's diagnosis of that habit?

A rubber-stamp approval checks that tests pass, not whether sensitive data is being logged — exactly the gap this lesson warns against.

3. During review, a developer pushes back hard when a reviewer questions why a new "device fingerprint" field was added, and the reviewer backs down and approves it to avoid conflict. Answer both parts.

(a) What professional obligation, first introduced in Lesson 2, does the reviewer compromise by backing down?

(b) Fill in the blank: the reviewer's original question — whether the device fingerprint field is actually needed right now — was a legitimate check for ___ ___, the same concept from Lesson 7.

(a) Lesson 2's obligation to give honest, substantiated review feedback doesn't disappear just because the author pushes back. (b) Questioning an unexplained new field is precisely a data-minimization check.

4. Fill in the blank: a short document that records a decision's context, the options that were considered, and the reasoning behind the final choice — kept alongside the code rather than buried in a chat thread — is what this lesson calls an ___ ___ ___ (ADR).

This is the lesson's definition box, word for word — the ADR keeps a decision's reasoning durable and easy to find later.

5. A developer pins a dependency to an older version for a specific, deliberate reason, but doesn't record that reason anywhere. Months later, another developer upgrades it during routine maintenance, reintroducing the original problem. What does this lesson say caused this?

The lesson's exact example is a dependency pinned for a reason — undocumented, it reads as neglect rather than intent, so it gets silently reverted.

6. A pull request comment reads "# skip validation here" with nothing else, versus a second version that reads "# Skipping range validation: this value was already validated upstream in the ingest service, so re-checking here is redundant." Answer both parts.

(a) Which comment satisfies this lesson's standard for a useful comment?

(b) Fill in the blank: a comment that only restates ___ the code already does — without adding the reasoning behind it — fails this lesson's bar for a useful comment.

(a) The first comment adds nothing beyond what the code line already shows; the second preserves reasoning that isn't visible in the code. (b) The lesson's repeated contrast is a comment that only restates "what" versus one that explains "why."

7. A team is choosing what demographic categories an evaluation dataset should collect for a system used company-wide, versus deciding the exact variable name for a temporary loop counter. Answer both parts.

(a) Which of these two decisions clears this lesson's bar for a full ADR rather than a quick comment?

(b) According to this lesson, what ultimately determines whether a decision deserves a full ADR?

(a) Deciding what demographic data to collect can shape fairness outcomes for an entire system — that's the kind of decision this lesson says merits a full ADR, unlike a throwaway variable name. (b) The lesson's test is about future recoverability of the reasoning, not decision size or where it happened.

8. Before shipping, a team explicitly discusses the licensing-attribution checklist item, decides it doesn't apply since no external code was copied into this particular project, and records that reasoning in the release notes. Does this match the capstone lesson's standard for handling a checklist item that doesn't apply?

The lesson's line is between a deliberate, examined decision and an unexamined skip — recording the reasoning is exactly what makes this the acceptable case.

9. A hiring model uses "distance from city center" as an input, and its published accuracy number is a single blended figure across all applicants. Answer both parts.

(a) Which checklist section covers both of these concerns, and from which unit?

(b) Fill in the blank: "distance from city center" is exactly the kind of supposedly neutral field that could be acting as a ___ for a protected characteristic.

(a) Both proxy variables and group-level accuracy testing sit under the Fairness (Unit 5) heading in the capstone checklist. (b) A geographic field like this is the checklist's own kind of example of a proxy risk.

10. A junior developer assumes that shipping ethically reviewed, well-documented code must always take significantly longer than skipping those habits. Answer both parts.

(a) What does the final lesson actually claim about this assumption?

(b) Fill in the blank: the lesson argues the cost of skipping these habits is paid later — often by someone other than the ___ who cut the corner.

(a) The lesson explicitly rejects the "always slower" framing — habitual practice costs minutes, not double the time. (b) The person who pays for a breach, lawsuit, or biased outcome is often not the developer who originally skipped the step.
