Documenting Decisions, Not Just Code

The code shows what happens. It rarely shows why — and "why" is what future decisions actually need.

Lesson 21 → Contents Glossary →

Good code is largely self-documenting about what it does — a well-named function like is_authorized doesn't need a comment explaining that it checks authorization. But nothing in the code itself explains why it fails closed instead of open, why a field was deliberately left out of the dataset, or why a dependency was pinned to an older version instead of upgraded. Six months later, a new developer looking at that decision has no way to tell "someone thought carefully about this" from "nobody's gotten around to fixing it yet" — and might change it back, undoing a deliberate safety decision.

A decision with no record of its reasoning 
def is_authorized(user, resource):
    try:
        return permissions_service.check(user, resource)
    except ServiceUnavailable:
        return False
The same decision, with its reasoning preserved 
def is_authorized(user, resource):
    try:
        return permissions_service.check(user, resource)
    except ServiceUnavailable:
        # Deliberately fail-closed: an outage here should deny
        # access, not grant it. See Ethics course Unit 4, Lesson 12,
        # and incident postmortem INC-4471 for the reasoning.
        return False

Notice this comment passes the Lesson-1-through-20 bar for a good comment: it explains a non-obvious why, not an obvious what. A comment saying # return False on error would just restate the code. This one preserves the reasoning — fail-closed was chosen deliberately, here's the source of that judgment — so the next person to touch this function inherits the decision instead of just the code.

Definition An Architecture Decision Record (ADR) is a short, standalone document capturing one significant technical decision: the context that prompted it, the options considered, the choice made, and the reasoning — kept alongside the code rather than buried in a chat thread or a closed pull request.

Not every decision needs a formal document

Most of this course's decisions fit in a code comment, like the fail-closed example above. A full ADR is worth the overhead for decisions with wider blast radius — choosing a password hashing algorithm for the whole system, deciding what demographic data an evaluation dataset will collect, picking which license to release your own project under. The test isn't "is this decision big" so much as "would someone reasonably ask 'why did we do it this way' months from now, without an easy way to find out."

Why it matters here Every good decision this course has walked through — hash instead of encrypt, fail closed instead of open, collect less instead of more — looks, from the outside, exactly like an arbitrary choice unless the reasoning travels with it. Undocumented good decisions get silently reverted by people who had no way to know they were deliberate; that's not a hypothetical, it's one of the most common ways security and privacy regressions actually happen in real codebases.
