Code Review Is an Ethical Practice, Not Just a Quality Gate

Every red flag in this course is easier to catch with a second set of eyes — that's what review is actually for.

Lesson 20 → Contents Glossary →

This final unit is about the practices that surround the code, not the code itself. Code review is usually framed as a bug-catching and style-consistency step — and it is that. But every single lesson in this course described a mistake made by one developer, alone, without anyone else looking at the code before it shipped: the hardcoded secret, the unhashed password, the fail-open permissions check, the zip code proxy, the unattributed snippet. A second reviewer, deliberately looking for these patterns, is one of the cheapest and most effective controls this whole course has to offer.

A review that only checks "does it work" 
# PR comment: "LGTM, tests pass 👍"
# (the PR added a new field to the signup form with no
#  data-minimization justification, and logged the raw request body)
A review that checks the patterns from this course 
# PR comment: "Tests pass. Two questions before I approve:
#  1. Do we need the new 'employer' field for anything we're
#     building now, or is this speculative? (data minimization)
#  2. This logs request.body directly — can we log just the
#     fields we actually need instead? (log leak risk)"

The second reviewer isn't slower because they're being difficult — they're applying the same checklist this course has built up, lesson by lesson, as a habit rather than a one-time read-through. Approving a pull request is a small act of trust extended to a colleague; taking five extra minutes to actually look for these patterns is what makes that trust well-placed instead of a formality.

Definition Code review is the practice of having at least one other person examine code before it's merged or shipped — for correctness, but also, as this lesson argues, for the security, privacy, fairness, and licensing patterns covered throughout this course.

Review is also where honesty about disagreement belongs

Lesson 2 covered the ACM's professional codes, including the obligation to give honest, substantiated evaluations. A review culture where reviewers rubber-stamp everything to avoid friction — or where authors get defensive at any pushback — quietly disables the exact mechanism that's supposed to catch the mistakes this course spent eighteen lessons cataloging. The goal of a good review comment isn't to find fault; it's the same goal as the rest of this course, applied by someone other than the original author.

Why it matters here Nearly every example used across this course — the hardcoded key, the SQL injection, the plaintext password log — is the kind of thing a reviewer who's seen this course's patterns before would catch in thirty seconds. The individual discipline this course teaches matters, but a review culture that expects and rewards catching these patterns is what makes the discipline durable across an entire team, not just one careful developer.
