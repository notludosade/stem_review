Unit 7 Test — Version A

Code as a Professional Artifact. 10 points across every lesson in this unit — 5 questions worth 1 point, 5 worth 1 point split across two parts. Score 90% or higher to clear this unit.

1. A team lead argues, "Code review is really just a bug-catcher — if the linter and tests pass, review is optional." What does this lesson argue code review's real value actually is?

Every earlier lesson's mistake was made by a single developer without a second reviewer — a review that deliberately looks for these patterns is a cheap, effective control, not just a bug-catching formality.

2. A reviewer approves nearly every pull request with a quick "LGTM, tests pass" — including one that added a new form field with no stated purpose and logged the full raw request body. According to this lesson, what's the real cost of that habit?

"Tests pass" says nothing about whether a field was actually needed or whether the log statement leaks sensitive data — a rubber-stamp review skips precisely the check meant to catch that.

3. A reviewer notices a colleague's pull request adds a new "household income" field to a signup form with no stated reason, and quietly approves it because raising the question feels confrontational. Answer both parts.

(a) Which obligation from Lesson 2's professional codes does this reviewer fail to uphold?

(b) Fill in the blank: the question this reviewer should have asked — whether the household income field is needed for anything currently being built — is a check for ___ ___, the Unit 3 concept from Lesson 7.

(a) Lesson 2 established a professional obligation to give honest, substantiated evaluations — rubber-stamping a questionable field to avoid friction breaks that obligation. (b) The unexamined field is exactly the kind of thing Lesson 7's data minimization principle asks reviewers to catch.

4. Fill in the blank: this lesson defines a short, standalone document that captures one significant technical decision's context, options considered, and final reasoning as an ___ ___ ___ (abbreviated ADR).

See the lesson's definition box — the Architecture Decision Record keeps the reasoning behind a decision alongside the code, rather than buried in chat or a closed pull request.

5. A developer deliberately chooses to fail closed on a permissions check during a service outage, but leaves no comment explaining the choice. Six months later, a new teammate finds the code and "fixes" it to fail open. What does this lesson say went wrong?

The lesson's whole point is that a deliberate decision and an unfinished one look the same from the outside unless the reasoning travels with the code — this is exactly that failure mode.

6. Compare two comments on the same line of code: Comment X says "# returns False on error." Comment Y says "# Deliberately fail-closed: an outage here should deny access, not grant it — see INC-4471." Answer both parts.

(a) Which comment meets this lesson's standard for a good comment, and why?

(b) Fill in the blank: this lesson's bar for a good comment is that it explains a non-obvious ___, not an obvious what the code already does.

(a) Comment X only restates the code's behavior; Comment Y preserves the reasoning that isn't visible anywhere else — that's the distinction this lesson draws. (b) The lesson's repeated standard is explaining "why," since the code itself already shows "what."

7. A team is choosing which password-hashing algorithm to use system-wide, versus deciding to leave a single inline code comment for a minor formatting choice. Answer both parts.

(a) According to this lesson, which of these two decisions is worth the overhead of a full ADR rather than a quick comment?

(b) What test does this lesson actually propose for deciding whether a decision needs a full ADR?

(a) A system-wide hashing algorithm has far more blast radius than a formatting choice, so it clears the lesson's bar for a full ADR. (b) The lesson's test isn't raw decision size — it's whether the reasoning would otherwise be hard to recover later.

8. Before shipping a small internal tool, a team consciously decides the fairness-testing checklist item doesn't apply, since the tool makes no user-facing predictions at all — and notes this reasoning in the pull request description. According to the capstone lesson, is this acceptable?

The lesson's distinction is deliberate, examined judgment versus an unexamined skip — noting the reasoning in the PR is exactly what makes this a professional judgment call rather than the failure mode described.

9. A team reviews their final checklist and confirms their model's inputs include zip code, and that their published accuracy metric is a single overall number. Answer both parts.

(a) Which checklist section, and unit, do both of these checks belong to?

(b) Fill in the blank: a supposedly neutral field like zip code can act as a ___ for a protected characteristic, which is exactly what the Fairness checklist asks reviewers to look for.

(a) The checklist groups "proxy for a protected characteristic" and "accuracy across groups, not just overall" both under Fairness (Unit 5). (b) Zip code is the checklist's own example of a field that can function as a proxy.

10. A manager worries that following this course's checklist on every project will roughly double development time. Answer both parts.

(a) Fill in the blank: the final lesson argues the actual cost of practicing this checklist as a habit, rather than bolting it on afterward, is close to ___.

(b) What does the lesson say actually carries a high cost, and who ends up paying it?

(a) Hashing instead of storing plainly, or checking a license before adding a dependency, cost minutes once habitual — the lesson's word is "close to zero." (b) The real cost surfaces later, in a breach, lawsuit, or biased outcome, or a silently reverted decision — and it's paid by someone other than the developer who skipped the step.
