Putting It All Together: An Ethics Checklist for Your Own Code

Twenty lessons compressed into the questions worth asking before you ship.

Contents Glossary →

This course opened with Lesson 1's claim that every line of code is a decision, whether or not the developer experiences it that way. Twenty lessons later, that claim should feel less abstract — you've now seen the specific, repeatable shapes those decisions take: a hardcoded secret, an unvalidated input, a field collected without a reason, an error message that overshares, a rule that's neutral in code but not in outcome, a dependency trusted without a second look. This lesson doesn't introduce new material. It's the checklist those twenty lessons collapse into.

The checklist Security (Units 1–2). Any secrets, credentials, or keys in source code instead of environment variables or a secret manager? Any external input — form field, URL parameter, file upload — used before its type, range, and format are checked? Any password stored instead of hashed with a slow, salted algorithm?

Privacy (Unit 3). Is every collected field actually needed for something being built now, not something that might be useful someday? Could anything in a log statement be a password, token, or full request body instead of the specific fields needed? Would "removing the name" actually anonymize this data, or just pseudonymize it?

Transparency (Unit 4). Does an error message give the user enough to act on without leaking internals like stack traces or hostnames? Is what's written to a log a deliberate, structured choice rather than a dumped exception object? On an unresolved error, does this fail closed or open — and was that an explicit choice?

Fairness (Unit 5). Could a supposedly neutral field — zip code, name, browsing history — be acting as a proxy for a protected characteristic? Do the tests check that accuracy holds up across groups, not just that outputs are technically correct?

Trust (Unit 6). Is every dependency's license actually compatible with how this project is distributed? Is any copied snippet attributed to where it came from? Was this dependency evaluated at all before being added, or just installed because it looked convenient?

Practice (Unit 7). Has someone other than the author actually looked for these patterns before this code ships? Will the reasoning behind a non-obvious decision still be findable six months from now?

No single project needs a perfect score on every item every time — that's not how real engineering works under real deadlines. What this checklist is for is making the tradeoff visible and deliberate, the same distinction Lesson 12 drew between choosing fail-open for a good reason and defaulting to it out of convenience. Skipping an item because you consciously decided the risk doesn't apply here is a professional judgment call. Skipping it because nobody asked the question is the failure mode this entire course has been about.

Why this course exists None of these twenty lessons required you to be a worse or slower programmer — hashing a password instead of storing it plainly is not more work once it's a habit; checking a license before adding a dependency takes minutes. The cost of ethical code, once it's practiced rather than bolted on afterward, is close to zero. The cost of skipping it shows up later, in a breach, a lawsuit, a biased outcome, or a colleague's silent revert of a decision nobody explained — paid by someone other than the developer who cut the corner.
