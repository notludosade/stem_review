Trusting a Dependency Is a Decision

Every import statement is a decision to run someone else's code with your program's own permissions.

Lesson 19 → Contents Glossary →

pip install, npm install, cargo add — these commands feel instantaneous and low-stakes, more like a search than a decision. But installing a package doesn't just add code to read later; for most languages, it runs that package's code immediately, during install scripts and at every subsequent import, with exactly the same permissions your own program has. A malicious or compromised dependency doesn't need to trick you into running anything — you already ran it, on purpose, the moment you added it.

Adding a dependency without checking anything 
# needed a quick date-formatting helper, found one with a
# nice-sounding name, added it straight to requirements.txt
pretty-dates==0.0.3
Evaluating a dependency before adding it 
# Checked before adding: maintained (last release 2 months ago),
# 40k+ weekly downloads, no open security advisories, source
# readable and small enough to skim end-to-end. Pinned exact version.
pretty-dates==2.4.1

This isn't paranoia for its own sake — it's a response to a well-documented attack pattern called supply chain compromise: an attacker publishes a malicious package with a name close to a popular one (typosquatting), or gains access to a legitimate, trusted package's publishing credentials and slips malicious code into a routine-looking update. Because the package is already trusted and already imported everywhere, the malicious code runs inside thousands of unrelated projects without any of those developers writing a single insecure line themselves.

Definition Supply chain compromise is an attack that targets a piece of software indirectly, by compromising one of its trusted dependencies, build tools, or distribution channels, rather than attacking the software directly.

Reasonable diligence, not paranoia

Nobody reads every line of every dependency's dependencies — that's not realistic, and it's not what this lesson is asking for. What's realistic: checking that a package is actively maintained, has a plausible number of other users, doesn't have open security advisories, and pinning a specific version rather than always pulling "latest" so an update can't silently change what's running without your knowledge. Tools like npm audit, pip-audit, and GitHub's Dependabot automate most of this check.

Why it matters here This closes the loop on the whole unit: Lesson 16 was about respecting the license terms attached to someone else's code, Lesson 17 was about being honest about where code in your project came from, and this lesson is about the risk you accept, on behalf of everyone who eventually uses your software, every time you decide to trust code you didn't write and mostly won't read.

Check your recall

1. Why is installing a package different from just "adding code to read later"?

Install scripts and imports both execute code — trusting a dependency means running its code, not just referencing it.

2. What is "typosquatting" in the context of package registries?

It relies on a developer mistyping a package name and getting the malicious lookalike instead of the real one.

3. Why does a supply chain attack on a trusted, widely-used package do more damage than attacking one project directly?

One compromised update can propagate to thousands of downstream projects without any of them writing insecure code themselves.

4. Fill in the blank: an attack that targets software indirectly, through a trusted dependency or distribution channel rather than the software itself, is called a ___ ___ ___.

See the definition box above.

5. Fill in the blank: locking a dependency to a specific, tested version instead of always pulling "latest" is called version ___.

This prevents an update from silently changing what code is running without your knowledge — see the good code example's comment.
