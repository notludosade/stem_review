Testing for Fairness, Not Just Correctness

A test suite can pass 100% and still ship a program that fails one group of users far more than another.

Lesson 15 → Contents Glossary →

A standard test checks: given this input, does the function return the right output? That question has nothing to do with fairness — a facial recognition function can correctly return "no match" or "match" on every test case in the suite and still be dramatically less accurate for some skin tones than others, if the test cases themselves don't cover that range. Testing for fairness means asking a second question on top of correctness: does accuracy hold up evenly across the groups of people who will actually use this?

A test suite that only checks correctness 
def test_face_match():
    assert recognize(sample_face_1) == "match"
    assert recognize(sample_face_2) == "no match"
    # both samples came from the same internal team photo set
A test suite that checks correctness across groups 
def test_face_match_across_demographics():
    for group_name, faces in demographic_test_sets.items():
        accuracy = evaluate_accuracy(recognize, faces)
        assert accuracy >= MINIMUM_ACCEPTABLE_ACCURACY, \
            f"Accuracy for {group_name} was {accuracy}, below threshold"

The second test doesn't just check that the function works — it checks that it works similarly well for every group in demographic_test_sets, and fails loudly if one group falls below an acceptable bar. This is the same discipline as normal edge-case testing (empty input, negative numbers, maximum size) applied to a different kind of edge case: a demographic your original test data didn't happen to include.

Definition Disparate impact is when a policy or system that appears neutral produces significantly different outcomes for different groups. It doesn't require intent to discriminate — only a measurable gap in outcomes, which is exactly what a fairness test is designed to catch before release.

You can't test what you didn't measure

The uncomfortable part of this lesson is that fairness testing requires collecting the demographic data needed to run the test — which sits in direct tension with Lesson 7's data minimization principle. There's no universal answer here; the practical resolution most teams use is to collect demographic data for evaluation datasets specifically (often anonymized or aggregated), separately from the production data pipeline the minimization principle governs. The two lessons aren't contradictory — they're about different datasets serving different purposes.

Why it matters here A passing test suite creates false confidence. "All tests pass" sounds like "this is safe to ship," but if the tests were never designed to catch a fairness gap, passing them proves nothing about whether that gap exists. The gap is discovered later, in production, by the people it harmed — which is the worst place to find it.
