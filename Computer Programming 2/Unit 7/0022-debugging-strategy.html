Debugging Strategy

A test tells you something is wrong. Debugging is the separate skill of finding out exactly what and where.

Lesson 23 → Contents Glossary →

An off-by-one error is one of the most common real bugs: a loop that runs one time too many or too few. Below, each version reads one index past the end of a list — and each language reports it completely differently.

Python 
scores = [90, 85, 77]
for i in range(len(scores) + 1):   # bug: should be len(scores)
    print(scores[i])
# IndexError: list index out of range
# Traceback shows the exact line and the call stack (Unit 4) leading to it
Java 
int[] scores = {90, 85, 77};
for (int i = 0; i <= scores.length; i++) {   // bug: should be <
    System.out.println(scores[i]);
}
// ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3
// Also prints a full stack trace pinpointing the exact line
JavaScript 
let scores = [90, 85, 77];
for (let i = 0; i <= scores.length; i++) {   // bug: should be <
    console.log(scores[i]);
}
// 90
// 85
// 77
// undefined   — NO ERROR AT ALL. JavaScript just returns undefined
// for an out-of-range index, silently continuing.
C++ 
std::vector<int> scores = {90, 85, 77};
for (size_t i = 0; i <= scores.size(); i++) {   // bug: should be <
    std::cout << scores[i] << std::endl;
}
// undefined behavior via operator[] — might print garbage, might
// crash, might appear to work. .at(i) would throw std::out_of_range
// instead, trading a little speed for a real, catchable error.

Python and Java fail loudly with a clear error and a stack trace — read from the top, it names the exact line and the chain of calls that led there (Unit 4's call stack, made visible). C++'s [] is the dangerous outlier once again, exactly as in Lesson 19: no promise of any error at all. JavaScript sits in between — no crash, but also no error, just a wrong value (undefined) quietly flowing forward into whatever uses it next, often failing somewhere far away from the actual bug.

A general strategy handles all four cases: reproduce it reliably first — a bug you can trigger on demand is a bug you can investigate. Read the error and stack trace when one exists; it usually names the exact line. When it doesn't — JavaScript's silent undefined, C++'s undefined behavior — bisect: check a value halfway through the suspect code, narrow to the half where things went wrong, and repeat. That's Unit 5's binary search, applied to a bug instead of a sorted list, and it turns "somewhere in this function" into the exact line in a handful of steps. A debugger's breakpoints let you pause and inspect state at any line directly, and are usually faster than sprinkling print statements once a bug resists the first two steps.

Definition Debugging is the process of locating the cause of a bug. Strategy: reproduce reliably, read the error and stack trace, then bisect — narrow the suspect range in half repeatedly — when no clear error points the way.
Why it matters here Bisecting a bug is Unit 5's binary search wearing a different hat — proof that ideas from earlier units keep resurfacing as tools, not just isolated facts. This closes Unit 7: assertions (Lesson 20) and tests (Lesson 21) try to catch bugs before they matter; this lesson is what to do once one gets through anyway.

Check your recall

1. What's the first step in the debugging strategy this lesson recommends?

A bug that can't be reliably triggered is very hard to confirm has actually been fixed.

2. Why is JavaScript's silent undefined arguably more dangerous to debug than Python's IndexError?

A loud, immediate error is often easier to debug than a quiet wrong value discovered much later.

3. What does "bisecting" a bug mean?

This is exactly Unit 5's binary search, applied to narrowing down a bug's location instead of a sorted list.
