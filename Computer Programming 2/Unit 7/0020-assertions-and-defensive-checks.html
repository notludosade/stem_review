Assertions and Defensive Checks

Unit 2's exceptions handle failures that can legitimately happen. Assertions catch failures that should be flatly impossible — if the code is correct.

Lesson 21 → Contents Glossary →

An assertion checks a condition that the programmer believes must always be true at that point in the code, and stops the program immediately if it isn't. Unlike Unit 2's exceptions — for failures that can happen even in correct code, like a file that doesn't exist — an assertion failing means the code itself has a bug. It documents an assumption and checks it, in one line.

Python 
def average(numbers):
    assert len(numbers) > 0, "average() requires a non-empty list"
    return sum(numbers) / len(numbers)

average([])   # AssertionError: average() requires a non-empty list
Java 
static double average(int[] numbers) {
    assert numbers.length > 0 : "average() requires a non-empty array";
    int total = 0;
    for (int n : numbers) total += n;
    return (double) total / numbers.length;
}
// Note: Java assertions are disabled by default — must run with the -ea flag
JavaScript 
function average(numbers) {
    console.assert(numbers.length > 0, "average() requires a non-empty array");
    return numbers.reduce((a, b) => a + b, 0) / numbers.length;
}
// Note: console.assert only logs a warning — it does NOT stop execution,
// unlike the assert in the other three languages
C++ 
#include <cassert>

double average(const std::vector<int>& numbers) {
    assert(!numbers.empty());   // no custom message built in
    int total = 0;
    for (int n : numbers) total += n;
    return static_cast<double>(total) / numbers.size();
}
// Note: assert() is stripped out entirely in release builds (when NDEBUG is defined)

All four have real gaps worth knowing. Python's assert can be globally disabled with the -O flag. Java's assert is disabled by default — it silently does nothing unless the program is run with -ea. C++'s assert() vanishes entirely in release builds. JavaScript's console.assert() is the biggest outlier of all: it only prints a warning to the console and lets execution continue regardless — it isn't really a stopping assertion at all, just a conditional log message. The shared lesson: assertions are a development-time safety net for catching bugs early, not a mechanism your program's actual runtime behavior should ever depend on.

Definition An assertion checks a condition the programmer believes must always hold, halting the program if it doesn't. Assertions guard against bugs (things that should never happen); exceptions handle expected failures (things that can happen even in correct code).
Why it matters here Custom exceptions (Unit 2) and assertions solve different problems that look similar on the surface. Confusing them is a common mistake: using an assertion for user input validation means the check silently vanishes in some languages' release builds — exactly the wrong place to lose a safety check.

Check your recall

1. What does an assertion failing indicate, as opposed to a caught exception?

Exceptions are for expected failures; assertions are for catching violations of assumptions the code relies on.

2. Why is JavaScript's console.assert() the biggest outlier of the four languages here?

Unlike Python, Java, and C++'s assert, a failed console.assert doesn't halt anything on its own.

3. Why is it risky to use an assertion for validating user input?

Java's -ea flag requirement and C++'s NDEBUG stripping are exactly this risk in practice.
