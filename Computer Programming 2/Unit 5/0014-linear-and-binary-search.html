Linear and Binary Search

Same goal — find a value in a list. One approach checks every element. The other throws half the list away with every guess.

Lesson 15 → Contents Glossary →

Linear search checks each element in order until it finds a match or runs out of elements. It works on any list, sorted or not — but in the worst case it looks at every single element, making it O(n).

Python 
def linear_search(items, target):
    for i, value in enumerate(items):
        if value == target:
            return i
    return -1
Java 
static int linearSearch(int[] items, int target) {
    for (int i = 0; i < items.length; i++) {
        if (items[i] == target) {
            return i;
        }
    }
    return -1;
}
JavaScript 
function linearSearch(items, target) {
    for (let i = 0; i < items.length; i++) {
        if (items[i] === target) {
            return i;
        }
    }
    return -1;
}
C++ 
int linearSearch(const std::vector<int>& items, int target) {
    for (size_t i = 0; i < items.size(); i++) {
        if (items[i] == target) {
            return static_cast<int>(i);
        }
    }
    return -1;
}

Binary search takes a shortcut only available on sorted data: check the middle element, and if it's not a match, the sorted order guarantees the target — if present — is entirely on one side. Discard the other half and repeat. Each check eliminates half of what's left.

Python 
def binary_search(sorted_items, target):
    low, high = 0, len(sorted_items) - 1
    while low <= high:
        mid = (low + high) // 2
        if sorted_items[mid] == target:
            return mid
        elif sorted_items[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1
Java 
static int binarySearch(int[] sortedItems, int target) {
    int low = 0, high = sortedItems.length - 1;
    while (low <= high) {
        int mid = (low + high) / 2;
        if (sortedItems[mid] == target) {
            return mid;
        } else if (sortedItems[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return -1;
}
JavaScript 
function binarySearch(sortedItems, target) {
    let low = 0, high = sortedItems.length - 1;
    while (low <= high) {
        const mid = Math.floor((low + high) / 2);
        if (sortedItems[mid] === target) {
            return mid;
        } else if (sortedItems[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return -1;
}
C++ 
int binarySearch(const std::vector<int>& sortedItems, int target) {
    int low = 0, high = static_cast<int>(sortedItems.size()) - 1;
    while (low <= high) {
        int mid = (low + high) / 2;
        if (sortedItems[mid] == target) {
            return mid;
        } else if (sortedItems[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return -1;
}

Cutting the remaining search space in half every step is exactly what makes binary search O(log n) — for a list of a million items, linear search might check a million elements in the worst case, while binary search needs at most about 20. That gap only widens as the list grows. The catch is the precondition: binary search's correctness depends entirely on the data already being sorted. Sort it once (next lesson), and every future search on that data gets the O(log n) discount.

Definition Linear search checks each element in order — O(n), works on any data. Binary search repeatedly halves the remaining range on sorted data — O(log n), but requires the data to already be sorted.
Why it matters here This is Big-O from last lesson made concrete: same problem, same correct answer, and a real, measurable difference in how the cost scales. Binary search's requirement — sorted data — is also the reason sorting algorithms, up next, are worth learning even though sorting itself costs time upfront.

Check your recall

1. What precondition does binary search require that linear search does not?

Without sorted order, discarding half the data based on a single comparison would be unsafe.

2. Why is binary search O(log n) instead of O(n)?

Halving repeatedly is what produces logarithmic — not linear — growth in worst-case comparisons.

3. When is linear search still the right choice over binary search?

Binary search's O(log n) advantage only pays off once the sorting precondition is satisfied.
