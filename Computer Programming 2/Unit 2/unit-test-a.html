1. What is the purpose of a try block?

The try block doesn't stop failures from happening — it just gives a matching catch block a place to respond.

2. Fill in the blank: Java, JavaScript, and C++ use the keyword ___ to manually raise an exception; Python uses a different keyword for the same job.

Python's equivalent keyword is raise — same job, different word.

3. How do all four languages define a custom exception type, such as InsufficientFundsError?

InsufficientFundsError/Exception is a subclass of Exception, Error, or std::runtime_error in every one of the four examples — the same inheritance mechanism from Unit 1.

4. What does Java's checked exception system require of a method that can throw one, like withdraw's InsufficientFundsException?

This compiler-enforced rule is unique to Java among these four languages — Python, JavaScript, and C++ have no equivalent.

5. Fill in the blank: attempting a risky operation directly and reacting if it fails, rather than checking first, is nicknamed ___ ("easier to ask forgiveness than permission").

This is Python's culturally preferred style for cases like a dictionary lookup.

6. Both parts are about which catch/except clause actually fires for a given exception:

(a) In Python: try: age = int("abc") except ValueError: print("bad") except TypeError: print("type problem") — what prints?

(b) In Java, a try block only has catch (ArithmeticException e), but the code inside throws a NumberFormatException. What happens?

(a) int("abc") raises ValueError, which matches the first except clause exactly. (b) A catch/except clause only fires when the exception's type matches the type it names — NumberFormatException isn't an ArithmeticException.

7. Both parts are about parseInt()'s unusual failure behavior:

(a) let age = parseInt("abc", 10); console.log(age); — what prints?

(b) Fill in the blank: because parseInt() never throws on bad input, code that wants fail-loud behavior must check for ___ and throw manually.

(a) Unlike Python's int(), Java's Integer.parseInt(), and C++'s std::stoi(), JavaScript's parseInt() quietly returns NaN ("not a number") instead of throwing. (b) An explicit if (isNaN(age)) throw ... is what gives this the same fail-loud behavior as the other three languages.

8. Both parts are about what a custom exception's inheritance relationship provides:

(a) In JavaScript, class InsufficientFundsError extends Error — what does this let calling code do?

(b) Fill in the blank: C++'s custom exceptions typically inherit from std::runtime_error, while Python's inherit from ___.

(a) Because InsufficientFundsError is a distinct named subclass of Error, a catch clause can check for it specifically rather than reacting to any Error at all. (b) class InsufficientFundsError(Exception) is Python's version of the same inheritance pattern used across all four languages.

9. Both parts are about why catching a specific exception type matters:

(a) Why catch a specific exception type like InsufficientFundsError instead of catching everything?

(b) Fill in the blank: catching a generic exception type instead of a specific one risks accidentally ___ an unrelated bug elsewhere in the program.

(a) A catch-all can accidentally treat a genuine, unrelated bug as if it were the specific failure it was meant to handle. (b) A generic except Exception or catch (...) can silently swallow a real bug that has nothing to do with insufficient funds.

10. Both parts compare the LBYL and EAFP dictionary-lookup styles from this unit:

(a) Assuming my_dict does NOT contain "key", what is the final value of value in both the LBYL (if/else) and EAFP (try/except) versions from the lesson?

(b) Which style do Java and C++'s cultures typically favor, given that unhandled exceptions are comparatively costly to set up there?

(a) Both snippets produce the exact same result — the difference is entirely about idiom and cost, not correctness. (b) Java and C++ tend to favor LBYL, while Python's own culture leans toward EAFP for cases like this.
