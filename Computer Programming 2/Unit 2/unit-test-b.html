1. If an exception is thrown inside a try block and no catch clause below it matches that exception's type, what happens?

A catch/except clause only fires when its named type matches the exception actually raised — otherwise, the exception keeps propagating.

2. Fill in the blank: Python uses the keyword ___ to manually create and raise an exception, unlike Java, JavaScript, and C++, which use throw.

raise InsufficientFundsError("Not enough funds.") is Python's version of the same job throw does elsewhere.

3. Why does defining InsufficientFundsError as a class inheriting from Exception (or Error, or std::runtime_error) matter, rather than just printing a message string?

A named exception type lets calling code catch precisely that failure and nothing else, unlike a generic message string.

4. Which of these exception categories exists uniquely in Java, with no direct equivalent in Python, JavaScript, or C++?

Python, JavaScript, and C++ all support custom exceptions and try/catch — checked exceptions specifically are Java's own compiler-enforced rule.

5. Fill in the blank: checking a condition before attempting a risky operation — the style more natural to Java and C++ — is nicknamed ___ ("look before you leap").

Checking containsKey or count before reading a map is the classic LBYL pattern.

6. Both parts are about which catch/except clause fires for a given exception:

(a) In C++: try { int age = std::stoi("xyz"); } catch (const std::out_of_range& e) { std::cout << "out of range"; } catch (const std::invalid_argument& e) { std::cout << "invalid"; } — what prints?

(b) In Python, code raises a ValueError, but the only except clause present is except TypeError. What happens?

(a) "xyz" has no leading numeric characters at all, so std::stoi throws std::invalid_argument, not std::out_of_range (which is for numbers too large to fit). (b) An except clause only fires for a matching type — a ValueError won't be caught by one written for TypeError.

7. Both parts are about parseInt()'s unusual failure behavior:

(a) let age = parseInt("", 10); console.log(age); — what prints?

(b) Fill in the blank: to replicate the other three languages' throw-on-bad-input behavior in JavaScript, code must explicitly check isNaN(age) and then manually ___ an error.

(a) parseInt() quietly returns NaN on input it can't convert, including an empty string, instead of throwing. (b) if (isNaN(age)) throw new Error(...) is what gives JavaScript the same fail-loud behavior the other three languages provide automatically.

8. Both parts are about which base class a custom exception ultimately inherits from:

(a) In Java, class InsufficientFundsException extends Exception — which built-in class is InsufficientFundsException ultimately a subclass of?

(b) Fill in the blank: in JavaScript, custom exception classes typically extend the built-in ___ class, and can set this.name inside their constructor.

(a) extends Exception is right there in the class declaration — the same inheritance mechanism from Unit 1. (b) class InsufficientFundsError extends Error is JavaScript's version of the same pattern.

9. Both parts are about the risk of catching too broadly:

(a) A program has a genuine, unrelated bug (say, a typo causing an undefined variable) inside code wrapped by a catch-all except Exception: meant only for InsufficientFundsError. What happens?

(b) Fill in the blank: catching only the exact exception type you expect, instead of everything, means an unrelated bug still surfaces as a ___ instead of being hidden.

(a) A broad except Exception: catches anything that's an Exception, including bugs that have nothing to do with insufficient funds. (b) Catching InsufficientFundsError specifically means a genuine typo elsewhere still surfaces as a crash, instead of being mistaken for a funds problem.

10. Both parts are about the lesson's broader point on choosing a handling style:

(a) The lesson mentions my_dict.get("key", "default") as a third option, written as a single expression. Which behavior category does it say this fits?

(b) The lesson concludes that neither defensive nor corrective handling is universally more correct. What does it say actually determines the better choice in a given codebase?

(a) my_dict.get("key", "default") never risks a missing-key failure at all, which is the defensive instinct, even though it reads as one expression. (b) Matching your language's idiom is itself part of writing professional code — Java or C++ written heavily EAFP, or Python written heavily LBYL, both work but read as unfamiliar.
