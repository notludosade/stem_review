Unit 1 — The Software Development Lifecycle

Non-functional requirement

A property like performance, reliability, security, or maintainability, rather than a specific correct output — first-class design goals, not afterthoughts.

Software development lifecycle (SDLC)

The standard sequence of phases software passes through: requirements, design, implementation, testing, deployment, and maintenance. Real teams loop between phases rather than executing them once in strict order.

Acceptance criteria

The specific, checkable conditions that turn a vague requirement into something a team can agree is either met or not met.

Unit 2 — Version Control with Git

Commit

A complete snapshot of the entire project at one moment, with a pointer to its parent commit — the fundamental unit of recorded history in Git.

Branch

A lightweight, movable pointer to a specific commit, not a copy of the codebase — what makes creating one nearly instant and lets people work in parallel.

Merge conflict

What happens when two branches changed the exact same lines of the exact same file in different ways, forcing a human to decide rather than letting Git silently guess.

Pull request

A request to merge one branch into another that shows the full diff and lets teammates comment, request changes, or approve before the merge happens.

Unit 3 — Software Testing

Regression

A previously working feature breaking as an unintended side effect of an unrelated change — the most common thing test suites catch in practice.

Testing pyramid

The recommended shape of a healthy test suite: many fast, cheap unit tests forming a wide base, with far fewer, slower integration tests above them.

Test-driven development (TDD)

Writing a failing test first (red), then the minimum code to pass it (green), then cleaning up with the test as a safety net (refactor).

Unit 4 — Design Patterns

Design pattern

A named, reusable shape of solution to a recurring design problem — a shared vocabulary for communication, not exact code to copy in.

Factory

A creational pattern that centralizes object-creation decision logic in one place, instead of duplicating it everywhere an object is needed.

Singleton

A creational pattern guaranteeing a class has exactly one instance with one global access point — frequently misused, since the hidden global it creates makes code harder to test.

Adapter

A structural pattern that wraps an existing class to translate its interface into one different calling code expects, without modifying the original.

Observer

A behavioral pattern letting a subject automatically notify a list of registered dependents whenever its own state changes.

Strategy

A behavioral pattern defining a family of interchangeable algorithms behind one shared interface, so calling code can switch between them without changing itself.

YAGNI

"You Aren't Gonna Need It" — build the simplest thing that satisfies today's actual requirement, and add flexibility later if a real second case appears.

Unit 5 — Software Architecture

Architectural decision

A decision that's expensive and disruptive to reverse once a system is built around it — the defining test is reversal cost, not perceived importance.

Monolith

An entire application built as a single, unified codebase, deployed and run as one unit — usually the right starting point for a new, small-team product.

Microservices

A system split into small, independently deployable services communicating over a network — a trade-off that pays off once real scale or team-independence constraints appear, not a default upgrade.

Coupling

How much one component depends on another's internal details rather than a small, stable interface. Low coupling lets components change independently.

Cohesion

How closely the responsibilities inside one component relate to each other. High cohesion means a component does one clear job.

Separation of concerns

The design principle that each part of a system should be responsible for one distinct concern — the goal that low coupling and high cohesion both serve.

Technical debt

The accumulated cost of a shortcut taken along the way. Deliberate debt is a conscious, tracked trade-off; accidental debt accumulates without anyone choosing it.

Unit 6 — Code Review and Collaboration

Code review's three jobs

Catching bugs, spreading knowledge across the team, and keeping the codebase consistent — bug-catching alone undersells what review is actually for.

Blocking issue

A genuine problem — a bug, a missed requirement, a real design flaw — that must be fixed before a pull request can merge.

Nit

A small, optional suggestion, commonly prefixed "nit:", that improves the code but isn't worth blocking the merge over.

Work-directed feedback

Feedback that names the specific, observable problem in the code and leaves room for the author to explain, rather than asserting a judgment about their competence.

Unit 7 — Agile Development in Practice

Agile

A set of values — favoring working software, responding to change, frequent collaboration — that concrete frameworks like Scrum and Kanban each try to embody.

Sprint

Scrum's fixed-length iteration, commonly one or two weeks, during which the team commits to a specific set of backlog work.

Kanban / WIP limit

Kanban manages a continuous flow of work with no fixed iterations; a work-in-progress (WIP) limit caps how many items can be "In Progress" at once, forcing work to finish before more starts.
