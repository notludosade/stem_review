Why We Test: Confidence, Not Perfection

Tests don't prove a program is correct — they prove it hasn't broken in the specific ways you checked.

← Unit 2, Lesson 6 Lesson 8 → Contents Glossary →

Unit 1 named testing as an SDLC phase; Unit 2 gave you the tool (Git and pull requests) for merging changes safely. This lesson answers a more basic question: why do professional teams write automated tests at all, when the code either works or it doesn't?

Manual checking doesn't scale

Why "I ran it once and it worked" isn't enough at team scale When one person writes and immediately runs a small script, manually checking the output is fine. Once a codebase has hundreds of functions modified by dozens of engineers over years, manually re-checking that every existing feature still works after every single change becomes physically impossible — there simply isn't enough human time. Automated tests are code that checks other code, and unlike a human, they can re-run thousands of checks in seconds, every time anything changes.

What a passing test suite actually proves

Why "all tests pass" doesn't mean "the program is correct" This is the single most important, most commonly misunderstood idea in testing: a test suite can only prove the program behaves correctly for the specific cases it checks. It says nothing about inputs nobody thought to test. A green test suite means "we haven't broken anything we already knew to check for" — a real and valuable guarantee, but a fundamentally different claim than "this program is provably correct."
Example A function that divides two numbers might have tests for divide(10, 2) and divide(9, 3), both passing. If nobody wrote a test for divide(5, 0), the test suite says nothing about what happens on that input — the suite passing gives real confidence about the cases it covers, and zero information about the case it doesn't.

Regression: the problem tests solve better than anything else

A regression is an old feature breaking from a new change The single most common thing automated tests catch in practice isn't a bug in brand-new code — it's a regression: a change made for an unrelated reason that accidentally breaks something that used to work. Without a test suite, a regression is often invisible until a user reports it in production. With one, the exact test that used to pass now fails, immediately, before the change is even merged.
Example An engineer refactors how discount codes are calculated to support a new promotion type. The refactor is correct for the new promotion — but it silently breaks free-shipping codes, a completely unrelated feature that happened to share the same function. A test written months earlier for free-shipping codes catches this immediately; without it, the break wouldn't surface until a customer complained.

Confidence to change code, not just confidence it works today

Why this connects to the maintenance phase from Unit 1 Unit 1 established that most of a system's cost is in maintenance — years of engineers changing code they didn't originally write. A solid test suite is what makes changing that code safe: an engineer can modify a function, run the tests, and immediately know whether anything they didn't intend to touch broke. Without tests, every change to old code is a leap of faith; with them, it's a checked, reversible step.
