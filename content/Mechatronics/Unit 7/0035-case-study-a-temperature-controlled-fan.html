Case Study: A Temperature-Controlled Fan

Every unit in this course, in one working loop — a thermistor, a PWM-driven fan, and a proportional control decision.

← Lesson 34 Lesson 36 → Contents Glossary →

This lesson walks Lesson 34's recipe through a complete, concrete system: a fan that spins faster the hotter it gets, cooling automatically without ever being told an exact speed by hand.

Step 1–2: sensor and actuator Sensor: a thermistor voltage divider (Unit 1, Lessons 2 and 6), read via analogRead() (Unit 3, Lesson 15) and converted from a raw ADC count to an estimated temperature using two-point calibration. Actuator: a PWM-driven DC fan (Unit 2, Lessons 7–8; Unit 4, Lesson 20), where fan speed scales with duty cycle.
Step 3: control strategy Since the fan can accept a smooth, continuously variable PWM duty cycle, a proportional controller (Unit 6, Lesson 29) is a reasonable, genuinely useful choice here — simpler than full PID, while still giving smoother behavior than bang-bang: fan speed increases gradually as temperature climbs above a target, rather than snapping straight to full speed.
Step 4: filtering Thermistor readings drift slowly and don't need a fast-reacting derivative term at all, so a simple moving average (Unit 4, Lesson 22) on the temperature reading is enough to steady the input without meaningfully slowing the fan's response to real temperature changes.
Step 5: the full loop 
setup():
    pinMode(FAN_PWM_PIN, OUTPUT)

loop():
    raw = analogRead(THERMISTOR_PIN)
    tempReading = calibrate(raw)              // Unit 1, Lesson 6
    smoothedTemp = movingAverage(tempReading)  // Unit 4, Lesson 22

    error = smoothedTemp - TARGET_TEMP          // positive when too hot
    output = Kp * error
    output = clamp(output, 0, 100)              // 0-100% duty cycle

    setPwmDutyCycle(FAN_PWM_PIN, output)
Why error is defined the other way around here Earlier lessons defined error as setpoint − measured value, positive when the system needs to work harder to close the gap (like a cold room needing more heat). Here, error is defined as measured − target, positive when the room is too hot and needs more fan speed — the sign convention just needs to match "more error, more corrective output" for whichever direction the specific system needs to push. Getting this sign backward is a classic, very real bug — Unit 7, Lesson 38 covers exactly this failure mode.

Check your recall

No peeking back up — answer from memory first, then check.

1. Why is a proportional (P) controller a reasonable choice for this fan system, rather than bang-bang control?

Matching the control strategy to the actuator’s real capability (from Lesson 34) is exactly why proportional control fits a PWM-driven fan well.

2. Why does this system use a simple moving average filter rather than worrying about a derivative term’s noise sensitivity?

With no derivative term in play, the stricter noise concerns from Unit 6, Lesson 31 don’t apply here — a simple moving average is sufficient smoothing for a slow-changing quantity like temperature.

3. In this system’s pseudocode, why is error defined as (measured temperature − target), rather than (target − measured) as in earlier lessons?

What matters is that increasing error produces increasing corrective output in the right direction for the specific system — here, hotter-than-target should mean faster fan, so the sign convention is set up accordingly.

4. Fill in the blank: in this system’s pseudocode, the final computed output is passed through a ___ function to keep it within the fan’s valid 0-100% PWM range.

Clamping (Unit 6, Lesson 32) ensures the computed output never exceeds what the actuator can actually accept.
