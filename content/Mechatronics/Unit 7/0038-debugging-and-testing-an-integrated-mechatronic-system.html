Debugging and Testing an Integrated Mechatronic System

Closing out Unit 7 with the skill that matters most once real hardware is involved: figuring out why it isn’t working.

← Lesson 37 Unit 8, Lesson 39 → Contents Glossary →

An integrated system — sensor, actuator, and control loop combined — has more moving pieces than any single earlier lesson, which means more places for something to go wrong. This lesson is about isolating exactly where.

The core debugging principle: test pieces separately before combining them Never bring up a sensor, a control loop, and an actuator all at once for the first time. Test the sensor reading alone first — print its raw values and confirm they make physical sense before trusting them. Test the actuator alone next — drive it with a fixed, hand-picked output value and confirm it responds correctly, with no control logic involved yet. Only once both pieces are independently confirmed working should they be combined into a full closed loop.

Common failure patterns and where they trace back to

Erratic, jumpy output despite a stable real-world condition Usually sensor noise reaching the control loop unfiltered — apply the moving average or EMA filtering from Unit 4 before the reading reaches the control calculation, especially if a derivative term is involved (Unit 6, Lesson 31).
Persistent oscillation that never settles Usually a tuning issue — Kp set too aggressively for the system's real lag (Unit 6, Lesson 29), or in a bang-bang system, too narrow a hysteresis deadband (Unit 5, Lesson 26).
Actuator not responding at all Check the driver and wiring first, not the control math — a motor driver's enable pin left unconfigured, a current limit tripped, or a GPIO pin trying to directly drive a load it can't supply (Unit 3, Lesson 16) are all far more common than a bug in the control formula itself.
The system actively fights itself, pushing the wrong direction A flipped error sign. If output increases when it should decrease (and vice versa), the controller isn't broken — its error calculation has the wrong sign convention for that specific system, exactly the detail flagged in Lesson 35's case study. This is one of the most common real integration bugs, and one of the easiest to overlook because the code "looks correct" at a glance.
Why this order of investigation matters Jumping straight to retuning PID gains when the real problem is a wiring fault (or vice versa) wastes time chasing the wrong layer of the system. Isolating sensor, actuator, and control logic separately — the way this lesson opened — is exactly what makes it possible to know which layer actually has the bug before trying to fix it.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the recommended first step when bringing up a new integrated sensor + actuator + control system?

Isolating each piece before combining them is the core principle of this lesson — it tells you which layer to look at first when something goes wrong.

2. A control loop’s output is erratic and jumpy even though the real-world condition being measured is stable. What is the most likely cause?

Jumpy output from a stable real condition is the classic signature of unfiltered noise, especially when amplified by a derivative term — the fix is filtering (Unit 4), not necessarily retuning gains.

3. A control loop’s output consistently pushes in the wrong direction, making the system worse instead of better. What is the most likely bug?

A controller actively fighting itself — pushing the wrong direction — is the signature of a flipped error sign, one of the most common and easy-to-overlook integration bugs.

4. Fill in the blank: when an actuator doesn’t respond at all, the recommended first things to check are the driver and ___ before assuming the control math is wrong.

Wiring and driver issues (a misconfigured enable pin, a current limit, an underpowered GPIO pin) are far more commonly the culprit than a bug in the control formula itself.

5. Fill in the blank: retuning PID gains when the real problem is actually a wiring fault wastes time chasing the wrong ___ of the system.

Isolating which layer — sensor, actuator, or control logic — actually contains the bug is exactly what testing each piece separately is meant to reveal.
