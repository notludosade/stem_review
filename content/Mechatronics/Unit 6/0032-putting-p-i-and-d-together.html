Putting P, I, and D Together

Three separately-motivated terms, summed into one output, then handed off to the actuator that closes the loop.

← Lesson 31 Lesson 33 → Contents Glossary →

Lessons 29 through 31 covered each PID term in isolation, with its own motivating weakness and its own risk. This lesson puts them back together, the way a real controller actually runs.

output = Kpe + Ki∫e dt + Kd(de/dt)

All three terms are computed from the same single error signal, every single control cycle, and simply added together into one final number. Nothing about combining them is more complicated than that summation — the complexity lives entirely in choosing good gains, which is Lesson 33's job.

Worked example At one instant: error = 4, the running integral sum = 22, and the rate of change of error = −1.5 (error is currently shrinking). With Kp = 2, Ki = 0.5, Kd = 3: output = (2 × 4) + (0.5 × 22) + (3 × −1.5) = 8 + 11 − 4.5 = 14.5. Notice the derivative term's negative contribution here — it's actively pulling the total down because the error is already closing fast, exactly the damping effect from Lesson 31.

Where the number actually goes

A raw PID output isn't automatically in a usable range for the actuator — it needs clamping (limiting) to whatever range the actuator can physically accept, most often a PWM duty cycle from 0–100% (or the corresponding 0–255-style integer range from Unit 4). A computed output of 140% or −20% is not physically meaningful and must be capped at the actuator's real limits before being sent out.

Pseudocode: one full control cycle 
loop():
    measured = readSensor()
    error = setpoint - measured
    integralSum = integralSum + error * dt
    derivative = (error - previousError) / dt

    output = Kp*error + Ki*integralSum + Kd*derivative
    output = clamp(output, 0, 100)     // stay within actuator’s real range

    setActuator(output)                // e.g. write a PWM duty cycle
    previousError = error
Why this is still the exact setup/loop pattern from Unit 3 Everything here — read a sensor, compute a decision, write an actuator — is the same read-decide-write shape from Unit 3, Lesson 17. A PID controller is not a different kind of program; it's a more sophisticated version of the "decide" step, running inside the same loop() that a simple if-statement occupied back in Unit 3.

Check your recall

No peeking back up — answer from memory first, then check.

1. At a given instant, error = 6, integral sum = 10, rate of change of error = 2, with Kp = 3, Ki = 1, Kd = 2. What is the total PID output?

(3 × 6) + (1 × 10) + (2 × 2) = 18 + 10 + 4 = 32.

2. Why must a raw PID output typically be clamped before being sent to the actuator?

A PID formula has no built-in awareness of the actuator’s real limits — clamping enforces those limits after the fact, before the value is actually used.

3. How does a full PID control cycle relate to the setup/loop program structure from Unit 3?

PID is still read sensor → decide (now via the PID formula) → write actuator, every pass through loop() — the same shape introduced in Unit 3, just with a richer decision step.

4. Fill in the blank: limiting a computed PID output to the actuator’s physically valid range before sending it out is called ___.

Clamping ensures an out-of-range computed value (like 140% duty cycle) never actually reaches hardware that can’t accept it.

5. Fill in the blank: in the pseudocode example, the variable that must be updated at the end of every cycle so the next cycle’s derivative calculation works correctly is ___.

previousError must be updated every cycle so the next derivative calculation (error − previousError) reflects the most recent change, not a stale one.
