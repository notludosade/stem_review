Where Data Goes After You Collect It

Sensitive data doesn't just live in the database. It leaks sideways, into logs, most often by accident.

Lesson 9 → Contents Glossary →

A team can do everything right in Lessons 6 and 7 — hash the password, minimize the fields collected — and still leak sensitive data through a place nobody thinks to check: the application logs. Logging is usually treated as a debugging convenience, invisible to users, so it gets far less scrutiny than the database schema. That's exactly why it's a common leak point.

Logging the whole request 
def handle_login(request):
    logger.info(f"Login attempt: {request.body}")
    # request.body contains { "email": "...", "password": "..." }
    return authenticate(request.body)
Logging what's needed to debug, nothing more 
def handle_login(request):
    logger.info(f"Login attempt for user: {request.body['email']}")
    return authenticate(request.body)

The first version is convenient — one line, logs everything, never needs updating when the request shape changes. That convenience is exactly the problem: it logs the plaintext password on every single login attempt, successful or not, into a log file that's typically kept for months, often copied to a third-party log aggregation service, often readable by a much larger set of engineers than the production database itself. A logging system was never designed to hold secrets, but a careless logger.info(request.body) turns it into one anyway.

Definition A log leak is the unintentional exposure of sensitive data through application logs, monitoring systems, or error trackers — channels that usually have weaker access controls and longer retention than the primary database.

The pattern to watch for

The general shape of this mistake is logging an entire object — a request, a form submission, a database row — instead of the specific fields actually needed for debugging. The OWASP Logging Cheat Sheet lists passwords, session tokens, credit card numbers, and other authentication data among the categories that should never appear in logs at all, in any form.

Why it matters here This is Unit 2's "secrets don't belong in source code" and Unit 3's "collect only what you need," applied to a place that's easy to forget: logs are a second copy of your data, created automatically, often with none of the protections applied to the first copy.

Check your recall

1. Why does this lesson call logging a common, accidental leak point?

Logging is usually treated as an invisible debugging convenience, so it doesn't get the same review a database schema or API response would.

2. What specifically is wrong with logger.info(f"Login attempt: {request.body}") in the example?

request.body contains the raw submitted password, which now sits in plaintext in a log file rather than only ever being hashed.

3. What does the OWASP Logging Cheat Sheet say about data like passwords and session tokens?

Even a truncated or partial version of a secret is still guidance to avoid — the cheat sheet's recommendation is exclusion, not partial logging.

4. Fill in the blank: unintentional exposure of sensitive data through logs or monitoring systems is called a ___ ___.

5. Fill in the blank: in the bad example, the field logged wholesale instead of picking out just the email was ___.

The fixed version logs request.body['email'] specifically, instead of the entire request.body object.
