Where Bias Enters a Program

Code doesn't need to be "trying" to discriminate to produce a discriminatory result.

Lesson 14 → Contents Glossary →

Every lesson so far has looked at a decision one developer makes in one function. This unit looks at a different kind of failure — one where every individual line of code is doing exactly what it was written to do, and the harm shows up only when you look at how the program treats different groups of people differently. This isn't unique to machine learning; it happens in ordinary rule-based code too.

A rule that looks neutral, but isn't 
def qualifies_for_fast_shipping(customer):
    # Fast shipping is only profitable in areas we can reach same-day
    return customer.zip_code in FAST_SHIPPING_ZIPS

# FAST_SHIPPING_ZIPS was built from the company's current warehouse
# locations, which happen to cluster in wealthier zip codes —
# so the rule quietly correlates with income and, in this city, race
Checking what a "neutral" rule actually produces 
# Before shipping this list to production, someone actually ran:
coverage_by_zip = analyze_coverage(FAST_SHIPPING_ZIPS, census_data)
# ...and found fast shipping covered 78% of high-income zip codes
# vs. 12% of low-income zip codes in the same metro area.
# The list gets revisited with that finding in hand, not shipped blind.

Nobody wrote if customer.is_low_income: deny(). The zip code list was built for an entirely defensible operational reason — warehouse proximity. The bias entered through a variable (zip code) that's correlated with a protected characteristic (income, and in many US cities, race) without anyone deciding that on purpose. This is the general shape of most real-world algorithmic bias: not malice, but an unexamined correlation baked into a rule or a training dataset.

Definition Algorithmic bias is a systematic, unfair difference in how a program's output treats different groups — even when no line of code explicitly references group membership. It commonly enters through historical data that reflects past discrimination, through a design choice like the shipping example, or through whoever built and tested the system sharing a narrow set of backgrounds.

Three common entry points

Bias tends to enter a program in one of three ways: biased training data (a model trained on past hiring decisions inherits whatever bias was in those decisions), biased rules (the zip code example — a rule that's neutral on paper but correlated with a protected group in practice), and biased testing (a system tested only on one demographic, so failures for anyone else are never caught before release — the subject of the next lesson).

Why it matters here "I didn't write anything discriminatory" is true and insufficient at the same time — the zip code developer is telling the truth, and the system still produces a discriminatory outcome. Treating fairness as something you check for, the way you'd check for a null pointer, is what catches this before it ships instead of after a customer complaint.

Check your recall

1. In the shipping example, what variable ends up correlating with income and race?

The warehouse-proximity list wasn't built with income or race in mind, but zip code correlates with both in many US metro areas.

2. Why is this kind of bias harder to spot than an explicit discriminatory rule?

The rule looks neutral by every normal code-review standard — the problem only shows up when you check the outcome against group membership.

3. What did the "good" example actually do differently from the bad one?

Checking coverage against census data is what surfaces the correlation — the code itself doesn't need to change to reveal the problem.
