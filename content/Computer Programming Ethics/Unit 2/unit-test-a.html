Unit 2 Test — Version A

1. A Stripe API key is written directly as a string literal inside a Python file, e.g. STRIPE_API_KEY = "sk_live_...". What does Lesson 4 call this?

Lesson 4 opens with exactly this pattern: an API key, database password, or signing key written directly into source code instead of loaded from somewhere secure.

2. Fill in the blank: Lesson 4 fixes the hardcoded key by reading it from an ___ ___ — a value set outside the program and read at startup instead of written into the source.

The key now lives outside the source file entirely — set by the hosting platform, a local .env file excluded from version control, or a secrets manager.

3. Why isn't deleting a hardcoded key in a later commit enough to fix the problem, according to Lesson 4?

Version control keeps every prior version of every file by design — the key remains fully readable in history to anyone with repo access, indefinitely, unless the history itself is rewritten.

4. In Lesson 5's boundary mental model, where should input validation actually happen?

Validating at the boundary means the rest of the program can trust the data without re-checking it everywhere — the check happens once, at the point of entry.

5. Fill in the blank: unlike hashing, ___ is deliberately reversible with the right key — which is exactly why passwords should never be stored this way.

Lesson 6's definition box draws this exact contrast: hashing is one-way, encryption is deliberately reversible with a key.

6. Answer both parts about Lesson 4's definition of a secret:

(a) Fill in the blank: any credential — an API key, password, signing key, or access token — that grants access and must not be readable by unauthorized people is called a ___.

(b) Why does GitHub run secret scanning on public repositories, according to Lesson 4?

(a) See Lesson 4's definition box — the term covers any credential that grants access. (b) Automated scanners exist on both sides: GitHub scans to warn maintainers, and attackers run their own scanners hoping to find a key first.

7. Lesson 5 lists four questions to ask of external input. Answer both parts using the set_age(age) example:

(a) The fixed set_age checks isinstance(age, int) and 0 <= age <= 130. Which two validation questions does this cover?

(b) Fill in the blank: checking that external data meets expected type, range, format, and value constraints before it's used is called ___ ___.

(a) isinstance checks type; the range comparison catches values like 9999999 that are valid integers but not valid ages. (b) See Lesson 5's definition box — it's the general principle behind Unit 1's specific SQL-injection fix.

8. Answer both parts about Lesson 6's create_user example:

(a) What does the fixed create_user function store in the database instead of the raw password?

(b) Fill in the blank: check_login compares a freshly-hashed version of the typed password against the stored ___ rather than comparing raw passwords directly.

(a) bcrypt.hashpw(...) replaces the plain password with its hash before it's ever written to the database. (b) The real password is never stored anywhere — only its hash, so there's nothing in plaintext for a breach to expose.

9. Answer both parts about bcrypt.gensalt() in Lesson 6:

(a) What problem does mixing a random salt into each password before hashing solve?

(b) Fill in the blank: without a salt, two users who choose the same password would end up with identical stored ___.

(a) A random salt means identical passwords no longer produce identical hashes, defeating precomputed lookup tables. (b) Without a salt, matching passwords hash to the exact same stored value every time.

10. Answer both parts about why SHA-256 is a poor fit for password storage, per Lesson 6:

(a) Why is a fast, general-purpose hash like SHA-256 a poor choice for passwords specifically?

(b) Fill in the blank: bcrypt and modern alternatives like ___ are deliberately slow and tunable, which is a liability for general use but a feature for password storage.

(a) Speed is exactly what you don't want in a password hash — it's a direct measure of how fast an attacker can brute-force a stolen hash. (b) Both are named in Lesson 6 as the deliberately slow, tunable alternatives to a fast general-purpose hash.
