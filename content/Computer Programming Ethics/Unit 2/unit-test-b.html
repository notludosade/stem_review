1. Lesson 4 shows the same hardcoded Stripe key written in Python, Java, JavaScript, and C++. What does this comparison demonstrate?

Just like the injection example in Unit 1, the syntax changes across languages but the underlying mistake — a secret written directly into source — doesn't.

2. Fill in the blank: os.environ[...] in Python, System.getenv(...) in Java, and std::getenv(...) in C++ all read the same kind of value — one set outside the program, known as an ___ ___.

Every language in this course reads them slightly differently, but the concept — configuration kept outside committed code — is identical.

3. According to Lesson 4, what stays fully readable in a repository even after a hardcoded key's line is deleted in a later commit?

Lesson 4 states it stays fully readable to anyone with repo access, indefinitely, unless the repo's history itself is rewritten and force-pushed.

4. What does treating validation as a boundary let the rest of the program do, according to Lesson 5?

Once data is validated at the boundary, the rest of the program can trust it instead of every function re-checking everything defensively forever.

5. Fill in the blank: passwords are stored using a one-way ___, not encryption, because the system should never need to recover the original password — only check whether a new one matches.

Login only requires checking whether a new password matches, never recovering the original — exactly what a one-way hash allows and encryption doesn't need to.

6. Answer both parts about what counts as a secret in Lesson 4:

(a) Which of these is an example of a secret, as Lesson 4 defines the term?

(b) Fill in the blank: a secrets manager, a local .env file excluded from version control, and hosting-platform configuration are all places a ___ can live instead of inside source code.

(a) API keys, passwords, signing keys, and access tokens are all examples of secrets. (b) All three are alternatives Lesson 4 names for keeping a secret out of committed code.

7. Answer both parts about the four validation questions from Lesson 5:

(a) A form field only accepts "small", "medium", or "large". Checking that a submitted value is one of those three is an example of checking:

(b) Fill in the blank: checking whether a submitted string actually looks like a real email address is an example of checking its ___.

(a) and (b) Lesson 5's four questions are type, range, format, and allowed values — each catching a different kind of bad input.

8. Answer both parts about why passwords are never stored directly:

(a) What happens if a database of plaintext passwords is ever read by the wrong person, according to Lesson 6?

(b) Fill in the blank: bcrypt.hashpw(password.encode(), bcrypt.gensalt()) is called before storing a password so the database only ever holds a password ___, never the password itself.

(a) Password reuse is common enough that a single leaked plaintext database routinely causes damage far outside the original system. (b) Storing only the hash means there's nothing in plaintext for a breach to expose.

9. Answer both parts about salts in Lesson 6:

(a) Fill in the blank: random data mixed into a password before hashing, so identical passwords produce different stored hashes, is called a ___.

(b) Where does the fixed create_user example in Lesson 6 generate this random value?

(a) See Lesson 6's definition box — a salt defeats precomputed hash lookup tables. (b) bcrypt.gensalt() generates a fresh random salt automatically for each password.

10. Answer both parts about hashing speed:

(a) Fill in the blank: bcrypt and Argon2 are deliberately ___, which is the opposite of what you want from a general-purpose hash function.

(b) Where does Lesson 6 say to check which specific password-hashing algorithm to use in a real project?

(a) Speed is a liability for password storage, since it directly determines how many guesses an attacker can try per second. (b) It's the field's authoritative, regularly-updated answer to "which algorithm, and how."
