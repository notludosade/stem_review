GPUs and Why Deep Learning Needs Parallel Hardware

Every lesson so far has quietly assumed training happens fast enough to iterate on. This lesson is about the specific hardware fact that makes that assumption true — and why it wasn't always true.

← Lesson 15 Lesson 17 → Contents Glossary →

Look back across this entire course: a layer's forward pass (Unit 1) is a matrix multiply. A convolution (Unit 3) is many small, independent multiply-add operations repeated across an image. Attention (Unit 5) is Q @ K.T and weights @ V — matrix multiplies again. Nearly everything a neural network does, forward or backward, reduces to enormous numbers of multiply-add operations that don't depend on each other's results within the same layer. That independence is the entire story.

Python — the same computation, framed two ways 
# Serial: one operation waits for the previous one to finish
total_time_cpu = num_operations * time_per_operation

# Parallel: operations that don't depend on each other run at the same time
total_time_gpu = time_per_operation * ceil(num_operations / num_cores)
# with enough cores, this collapses toward roughly one operation's worth of time

A CPU has a handful of powerful cores, each excellent at running a long, branching, sequential program — exactly what most software needs. A GPU has thousands of much simpler cores, built originally to compute the same operation on millions of independent pixels at once for rendering graphics — and a matrix multiply's independent multiply-add operations are, structurally, the exact same shape of problem. Serial computation processes operations one after another, so total time scales with how many operations there are; parallel computation processes many independent operations simultaneously, so total time depends far more on how many cores are available than on the operation count itself. This is why throughput — total work completed per unit time, not the speed of any single operation — is the number that actually matters for training, and it's why a modern GPU can train in hours what would take a CPU weeks, despite no single GPU core being faster than a CPU core on its own.

Definition Serial computation processes operations one at a time, in sequence. Parallel computation processes many independent operations simultaneously across multiple cores. Throughput is total work completed per unit time — the metric parallel hardware is built to maximize, even when no individual core is unusually fast.
Why "independent" is the load-bearing word Parallelism only helps when operations genuinely don't depend on each other's results. A single layer's weighted sums are independent of one another — that's exactly why they parallelize beautifully on a GPU. But Unit 2's training loop, one iteration after another, is inherently sequential: iteration 50 needs the weights iteration 49 just updated. A GPU speeds up the (massively parallel) work inside each iteration; it does nothing to make the (inherently sequential) count of iterations themselves go any faster. Every lesson in this course that assumed "just run more epochs" was quietly assuming that iteration-to-iteration sequential cost, not the within-iteration cost a GPU parallelizes away.

1. Why is a matrix multiply well suited to GPU hardware specifically?

A GPU's thousands of simple cores match the independent, repeated structure of matrix multiplication almost exactly.

2. What does throughput actually measure?

Throughput is about aggregate completed work, which is exactly what many parallel cores boost even without any single core being fast.

3. Why doesn't a GPU speed up the sequential nature of a training loop's iterations themselves?

Parallelism helps within an iteration's independent operations, not across genuinely dependent, sequential iterations.
