Designing a Robot FSM — A Worked Example

Turning a task description into states and transitions is a specific skill — worth walking through completely once, on a task with real edge cases.

← Lesson 31 Lesson 33 → Contents Glossary →

Lesson 31 introduced FSMs with a clean three-state example. This lesson works through a slightly messier, more realistic task end to end — a warehouse robot fetching a specific item — to make the actual design process concrete, edge cases included.

The task A robot receives an order for a specific shelf item. It must: navigate to the shelf (Unit 4's planning and Unit 5's motion control), pick the item (Unit 7 will cover manipulation directly, but for now, treat "pick" as a single sub-task), navigate to a drop-off station, and release the item — while handling the possibility that the item isn't actually where expected once the robot arrives.

A first pass at states: NavigatingToShelf, Picking, NavigatingToDropoff, Releasing, and Done. The straight-line transitions are the easy part: each state transitions to the next once its sub-task completes successfully. The design work that actually matters is in the conditions that don't go according to plan.

Why the failure transitions are the real design work A clean FSM design isn't the one that handles the expected path — that part is close to trivial. It's the one that has an explicit state and transition for every plausible way a sub-task can fail. What happens if the item isn't on the shelf? What happens if the pick attempt fails (Unit 7 will cover why grasps can fail)? A state machine with no transition defined for a real failure case doesn't handle it gracefully — it either crashes, hangs, or silently does the wrong thing, none of which is acceptable for hardware operating in a shared space.
Worked example Add an ItemMissing state, reached from NavigatingToShelf if the expected item isn't detected on arrival — transitioning onward to a ReportingIssue state rather than getting stuck. Add a retry path from Picking back to Picking itself (up to some attempt limit) if a single grasp attempt fails, since Unit 7 will establish that grasp failure is a normal, expected occurrence, not an emergency — with a transition to ReportingIssue only after repeated failures. Neither of these is exotic; both are exactly the kind of case a real warehouse robot encounters routinely, and both are things the clean three-state vacuum example from Lesson 31 never had to consider.

Notice how quickly the state count grew once real failure handling was added — five "happy path" states became seven or more once ItemMissing, ReportingIssue, and a retry loop were included, and this is still a comparatively simple task. That growth is exactly the scaling problem Lesson 31 flagged, and it's about to motivate the alternative the next two lessons introduce.

1. In designing a robot FSM for a real task, what does this lesson identify as the actual design work, as opposed to the easy part?

The straight-line 'everything works' transitions are close to trivial; handling plausible failure cases explicitly is where real design effort goes.

2. What happens to a state machine that has no transition defined for a real failure case it actually encounters?

An FSM with a missing transition for a real situation has no defined behavior for it, which is unacceptable for hardware operating in a shared space.

3. What happened to the state count in the worked example once real failure handling (ItemMissing, retries, ReportingIssue) was added?

Adding realistic failure handling grew the state count from five to seven or more — exactly the scaling problem that motivates looking at an alternative structure.

4. Fill in the blank: in the worked example, if the expected item isn't detected on the shelf, the FSM transitions to an ___ state rather than getting stuck.

The ItemMissing state explicitly handles this real failure case instead of leaving it undefined.

5. Fill in the blank: a transition from a state back to itself, used to allow a limited number of retry attempts before escalating, is called a ___ path.

A retry path lets a sub-task like picking be attempted more than once before escalating to a failure-handling state.
