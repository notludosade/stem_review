Finite State Machines for Robot Behavior

A robot's high-level behavior can often be described as a small number of named modes, and clear rules for switching between them.

← Lesson 30 Lesson 32 → Contents Glossary →

The CP1-level idea of a finite state machine — a fixed set of named states, with rules for transitioning between them based on conditions — turns out to be a natural way to structure the reactive-plus-deliberative decision logic Lesson 30 was building toward.

Definition A finite state machine (FSM) for robot behavior consists of a fixed set of states (named behavioral modes, like "searching," "approaching," "docked"), and transitions between them triggered by specific conditions (a sensor threshold, a timer, a completed sub-task). At any moment, the robot is in exactly one state, and its behavior is entirely determined by which state that is — plus whatever brought about the most recent transition.
Example A simple robot vacuum's high-level behavior can be modeled with three states: Cleaning (the default — driving a coverage pattern), Returning (heading back to its charging dock), and Charging (docked, topping up battery). The transition Cleaning → Returning fires when battery level drops below a threshold; Returning → Charging fires when the dock connection is detected; Charging → Cleaning fires once battery reaches full and some resume condition is met. Each state has simple, largely reactive behavior within it; the transitions are where the more deliberate "what should I be doing now" decisions live.
Why FSMs make behavior easier to reason about — and where that breaks down Because the robot is always in exactly one clearly named state, an FSM makes it straightforward to answer "what is the robot doing right now, and why" — a real advantage over an unstructured pile of conditional logic. The cost shows up as behaviors grow more complex: covering every situation with a manageable number of states, and every valid transition between them, gets unwieldy fast. Real robot behavior often needs many context-dependent variations within what conceptually feels like "one mode," which either explodes the state count or forces awkward workarounds — the exact problem Lesson 33's behavior trees are built to solve differently.

FSMs are a genuinely good fit for behavior that really does decompose into a small number of clearly distinct modes with clean transition conditions, and this lesson's vacuum example is a fair one. The next lesson works through a slightly richer worked example to make the diagramming and transition-writing concrete, before Lesson 33 introduces the alternative that scales better as behavior grows more complex.

Check your recall

No peeking back up — answer from memory first, then check.

1. In a finite state machine for robot behavior, what determines the robot's current behavior?

An FSM's robot is always in exactly one named state at a time, and that state fully determines its current behavior.

2. In the robot vacuum FSM example, what triggers the transition from Cleaning to Returning?

The example specifies battery level dropping below a threshold as the Cleaning → Returning transition condition.

3. What is the main drawback of finite state machines as robot behavior grows more complex?

As behavior complexity grows, FSMs tend to need an unwieldy number of states and transitions to capture every variation cleanly — the problem behavior trees are designed to address differently.

4. Fill in the blank: in a finite state machine, a named behavioral mode like 'searching' or 'docked' is called a ___.

States are the fixed set of named modes an FSM can be in; the robot is always in exactly one at a time.

5. Fill in the blank: the rule that moves an FSM from one state to another, triggered by a specific condition, is called a ___.

Transitions are triggered by conditions like sensor thresholds, timers, or completed sub-tasks.
