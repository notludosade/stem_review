Building and Reading a Behavior Tree

With the vocabulary in place, the remaining skill is purely practical: tracing execution through a tree, and building one for a task from scratch.

← Lesson 33 Lesson 35 → Contents Glossary →

Lesson 33 introduced the pieces. This lesson is about fluency — reading a tree diagram and correctly tracing what a robot running it would actually do, then building one for the full warehouse-fetch task from Lesson 32.

How to trace execution correctly Start at the root every tick, and evaluate top to bottom, left to right, exactly following each node's rule. For the tree above: the Selector tries its first child (the Sequence) first. The Sequence tries Attempt Grasp; if that fails, the Sequence immediately fails (without trying Verify Grasp), and the Selector then falls through to its second child, Report Failure. If Attempt Grasp succeeds, the Sequence proceeds to Verify Grasp; if that also succeeds, the whole Sequence succeeds, and the Selector — having gotten a success from its first child — never even looks at Report Failure at all.
Building the full warehouse-fetch tree Lesson 32's whole task becomes a top-level Sequence: [Navigate to Shelf] → [Picking subtree, as diagrammed above] → [Navigate to Dropoff] → [Release Item]. The ItemMissing handling from Lesson 32 slots in as its own Selector around the Navigate to Shelf step: try navigating and confirming the item is present; if that combination fails, fall through to a Report Issue leaf instead of proceeding to Picking. Every FSM state and transition from Lesson 32 has a direct structural counterpart here — the tree is not a different design, it's the same decisions, organized so that adding one more failure case means adding one more branch, not rewiring the whole machine.

Notice what didn't need a special mechanism: a critical-battery check can be added as a high-priority Selector branch checked before Navigate to Shelf even begins, and because the whole tree re-evaluates from the root every cycle (Lesson 33's Running status), that check keeps getting reconsidered throughout execution — reactive behavior, built directly into the same structure as the deliberate task sequence, exactly the reactive-plus-deliberative combination Lesson 30 said real robots need.

Check your recall

No peeking back up — answer from memory first, then check.

1. In the diagrammed tree (Selector over [Sequence of Attempt Grasp, Verify Grasp] and Report Failure), if Attempt Grasp fails, what happens next?

A Sequence fails immediately when any child fails, without running the remaining children — the Selector then tries its next option, Report Failure.

2. If both Attempt Grasp and Verify Grasp succeed, does the Selector ever evaluate Report Failure?

A Selector stops as soon as one child succeeds — since the Sequence succeeded, the Selector never needs to try Report Failure.

3. How does adding a critical-battery check as a high-priority Selector branch achieve reactive behavior without a separate mechanism?

Re-evaluating from the root every tick means a high-priority branch is checked repeatedly, letting it interrupt a Running lower-priority action without any bolted-on interrupt logic.

4. Fill in the blank: correctly tracing a behavior tree's execution means evaluating from the root, top to bottom, ___ to right, following each node's rule.

Standard behavior tree convention evaluates children left to right within each composite node.

5. Fill in the blank: in the warehouse-fetch tree, adding one more failure case to a behavior tree generally means adding one more ___, not rewiring the whole structure.

Behavior trees let new failure handling be added as an additional branch, unlike an FSM's need to wire new states and transitions throughout.
