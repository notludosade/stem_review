From Path to Motion Commands

A* hands back a list of waypoints. Motors need voltages and velocities. Something has to bridge that gap, continuously, in real time.

← Unit 4, Lesson 24 Lesson 26 → Contents Glossary →

Unit 4 ended with a robot able to compute a safe route: a sequence of graph nodes from start to goal, adjusted on the fly when reality disagreed with the map. That sequence of nodes is not, by itself, something a motor can act on. This unit is about motion control — turning a planned path into the specific, continuous commands that actually drive the robot along it.

Definition Motion control is the layer that converts a planned path (a sequence of positions, or waypoints, from Unit 4) into the low-level commands — wheel velocities, joint torques, motor voltages — that physically move the robot along that path. It sits between planning (deciding where to go) and the control-loop fundamentals this course's prerequisites already gave you (turning a commanded velocity into an actual motor signal).
Why "just drive toward the next waypoint" isn't quite enough A path from A* is a set of discrete points with no timing or smoothness attached — it says where, not how fast or how gently. Driving straight at each waypoint in turn, stopping and re-aiming at each one, would work but ride roughly and waste time. A robot needs a plan for when it should be at each point along the path (Lesson 26), a way to correct for the small errors that build up while executing that plan (Lesson 28), and — since real motors and wheels can't change speed or direction instantly — some smoothing of sharp corners into paths the robot can physically follow (Lesson 29).
Example A* returns the waypoints (0, 0) → (2, 0) → (2, 3) — a path with a sharp 90° corner. A robot literally trying to hit (2, 0) exactly before turning toward (2, 3) would have to stop dead, pivot in place, and accelerate again — slow, jerky, and hard on the hardware. Motion control's job is producing a smoother, still-safe motion that gets the robot from one leg of the path to the next without that abrupt stop, while still respecting the obstacles the path was planned around.

This unit assumes you already know, from Mechatronics-level prerequisites, that a control loop compares a desired value against a measured one and produces a correcting command. What's new here is what gets fed into that loop: not a single fixed setpoint, but a moving target — a point on the path that itself advances as the robot progresses. The next four lessons build that up in order: first timing the path, then following it, then correcting drift from it, then smoothing its rough edges.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the role of motion control in the pipeline this course has been building?

Motion control sits after planning (Unit 4) and turns its output — a sequence of waypoints — into actual motor commands.

2. Why is a raw list of waypoints from A* not sufficient by itself to drive a robot smoothly?

A* answers 'where' but not 'how fast' or 'how gently' — motion control has to add timing and smoothness the raw path doesn't specify.

3. What problem does driving straight at each waypoint in turn, stopping and re-aiming at each one, create?

Stopping to pivot at each waypoint corner produces slow, jerky motion — motivating the trajectory generation and smoothing this unit covers.

4. Fill in the blank: the layer that converts a planned path into low-level commands like wheel velocities or motor voltages is called motion ___.

Motion control bridges planning (deciding where to go) and the underlying control-loop hardware that actually moves the robot.

5. Fill in the blank: a single point along a planned path, such as one of A*'s returned positions, is called a ___.

Waypoints are the discrete points a path passes through; motion control is what turns them into continuous motion.
