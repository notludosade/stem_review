Trajectory Smoothing

The best correction is the one you never had to make — smoothing a path's sharp corners before execution reduces the whole burden on everything downstream.

← Lesson 28 Unit 6, Lesson 30 → Contents Glossary →

Lessons 26 through 28 built a full pipeline for executing a path: time it, steer along it, correct for drift from it. This closing lesson covers a complementary idea — improving the path itself, before execution ever starts, so there's simply less for that pipeline to fight against.

Definition Trajectory smoothing is the process of modifying a planned path to reduce sharp corners and abrupt direction changes, producing a path with gentler curvature the robot can follow at higher speed with less aggressive steering — while still respecting the obstacles the original path was planned around.

A* (Unit 4) returns paths built from the discrete grid it searched — often exactly the sharp 90° turns and blocky corners Lesson 25 used as its motivating example, because those are the only moves the underlying graph offered. Nothing about A*'s search process favors smooth motion; it only favors low-cost paths through the graph as built. Smoothing is a separate step, run after search, that reshapes the returned path into something closer to what a real robot can execute gracefully.

Why smoothing pays off at every downstream stage A smoother path lets Lesson 26's trajectory generation produce a schedule with less deceleration-and-reacceleration around corners, lets Lesson 27's steering track more gently, and reduces how hard Lesson 28's feedback controller has to work to correct tracking error — because there's less abrupt geometry for any of those stages to struggle against in the first place. Smoothing is not a cosmetic nicety; it reduces real, physical demand on the whole downstream pipeline.
Example The blocky path (0,0) → (2,0) → (2,3) from Lesson 25's sharp-corner example can be replaced with a smooth curve that starts bending before reaching (2,0) and finishes bending shortly after, passing near — but not exactly through — the original corner point, while staying clear of the same obstacles the original path avoided. The robot never has to fully stop and pivot; it flows through the turn at reduced but nonzero speed instead.

Smoothing has to be checked against the same obstacles the original path respected — a smoothed curve that cuts a corner too aggressively could reenter an obstacle the blocky path correctly avoided, which is exactly why smoothing is a refinement layered on top of a validated path, not a replacement for the planning and configuration-space reasoning (Unit 4) that made the original path safe.

This closes Unit 5. A planned path can now be timed, followed, corrected, and smoothed into an actual, physically executable motion. Check your recall

No peeking back up — answer from memory first, then check.

1. What is the goal of trajectory smoothing?

Smoothing reshapes a path's geometry for gentler, more executable motion, without abandoning the obstacle clearance the original path already established.

2. Why do A*-generated paths often contain sharp corners in the first place?

A*'s output reflects the discrete graph structure it searched; smoothness was never part of what the search algorithm was optimizing for, only path cost.

3. Why must a smoothed path still be checked against the original obstacles, rather than trusted automatically?

Smoothing reshapes geometry near corners, which risks cutting into an obstacle if not explicitly re-checked — it's a refinement on a validated path, not an independent guarantee of safety.

4. Fill in the blank: modifying a planned path to reduce sharp corners while still respecting obstacles is called trajectory ___.

Trajectory smoothing is the process of reshaping a path for gentler, more executable motion.

5. Fill in the blank: a smoother path reduces demand on trajectory generation, steering, and feedback correction because there is less abrupt ___ for any of those stages to fight against.

Smoother geometry means less deceleration, gentler steering, and smaller tracking corrections needed throughout the downstream execution pipeline.
