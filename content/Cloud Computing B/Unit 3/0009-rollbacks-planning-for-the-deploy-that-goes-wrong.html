Rollbacks: Planning for the Deploy That Goes Wrong

Lesson 8's canary and blue-green strategies limit how many users see a bad deploy. Neither one decides what to actually do once one's been caught — that's a separate decision, and it needs to be made before the incident, not during it.

← Lesson 8 Unit 4, Lesson 10 → Contents Glossary →

Every deployment strategy in this unit reduces risk — none of them reduces it to zero. Something will eventually pass every test, look clean on a canary slice, and still break in a way nobody predicted. What happens in the next five minutes depends entirely on whether the team decided how to respond back when they were calm, or is deciding it for the first time while the site is down.

Three ways to actually respond

Definition A rollback reverts a deployment to the last known-good version — undoing the bad change rather than fixing it in place. Roll-forward is the opposite: instead of reverting, the team ships a new deploy that fixes the problem. Rollback is usually faster, since the previous version is already known to work; roll-forward is sometimes the only real option, if reverting isn't safe (for example, a database migration that already ran can't simply be un-run).
Definition A feature flag is a runtime switch, checked by the running code itself, that turns a specific piece of functionality on or off without a new deployment. Used as a "kill switch," a feature flag can disable exactly the broken feature in seconds — faster than any rollback or roll-forward, since nothing has to be rebuilt, retested, or redeployed at all.

Worked example: why a rollback isn't always available A deploy adds a new required column to the production database and starts writing to it immediately. The new code breaks — but rolling back the application code alone now points old code at a database schema it was never written for, which can break just as badly, sometimes worse. Here the safe path is usually roll-forward: ship a fix that doesn't depend on reverting the database change. This is exactly why database migrations get special handling in serious infrastructure as code practice (Unit 4) — they're one of the few changes that a rollback can't cleanly undo.
Why the rollback plan has to exist before the deploy, not after Deciding "how would we undo this if it goes wrong" during the incident wastes exactly the time that matters most — every minute spent figuring out whether a rollback is safe, whether a feature flag exists for this code path, or who has permission to trigger either one, is a minute the bad deploy keeps affecting real users. Teams that treat rollback planning as part of writing the deploy, not as an afterthought, turn "the deploy broke something" from a crisis into a five-minute routine.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the key difference between a rollback and rolling forward?

Rollback reverts; roll-forward fixes without reverting — they solve the same problem two different ways.

2. Why might a rollback not be safe after a deploy that included a database migration?

A schema change that already ran can leave reverted code mismatched with the current database state.

3. Why can a feature flag "kill switch" mitigate an incident faster than a rollback or roll-forward?

A flag flip is nearly instant because it skips the entire build-test-deploy cycle.

4. Fill in the blank: reverting a deployment to the last known-good version, rather than fixing the problem in place, is called a ___.

A rollback is usually faster than a fix, since the previous version is already known to work.

5. Fill in the blank: a runtime switch checked by running code that turns a specific piece of functionality on or off without a new deployment is called a ___.

Feature flags can disable broken functionality in seconds, without touching the deployment pipeline at all.
