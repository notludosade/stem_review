Designing a CI/CD Pipeline for a Real Application

Every unit so far taught one stage of the pipeline Lesson 3 mapped, in isolation. This lesson doesn't introduce anything new — it's about combining all six units into one coherent pipeline design, and noticing that the right combination changes completely depending on what's actually being built.

← Unit 6, Lesson 18 Lesson 20 → Contents Glossary →

There's no single "correct" CI/CD pipeline — only a pipeline that fits a specific team's risk tolerance, a specific application's blast radius if something breaks, and a specific organization's regulatory or business constraints. This lesson is the judgment call of combining CI cadence, deployment strategy, infrastructure management, orchestration, and observability into one design, for three genuinely different real applications.

A shared measuring stick

Definition The DORA metrics are four measures — deployment frequency, lead time for changes, change failure rate, and time to restore service — that research has repeatedly found separate high-performing DevOps teams from low-performing ones, regardless of company size or industry. Nearly every practice this course has covered exists to move one of these four in the right direction: CI (Unit 2) and small merges shrink lead time; canary releases and rollback plans (Unit 3) shrink change failure rate; self-healing (Unit 5) and good alerting (Unit 6) shrink time to restore. A pipeline design is really just a set of concrete choices aimed at all four at once.

See how the design changes with the application

The same six units of tools and practices produce three different pipelines below, depending only on what's actually being shipped.

Interactive: matching a pipeline design to a real application

Shape: five engineers, low regulatory burden, needs to move fast to find product-market fit.

  • CI (Unit 2): every merge auto-built and tested; a small, fast suite that gives an answer in minutes.
  • Deployment (Unit 3): Continuous Deployment, no release gate — the team trusts its test suite and ships many small changes a day, using blue-green for simplicity.
  • IaC (Unit 4): one declarative repo, reconciled automatically on every merge to main.
  • Orchestration (Unit 5): a small cluster, desired replica count of 2–3, mostly for redundancy rather than raw scale.
  • Observability (Unit 6): a handful of high-signal alerts (error rate, uptime) pointed at a single-person on-call rotation.

Shape: handles real money, subject to audit, a bad deploy has real regulatory and financial consequences.

  • CI (Unit 2): the same build-and-test rigor, plus a mandatory security scanning step before anything is considered green.
  • Deployment (Unit 3): Continuous Delivery with a release gate — compliance requires human sign-off — followed by a canary release, since limiting blast radius on financial data matters.
  • IaC (Unit 4): every infrastructure change requires two-reviewer approval; reconciliation runs on a strict schedule, and drift triggers an alert instead of silently auto-correcting.
  • Orchestration (Unit 5): higher replica counts spread across multiple availability zones, with explicit resource limits per pod.
  • Observability (Unit 6): tracing is mandatory on every request for audit purposes; tiered alerts mean only true customer-impacting issues page the rotation, the rest become tickets.

Shape: millions of users, traffic that spikes unpredictably, a bug at 100% rollout affects an enormous number of people instantly.

  • CI (Unit 2): a fast, heavily parallelized suite — the fail-fast ordering from Unit 2 matters enormously at this size of codebase.
  • Deployment (Unit 3): canary releases by default, gradually shifting traffic, since even a small bug affects a large absolute number of users.
  • IaC (Unit 4): infrastructure defined per-region, since the application runs across many regions at once.
  • Orchestration (Unit 5): aggressive autoscaling, with replica count driven by real-time request-rate metrics rather than a fixed number.
  • Observability (Unit 6): genuinely uses all three signals from Lesson 16 — metrics for trend dashboards, logs for incident deep-dives, and traces for cross-service latency debugging.
Why the "right" pipeline differs by trust and risk, not just by app type Two companies with nearly identical applications can reasonably land on different pipelines, because the difference isn't really about the code — it's about how much a bad deploy costs, and how much the team currently trusts its own tests and monitoring. That's exactly the same trust decision Unit 3 raised about release gates, and Unit 3's point about canary requiring mature per-slice monitoring: a team can't safely skip a release gate it doesn't yet have the test coverage to justify skipping, and it can't safely lean on a canary strategy without the observability from Unit 6 to actually notice a problem in a thin slice of traffic. A pipeline design is only as good as the trust it's actually built on.

A high-traffic app's varied observability needs are exactly why the three signals are complementary, not redundant.
