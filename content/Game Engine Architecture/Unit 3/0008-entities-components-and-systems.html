Entities, Components, and Systems

Lesson 7's flying-swimming boss had no clean home in an inheritance tree. This lesson introduces the model nearly every modern engine uses instead — one that makes "flies and swims" a non-event.

← Lesson 7 Lesson 9 → Contents Glossary →

Instead of asking "what class of thing is this object?", an ECS asks a different question entirely: "what data does this object currently have attached to it?" A flying, swimming boss isn't a special class squeezed into a tree — it's just an object with a Flying component and a Swimming component both attached, exactly like any other combination.

Three words, three very different jobs

Definition An Entity is nothing more than an identifier — often literally just an integer ID — with no behavior and no data of its own. A Component is a plain bundle of data (a Position component holds x/y coordinates; a Health component holds a current and max value) with no logic attached. A System is where all the logic lives: a function that runs every frame, finds every entity that has a specific combination of components, and operates on their data. An entity's "type" is entirely defined by which components happen to be attached to it right now — nothing more.

Worked example An entity with Position and Sprite gets drawn by the Render System but ignored by the Movement System (no Velocity) — a perfectly normal static prop. Add Velocity and the exact same entity, unchanged otherwise, is now also picked up by the Movement System next frame. Nothing was reclassified, no class hierarchy was touched — a system's job is entirely defined by which components it looks for, not by what "kind" of object it's looking at.
Why this fixes Lesson 7's diamond problem outright The flying-swimming boss from Lesson 7 simply has a Flying component and a Swimming component attached to the same entity — there is no tree to strain, because there is no tree. Adding a new behavior to an existing object type is just attaching one more component; it never requires restructuring anything else, and it never asks "which parent's version wins" because components don't have parents at all. This is composition, not inheritance, applied at the scale an entire game world needs.

1. In an ECS, what actually defines an entity's "type"?

An entity's effective "type" is just whatever components are currently attached.

2. Where does game logic actually live in an ECS?

Systems are specifically where all behavior/logic lives in this pattern.

3. Why does giving an existing entity a new behavior (say, making it fly) not require restructuring anything else?

Components are flat, independent data bundles with no hierarchy to strain when combined.

4. Fill in the blank: a plain bundle of data with no attached logic, like Position or Health, is called a ___.

A component is data-only, with logic living elsewhere, in systems.

5. Fill in the blank: an identifier with no behavior and no data of its own, which components get attached to, is called an ___.

An entity is just an ID — the components attached to it carry the actual data.
