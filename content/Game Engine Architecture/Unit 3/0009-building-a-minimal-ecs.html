Building a Minimal ECS

Lesson 8 explained entities, components, and systems conceptually. This lesson makes it concrete: a tiny ECS in pseudocode, and a live simulation of one tick of its update loop.

← Lesson 8 Unit 4, Lesson 10 → Contents Glossary →

Strip an ECS down to its essentials and it's really just three things: a way to create entity IDs, a way to attach component data to an ID, and a loop that runs each system over the entities that match what it needs.

The whole thing, minimized

Definition A minimal ECS needs: (1) an entity registry that hands out fresh IDs and tracks which are alive, (2) one component store per component type — commonly a map from entity ID to that component's data — and (3) a system update loop, run once per game-loop tick (Unit 2), where each system queries for every entity ID present in all of its required component stores at once, then updates that data in place. 
// pseudocode: a movement system's entire body
function MovementSystem(world, dt) {
    // query: entities present in BOTH the Position and Velocity stores
    for (id in world.query(Position, Velocity)) {
        world.Position[id].x += world.Velocity[id].dx * dt;
        world.Position[id].y += world.Velocity[id].dy * dt;
    }
}

Notice dt in that loop — Unit 2's delta time shows up again here, exactly as it does in every other per-frame update.

Worked example Entity #1 has Position{x:0} and Velocity{dx:5}. The registry knows #1 exists; the Position store knows its x; the Velocity store knows its dx — three completely separate pieces of storage, tied together only by sharing the same ID, #1. When Movement System's query runs, it asks each store "do you have data for #1?" — both say yes, so #1 gets updated. An entity with only Health would fail that same query instantly, because the Position store has nothing filed under its ID at all.
Why storing components this way (not as objects on the entity) matters It would be simpler to just attach a list of component objects directly onto each entity object. Real ECS implementations usually don't, because storing all Position data contiguously in one array — rather than scattered across many separate entity objects — lets a system iterate through it with far better memory access patterns, which matters enormously at thousands of entities and sixty updates a second. This performance-driven layout choice is exactly why ECS became the standard in performance-critical engines rather than staying a purely academic idea.

Check your recall

No peeking back up — answer from memory first, then check.

1. What ties an entity's separate pieces of component data together?

The shared entity ID, used as a key into each component store, is what ties the data together.

2. What does a system's "query" actually do?

A query filters entities down to those matching a required set of components.

3. Why do real ECS implementations usually store each component type contiguously in its own array, rather than as a list of objects on each entity?

Contiguous, per-type storage is a performance-driven choice for large-scale, per-frame iteration.

4. Fill in the blank: the operation a system performs to find every entity that has all of its required components is called a ___.

A query is exactly this component-matching lookup a system performs.

5. Fill in the blank: a map from entity ID to that component type's data, one per component type, is called a ___.

Each component type gets its own store, keyed by entity ID.
