Scene Management and State Machines

Every lesson so far assumed one continuous game world. Real games have a main menu, a pause screen, a level, a game-over screen — very different modes, and the engine has to know exactly which one it's in at all times.

← Lesson 19 Lesson 21 → Contents Glossary →

Pressing "Start" should load a level and not somehow also render the main menu underneath it, still listening for menu clicks. Pressing "Pause" should stop the world from updating without unloading it — the player should come back to exactly where they left off. Both of these are the same underlying problem: the game is always in exactly one well-defined mode, and something has to enforce that.

Exactly one state at a time, with defined transitions

Definition A scene is a distinct, loadable collection of game state — a menu, a level, a loading screen — usually with its own scene graph (Unit 4). A state machine is a system that's always in exactly one of a fixed set of named states, moving between them only along explicitly defined transitions (Menu → Playing is valid; Playing → Menu directly, skipping Pause, might not be). Engines commonly use a state machine to manage which scene is active, ensuring the game is never rendering or updating two incompatible modes at once.

Worked example From Playing, pressing pause transitions to Paused — the level's scene stays fully loaded in memory, its update() calls simply stop running (Unit 2's game loop, selectively frozen), while render() keeps drawing its last frame underneath a pause overlay. From Paused, only two transitions are valid: back to Playing (resume exactly where the player left off) or to Menu (quit to menu, unloading the level entirely). Jumping straight from Paused to GameOver was never a transition anyone defined — the state machine simply won't allow it.
Why an explicit state machine beats a tangle of boolean flags An early, informal version of this might be a handful of booleans — isPaused, isInMenu, isGameOver — checked all over the codebase. Nothing stops isPaused and isGameOver from both accidentally being true at once, a combination that was never supposed to exist and that no single piece of code is responsible for preventing. An explicit state machine makes "exactly one state, only valid transitions" a property of the system's structure itself, not a rule every future contributor has to remember and re-enforce by hand.

1. What guarantee does a state machine provide that a handful of independent boolean flags doesn't?

Structural enforcement of "exactly one state" is the core guarantee a state machine provides.

2. What happens to a level's scene when the game transitions from Playing to Paused?

Pausing selectively stops update() while keeping the scene resident and still rendering.

3. Why can independent boolean flags like isPaused and isGameOver lead to bugs a state machine avoids?

Unconstrained flags allow invalid combinations that a state machine's structure rules out entirely.
