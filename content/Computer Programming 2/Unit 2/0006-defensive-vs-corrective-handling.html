Defensive vs Corrective Handling

Two honest ways to handle a risky operation: check first, or try it and catch the failure. Neither is universally "more correct."

Lesson 7 → Contents Glossary →

Defensive handling checks a condition before acting, so the risky operation never runs unless it's safe. Below, all four look up a key in a map before reading it, avoiding a missing-key failure entirely.

Python 
if "key" in my_dict:
    value = my_dict["key"]
else:
    value = "default"
Java 
String value;
if (myMap.containsKey("key")) {
    value = myMap.get("key");
} else {
    value = "default";
}
JavaScript 
let value = myMap.has("key") ? myMap.get("key") : "default";
C++ 
std::string value;
if (myMap.count("key")) {
    value = myMap["key"];
} else {
    value = "default";
}

This style is often called LBYL — "look before you leap." It's the natural fit in Java and C++, where an unhandled exception is comparatively costly to set up and where a missing key might not even throw a catchable exception at all. Python's own standard culture actually leans the opposite way for exactly this situation, a style called EAFP — "easier to ask forgiveness than permission." A Pythonic version of the same lookup just tries the access and reacts if it fails:

try:
    value = my_dict["key"]
except KeyError:
    value = "default"

Both snippets above produce the exact same result. The difference is entirely about idiom and cost. Python's dictionary lookups are cheap to try and its exceptions are cheap to raise, so checking first buys nothing and is considered less idiomatic there — most Python style guides actively prefer the try/except version. (Python actually offers a third option here too — my_dict.get("key", "default") — which is defensive in spirit but written as a single expression; worth knowing it exists, even though it doesn't fit this lesson's four-language comparison.)

Definition Defensive (LBYL) handling checks a condition before attempting a risky operation, preventing failure rather than reacting to it. Corrective (EAFP) handling attempts the operation directly and reacts if it fails, via try/catch.
Why it matters here Neither approach is more "correct" in the abstract — matching the idiom your language's community actually expects is itself part of writing professional code, the same theme the ethics course raised about code as something other people have to read and trust. Java or C++ written in a heavily EAFP style, or Python written in a heavily LBYL style, both work — but both read as unfamiliar to someone fluent in that language's usual conventions.
