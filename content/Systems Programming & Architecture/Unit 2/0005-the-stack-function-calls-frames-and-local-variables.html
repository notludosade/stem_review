The Stack: Function Calls, Frames, and Local Variables

Every function call you've ever written — in Python, Java, or C — used a stack to do it, whether you noticed or not. This lesson makes that machinery visible: what actually gets pushed, what gets popped, and why local variables vanish the instant a function returns.

← Lesson 4 Lesson 6 → Contents Glossary →

Lesson 4 named the stack as one of the four regions of a process's address space. This lesson opens it up: every time a function is called, something concrete gets added to the stack, and every time a function returns, that same thing gets removed — in strict last-in-first-out order.

Stack frames: one per active function call

Definition A stack frame (or activation record) is a block of memory pushed onto the stack every time a function is called, holding that call's local variables, its parameters, and its return address — where execution should resume in the calling function once this one finishes. When the function returns, its entire frame is popped off the stack in one step, and every local variable it held is gone — not zeroed out and cleaned up individually, just no longer considered part of the stack at all.
Worked example Consider main() calling square(3), which calls multiply(3, 3). At the deepest point, the stack holds three frames at once, bottom to top: main's frame, then square's frame (holding its parameter n = 3 and the return address back into main), then multiply's frame (holding a = 3, b = 3, and the return address back into square). When multiply returns its result, its frame is popped, execution resumes in square exactly where it left off, and the stack is back to two frames.

Why local variables can't outlive their function

Why a pointer to a local variable becomes invalid the moment its function returns A local variable's storage is a specific slice of its stack frame. The instant that function returns, its frame is popped — that memory is no longer reserved for anything, and the very next function call can (and often will) immediately overwrite it with a completely different frame. A function that returns the address of one of its own local variables is handing back a pointer to memory that is about to be reused for something else entirely. This exact mistake gets its own name and its own lesson later this unit (Lesson 9) — remember it started here: local variables live and die with their stack frame, full stop.

Stack overflow: running out of room

Definition A stack overflow happens when the stack grows past the space reserved for it — most commonly from recursion that never reaches its base case, pushing a new frame for every call with nothing to stop it. The OS detects the stack running into memory it doesn't own and terminates the program immediately, rather than letting it silently corrupt whatever comes next in memory.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does a stack frame hold?

A frame is per-call bookkeeping: locals, parameters, and where to resume execution afterward.

2. In what order are stack frames removed relative to the order they were added?

The stack is strictly last-in-first-out: whichever call is deepest returns, and is popped, first.

3. Why is returning the address of a local variable from a function dangerous?

The frame's memory isn't erased, but it's no longer reserved — the next call can overwrite it at any time.

4. Fill in the blank: the value stored in a stack frame telling execution exactly where to resume in the calling function is called the ___.

The return address is exactly how the CPU knows where to continue once the called function finishes.

5. Fill in the blank: when unbounded recursion pushes frames past the space reserved for the stack, and the OS terminates the program, this is called a ___.

Stack overflow is the OS's way of stopping a runaway stack before it corrupts adjacent memory.
