How Integers Are Actually Stored (Two's Complement, Overflow)

Units 2 and 3 treated an int as an opaque four-byte value. This unit opens it up. First question: how does a fixed number of bits represent negative numbers at all — and what happens when a number gets too big to fit?

← Unit 3, Lesson 9 Lesson 11 → Contents Glossary →

A 32-bit int is exactly 32 bits — no more, no less — no matter what value it holds. Every representation scheme has to answer two questions inside that fixed budget: how do you represent a negative number using only 0s and 1s, and what happens the instant a calculation's true answer needs one more bit than you have?

Unsigned: the easy case

Definition An unsigned integer stores only non-negative values, interpreting its bits directly as a plain binary number. An 8-bit unsigned value ranges from 00000000 (0) to 11111111 (255) — 28 = 256 distinct values, all non-negative.

Two's complement: how negatives actually work

Definition Two's complement is the representation essentially every modern processor uses for signed integers. The leading bit still participates in the value's magnitude, but it's weighted negative: for an 8-bit value, the bits represent −128, 64, 32, 16, 8, 4, 2, 1 from left to right, instead of unsigned's 128, 64, 32, 16, 8, 4, 2, 1. To negate a value, flip every bit and add 1 — 00000101 (5) becomes 11111010, plus 1 is 11111011 (−5). The huge practical payoff: addition works identically whether the processor is treating the bits as signed or unsigned — one adder circuit handles both, with no special-casing for negative numbers at all.

Overflow: running out of bits

Definition Integer overflow happens when the true mathematical result of an operation needs more bits than the type has. For an 8-bit signed value, the maximum is 127 (01111111); adding 1 produces 10000000 — which, read as two's complement, is −128, not 128. The bits did exactly what addition always does; there simply weren't enough of them to hold the true answer, so the result silently wrapped around.
Worked example In C, int8_t x = 127; x = x + 1; gives x the value -128 — not an error, not a crash, just a wrong-looking number that is nonetheless exactly what two's complement arithmetic produces from those bits. Signed overflow in C is technically undefined behavior (Unit 8) rather than a guaranteed wraparound, which is precisely why compilers are allowed to optimize code as if it never happens — a real and recurring source of subtle bugs in C code that assumes wraparound is safe to rely on.
Why this isn't just trivia — it causes real bugs A loop counter of type unsigned int that's decremented past zero doesn't go negative — it wraps around to a huge positive number (4,294,967,295 for a 32-bit unsigned int), instantly turning a "loop until this reaches zero" into an effectively infinite loop that reads or writes memory far outside where it should. This exact bug class has caused real, shipped security vulnerabilities: an attacker supplies a length value designed to overflow a size calculation, and code that trusted the wrapped-around result ends up allocating far less memory than it thinks it did.
