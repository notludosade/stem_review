Object Storage vs. Block Storage vs. File Storage

A VM's disk, a database's data files, and a bucket of user-uploaded photos are all "storage" — but they need three genuinely different kinds of storage underneath, and picking the wrong one shows up immediately as either terrible performance or needless cost.

← Unit 2, Lesson 6 Lesson 8 → Contents Glossary →

A VM in Unit 2 is often ephemeral — stop it, and whatever was only in its memory is gone. Data that needs to survive past any one VM's lifetime, or be shared across many of them, has to live in a separate storage service. Cloud providers offer three distinct storage models, and they are not interchangeable: each is optimized for a different access pattern, and using the wrong one for a given job is one of the most common early cloud-architecture mistakes.

Object storage: flat, massive, and accessed as whole files

Definition Object storage (Amazon S3, Google Cloud Storage, Azure Blob Storage) stores data as discrete "objects" — a file plus its metadata — in a flat namespace, retrieved and written as whole units through a simple HTTP-based API, not mounted as a traditional filesystem. It scales to effectively unlimited size and is built for durability (Lesson 8) at very low cost per gigabyte, but it's not designed for editing a small piece of a large file in place — you replace the whole object.

Block storage: raw disks, attached to one machine

Definition Block storage (Amazon EBS, Azure Managed Disks) presents raw storage as fixed-size blocks, functioning as a virtual hard disk attached to a single VM at a time. The VM's operating system formats it with a normal filesystem and reads/writes small chunks of it constantly and with very low latency — exactly what a database or a VM's own boot disk needs, since both make frequent, small, random reads and writes rather than replacing whole files at once.

File storage: one shared filesystem, many machines at once

Definition File storage (Amazon EFS, Azure Files) provides a traditional hierarchical filesystem — folders and files, accessed with normal file operations — but over the network, so multiple VMs can mount and read/write the same filesystem concurrently. Block storage, by contrast, normally attaches to only one VM at a time.
Matching each to a real job A photo-sharing app storing millions of user-uploaded images, each written once and read many times, belongs in object storage — cheap, durable, and never needs in-place editing. A production database's data files, constantly read and rewritten in small chunks with strict low-latency demands, belong on block storage attached directly to the database server's VM. A fleet of 50 web servers that all need to read and write the same shared configuration directory or content library simultaneously needs file storage, since block storage can't be attached to 50 machines at once.

Why the wrong choice hurts immediately Put a busy database's data files on object storage and every write becomes a slow whole-object replacement instead of a fast small in-place update — the database grinds to a crawl. Put millions of rarely-changed user photos on block storage and you're paying for an always-attached virtual disk sized for your whole photo library, plus you still need to build your own way to serve those files to the internet, reinventing what object storage already does for free. The three models aren't ranked best-to-worst; they're matched to genuinely different access patterns.

Check your recall

No peeking back up — answer from memory first, then check.

1. Which storage model is the best fit for millions of user-uploaded photos, each written once and read many times?

Object storage is built exactly for large volumes of whole files written once and read often.

2. Why is block storage a better fit than object storage for a busy production database's data files?

The access pattern — small, frequent, random reads/writes — is exactly what block storage is optimized for.

3. A fleet of 50 web servers all need to read and write the same shared content directory at the same time. Which storage model fits, and why?

File storage is specifically built for concurrent, multi-machine access to one shared filesystem — block storage normally attaches to only one VM at a time.

4. Fill in the blank: storage that keeps data as discrete files-plus-metadata in a flat namespace, accessed as whole units through an HTTP API, is called ___ storage.

Object storage's flat namespace and whole-object API access set it apart from block and file storage.

5. Fill in the blank: storage that presents raw, fixed-size storage as a virtual hard disk attached to a single VM at a time is called ___ storage.

Block storage's single-VM attachment and raw-block access make it the right fit for a database's data files.
