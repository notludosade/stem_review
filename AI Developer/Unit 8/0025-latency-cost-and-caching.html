Latency, Cost, and Caching

Lesson 24's endpoint works for one request. Once real users depend on it, every single call has a real cost and a real wait attached — and both add up fast.

Lesson 26 → Contents Glossary →

Latency is the time between sending a request and receiving a response — for an LLM API call, often a full second or more, since the model generates its answer piece by piece. Every call also has a real dollar cost, typically priced per token of input and output. A tool called by thousands of users, on the same handful of repeated questions, pays that cost and that wait again for every single one — unless identical requests are answered from a cache instead.

Python — measuring latency and caching repeats 
import time
import hashlib

cache = {}

def triage_ticket_cached(ticket_text):
    key = hashlib.sha256(ticket_text.encode()).hexdigest()
    if key in cache:
        return cache[key]

    start = time.time()
    result = triage_ticket(ticket_text)   # from Lesson 23
    elapsed = time.time() - start
    print(f"latency: {elapsed:.2f}s")

    cache[key] = result
    return result

hashlib.sha256 turns the ticket text into a fixed-length key, so two identical tickets produce the exact same cache entry. The first time a given ticket text arrives, it pays the full latency and cost of a real API call; every identical repeat after that returns instantly from cache, with no API call at all. A cache like this only helps when genuinely identical requests repeat — for a support-ticket tool where wording rarely matches exactly, a real system would need a smarter cache, perhaps keyed on Lesson 19's embeddings instead of exact text.

Definition Latency is the time between sending a request and receiving a response. A cache stores the result of a previous request so an identical future request can be answered instantly, without repeating the original work.
Why it matters here Every lesson through Unit 7 treated a model call as free and instant, for the sake of focusing on what the call actually does. In a real deployed system, it's neither — cost and latency are constraints just as real as accuracy, and ignoring them is exactly how a working prototype turns into an unusably slow or expensive production system.
