1. A team wants to detect duplicate support tickets. Which of these best describes the "baseline" Lesson 22 recommends starting with?

A baseline is the simplest possible working solution, built first as a benchmark for anything more complex.

2. Fill in the blank: per Lesson 22, if a handful of simple if-statements would already correctly solve the task, the fastest, cheapest, and easiest-to-debug choice is plain ___ code.

choose_approach checks rules_would_work first — genuinely sufficient rule-based code beats any model on cost and simplicity.

3. A developer building a recipe app wants a model to reply with {"dish": "...", "servings": "..."} instead of a paragraph description. What should the API call request?

Requesting a response shaped as data, like JSON, instead of free-form prose is exactly what structured output means.

4. Fill in the blank: Lesson 23 keeps triage_ticket free of any database or user-interface code so it can be tested with ordinary function calls, entirely in ___ — separate from any live application.

Testing the core logic in isolation is far easier than testing it through a live application.

5. What best describes an API endpoint, as used in Lesson 24?

/triage in Lesson 24 is exactly this: a URL the application listens on for incoming requests.

6. Answer both parts about a task that is common and general, like drafting a routine email reply:

(a) What does Lesson 22 say is the right first move for a task like this?

(b) Fill in the blank: whichever option is tried first should be treated as a ___ that any fancier approach must then clearly beat.

(a) A common, general task has likely already been solved well by a pretrained API. (b) Whatever is tried first is still a baseline — something for a fancier approach to beat.

7. Suppose the model responds with valid JSON but sets "urgency": "urgent" instead of one of the three allowed categories. Answer both parts:

(a) What happens in triage_ticket?

(b) Fill in the blank: this safe substitute result, returned when the primary logic can't be trusted, is called a ___.

(a) "urgent" isn't one of the three allowed categories, so the ValueError check catches it and a safe default is returned. (b) That safe substitute is called a fallback.

8. Answer both parts about why triage_ticket checks the urgency value against ("low", "medium", "high") even after explicitly asking the model for one of them:

(a) Why is this check needed at all?

(b) Fill in the blank: an urgency value outside the three allowed categories triggers a ___, which the except block then catches.

(a) A model's structured output can still come back malformed, so it's checked rather than blindly trusted. (b) That check raises a ValueError, caught by the surrounding except block.

9. A different endpoint declares class ReviewRequest(BaseModel): text: str = Field(min_length=1, max_length=2000), and FastAPI rejects a request with an empty text field before the core function ever runs. Answer both parts:

(a) What is this an example of?

(b) Fill in the blank: this general practice — checking incoming data against an expected shape before use — is called input ___.

(a) FastAPI enforces the declared shape automatically, rejecting anything that doesn't match — that's input validation. (b) The general term for this practice is input validation.

10. Answer both parts about why triage_ticket could be dropped into a FastAPI endpoint with zero changes:

(a) Why didn't it need any changes?

(b) Fill in the blank: keeping a feature's core ___ separate from its application wiring is exactly what makes it reusable across different interfaces.

(a) It was already built and tested as a plain, self-contained function. (b) Separating core logic from application wiring is exactly what makes it reusable.
