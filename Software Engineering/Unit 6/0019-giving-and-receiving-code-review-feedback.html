Giving and Receiving Code Review Feedback

Blocking issues versus nits, and how to leave a comment that improves the code without stalling the team.

← Lesson 18 Unit 7, Lesson 20 → Contents Glossary →

Lesson 18 covered why code review matters. This lesson covers the practical skill of actually doing it well — a skill distinct from writing good code, and one that's rarely taught directly even though nearly every professional engineer practices it daily.

Not every comment carries the same weight

Blocking issues A genuine problem that must be fixed before the change can merge: a bug, a missed requirement, a real design flaw. These should be labeled unambiguously so the author knows the pull request can't merge until addressed.
Nits Small, optional suggestions — a naming preference, a minor style choice — that improve the code but aren't worth blocking the merge over. Reviewers who mark these clearly as nits (many teams literally prefix the comment with "nit:") let the author use judgment about whether to act on them, without stalling the whole change.
Why conflating the two is a common, costly mistake A reviewer who treats every comment as equally mandatory — insisting a variable be renamed with the same urgency as fixing a real bug — trains authors to either dread review or start ignoring it, since there's no way to tell what actually matters. Distinguishing severity is what keeps review fast without making it toothless.

Giving feedback: focused on the code, not the person

Person-directed 
"You clearly didn't think about concurrent access here."
Work-directed 
"This increments the counter without a lock — two concurrent
requests could both read the same value before either writes it back.
Worth adding a lock here, or is there a reason concurrent access
isn't a concern for this endpoint?"
Why the work-directed version is more effective, not just more polite This is the same distinction Career Applied Engineering's feedback lesson covers for professional feedback generally: naming the specific, observable problem, and asking a genuine question rather than asserting a judgment about the author, gets a better response and is more likely to be actually correct — sometimes there really is a reason, and the question leaves room for the author to explain it instead of just being told they were wrong.

Receiving feedback: defensiveness is the biggest failure mode

Why a reviewer's comment isn't a verdict on your competence A comment on a pull request is a check on the code, not a referendum on the author's skill — treating every comment as a personal criticism (or, just as damaging, treating it as an unquestionable command to blindly obey) both work against the actual goal of review, which is producing correct, maintainable code. The most effective response to a review comment is the same posture as receiving any professional feedback: assume good intent, engage with the specific claim, and push back with reasoning if you genuinely disagree — silently complying with something you think is wrong helps nobody.
Example A reviewer leaves a nit suggesting a different variable name. Instead of silently renaming it without a second thought, or getting defensive, the author replies: "I named it that way to match the field name in the API response — happy to change it if you feel strongly, but wanted to explain the reasoning." This is neither blind compliance nor defensiveness — it's exactly the kind of engaged, reasoned exchange review is supposed to produce.

Check your recall

No peeking back up — answer from memory first, then check.

1. Why should reviewers distinguish blocking issues from nits?

Clear severity signals keep review fast and meaningful, rather than either paralyzing or being ignored entirely.

2. What makes work-directed feedback ("this code does X, which could cause Y") more effective than person-directed feedback ("you didn't think about X")?

Focusing on the specific code behavior, and asking rather than asserting, produces a better and more accurate response.

3. What is the recommended response to receiving a code review comment you genuinely disagree with?

Neither blind compliance nor defensiveness serves the goal of review — engaged, reasoned disagreement does.

4. Fill in the blank: many teams literally prefix an optional, non-blocking suggestion with "___:" so the author knows it isn't mandatory.

"Nit:" is the common convention marking a comment as a minor, optional suggestion.

5. Fill in the blank: treating a review comment as a personal attack instead of a check on the code is a form of ___, which this lesson names as the biggest failure mode in receiving feedback.

Defensiveness is the specific failure mode named — reacting to a comment on the code as if it were a judgment on the author.
