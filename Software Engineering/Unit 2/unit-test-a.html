Unit 2 Test — Version A

Version Control with Git. 10 points across every lesson in this unit — 5 questions worth 1 point, 5 worth 1 point split across two parts. Score 90% or higher to clear this unit.

1. Two engineers each copy a shared file, make different edits, and save their copies back to a shared drive one after the other. What specifically goes wrong without version control?

File-copy "versioning" fails because a later save can silently overwrite an earlier one's work with no warning or record.

2. Which of these is something version control specifically provides, according to Lesson 4?

A complete history, safe parallel work via branches, and the ability to undo are the three things version control provides.

3. What does it mean that Git is "distributed"?

Being distributed means the full project history lives locally with every developer, not just on a central server.

4. Fill in the blank: the correct mental model for a Git commit is a full ___ of the entire project at that moment, not a list of line-by-line changes.

Every commit is a complete snapshot of the tracked project, with a pointer to its parent commit.

5. Fill in the blank: a Git branch is just a lightweight, movable ___ to a specific commit, not a full duplicate of the codebase — which is exactly why creating one is nearly instant.

Since a branch is just a pointer, creating one costs almost nothing — there's nothing to copy.

6. An engineer runs git checkout feature-login to switch branches. Answer both parts:

(a) What does this command actually do to HEAD?

(b) Fill in the blank: HEAD is Git's name for whatever ___ (and therefore commit) you're currently on.

HEAD tracks your current position in the project's history by pointing at your current branch, which in turn points at a commit.

7. One commit message reads "fix bug." Another reads "Fix null pointer when cart is empty at checkout," with a body explaining the assumption that broke. Answer both parts:

(a) Why is the second message considered better practice?

(b) Fill in the blank: a good commit message documents ___ a change was made, since the code's diff already shows what changed.

A commit message is read far more often than it's written; one that only restates what changed wastes the one place built to record why.

8. Two branches touched entirely different files and are merged together. Answer both parts:

(a) What happens in this case?

(b) Fill in the blank: the resulting merge commit has two ___, recording that two lines of history rejoined at that point.

When branches touch different parts of the code, Git merges automatically — this is the overwhelmingly common case, and it's why merge conflicts are the exception, not the rule.

9. Two branches changed the exact same line of the exact same file in different ways, and a merge is attempted. Answer both parts:

(a) Why does Git stop and ask a human to resolve this, instead of picking one version automatically?

(b) Fill in the blank: this situation is called a merge ___ — Git marks both versions directly in the file and waits for a human decision.

This is the direct payoff of version control's core promise: never silently overwrite someone's work.

10. An engineer finishes a branch and opens it for teammates to review on GitHub before it merges into main. Answer both parts:

(a) What does this add on top of a plain merge?

(b) Fill in the blank: a pull request (or merge request) exists to add a ___ step before a branch's changes join the shared codebase.

A pull request is fundamentally a review gate placed in front of a merge — the full review process itself is covered in Unit 6.
