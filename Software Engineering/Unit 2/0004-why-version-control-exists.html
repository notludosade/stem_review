Why Version Control Exists

The collaboration and history problem every team has, and why "final_v3_FINAL.py" isn't a solution to it.

← Unit 1, Lesson 3 Lesson 5 → Contents Glossary →

Unit 1 established that real software is built by teams, over years, with changing requirements. That immediately creates a concrete problem: how do multiple people change the same files without overwriting each other's work, and how does anyone recover a version of the code from last month if today's turns out to be broken? Version control is the tool built specifically to solve both problems at once.

The problem without version control

Why file-copy "versioning" falls apart Without a real tool, teams reach for folder names and file suffixes: project_v2, project_v2_fixed, project_v2_fixed_FINAL. This fails in two specific ways: two people can't safely edit the same file at the same time without one silently discarding the other's work, and there's no reliable way to answer "what exactly changed between these two folders, and who changed it, and why?"
Example Two engineers each copy app_v4.py, make different fixes, and email their copies back. Whoever's copy gets saved to the shared drive last silently erases the other person's fix — with no error, no warning, and no record that it ever happened. Multiply this by a team of ten people editing daily, and the file-copy approach doesn't just become inconvenient — it becomes actively unsafe to use.

What version control actually provides

A complete history Every saved change (a commit, covered in the next lesson) is recorded permanently, along with who made it, when, and why. Nothing is ever silently overwritten — even a change nobody remembers making from two years ago can be found and inspected.
Safe parallel work Multiple people can work on the same codebase at the same time, in isolated lines of work called branches, and the tool provides a structured way to combine their changes back together — flagging the rare cases where two people changed the exact same lines, rather than silently picking one.
The ability to undo If a change turns out to be wrong, version control makes it possible to see exactly what changed and revert it — restoring a known-good state instead of trying to manually remember and undo every edit by hand.

Git specifically

Why this course teaches Git, not "version control" in the abstract Several version control systems exist, but Git — created by Linus Torvalds in 2005 to manage the Linux kernel's own development — is by far the dominant tool in the industry today. It's distributed: every developer's local copy contains the entire project history, not just the current files, which is exactly what makes offline work, fast operations, and platforms like GitHub and GitLab possible. The rest of this unit teaches Git's actual mental model, not just the theory of version control in general.

Check your recall

1. What specifically goes wrong with naming folders "v2," "v2_fixed," "v2_fixed_FINAL" instead of using version control?

The two specific failures are silent overwrites during parallel work and the lack of a real change history.

2. What lets multiple engineers work on the same codebase at the same time without directly interfering with each other?

Branches let people work in parallel; version control then provides a structured way to merge that work back together.

3. What does it mean that Git is "distributed"?

Being distributed means the full history lives locally with every developer, not just on a central server.

4. Fill in the blank: every saved change in version control is recorded as a ___, permanently preserving who made it, when, and why.

A commit is the fundamental unit of recorded history in a version control system.

5. Fill in the blank: ___, created by Linus Torvalds in 2005 to manage the Linux kernel, is the dominant version control system in the industry today.

Git is the specific, dominant tool this unit focuses on, rather than version control in the abstract.
