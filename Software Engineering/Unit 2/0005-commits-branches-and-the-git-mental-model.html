Commits, Branches, and the Git Mental Model

Git tracks snapshots, not differences — and a branch is just a movable pointer, not a copy.

← Lesson 4 Lesson 6 → Contents Glossary →

Lesson 4 established why version control exists. This lesson covers Git's actual internal model — the picture that makes commands like commit, branch, and checkout make sense, instead of feeling like memorized incantations.

A commit is a snapshot, not a diff

Why this is the single most important mental model in Git A common misconception is that Git stores a list of line-by-line changes, like a stack of patches. It doesn't. Every commit is a complete snapshot of the entire project at that moment (Git is smart enough to only store what actually changed internally, but the model you should reason with is: every commit is a full picture of the project). Each commit also stores a pointer to its parent commit, which is what turns the whole set of commits into a chain — a project's history.
Example 
git add README.md
git commit -m "Add setup instructions to README"
This doesn't record "3 lines were added to README.md." It records a full snapshot of every tracked file in the project at that instant, tagged with that commit message, with a pointer back to whatever commit came right before it.

A branch is a movable pointer, not a copy

Why branches are cheap and instant in Git A branch is often pictured as a full duplicate of the codebase, which makes creating one feel like it should be slow and heavy. It isn't. A branch is just a lightweight, movable label pointing at one specific commit. Creating a branch instantly costs almost nothing, because there's nothing to copy — just a new pointer, right where you already are.
Example 
git branch feature-login
git checkout feature-login
# equivalent to: git checkout -b feature-login
After this, feature-login and the branch you started from point at the exact same commit. As soon as you make a new commit while on feature-login, only that branch's pointer moves forward to the new commit — the original branch's pointer stays exactly where it was.

HEAD: where you currently are

HEAD is a pointer to your current branch HEAD is Git's name for "whatever commit you're currently looking at." Normally it points at a branch, which in turn points at a commit — so when you commit, HEAD's branch moves forward, and HEAD moves with it. Switching branches with checkout or switch just repoints HEAD at a different branch.

Writing commits that are actually useful later

Why commit messages are documentation, not a formality A commit message is read far more often than it's written — by teammates during code review, and by you, months later, trying to understand why a change was made. A commit that only describes what changed wastes the one place in the history built specifically to record why.

fix bug
Informative

1. What does a single Git commit actually store?

Git's model is a full snapshot per commit (even though it's stored efficiently internally), chained together by parent pointers.

2. Why is creating a new Git branch nearly instant, regardless of project size?

Since a branch is just a pointer, creating one requires no copying — just a new label placed at the current commit.

3. What does HEAD represent in Git?

HEAD tracks your current position in the project's history, typically by pointing at your current branch.

4. Fill in the blank: the correct mental model for a Git commit is a full ___ of the project at that moment, not a list of line-by-line changes.

Thinking in snapshots, not diffs, is what makes the rest of Git's behavior make sense.

5. Fill in the blank: a good commit message documents ___ a change was made, since the code itself already shows what changed.

The diff already shows what changed; a useful commit message adds the reasoning a diff can't show on its own.
