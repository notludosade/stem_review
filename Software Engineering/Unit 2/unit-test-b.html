Unit 2 Test — Version B

Version Control with Git. 10 points across every lesson in this unit — 5 questions worth 1 point, 5 worth 1 point split across two parts. Score 90% or higher to clear this unit.

1. A team names its project folders project_v2, project_v2_fixed, and project_v2_fixed_FINAL instead of using version control. What specifically fails about this approach?

The two specific failures are silent overwrites during parallel work and the lack of a real change history.

2. What lets multiple engineers work on the same codebase at the same time without directly interfering with each other's changes?

Branches let engineers work in parallel; version control then provides a structured way to merge that work back together.

3. A new engineer joins a team and clones a Git repository onto their laptop. What do they now have a copy of?

Being distributed means every developer's local copy contains the entire project history, not just its current files.

4. Fill in the blank: besides a full snapshot of the project, every commit also stores a pointer to its ___ commit, which is what turns the set of commits into a chain.

The parent pointer is what links each snapshot into the project's ongoing history.

5. Fill in the blank: because a branch is just a movable pointer with nothing to copy, creating a new one in Git is ___, regardless of how large the project is.

Since a branch is only a lightweight label pointing at a commit, creating one costs almost nothing.

6. While on branch main, an engineer creates and commits to a new branch called feature-x. Answer both parts:

(a) What happens to main's pointer once the new commit is made on feature-x?

(b) Fill in the blank: since the engineer is on feature-x, ___ points at feature-x, and moves forward with it as new commits are made.

HEAD points at whatever branch you're currently on; committing moves that branch's pointer forward, leaving other branches untouched.

7. A teammate reviewing a pull request months from now needs to understand why a change was made, not just what lines changed. Answer both parts:

(a) What should a good commit message prioritize recording?

(b) Fill in the blank: a commit message is read far more often than it's written, which is why this lesson treats it as ___, not a formality.

Commit messages are documentation for teammates and for the author's own future self, not busywork required by Git.

8. A branch adding a new page and a branch fixing an unrelated typo elsewhere in the project are merged into main. Answer both parts:

(a) Since the two branches touched entirely different lines, what does Git do?

(b) Fill in the blank: Git records this rejoining of two lines of history with a new ___ commit that has two parents.

A merge commit with two parents is how Git records that two previously separate lines of history rejoined.

9. Two branches both changed the same tax-calculation line in a checkout function, to two different values. Answer both parts:

(a) What does this situation trigger when the branches are merged?

(b) Fill in the blank: Git has no way to know which version is correct, so instead of guessing, it stops and asks a ___ to decide.

Merge conflicts only happen when two branches edit the exact same lines differently — a deliberate safety feature, not a Git failure.

10. A reviewer leaves a comment on an open pull request asking why a specific edge case wasn't handled, and the author pushes a fix to the same branch. Answer both parts:

(a) What happens to the open pull request when the author pushes that fix?

(b) Fill in the blank: only after the reviewer's ___ does the actual merge into main happen.

A pull request stays open and updates live as new commits are pushed, and the merge itself waits for approval — that review gate is the whole point of the workflow.
