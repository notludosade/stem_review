Merging, Conflicts, and Pull Requests

What a merge conflict actually is, and how a pull request turns a branch into a reviewed, mergeable change.

← Lesson 5 Unit 3, Lesson 7 → Contents Glossary →

Lesson 5 covered how branches let engineers work in parallel. Eventually, that work has to come back together. This lesson covers merging — how Git combines two branches' histories — and pull requests, the workflow that wraps a merge in review before it happens.

What a merge actually does

Merging combines two branches' histories into one A merge takes the changes made on one branch and integrates them into another. If the two branches touched entirely different parts of the code, Git combines them automatically — this is the overwhelmingly common case. A new merge commit is created with two parents, recording that two lines of history rejoined at that point.

Merge conflicts: when Git can't decide for you

Why conflicts happen, and why they're actually a safety feature A merge conflict occurs specifically when two branches changed the exact same lines of the exact same file in different ways. Git has no way to know which version — or what combination — is correct, so instead of silently guessing (and possibly discarding someone's work), it stops and asks a human to decide. This is the direct payoff of Lesson 4's core complaint about file-copy "versioning": Git refuses to silently overwrite anyone's changes.
Example 
<<<<<<< HEAD
return price * 1.08;  // 8% tax
=======
return price * 1.0725;  // updated tax rate
>>>>>>> feature-tax-update
Two branches both changed the same tax calculation line differently. Git marks both versions directly in the file with these conflict markers and waits — the engineer resolving the conflict deletes the markers, keeps (or combines) the correct code, and commits the result to finish the merge.

Pull requests: review before merge

Why teams don't just merge branches directly A pull request (sometimes called a merge request) is a request to merge one branch into another, opened on a platform like GitHub or GitLab, that shows the full diff of proposed changes and lets other engineers comment, request changes, or approve before the merge actually happens. Almost every professional team requires this step — Unit 6 covers the review process itself in depth, but the mechanical point here is that a pull request is what turns "I finished a branch" into "the team has actually looked at this before it joins the main codebase."
Example An engineer finishes the feature-login branch from Lesson 5 and opens a pull request to merge it into main. A teammate reviews the diff, leaves a comment asking why a specific edge case isn't handled, the engineer pushes a fix to the same branch (which automatically updates the open pull request), and only after approval does the actual merge happen.

Why this whole workflow matters at team scale

Why merging and pull requests are the mechanical backbone of team collaboration Everything Unit 1 said about software being built by teams, over years, ultimately routes through this exact mechanism: engineers branch off to work in isolation, merge conflicts are Git's way of forcing a human decision only when it's genuinely needed, and pull requests add a human review step before any of it reaches the shared codebase. Nearly every collaborative workflow in professional software engineering is some variation on this same pattern.
