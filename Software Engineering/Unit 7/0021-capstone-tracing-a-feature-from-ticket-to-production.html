Capstone — Tracing a Feature from Ticket to Production

Following one feature through every practice in this course, from a backlog ticket to a merged, deployed change.

← Lesson 20 Contents Glossary →

Every unit in this course covered one piece of professional software engineering in isolation. In practice, they all operate together, continuously, on the same piece of work. This closing lesson traces one feature — "let users apply a promo code at checkout" — through every stage, naming which unit's practice is active at each step.

1. The ticket enters the backlog

Requirements (Unit 1) meet the agile board (Unit 7) A product manager writes a ticket: "Users can apply a promo code at checkout." As written, this is exactly the vague requirement Lesson 3 warned about — it needs acceptance criteria before an engineer should start: what happens with an invalid code? Can codes stack? Is there an expiration? The team clarifies these before the ticket is considered ready, and it's prioritized into the current sprint (Lesson 20) alongside the rest of the backlog.

2. A branch is created

Version control (Unit 2) An engineer creates a branch, feature-promo-codes, off main — an instant, lightweight pointer per Lesson 5, isolating this work from everyone else's in-progress changes.

3. Design decisions get made

Patterns and architecture (Units 4 and 5) The engineer notices the checkout system already has a Strategy pattern (Lesson 12) for shipping-cost calculation, and reuses that same shape for discount calculation, rather than hardcoding a branching if/elif chain. They also confirm this fits within the existing monolith's checkout module (Lesson 15) without needing a new service — no architectural decision is being made here, just an implementation choice within the existing structure.

4. Tests are written first

Test-driven development (Unit 3) Following the red-green-refactor cycle from Lesson 9, the engineer writes a failing test for a valid promo code, then the minimum code to pass it, then a failing test for an expired code, and so on — building up the feature through the same testing pyramid (Lesson 8) of mostly-unit, some-integration tests, verifying real interaction with the order database.

5. A deliberate shortcut gets named

Technical debt (Unit 5) Stacking multiple promo codes turns out to be significantly more complex than expected, and isn't actually required by the ticket's acceptance criteria. The engineer deliberately scopes it out, and — per Lesson 17 — writes a comment and a follow-up ticket naming the shortcut explicitly, rather than letting it become an accidental gap nobody remembers deciding on.

6. A pull request is opened

Pull requests and code review (Units 2 and 6) The engineer opens a pull request (Lesson 6). A teammate reviews it: one blocking comment (a missing null check on an edge case), and two nits (a naming preference) clearly marked as optional, per Lesson 19's severity distinction. The engineer addresses the blocking issue, explains their reasoning on one nit instead of silently complying, and pushes an update to the same branch.

7. The branch merges

Merging (Unit 2) After approval, the branch merges into main. Since another engineer's unrelated change touched a nearby line in the same file, Git flags a merge conflict (Lesson 6) — resolved in minutes because the two changes are conceptually unrelated and easy to tell apart.

8. It deploys, and the sprint reflects on it

Deployment (Unit 1) and the retrospective (Unit 7) The change deploys to production as part of the SDLC's deployment phase (Lesson 2). At the end of the sprint, the team's retrospective surfaces that the promo-code ticket took longer than estimated because the requirements weren't fully clarified upfront — direct, lived confirmation of Lesson 3's warning that ambiguity caught late costs more than ambiguity caught early.

What this traces out

Why no single unit was sufficient on its own Every practice in this course showed up in service of a single, ordinary feature: clear requirements, safe parallel work, deliberate design choices, tests written before the code, an explicit rather than accidental shortcut, reviewed and discussed rather than silently merged, and a process that reflects on itself afterward. None of these practices is optional flourish — each one is answering a specific, real failure mode that shows up the moment code is built by more than one person, over more than a few weeks. That is the entire difference this course opened with, back in Lesson 1, between writing correct code and engineering software.
