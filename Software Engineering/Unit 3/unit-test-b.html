Unit 3 Test — Version B

Software Testing. 10 points across every lesson in this unit — 5 questions worth 1 point, 5 worth 1 point split across two parts. Score 90% or higher to clear this unit.

1. When one person writes and immediately runs a small script, manually checking the output is fine. Why does this stop being true once a codebase is modified by dozens of engineers over years?

Automated tests exist because manual re-verification of everything, at real team scale, simply isn't possible in the available human time.

2. Every single test in a project's suite is green. What is the most accurate description of what this actually proves?

Tests only speak to the cases they check — an untested input could still fail even with a fully green suite.

3. Which scenario below is a regression, in the sense this lesson defines it?

A regression is specifically a previously working feature breaking as a side effect of a change made for a different reason.

4. Fill in the blank: assert calculate_discount(price=100, percent=20) == 80 is a unit test because it checks exactly one small ___, with no database, network, or other part of the system involved.

A unit test isolates one function or method, so if it fails, it points at almost exactly one place to look.

5. Fill in the blank: instead of testing calculate_discount() alone, an integration test places a real order through the actual checkout flow, hitting a real (test) ___, to confirm the final charged amount is correct.

Integration tests verify real components working together, catching bugs in the wiring between individually-correct pieces.

6. A healthy test suite has thousands of fast unit tests forming a wide base, and a much smaller number of slower integration tests above them. Answer both parts:

(a) Why can a team afford so many more unit tests than integration tests?

(b) Fill in the blank: too many slow integration tests make a suite ___ — failing intermittently for reasons unrelated to the actual code, like a database timing hiccup.

The pyramid shape balances speed and precision against realistic end-to-end coverage — it's what keeps a large suite fast enough to actually run constantly.

7. After the "red" step of TDD produces a failing test for a feature that doesn't exist yet, what happens next? Answer both parts:

(a) What is the very next step, called "green"?

(b) Fill in the blank: the final step, cleaning up the code without changing its behavior using the now-passing test as a safety net, is called ___.

Green is writing the minimum passing code; refactor is cleaning it up afterward, protected by the test that already passes.

8. TDD reverses the usual order: the test for a feature is written before the feature's code exists. Answer both parts:

(a) What does writing the test first force an engineer to do?

(b) Fill in the blank: a test written ___ the code already exists can accidentally pass without checking anything meaningful, since it was shaped to match code that's already there.

Writing the test first guarantees it actually works, since it defines correctness independently of whatever the implementation happens to already do.

9. A function can't be tested without a live database and a real network connection close at hand, and it also does several unrelated jobs at once. Answer both parts:

(a) What does this lesson say this difficulty usually signals?

(b) Fill in the blank: small, ___ pieces of code with clear, explicit dependencies are both easier to test and easier for a human to understand.

Doing too many things at once and relying on hidden dependencies are exactly the traits that make code both hard to test and hard to maintain.

10. calculate_total(price, tax_rate=0.08) is pulled out of a larger process_order() function that used to hardcode the tax rate and call a database directly. Answer both parts:

(a) Why can calculate_total() now be tested with just a plain number?

(b) Fill in the blank: in the testable version, process_order(order, db, mailer) receives its dependencies as explicit parameters, so a test can pass in a fake db and a fake ___ instead of hitting real infrastructure.

Making dependencies explicit parameters instead of hidden calls is the structural change that makes code both testable and easier to read.
