Unit Tests, Integration Tests, and the Testing Pyramid

Why most of a test suite should be small and fast, with fewer, slower tests checking how pieces work together.

← Lesson 7 Lesson 9 → Contents Glossary →

Lesson 7 established why tests exist. Not all tests are the same kind of check, though — they operate at different scopes, with different costs. This lesson covers the two most common categories, and the shape a healthy test suite should actually have across them.

Unit tests: one small piece, in isolation

A unit test checks one function or class, on its own A unit test verifies a single, small piece of code — typically one function or method — in isolation from the rest of the system. Anything that piece depends on (a database, a network call, another class) is typically replaced with a fake stand-in so the test only measures the one piece of logic being checked.
Example 
def test_calculate_discount_applies_percentage():
    assert calculate_discount(price=100, percent=20) == 80
This test checks exactly one function, with no database, no network, and no other part of the system involved. It runs in milliseconds and, if it fails, points at almost exactly one place to look.

Integration tests: do the pieces work together?

An integration test checks multiple real pieces working together An integration test verifies that several components — often including real infrastructure like a database or an external API — work correctly together, not in isolation. It answers a question a unit test can't: does the wiring between pieces, each individually correct, actually work when combined?
Example A unit test can confirm calculate_discount() works correctly on its own. An integration test instead places a real order through the actual checkout flow — hitting a real (test) database — and confirms the final charged amount reflects the discount correctly. It's slower and touches more of the system, but it catches a category of bug (like a wrong parameter passed between two individually-correct functions) that isolated unit tests structurally cannot.

The testing pyramid: why most tests should be unit tests

Why the balance between the two matters, not just having both The testing pyramid describes the recommended shape of a healthy test suite: many fast, cheap unit tests forming a wide base, and a much smaller number of slower, more expensive integration tests above them. Unit tests are fast and isolate failures precisely, so a team can afford thousands of them; integration tests are slower and touch more moving parts (a database, a network), so having too many makes the whole suite slow and unreliable without adding proportional value.
Why an inverted pyramid is a common, costly mistake A team that writes mostly integration tests and few unit tests ends up with a test suite that's slow to run, flaky (failing for reasons unrelated to the actual code, like a database timing hiccup), and unhelpful when it fails, since a failure in a test touching ten components doesn't say which one broke. The pyramid shape isn't a stylistic preference — it's what keeps a large test suite fast enough and precise enough to actually be run constantly, which is the entire point of Lesson 7's argument.

Check your recall

1. What distinguishes a unit test from an integration test?

Scope of what's being checked is the actual distinction — isolated single-piece versus multiple real pieces combined.

2. Why should a healthy test suite have far more unit tests than integration tests?

The pyramid shape balances speed and precision (unit tests) against realistic end-to-end coverage (fewer integration tests).

3. What kind of bug can an integration test catch that an isolated unit test structurally cannot?

Unit tests isolate one piece, so bugs in how correctly-working pieces interact are exactly what only an integration test can reveal.

4. Fill in the blank: the testing ___ describes a healthy test suite as many fast unit tests at the base, with far fewer, slower integration tests above them.

The pyramid shape reflects the tradeoff between a test's speed/precision and its realism.

5. Fill in the blank: a test that fails intermittently for reasons unrelated to the actual code being tested — like a timing hiccup — is called ___.

Flaky tests are a specific, costly failure mode that's more common the more infrastructure a test touches.
