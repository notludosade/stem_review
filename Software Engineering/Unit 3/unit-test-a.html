Unit 3 Test — Version A

Software Testing. 10 points across every lesson in this unit — 5 questions worth 1 point, 5 worth 1 point split across two parts. Score 90% or higher to clear this unit.

1. A codebase has hundreds of functions modified by dozens of engineers over several years. Why does manually re-checking every existing feature after each change become impossible at this scale?

The sheer volume of features and changes at team scale is what makes automation necessary, not a flaw in manual checking at small scale.

2. A divide() function has passing tests for divide(10, 2) and divide(9, 3), but nobody wrote a test for divide(5, 0). What does the fully passing suite actually tell you?

A green test suite means "we haven't broken anything we already knew to check for" — it says nothing about inputs nobody thought to test.

3. An engineer refactors how discount codes are calculated to support a new promotion type. The refactor works correctly for the new promotion, but silently breaks an unrelated free-shipping code feature that shared the same function. What is this an example of?

A regression is specifically something that used to work breaking due to a change made for a different reason — the most common thing test suites catch in practice.

4. Fill in the blank: a unit test verifies one small piece of code, typically a single function, in ___ from the rest of the system, with its dependencies replaced by fake stand-ins.

A unit test measures only the one piece of logic being checked, with everything it depends on faked out.

5. Fill in the blank: an integration test verifies that several real components, often including real infrastructure like a database, work correctly ___, answering a question isolated unit tests structurally cannot.

Integration tests check the wiring between individually-correct pieces, not any one piece in isolation.

6. A team's test suite is shaped like an inverted pyramid — mostly slow integration tests, with very few fast unit tests. Answer both parts:

(a) What problem does this shape typically cause?

(b) Fill in the blank: the testing ___ describes the recommended, opposite shape instead — many fast unit tests at the base, and far fewer, slower integration tests above them.

An inverted pyramid is a common, costly mistake — the recommended shape keeps a large suite fast enough and precise enough to actually run constantly.

7. An engineer practicing TDD writes a test for calculate_discount() before the function exists, watches it fail, writes the simplest working version, and then cleans it up. Answer both parts:

(a) What is the correct order of this cycle?

(b) Fill in the blank: the first step, writing a test that fails because the feature doesn't exist yet, is called ___.

Red-green-refactor is the repeated cycle: fail first, pass minimally, then improve with the test as a safety net.

8. A test is written after the implementation already exists, versus a test written first, before any code. Answer both parts:

(a) Why might the after-the-fact test be less trustworthy?

(b) Fill in the blank: writing the test first forces you to define exactly what "___" means for a piece of code before you're tempted to write code that just matches whatever the implementation happens to do.

Writing the test first defines correctness independently of the implementation, rather than being shaped around whatever it happens to already do.

9. A function is difficult to write a test for because it does several unrelated things at once and depends on hidden global state. Answer both parts:

(a) What does this usually indicate, beyond just being inconvenient to test?

(b) Fill in the blank: making a function's ___ explicit parameters, instead of hidden global calls, is what makes it possible to substitute fakes during a test.

Small, focused code with explicit, visible dependencies is both easier to test and easier for a human to understand.

10. Compare process_order(order_id), which directly queries a database and calls a global mailer inside its own body, to process_order(order, db, mailer), which receives both as parameters. Answer both parts:

(a) Why is the second version easier to write a test for?

(b) Fill in the blank: a separate helper like calculate_total(price, tax_rate) can be tested with plain numbers alone, needing no real ___ or email service at all.

Pulling pure calculation logic out from side-effecting dependencies makes both pieces easier to test and easier to read.
