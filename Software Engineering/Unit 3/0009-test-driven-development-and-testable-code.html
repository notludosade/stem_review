Test-Driven Development and Writing Testable Code

Red, green, refactor — and why code that's hard to test is usually a sign of a deeper design problem.

← Lesson 8 Unit 4, Lesson 10 → Contents Glossary →

Lessons 7 and 8 covered why tests exist and what kinds there are. This lesson covers a specific practice for writing them — test-driven development — and a more general idea that follows from it: how a piece of code is designed directly affects how easy it is to test.

Test-driven development: red, green, refactor

Writing the test before the code it tests Test-driven development (TDD) reverses the usual order: instead of writing code and then a test for it, you write a failing test first, for behavior that doesn't exist yet, then write the minimum code to make it pass. The cycle has three steps, repeated continuously: red (write a test that fails, since the feature doesn't exist yet), green (write the simplest code that makes it pass), refactor (clean up the code without changing its behavior, using the now-passing test as a safety net).
Example 
# Red: write this test first — it fails, calculate_discount doesn't exist yet
def test_calculate_discount_applies_percentage():
    assert calculate_discount(price=100, percent=20) == 80

# Green: write just enough code to pass
def calculate_discount(price, percent):
    return price - (price * percent / 100)

# Refactor: now safe to clean up, the test catches any regression
def calculate_discount(price, percent):
    return price * (1 - percent / 100)
Why writing the test first changes anything Writing the test first forces you to define exactly what "correct" means for a piece of code before you're tempted to write code that matches whatever behavior happens to fall out of the implementation. It also guarantees the test actually works — a test written after the code can accidentally pass even when it isn't checking anything meaningful, since it was shaped to match code that already exists.

Testable code is usually just well-designed code

Why "hard to test" is a design smell, not just a testing inconvenience A function that's difficult to write a test for is very often difficult for a deeper reason: it does too many things at once, depends on hidden global state, or can't be used without a real database and network connection close at hand. Testability and good design point at the same underlying property — small, focused pieces of code with clear, explicit dependencies are both easier to test and easier for a human to understand.
Hard to test 
def process_order(order_id):
    order = db.query(f"SELECT * FROM orders WHERE id={order_id}")
    total = order.price * 1.08  # hardcoded tax rate
    send_email(order.customer_email, f"Total: {total}")
    return total
Testable 
def calculate_total(price, tax_rate=0.08):
    return price * (1 + tax_rate)

def process_order(order, db, mailer):
    total = calculate_total(order.price)
    mailer.send(order.customer_email, f"Total: {total}")
    return total
Why the second version is easier to test calculate_total() can be tested with a plain number, no database or email service required. The dependencies in process_order() (db, mailer) are now explicit parameters instead of hidden global calls, so a test can pass in fakes for both — a structural change that makes the code both testable and easier to read.

1. What is the correct order of the TDD cycle?

Red-green-refactor is the specific repeated cycle: fail first, pass minimally, then improve with the test as a safety net.

2. Why might a test written after the code already exists be less trustworthy than one written first?

Writing the test first forces you to define correctness independently of whatever the implementation happens to already do.

3. Why is code that's hard to test often considered poorly designed, not just inconvenient to test?

Testability and good design share the same root cause: small, focused pieces with explicit, visible dependencies.

4. Fill in the blank: the first step of the TDD cycle is ___ — writing a test that fails because the feature doesn't exist yet.

Red is the failing-test step that starts every cycle of test-driven development.

5. Fill in the blank: making a function's ___ explicit parameters, instead of hidden global calls, is what makes it possible to substitute fakes during a test.

Explicit, passed-in dependencies are what let a test swap in a fake database or mailer without touching real infrastructure.
