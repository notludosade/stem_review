Unit 1 Test — Version A

1. A developer says, "My function returns the correct output for every input I tested, so I'm done." Why might this be an incomplete standard for professional software engineering, even if true?

Programming targets correctness for a given input; engineering additionally targets correctness that survives time, teams, and changing requirements.

2. Why does a second engineer joining a one-person codebase suddenly create a need for conventions and a way to combine changes safely?

Scale is exactly the dimension that creates coordination costs no single-author script ever has to deal with.

3. A login() function returns the correct answer for every test case, but takes eight seconds to respond under real traffic. What kind of requirement is this failing?

Non-functional requirements — performance, reliability, security, maintainability — are first-class design goals separate from whether an output is correct.

4. Fill in the blank: deciding the shape of a solution — its major components, how they communicate, and what data structures or architecture to use — is the SDLC phase called ___, and is where Units 4 and 5 of this course live.

Design is the phase between requirements and implementation that decides the solution's shape before any code is written.

5. Fill in the blank: deployment is closer to a system's midpoint than its end, because the ___ phase that follows commonly lasts years and outweighs every earlier phase combined.

Maintenance is the long-running phase where most engineering hours across a system's life actually get spent.

6. A team executes all six SDLC phases exactly once, in strict order, with no phase ever revisited. Answer both parts:

(a) What is this specific, rigid process called?

(b) Fill in the blank: in most real teams, a bug found during testing can send the team back to an earlier phase — showing the six phases describe what kinds of work exist, not a strict one-way ___.

Waterfall is the strict once-through version of the SDLC; most real teams loop back between phases instead of following it rigidly.

7. One requirement states: "Users can filter search results by price range." A second states: "Search results must return within 500 milliseconds." Answer both parts:

(a) Which requirement is functional?

(b) Fill in the blank: because it describes how well the system performs rather than a specific behavior, the 500-millisecond requirement is ___.

Functional requirements describe a specific behavior; describing how well the system performs instead makes a requirement non-functional.

8. A ticket says "the checkout page should be user-friendly." Answer both parts:

(a) What is the main problem with this requirement as written?

(b) Fill in the blank: rewriting it as "a user completes checkout in under three clicks, with a specific error message on any invalid input" gives the requirement ___ criteria — a specific, checkable definition of done.

Acceptance criteria turn a vague requirement into specific, checkable conditions a team can agree are met or not.

9. A requirement was misunderstood, but the mistake wasn't caught until after the feature had already been implemented and tested. Answer both parts:

(a) Why is this more expensive to fix than catching it during the requirements conversation?

(b) Fill in the blank: a requirement misunderstanding caught in conversation costs a few minutes; the same misunderstanding surviving into ___ and beyond costs progressively more to undo.

A wrong assumption compounds as later phases build on it, so unwinding it later means unwinding everything built on top of it too.

10. A requirement that was correct when it was written turns out to be wrong six months later, after the business changed direction. Answer both parts:

(a) According to Lesson 3, how should this be understood?

(b) Fill in the blank: Unit 7 covers how ___ processes are specifically built around the expectation that requirements will keep changing.

Good requirements practice accepts that requirements captured today can become outdated later — that's expected, not a planning failure.
