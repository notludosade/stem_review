When Not to Use a Pattern

Overengineering, YAGNI, and why forcing a pattern onto a simple problem often makes it worse, not better.

← Lesson 12 Unit 5, Lesson 14 → Contents Glossary →

Lesson 10 warned that patterns are a vocabulary, not a rulebook. This lesson makes that warning concrete: applying a pattern where the underlying problem doesn't actually exist is a common, real mistake — and one that experienced engineers specifically watch for, in themselves as much as in others.

Overengineering: solving a problem you don't have yet

Why "it might need this later" is a trap Overengineering means building more flexibility, abstraction, or generality than a problem currently requires, usually justified by "we might need this later." The trouble is that "later" is a guess — and the guess is very often wrong, leaving behind extra complexity that every future engineer has to read, understand, and maintain, in service of a flexibility need that may never actually arrive.
Example calculate_shipping() from Lesson 12 has exactly one shipping method in the entire product, with no plan to add more. Building a full Strategy pattern with an interface and a class per method, for one single method, adds indirection with no present benefit — a plain function is simpler, equally correct, and easier for the next engineer to read.

YAGNI: "You Aren't Gonna Need It"

A guiding principle against speculative generality YAGNI is a shorthand principle from Extreme Programming: don't build capability for a requirement you don't have yet, even if you're fairly confident you'll need it eventually. Build the simplest thing that satisfies today's actual requirement, and add the pattern later, when (and if) the second concrete case that needs it actually shows up.
Why "add it later" is usually cheaper than it sounds Engineers often overbuild flexibility because they assume refactoring later will be expensive or risky. But Unit 3 already gave you the tool that makes "later" safe: a solid test suite. Turning a plain function into a Strategy pattern once a second real shipping method actually appears is a small, test-covered refactor — not a rewrite — which removes most of the justification for building the abstraction speculatively, before it's needed.

A pattern applied where the problem doesn't exist

Singleton for a value that isn't actually shared or scarce 
class MathConstants:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
    PI = 3.14159
Just a constant 
PI = 3.14159
Why the plain version wins here Singleton exists to control access to a shared, often stateful or expensive resource. A math constant is neither shared state nor expensive to create — wrapping it in a Singleton adds real complexity (as seen in Lesson 11's testing concerns) to solve a problem that was never actually present.

The actual skill: recognizing the problem before reaching for the name

Why experienced engineers start from the problem, not the pattern A common junior mistake is to learn a pattern and then look for places to use it. The more reliable approach, and the one experienced engineers actually use, is the reverse: notice a real, current problem (duplicated creation logic, a class doing too many unrelated jobs, a family of interchangeable algorithms), and only then recognize which pattern — if any — actually fits. The pattern should follow from the problem, never the other way around.
