Creational Patterns: Factory and Singleton

Two patterns for controlling how objects get created — and why Singleton is more often misused than needed.

← Lesson 10 Lesson 12 → Contents Glossary →

Lesson 10 introduced patterns as a shared vocabulary. This lesson covers the first category: creational patterns, which deal with controlling how and when objects get created, rather than leaving object creation scattered and duplicated throughout a codebase.

Factory: centralizing object creation logic

Why creating objects directly, everywhere, becomes a problem When object creation involves a decision (which subclass to create, based on some condition) and that logic is copy-pasted at every place an object is needed, changing the decision later means hunting down and updating every copy. A Factory centralizes that decision in one place: callers ask the factory for an object and get back the right kind, without needing to know or duplicate the decision logic themselves.
Creation logic scattered everywhere 
if payment_type == "credit_card":
    processor = CreditCardProcessor()
elif payment_type == "paypal":
    processor = PayPalProcessor()
elif payment_type == "crypto":
    processor = CryptoProcessor()
# ...this same block copy-pasted in five other files
Centralized in a Factory 
def create_payment_processor(payment_type):
    processors = {
        "credit_card": CreditCardProcessor,
        "paypal": PayPalProcessor,
        "crypto": CryptoProcessor,
    }
    return processors[payment_type]()

processor = create_payment_processor(payment_type)
Why this is better Adding a new payment type now means changing one function in one place, instead of finding and updating every scattered copy of the decision — exactly the kind of change-safety Unit 3's testable-code discussion was also pointing at.

Singleton: guaranteeing exactly one instance

What Singleton actually guarantees A Singleton ensures a class has exactly one instance across the entire program, and provides one global point of access to it — commonly used for things like a single shared configuration object or a single connection pool.
Why Singleton is the most misused pattern in this unit Singleton is frequently reached for whenever a class "should probably only exist once" — but the global, shared access point it provides makes code harder to test (Unit 3's Lesson 9 covered exactly this: hidden global dependencies are hard to substitute with fakes) and can hide surprising coupling between unrelated parts of a system that secretly share the same global state. Many experienced engineers now recommend passing a single shared instance explicitly as a parameter (called dependency injection) over using an actual Singleton, specifically to avoid that hidden global.
Example A global Logger singleton seems harmless, until a test wants to check what got logged during one specific function call — it has no clean way to isolate its own logger instance from every other test running in the same process, since they all silently share the exact same global singleton.
