HTTP Requests and Responses

Everything below this point in the stack — packets, ports, TCP connections — exists to deliver one plain-text message: an HTTP request, and the response that answers it.

← Lesson 16 Lesson 18 → Contents Glossary →

Lesson 5 put HTTP at the top of the stack, in the Application layer — the layer that defines what the actual data means, once every layer below has finished the job of getting bits to the right place. HTTP (HyperText Transfer Protocol) is the request-response protocol nearly every website is built on, and — refreshingly, compared to the binary headers of earlier units — it's just structured, human-readable text.

The request-response pattern

Definition HTTP follows a strict request-response pattern: a client sends one request over an already-established TCP connection (Lesson 15), and the server sends back exactly one response. The client always initiates; a server never sends data to a client that hasn't asked for it first. Every request specifies a method (what action to perform — GET to retrieve data, POST to submit new data, among others covered fully in Lesson 20) and a URL (which resource on the server it wants).
A Real Request and Its Response
<- request line: method, path, HTTP version
GET /articles/networking-basics HTTP/1.1
<- headers: metadata about the request
Host: example.com
Accept: text/html
User-Agent: Mozilla/5.0
<- blank line marks the end of headers

<- body: empty for a GET request
<- status line: HTTP version, status code, reason
HTTP/1.1 200 OK
<- headers: metadata about the response
Content-Type: text/html
Content-Length: 1583
<- blank line marks the end of headers

<- body: the actual content being returned
<html><body><h1>Networking Basics</h1>...</body></html>

Every HTTP message has the same shape

Structure Whether it's a request or a response, an HTTP message has the same four parts, in the same order: a start line (the request line for a request, or the status line for a response — Lesson 18 covers status codes in full), one or more headers (key-value metadata about the message), a required blank line marking the end of the headers, and an optional body (the actual content, if any — a GET request typically has none, but a response usually does).
Why the header/body split matters Separating headers from the body means a receiving program can read just the metadata first — enough to decide, say, how large the body is (Content-Length) or what format it's in (Content-Type) — before it has to process a single byte of the actual content. This is the same principle Lesson 6's encapsulation relied on: read your own layer's header, act on it, without needing to fully understand the payload underneath it. HTTP headers give an Application-layer program the exact same convenience within its own message format.
Worked example: what happens when you load a web page Your browser opens a TCP connection to the server (Lesson 15's three-way handshake), then sends an HTTP GET request for / (the site's homepage). The server processes the request, and sends back an HTTP response: a status line (200 OK, meaning success), headers describing the content, a blank line, and finally the actual HTML that becomes the page you see. Every image, stylesheet, and script the page references triggers its own separate GET request-response exchange — a single "page load" is really many independent HTTP round trips happening in quick succession.

Check your recall

No peeking back up — answer from memory first, then check.

1. In the HTTP request-response pattern, who is allowed to initiate sending data?

HTTP is strictly request-then-response; the client always initiates.

2. What four parts make up every HTTP message, request or response, in order?

The start line, headers, blank line, and optional body are consistent across every HTTP request and response.

3. Why does separating headers from the body matter for a program processing an HTTP message?

The header/body split mirrors the same "read your own metadata first" principle Lesson 6 introduced for encapsulation.

4. Fill in the blank: the HTTP method used to retrieve data from a server, with no body of its own, is ___.

GET is the standard method for retrieving a resource; Lesson 20 covers POST and other methods for submitting or modifying data.
