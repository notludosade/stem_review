HTTPS and TLS — Encrypting the Conversation

Every HTTP request and response from Lessons 17 and 18 was plain, readable text. Anyone with access to the wire in between could read every word — this lesson is the fix.

← Lesson 18 Lesson 20 → Contents Glossary →

Recall that a packet's journey (Lesson 2) typically crosses several independently owned networks — your home network, your ISP, one or more backbone carriers, the destination's ISP. Plain HTTP, exactly as shown in Lesson 17's widget, travels through every one of those hops as completely readable text. Any device along that path capable of inspecting traffic could read your password, your messages, or your search terms, in plain sight. HTTPS exists to close that gap.

HTTPS: HTTP, plus encryption

Definition HTTPS (HTTP Secure) is ordinary HTTP — the exact same request-response pattern, methods, and status codes from Lessons 17 and 18 — sent over an encrypted connection instead of a plain one. Encryption transforms readable data into a scrambled form that's computationally infeasible to reverse without possessing the correct key, so that anyone intercepting the traffic along the way sees only that scrambled form, not the original request or response.

TLS: the protocol doing the actual encrypting

Definition TLS (Transport Layer Security) is the protocol that actually performs HTTPS's encryption, sitting logically between the Transport layer (Lesson 15's TCP) and the Application layer (HTTP) — it wraps an ordinary TCP connection in an encrypted tunnel before any HTTP request or response is sent through it. TLS also verifies the server's identity using a certificate — a credential, issued by a trusted third party, proving that a server claiming to be example.com actually is.
Why verifying identity matters just as much as encrypting the data Encryption alone protects data from being read by an eavesdropper, but it does nothing to stop you from being tricked into having an encrypted conversation with the wrong party entirely. Without a way to verify who's actually on the other end, an attacker could intercept a connection, present themselves as the real server, and have a perfectly encrypted — but completely compromised — conversation with you, reading everything you send before quietly forwarding it (or not) to the real destination. This exact scenario, called a man-in-the-middle attack, is covered directly in Lesson 25; a certificate is what makes it far harder to pull off, because your browser refuses to proceed if the certificate presented doesn't check out.

The TLS handshake, briefly

Before any encrypted HTTP traffic flows, TLS performs its own handshake — layered on top of, and happening right after, TCP's own three-way handshake from Lesson 15. In broad strokes: the client and server agree on which encryption method to use, the server presents its certificate for the client to verify, and both sides derive a shared secret key that only the two of them know, used to encrypt everything that follows. Only once this TLS handshake completes does the actual HTTP request finally get sent — meaning an HTTPS connection has strictly more setup overhead than plain HTTP, a small, worthwhile cost for the protection it buys.

Worked example: what actually happens when you load an HTTPS site Your browser opens a TCP connection (Lesson 15's handshake). Then TLS performs its own handshake: negotiating encryption, verifying the server's certificate, and establishing a shared key. Only after both handshakes complete does your browser send its actual HTTP GET request — but now it's encrypted before it ever leaves your device, and every intermediate network it crosses only ever sees scrambled bytes, not your original request or the server's response.
Recognizing it Port-wise, this lesson connects directly back to Lesson 14: plain HTTP defaults to port 80; HTTPS defaults to port 443. A browser's padlock icon, and a URL beginning with https:// instead of http://, are the everyday, user-facing signals that a connection's TLS handshake succeeded and the conversation that follows is encrypted.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does HTTPS actually add on top of ordinary HTTP?

HTTPS is ordinary HTTP encrypted by TLS — the request-response pattern itself is unchanged.

2. Why does TLS verify the server's identity using a certificate, instead of just encrypting the data and stopping there?

Encryption protects data from being read; a certificate protects against talking to the wrong party in the first place — both matter.

3. When does an HTTPS connection actually start sending the HTTP request?

TLS's handshake happens on top of, and after, TCP's own handshake — only then does the encrypted HTTP request get sent.

4. Fill in the blank: a credential, issued by a trusted third party, that proves a server is who it claims to be, is called a ___.

A certificate is what lets a browser verify server identity before proceeding with an encrypted connection.
