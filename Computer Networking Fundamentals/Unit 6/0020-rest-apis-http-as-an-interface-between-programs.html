REST APIs — HTTP as an Interface Between Programs

Every lesson in this unit assumed a browser and a human on one end. Swap the browser for a program you wrote yourself, and HTTP becomes something else entirely: a general-purpose way for two programs to talk.

← Lesson 19 Unit 7, Lesson 21 → Contents Glossary →

Nothing about HTTP requires the client to be a web browser or the response to be an HTML page for a human to read. A program you write can send a GET request just as easily as a browser can — and instead of getting back HTML, it's common to get back structured data a program can parse directly. This is what an API built on HTTP looks like, and it's the direct bridge from this unit's browser-and-webpage framing to Unit 7's "write your own networked program."

APIs and REST

Definitions An API (Application Programming Interface) is a defined way for one piece of software to interact with another. A REST API (Representational State Transfer) is an API built directly on top of standard HTTP, treating each URL as an endpoint representing a specific resource (a piece of data, like "a specific user" or "a list of orders"), and using HTTP's existing methods to act on that resource, rather than inventing a whole new protocol from scratch.
Try It — HTTP Methods as CRUD Operations

CRUD action: Read

GET /users/42 HTTP/1.1
Host: api.example.com

Retrieves the current data for user 42, with no side effects — sending the same GET request a hundred times just returns the same data a hundred times.

CRUD action: Create

POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"name": "Amara", "email": "amara@example.com"}

Creates a brand-new user resource, sent in the request body. Unlike GET, sending this same request twice creates two separate new users.

CRUD action: Update

PUT /users/42 HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"name": "Amara Okafor", "email": "amara@example.com"}

Replaces user 42's existing data with the data in the request body — an update to a resource that already exists, addressed directly by its own URL.

CRUD action: Delete

DELETE /users/42 HTTP/1.1
Host: api.example.com

Removes user 42's resource entirely. Like GET, no request body is needed — the URL alone identifies exactly what to delete.

Why reusing HTTP's methods, instead of inventing new verbs A REST API could, in principle, define its own custom action names instead of reusing GET/POST/PUT/DELETE — but doing so would throw away everything HTTP already provides for free: every web browser, every programming language, every piece of network infrastructure already knows how to send these four methods, handle these status codes, and route this traffic. By mapping create/read/update/delete onto POST/GET/PUT/DELETE, a REST API gets to reuse the entire HTTP ecosystem — caching behavior, status codes (Lesson 18), and even HTTPS's encryption (Lesson 19) — instead of building any of that from scratch.
Worked example: a weather app calling an API A weather app on your phone sends GET https://api.weather.example.com/forecast?city=Austin. The server responds with status 200 OK, a Content-Type: application/json header, and a body like {"city": "Austin", "high": 91, "low": 74} — structured data the app's code parses directly and displays as a forecast, with no HTML and no human ever looking at the raw response. Same request-response pattern as loading a web page (Lesson 17); the only difference is who's on the receiving end and what they do with the response.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does a REST API build directly on top of?

REST reuses standard HTTP entirely, treating URLs as resources and HTTP methods as actions on them.

2. Which HTTP method typically corresponds to creating a brand-new resource?

POST is conventionally used to create a new resource, distinct from GET's read-only retrieval.

3. Why do REST APIs reuse HTTP's existing methods (GET, POST, PUT, DELETE) instead of inventing entirely new custom actions?

Reusing HTTP's existing, universally supported machinery is far more practical than reinventing an equivalent from scratch.

4. Fill in the blank: a specific URL in a REST API, representing one resource that can be acted on, is called an ___.

An endpoint is the specific URL a REST API exposes for a given resource, like /users/42.
