The Layered Model — OSI and TCP/IP Side by Side

No single protocol handles "send data across the internet." The job is split into stacked layers, each solving one narrow piece and trusting the layer below it to handle everything beneath that.

← Lesson 4 Lesson 6 → Contents Glossary →

Think back to Lesson 1's flashlight problem: addressing, formatting, ordering, error recovery — that's a lot of separate concerns for one protocol to handle at once. Real networking software doesn't try. Instead, the problem is split into layers, each one responsible for a narrow slice of the job, each one only talking to the layers directly above and below it, and each one trusting that the layer beneath it already solved its own piece correctly. This lesson introduces two competing (but closely related) ways of naming those layers — the OSI model and the TCP/IP model — because you'll see both used in the wild, sometimes in the same conversation.

Definition A layer is a self-contained slice of the networking problem, with a defined job and a defined interface to the layers immediately above and below it. Layering means a change inside one layer — say, switching from Wi-Fi to a wired connection — doesn't require the layers above it to know or care, as long as the interface between layers stays the same.

The OSI model: seven layers, mostly used as a reference

The OSI model (Open Systems Interconnection) is a seven-layer reference model, developed in the 1980s, that describes networking in maximum conceptual detail. It's rarely implemented exactly as specified, but its vocabulary — especially "Layer 3" for addressing and "Layer 7" for applications — is used constantly by working engineers, so it's worth knowing even though the internet itself doesn't literally run on it.

The TCP/IP model: four layers, what the internet actually runs

The TCP/IP model is a simpler, four-layer model that describes what the internet's actual protocol suite does. It's less detailed than OSI but it's the model this course's later units follow directly, because it maps onto real, deployed protocols rather than a theoretical ideal.

Explore Each TCP/IP Layer

Job: get bits across one physical hop — one wire, one Wi-Fi signal, one cable segment — between two directly connected devices.

Addresses using: MAC addresses (Lesson 7).

OSI equivalent: combines OSI's Physical (Layer 1) and Data Link (Layer 2).

Example protocols: Ethernet, Wi-Fi (802.11).

Job: get a packet from its source device to its destination device, potentially across many intermediate hops and networks.

Addresses using: IP addresses (Lessons 8-10).

OSI equivalent: OSI's Network layer (Layer 3).

Example protocols: IP (IPv4, IPv6).

Job: deliver data between the correct programs running on the source and destination devices (not just the correct devices), and optionally guarantee reliable, ordered delivery.

Addresses using: port numbers (Lesson 14).

OSI equivalent: OSI's Transport layer (Layer 4).

Example protocols: TCP, UDP (Unit 5).

Job: define the actual meaning and format of the data two programs exchange — what a request looks like, what a response looks like, what each field means.

Addresses using: nothing new — it relies entirely on the layers below for delivery.

OSI equivalent: combines OSI's Session (5), Presentation (6), and Application (7) layers.

Example protocols: HTTP, DNS (Units 4 and 6).

Why layering, instead of one protocol that does everything Layering means each layer can change independently without breaking the others. Your laptop can switch from Wi-Fi to a wired Ethernet cable — a Link-layer change — and every website you're loading (an Application-layer concern) keeps working without modification, because the Internet, Transport, and Application layers never had to know or care which physical medium was carrying their data. The same IP address, the same TCP connection logic, and the same HTTP requests work identically whether the Link layer underneath is Wi-Fi, Ethernet, or a cellular signal. Without layering, every application would need its own code for every possible physical medium — an unmanageable combinatorial mess.
A layer only talks to its neighbors When your browser (Application layer) wants to send an HTTP request, it hands the request down to the Transport layer and doesn't think about IP addresses or Wi-Fi signals at all — that's not its job. The Transport layer wraps it and hands it to the Internet layer, which wraps it and hands it to the Link layer, which is the only layer that actually knows or cares whether it's talking to a Wi-Fi radio or an Ethernet cable. Each layer's world is deliberately small.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the core idea behind organizing networking into layers?

Isolation between layers is the whole point — it's what lets, e.g., Wi-Fi swap for Ethernet without breaking web browsing.

2. Which model does this course's later units follow directly, and why?

OSI's vocabulary is still widely used, but TCP/IP is the model that corresponds to real, running protocols like IP, TCP, and HTTP.

3. A laptop switches from Wi-Fi to a wired Ethernet connection, and every website keeps loading normally with no changes needed elsewhere. What does this demonstrate?

This is exactly the isolation layering is designed to provide — a lower-layer swap doesn't ripple upward.

4. Fill in the blank: the TCP/IP layer responsible for delivering data to the correct program (not just the correct device), addressed using port numbers, is the ___ layer.

The Transport layer (TCP or UDP) is what distinguishes between programs on the same device, using port numbers.
