Diagnosing a Broken Connection — ping, traceroute, and Reading the Layers

"The internet is down" is never actually the problem. Some specific layer, at some specific point along the path, failed — and this course's entire vocabulary is what lets you find out which one.

← Lesson 25 Contents Glossary →

This is the last lesson of the course, and it's deliberately not a new topic — it's a method for using everything already covered. "My connection isn't working" could mean a dozen different specific failures at a dozen different specific layers, and guessing randomly wastes time. The two tools below, plus Lesson 2's LAN/WAN/internet framing and Unit 2's layered model, turn a vague complaint into a precise diagnosis.

ping: is the destination reachable at all?

Definition ping is a diagnostic tool that sends a small message to a target address and measures whether — and how quickly — a reply comes back, using ICMP (Internet Control Message Protocol), a lightweight Internet-layer protocol built specifically for network diagnostics and error reporting rather than carrying application data. A successful ping confirms basic Internet-layer reachability: the target exists, is reachable, and the round-trip path currently works (and reports the round-trip latency, connecting directly back to Lesson 3). A failed ping means something is broken somewhere on the IP path between you and the target — but not yet exactly where.

traceroute: which specific hop is the problem?

Definition traceroute is a diagnostic tool that reveals every router hop between you and a destination, along with the round-trip time to each one, by cleverly exploiting Lesson 11's TTL mechanism: it sends a series of packets with TTL set to 1, then 2, then 3, and so on, and each router that discards a TTL-expired packet sends back an ICMP message identifying itself — building up the full hop-by-hop path one router at a time. Where ping only tells you "reachable" or "not reachable," traceroute tells you exactly how far the packet actually got before something went wrong.
Try It — Read a Simulated traceroute
1  home-router.local        1 ms
2  isp-gateway.net           8 ms
3  backbone-1.example.net   14 ms
4  backbone-2.example.net   22 ms
5  destination.example.com  25 ms
Trace complete.

Reading it: every hop replied, and latency climbed smoothly and only slightly, hop by hop — a healthy path, matching Lesson 3's expectation that latency grows with distance and hop count, not a sign of anything broken.

1  home-router.local        1 ms
2  isp-gateway.net           9 ms
3  * * * Request timed out
4  * * * Request timed out
5  * * * Request timed out
Trace incomplete.

Reading it: the first two hops replied normally, but nothing beyond hop 2 ever responds. The problem isn't your device or your home network (both hops there worked) — it's somewhere at or just past your ISP's gateway. This narrows a vague "the internet is down" complaint down to one specific, nameable segment of the path.

> ping example.com
ping: cannot resolve example.com: Unknown host

> ping 8.8.8.8
Reply from 8.8.8.8: time=12ms
Reply from 8.8.8.8: time=11ms

Reading it: pinging a known-good IP address directly (8.8.8.8, a well-known public DNS server) succeeds — so the Internet layer and everything below it is working fine. Pinging the domain name fails at the resolution step itself, before any packet even attempts to leave for a destination. This isolates the failure to DNS (Lesson 13) specifically, not routing, not the Link layer, not the destination server.

Reading the layers: a diagnostic order, not a random guess

Why working bottom-up through the layers is the efficient approach Unit 2's layered model isn't just a way to organize protocols — it's a checklist for troubleshooting, worked from the bottom up: is the Link layer even connected (is Wi-Fi on, is the cable plugged in)? Does ping succeed to a known-good IP address (Internet layer reachability, ruling out DNS entirely)? Does ping succeed to the actual domain name (DNS, Lesson 13)? Does a connection succeed on the specific port the service uses (Transport layer, Lesson 14 — a device can be perfectly reachable overall while one specific service's port is closed or blocked)? Finally, does the application itself respond sensibly (Application layer, Unit 6 — checking, for instance, the actual HTTP status code returned)? Each step rules out an entire layer's worth of possible causes before moving to the next, instead of guessing at the answer directly — the same "narrow it down systematically" logic behind Unit 4's DNS delegation and Unit 4's routing, now pointed at a human problem instead of a protocol's own internal design.
Worked example: "the website won't load" Step 1: Wi-Fi icon shows connected — Link layer is fine. Step 2: ping 8.8.8.8 succeeds — Internet layer and routing are fine. Step 3: ping example.com fails to resolve — the problem is isolated to DNS. The fix (switching to a different DNS resolver, or waiting out a temporary outage at the current one) is now obvious, because the layered checklist ruled out every other explanation along the way, instead of leaving "something's wrong with the internet" as the only available diagnosis.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does a successful ping confirm?

Ping only confirms Internet-layer reachability and round-trip time — it says nothing about DNS, ports, or the application itself.

2. How does traceroute reveal each individual router along a path?

Traceroute cleverly exploits TTL expiration (Lesson 11) to reveal one hop at a time.

3. Why does working through the layers from bottom to top (Link, then Internet, then DNS, then Transport, then Application) make sense as a diagnostic order?

Systematically ruling out layers one at a time, from the bottom up, avoids wasted effort chasing the wrong explanation.

4. Fill in the blank: the lightweight Internet-layer protocol built specifically for diagnostics and error reporting, used by both ping and traceroute, is ___.

ICMP carries the diagnostic messages both ping and traceroute rely on, rather than carrying application data.
