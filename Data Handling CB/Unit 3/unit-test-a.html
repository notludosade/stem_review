1. A Students table needs a primary key. Which column is the right choice?

A primary key must uniquely identify every row and can never be blank — Student ID is the only option here that's guaranteed to satisfy both.

2. Fill in the blank: storing a Customer ID in the Orders table, instead of repeating each customer's full name and address on every order row, is an example of ___ — splitting data into linked tables so any fact is stored in exactly one place.

Normalization is the principle behind splitting data this way, so updating a customer's details only ever requires changing one row.

3. A table orders has columns order_id, region, total. Rows: (1, West, 250), (2, East, 90), (3, West, 400), (4, West, 150). What does SELECT order_id FROM orders WHERE region = 'West' AND total > 200; return?

WHERE filters on region = West and total > 200 first — order 4's total of 150 fails that second condition — then SELECT displays only order_id from the two surviving rows.

4. Fill in the blank: the SQL clause that restricts a query's results to only the first n rows, typically paired with ORDER BY to get a "top N" result, is ___.

LIMIT caps the number of rows returned, applied after ORDER BY has sorted the results.

5. In SELECT name FROM orders WHERE total > 100 ORDER BY total DESC;, which best describes the conceptual evaluation order?

Filtering on the full row happens before column selection narrows the display, which is exactly why WHERE can reference a column that SELECT never displays.

6. customers: (101, Ada), (102, Grace), (103, Alan). orders: (order 1, customer_id 101), (order 2, customer_id 102), (order 3, customer_id 999 — no such customer). Answer both parts:

(a) An INNER JOIN of orders to customers on customer_id would exclude which order?

(b) A LEFT JOIN from customers to orders would still include Alan (customer_id 103) in the result, with the order columns filled in as what?

INNER JOIN silently drops rows with no match on either side — order 3's invalid customer_id has no match, so it's excluded. LEFT JOIN keeps every row from the left table regardless, filling NULL where no match exists.

7. Using the same orders table as question 3, plus a fifth row (5, East, 300): SELECT region, COUNT(*) AS n, SUM(total) AS total_sum FROM orders GROUP BY region;. Answer both parts:

(a) How many rows fall into the West group?

(b) Fill in the blank: SUM(total) for the East group equals ___.

West has three rows (250, 400, 150). East has two rows (90 and 300), summing to 390. GROUP BY collapses each region into one row with its own aggregate values.

8. A query needs to keep only regions whose total sales exceed $500. Answer both parts:

(a) Which clause should filter on the condition SUM(total) > 500, applied after grouping?

(b) Why can't the other clause do this instead?

WHERE filters raw rows before GROUP BY computes any aggregate, so it has nothing to compare a summed total against — that's exactly what HAVING is for.

9. Using the five-row orders table from question 7 (totals 250, 90, 400, 150, 300 — average 238): SELECT order_id FROM orders WHERE total > (SELECT AVG(total) FROM orders);. Answer both parts:

(a) What does the subquery (SELECT AVG(total) FROM orders) compute?

(b) Which order_ids does the outer query return?

The subquery computes the overall average (238); the outer query keeps only rows exceeding it — 250, 400, and 300 all exceed 238, while 90 and 150 don't.

10. A multi-step query names an intermediate result with WITH regional_totals AS (...) before its main SELECT. Answer both parts:

(a) Fill in the blank: the SQL keyword that introduces this named result is ___.

(b) What is the main practical benefit of writing this as a CTE instead of an equivalent nested subquery?

A CTE (introduced with WITH) and an equivalent subquery often produce the identical result — the real advantage is readability from naming each step.
