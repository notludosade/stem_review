The Relational Model

Before writing a single SQL query, you need the mental model a relational database is built on: tables, keys, and the rule that lets many small tables stand in for one big, redundant one.

← Lesson 8 Lesson 10 → Contents Glossary →

Lesson 4 introduced databases as the tool for large, multi-user, rule-enforced data. This lesson opens the hood: a relational database organizes data into multiple linked tables rather than one giant sheet — and that linking is the entire point of the design.

Tables, rows, and columns — again, but stricter

Definitions A relational database is made of tables (also called relations). Each table has a fixed set of columns (fields, each with a declared data type — number, text, date) and any number of rows (records). Unlike a spreadsheet, a database table enforces its column types strictly: a "quantity" column declared as a number will reject an attempt to insert the text "unknown."

Primary keys

Definition A primary key is a column (or combination of columns) that uniquely identifies each row in a table — no two rows can share the same primary key value, and it can't be blank. A Customers table's primary key is typically a Customer ID; no two customers share an ID, and every customer has one.

Foreign keys and why data is split across tables

Definition A foreign key is a column in one table that refers to a primary key in another table, linking the two. An Orders table doesn't repeat a customer's full name and address on every single order row — it stores just the Customer ID as a foreign key, pointing back to one row in a separate Customers table.
Why splitting data this way is the whole point If every order row repeated the customer's full name, email, and address directly, updating one customer's email would mean finding and editing every order row they've ever placed — miss one, and the data becomes inconsistent (recall Lesson 3's consistency dimension), with two different emails on file for the same real customer. Storing customer details once, in one Customers row, and referencing it everywhere else by ID (a foreign key) means an update happens in exactly one place. This splitting-to-avoid-repetition principle is called normalization, and it's the core reason relational databases are organized into many small linked tables instead of one wide one.
Worked example A Customers table: Customer ID (primary key), Name, Region. An Orders table: Order ID (primary key), Customer ID (foreign key, referencing Customers), Order Total, Order Date. Order row 4471 doesn't contain "Ada Lovelace" anywhere — it contains Customer ID 102, and looking up 102 in the Customers table is what gets you the name. This is precisely the spreadsheet lookup from Lesson 6, formalized as the database's actual storage structure rather than something you compute after the fact.

Check your recall

No peeking back up — answer from memory first, then check.

1. What must be true of a table's primary key?

Uniqueness and non-blankness are what make a primary key usable as a reliable row identifier — that's what a foreign key elsewhere ends up pointing to.

2. What problem does storing a Customer ID (a foreign key) in the Orders table, instead of repeating the customer's full name and address on every order row, solve?

Storing details once and referencing them by key is exactly what prevents the update-consistency problem of repeated data.

3. What is the relationship between a foreign key in one table and a primary key in another?

The foreign key's whole purpose is pointing at another table's primary key, creating the link between the two tables.

4. Fill in the blank: the principle of splitting data into multiple linked tables to avoid repeating the same information, so any fact is stored in exactly one place, is called ___.

Normalization is the design principle behind splitting a database into many small tables linked by keys rather than one repetitive wide table.

5. Fill in the blank: a column in one table that refers to the primary key of a different table, creating a link between the two, is called a ___.

The foreign key is the mechanism that links tables together without repeating data across them.
