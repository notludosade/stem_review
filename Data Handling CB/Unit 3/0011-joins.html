Joins

Lesson 9 explained why data lives in separate, linked tables. This lesson is how you put it back together in a query — the SQL JOIN, doing in one keyword what Lesson 6's spreadsheet lookups did with VLOOKUP or XLOOKUP.

← Lesson 10 Lesson 12 → Contents Glossary →

Recall Unit 2, Lesson 6: an Orders sheet and a Customers sheet, linked by a shared Customer ID, combined with XLOOKUP to pull each order's customer name and region. A relational database stores that exact same split — Lesson 9's Orders and Customers tables, linked by Customer ID as a foreign key. A JOIN is how SQL recombines them.

INNER JOIN

Syntax SELECT orders.order_id, customers.name FROM orders INNER JOIN customers ON orders.customer_id = customers.customer_id; — this matches each row in orders to the row in customers where the ON condition holds, and returns one combined row per match. An INNER JOIN (the default kind, and by far the most common) only returns rows where a match exists in both tables — an order with a customer_id that doesn't exist in the customers table would be silently excluded entirely.

LEFT JOIN

Syntax SELECT orders.order_id, customers.name FROM orders LEFT JOIN customers ON orders.customer_id = customers.customer_id; — a LEFT JOIN keeps every row from the left table (orders) regardless of whether a match exists in the right table, filling in NULL (SQL's "no value" marker) for the right table's columns when no match is found. This matters whenever you specifically want to know about unmatched rows — e.g. finding orders whose customer_id doesn't correspond to any real customer, a data-quality problem Lesson 3's validity dimension would flag.
Why choosing INNER vs. LEFT changes your answer, not just your syntax If you want "total revenue per customer, only counting customers who have actually ordered," INNER JOIN is correct — customers with zero orders simply shouldn't appear. If you want "every customer, including ones with zero orders, showing 0 or blank where they haven't ordered," you need LEFT JOIN from the customers side. Using the wrong one doesn't cause an error — it silently drops or silently includes rows, producing a technically-successful query with the wrong answer. This is the SQL equivalent of Lesson 5's absolute-reference bug: no error is raised, so the mistake is only caught by checking the result against what you expected.
Worked example Orders table: order_id, customer_id, order_total. Customers table: customer_id, name, region. SELECT customers.region, orders.order_total FROM orders INNER JOIN customers ON orders.customer_id = customers.customer_id WHERE orders.order_total > 100; — this joins the two tables on the shared customer_id, then filters to only orders over 100, returning each qualifying order's total alongside its customer's region — the same combined view Lesson 6 built with XLOOKUP, now expressed as one SQL query.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does an INNER JOIN do with a row that has no matching row in the other table?

INNER JOIN only returns rows where a match exists on both sides — unmatched rows are dropped silently, no error raised.

2. Why would you specifically choose a LEFT JOIN over an INNER JOIN?

LEFT JOIN's whole purpose is preserving unmatched left-side rows, which is exactly what INNER JOIN discards.

3. Why is choosing the wrong join type (INNER vs. LEFT) described as similar to Lesson 5's absolute-reference bug?

Both are silent-failure bugs — the tool doesn't complain, it just quietly computes something other than what was intended.

4. Fill in the blank: the join type that returns only rows where a match exists in both tables is called an ___.

INNER JOIN is the default, most common join, keeping only rows matched on both sides.

5. Fill in the blank: in a LEFT JOIN, when no matching row exists in the right table, SQL fills the right table's columns with ___, its marker for "no value."

NULL is SQL's representation of "no value here," distinct from zero or an empty string.
