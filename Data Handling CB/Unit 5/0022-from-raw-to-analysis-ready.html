From Raw to Analysis-Ready

Missing values, outliers, duplicates, inconsistency — Lessons 19 through 21 handled each in isolation. This lesson closes Unit 5 by putting them in order, as one workflow, and by making the case for writing every decision down.

← Lesson 21 Lesson 23 → Contents Glossary →

A dataset that has been checked for missing values, outliers, and duplicates, and standardized for consistency, is often called analysis-ready. Getting there isn't one step — it's a short sequence, and the order matters more than it might seem.

A working order

Suggested sequence 1. Standardize first (Lesson 21) — fix case, whitespace, formatting, and category values before anything else, since a value like "N/A" typed inconsistently can otherwise slip past a missing-data check that's looking for a true blank. 2. Deduplicate (Lesson 21) — remove exact and fuzzy duplicates before any counting or aggregation happens, since duplicates distort the very numbers you'd use to spot outliers. 3. Handle missing data (Lesson 19) — decide, field by field, whether to delete, impute, or flag, using the MCAR/MAR/MNAR judgment from that lesson. 4. Check for outliers (Lesson 20) — apply the IQR rule, then judge each flagged value as error or genuine extreme case. This order isn't arbitrary: each step makes the next one more trustworthy, because it removes a source of noise that could otherwise disguise or mimic the problem the next step is looking for.
Why every decision in this workflow needs to be written down Every step above involves a judgment call — which rows counted as fuzzy duplicates, which missing values were imputed versus dropped, which flagged outliers were kept as genuine. None of these calls are automatic or objectively "correct" in the way a SQL query's result is; two careful analysts could reasonably make different calls on the same messy dataset. If those decisions aren't recorded, the final "clean" numbers look exactly as authoritative as if no judgment had been involved at all — and anyone downstream (including future-you) has no way to know what was decided, question it, or reproduce it. A short data-cleaning log — what was changed, why, and what rule was used — is what turns a cleaned dataset back into something someone else can trust and check, rather than a black box that happens to look tidy.
Worked example: one dataset, start to finish A raw customer export has: state values spelled three different ways, two rows for the same customer with a formatting difference in phone number, 4% of rows missing an email address, and one row listing "50,000 orders" for a single customer in a year. Working the sequence: standardize state spellings to one code; deduplicate the two customer rows into one; for missing emails, check whether they're concentrated in one signup channel (MAR) before deciding to flag rather than drop; for the 50,000-orders row, apply the IQR rule, confirm it's implausible for any real customer, and correct or remove it as a likely data-entry error rather than a genuine extreme value. Each decision — and the rule behind it — gets one line in a cleaning log before the dataset is called ready.

Check your recall

No peeking back up — answer from memory first, then check.

1. Why does standardization (Lesson 21) generally come before checking for missing data (Lesson 19) in this workflow?

Standardizing first ensures sentinel-style placeholders are recognizable as missing, rather than looking like valid but inconsistent data.

2. Why does deduplication generally happen before checking for outliers in this workflow?

Removing duplicates first keeps the counts and spread measures used for outlier detection trustworthy.

3. Why does a cleaned dataset need a record of the judgment calls made during cleaning (a cleaning log)?

Recording the reasoning behind each judgment call is what lets someone else trust, question, or reproduce the cleaning process.

4. Fill in the blank: a dataset that has been checked for missing values, outliers, and duplicates, and standardized for consistency, is commonly described as ___.

Analysis-ready is the term for data that has passed through this full cleaning sequence.

5. Fill in the blank: a short written record of what was changed during data cleaning, why, and what rule was used, is called a ___.

A cleaning log is what makes cleaning judgment calls checkable and reproducible by someone else.
