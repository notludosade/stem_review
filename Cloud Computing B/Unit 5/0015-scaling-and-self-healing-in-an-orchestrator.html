Scaling and Self-Healing in an Orchestrator

Lesson 14 named the pieces an orchestrator schedules. This lesson is about what it does with them the moment reality stops matching what was asked for — a pod crashes, or traffic changes, and nobody has to notice by hand.

← Lesson 14 Unit 6, Lesson 16 → Contents Glossary →

Unit 4 built a habit worth recognizing again here: declare a desired state, and let a tool continuously reconcile reality against it. An orchestrator applies that exact same idea to running pods, checking constantly, not just when a human remembers to look.

Desired state, continuously enforced

Definition A replica count is the number of identical pod copies an orchestrator is told should be running at all times — the desired state for that workload. The orchestrator continuously compares the actual running count against this number: if a pod crashes and the count drops below it, the orchestrator starts a replacement automatically, without anyone paging anyone. This automatic, unattended recovery is called self-healing.
Definition Scaling a replica count up or down in response to demand is the same elasticity idea from Cloud Computing A's auto scaling groups, applied one layer down — instead of adding or removing whole servers, the orchestrator adds or removes pods, often across the same fleet of nodes, based on metrics like CPU usage or request rate.

Worked example A checkout service is set to 6 replicas. One node hosting 2 of those pods fails entirely — hardware failure, exactly the kind Cloud Computing A's Unit 6 covered. The orchestrator notices the running count drop to 4, compares it against the desired 6, and schedules 2 new pods onto the cluster's remaining healthy nodes within seconds — the same automatic-failover instinct from redundancy and failover, just applied at the pod level instead of the availability-zone level.
Why self-healing only works if the desired state was set correctly in the first place An orchestrator has no opinion about whether 6 replicas is actually the right number — it just enforces whatever number it was told, relentlessly. If a deploy accidentally sets the desired count to 0, the orchestrator will just as diligently keep it at 0, "healing" a running service back down to nothing. Self-healing recovers from failures within the declared desired state; it can't recover from a wrong desired state, which is exactly why Unit 4's version-controlled, reviewed configuration matters just as much here as it did for infrastructure.

1. What does an orchestrator do when a pod crashes and the running count drops below the desired replica count?

Self-healing means the orchestrator reconciles actual state against desired state automatically.

2. How is orchestrator-level scaling similar to Cloud Computing A's auto scaling groups?

Both apply the same elastic, demand-driven scaling principle, just at different layers.

3. Why can't self-healing recover from a desired replica count that was set incorrectly, like accidentally set to 0?

Self-healing enforces the declared state faithfully, including a mistaken one — it can't judge correctness.

4. Fill in the blank: an orchestrator's automatic, unattended recovery of crashed pods back to the desired replica count is called ___.

5. Fill in the blank: the number of identical pod copies an orchestrator is told should be running at all times is called the ___.

The replica count is the desired state the orchestrator continuously enforces.
