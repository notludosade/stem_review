Core Concepts: Pods, Nodes, and Clusters

Lesson 13 established that an orchestrator schedules containers onto machines. This lesson names the actual pieces it's working with — the vocabulary every orchestrator, including the most popular one, is built on.

← Lesson 13 Lesson 15 → Contents Glossary →

"The orchestrator schedules containers onto machines" hides three separate concepts worth naming individually: the smallest thing being scheduled, the machine it's scheduled onto, and the whole group of machines being managed together as one system.

Pods, nodes, and clusters

Definition A pod is the smallest deployable unit an orchestrator schedules — usually one container, occasionally a small group of tightly-coupled containers that must always run together on the same machine (like a main application container and a small helper that ships its logs). The orchestrator schedules whole pods, never individual containers separately from the pod they belong to.
Definition A node is a single machine — physical or virtual — that's part of the orchestrator's available capacity, capable of running one or more pods. A cluster is the whole collection of nodes managed together as a single system, with the orchestrator's own coordination software (the control plane) making scheduling decisions across every node in it, so pods are placed based on total available capacity across the whole cluster, not judged node by node by hand.

Why a pod, not a container, is the unit of scheduling A logging helper that has to read a main application's log files needs to share that container's filesystem and network address — it only makes sense running on the exact same machine, at the exact same time, as the container it's helping. Scheduling containers individually could scatter these two across different nodes, breaking the whole point of the helper. Grouping them into one pod guarantees the orchestrator always places (and removes) both together, treating "things that must run in the same place" as a single schedulable unit instead of hoping two independent scheduling decisions happen to agree.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is a pod?

A pod is the atomic unit the orchestrator actually schedules, not a container by itself.

2. What is the relationship between a node and a cluster?

A cluster is the group; a node is one member machine within that group.

3. Why are a main application container and its tightly-coupled logging helper usually grouped into the same pod?

A shared pod is what guarantees co-location for containers that depend on running together.

4. Fill in the blank: a single physical or virtual machine that's part of an orchestrator's available capacity is called a ___.

A node is one machine capable of running one or more pods.

5. Fill in the blank: the whole collection of nodes managed together as a single system by the orchestrator's control plane is called a ___.

The cluster is the whole managed group of nodes, scheduled as one system rather than node by node.
