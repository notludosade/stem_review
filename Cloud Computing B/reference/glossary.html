Unit 1 — Why DevOps?

Development ("Dev") / Operations ("Ops")

Dev is the team that writes application code and is judged on shipping change quickly; Ops is the team that keeps that code running reliably in production and is judged on uptime, not feature velocity — historically separate teams with opposite incentives.

The wall

The informal handoff boundary where responsibility for deploying and running code passes from Dev to a separate Ops team, who then deploys code they didn't write and gets paged if it breaks.

DevOps

A set of cultural practices and shared responsibility that unites development and operations around one goal — shipping reliable software quickly, together — which the tools this course covers support but don't create by themselves.

Blameless postmortem

A review of an incident, after the fact, focused entirely on what happened in the system and the process — not on which individual to blame, on the premise that a reasonable decision usually isn't the root cause.

Deployment pipeline / CI/CD pipeline

The automated sequence of stages a code change passes through between being committed and running in production — typically build, test, package, deploy, and release — running the same way every time without manual repetition.

Build artifact

The packaged, runnable output of the build stage — a compiled binary, bundled application, or container image — versioned and carried unchanged through the rest of the pipeline instead of rebuilt at each stage.

Unit 2 — Continuous Integration

Continuous Integration (CI)

The practice of merging every developer's code changes into a shared main branch frequently — multiple times a day — with each merge automatically built and tested right away.

Merge conflict

What happens when two changes touch overlapping code in a way that can't be combined automatically, forcing a human to manually reconcile them; CI controls their size, not their existence.

CI server

The automated system that watches a shared repository and, on every merge, runs a defined build step followed by a test suite — reacting to the merge itself, with no human needing to click anything.

Build step / test suite

The build step compiles or bundles the code; the test suite is the collection of automated tests that runs afterward to check the code still behaves correctly.

Build status: green / red

Green means the build compiled and every test passed; red means something failed somewhere in the sequence — a signal to investigate, not a punishment.

Build log

The recorded output of every stage a CI server ran, in order, including exactly where it stopped and why — best read starting from the first failure, not the last line.

Flaky test

A test that sometimes passes and sometimes fails against the exact same, unchanged code, usually from timing assumptions or shared state — worse than a wrong test because it erodes trust in red builds over time.

Unit 3 — Continuous Delivery & Deployment

Continuous Delivery (CD) / Continuous Deployment

Continuous Delivery packages every change that passes CI into a release ready to deploy at any time, with a human still deciding when; Continuous Deployment removes that manual step and releases automatically.

Release gate

The manual approval step that separates Continuous Delivery from Continuous Deployment — removing it is the entire difference between the two.

Blue-green deployment

Running two identical, complete production environments — "blue" (current) and "green" (new) — side by side, then switching all traffic between them instantly, with an equally instant switch back if something's wrong.

Canary release / traffic shifting

Sending only a small percentage of real traffic to a new version first, monitoring it closely, then gradually increasing that percentage (traffic shifting) until it serves everyone or is rolled back.

Rollback / roll-forward

A rollback reverts a deployment to the last known-good version; roll-forward ships a new deploy that fixes the problem instead of reverting — sometimes the only option when reverting isn't safe.

Feature flag

A runtime switch, checked by the running code itself, that turns a specific piece of functionality on or off without a new deployment — usable as a near-instant "kill switch."

Unit 4 — Infrastructure as Code

Infrastructure as Code (IaC)

Defining servers, networking, and other infrastructure in version-controlled configuration files that a tool reads to provision the actual resources, instead of an engineer manually clicking through a console.

Imperative / declarative

An imperative approach lists exact steps to execute in order; a declarative approach states the desired end state and lets a tool figure out what changes are needed to reach it.

Idempotent

An operation where running it once has the same effect as running it many times — the property declarative IaC tools are built around, making reapplying a configuration file always safe.

Configuration drift

The gap that opens up between a system's actual, running configuration and what its IaC file says it should be, caused by any manual change made outside the IaC process.

Reconciliation

The process, run manually or on a schedule, of comparing actual state against declared desired state and correcting any difference found — what actually catches drift.

Immutable infrastructure

Instead of patching a running server, any change replaces it with a freshly-provisioned one built from the current IaC file, making drift structurally impossible rather than just detectable.

Unit 5 — Container Orchestration

Container orchestration / orchestrator

Orchestration is the automated scheduling, networking, scaling, and health management of many containers across many machines; an orchestrator is the system that does it, continuously and without manual placement decisions.

Pod

The smallest deployable unit an orchestrator schedules — usually one container, occasionally a small group of tightly-coupled containers that must always run together on the same machine.

Node / cluster

A node is a single physical or virtual machine capable of running one or more pods; a cluster is the whole collection of nodes managed together as a single system.

Control plane

The orchestrator's own coordination software, making scheduling decisions across every node in a cluster based on total available capacity, not node by node by hand.

Replica count

The number of identical pod copies an orchestrator is told should be running at all times — the desired state it continuously compares the actual running count against.

Self-healing

An orchestrator's automatic, unattended recovery of crashed pods back to the desired replica count, with no human needing to notice or intervene.

Elasticity

The same auto-scaling-group idea from Cloud Computing A applied one layer down — adding or removing pods, based on demand, instead of whole servers.

Unit 6 — Observability

Log

A timestamped, discrete record of a single event, written as free-form text or structured fields, answering "what exactly happened" in one specific instance.

Metric

A numeric measurement sampled at regular intervals and stored as a series over time — cheap to store and fast to graph, good at trends but not detail on any one event.

Trace / span

A trace follows a single request's entire path across multiple services, stitched into one timeline; a span is the record, within a trace, of how long that request spent inside one particular service.

Alert

An automated notification triggered when a monitored signal — a metric crossing a threshold, an error spike, a log pattern — indicates something needs a human's attention right now.

Alert fatigue

The desensitization that sets in when alerts fire too often or for non-actionable conditions, until people start muting or ignoring them, including the one that mattered.

Actionable alert

An alert with a specific, known response a human can actually take right now — the property that separates a genuinely useful page from one that just adds fatigue.

On-call rotation

A schedule where responsibility for responding to pages rotates among a defined group of engineers on a set cadence, so no single person is always on the hook.

Incident / incident commander

An incident is a formally declared event where a system is degraded in a way that affects users, kicking off a coordinated response; the incident commander coordinates that response without necessarily writing the fix themselves.

Unit 7 — Putting It Together

DORA metrics

Four measures — deployment frequency, lead time for changes, change failure rate, and time to restore service — that research has repeatedly found separate high-performing DevOps teams from low-performing ones.

Anti-pattern

A common response to a recurring problem that looks reasonable, or even feels responsible, but is actually counterproductive — a repeated habit, not a one-time mistake.

Toil

Manual, repetitive operational work that has no lasting value and grows roughly in proportion to a system's size, unless someone automates it away.
