Automated Builds and Test Suites in CI

Merging often, from Lesson 4, only helps if every merge is actually checked. A CI server is the thing that turns "we merge frequently" into "we know within minutes whether each merge actually works."

← Lesson 4 Lesson 6 → Contents Glossary →

Merging code without checking it is really just a faster way to break the shared main branch for everyone at once. What actually makes frequent merging safe is that every single merge automatically triggers the same sequence of checks, in the same order, without anyone having to remember to run them.

The CI server's job

Definition A CI server is the automated system that watches a shared repository and, on every merge, runs a defined build step (compiling or bundling the code) followed by a test suite — a collection of automated tests that check the code still behaves correctly. Nothing about this requires a human to remember to click anything; the CI server reacts to the merge itself.
Definition A build's status is usually summarized as green (the build compiled and every test passed) or red (something failed, anywhere in the sequence). A red build is a signal, not a punishment: it means whatever just merged needs attention before anyone builds more work on top of it.

Worked example: why stage order matters Lint checks (fast, seconds) run before unit tests (fast, seconds) which run before integration tests (slower, minutes) which run before end-to-end tests (slowest, sometimes many minutes). Ordering cheap, fast checks first means a build with a trivial typo fails in seconds instead of after waiting for a ten-minute end-to-end suite to grind through first. This ordering is usually called "fail fast" — it doesn't make the code more correct, but it gives the developer their answer as quickly as possible.
Why a test suite has to actually be trustworthy to be useful An automated test suite only pays for itself if a green build genuinely means "this is safe to build on" and a red build genuinely means "something is actually wrong." A suite with weak or missing coverage can go green on code that's badly broken, giving false confidence; the opposite failure mode — tests that fail for reasons unrelated to the actual change — is common enough that it gets a name and its own lesson next: a flaky test.
