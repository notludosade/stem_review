Deployment Strategies: Blue-Green and Canary Releases

Lesson 7's release gate decides when a change ships. This lesson is about how it actually reaches users — because "deploy the new version" can mean flipping a switch for everyone at once, or something far more careful.

← Lesson 7 Lesson 9 → Contents Glossary →

The simplest possible deployment stops the old version and starts the new one in its place. It's also the riskiest: every user hits the new code at the same instant, and if something's wrong, everyone finds out at once. Both strategies below exist to avoid exactly that all-or-nothing moment, using Cloud Computing A's load balancer to control who sees what.

Blue-green: two full environments, one switch

Definition A blue-green deployment runs two identical, complete production environments — "blue" (the current live version) and "green" (the new version) — side by side. The new version is deployed and fully tested on green while blue keeps serving all real traffic. Once green checks out, the load balancer's routing is switched to send all traffic to green instantly. If something's wrong, switching back to blue is just as instant, since it never stopped running.

Canary: a small slice of real traffic first

Definition A canary release sends only a small percentage of real traffic to the new version first — say 5% — while the rest keeps hitting the proven old version, monitoring the canary slice closely for errors. If it looks healthy, the percentage gradually increases (traffic shifting) until the new version serves everyone; if it doesn't, traffic shifts back with only a small fraction of users ever having been affected.

Worked example: the same bug, two different blast radii A new version has a bug that only appears under real production load. Deployed blue-green, 100% of users hit it the instant the switch flips — the bug is caught only after it's already affected everyone, even though rolling back is fast once it's noticed. Deployed as a canary starting at 5%, the same bug only affects the 5% of users in the canary slice; monitoring catches the elevated error rate before traffic ever shifts further, and the other 95% of users never see the bug at all.
Why canary costs more effort than blue-green, and isn't always worth it Canary releases need real, per-slice monitoring — the ability to compare the canary's error rate against the stable version's, in real time, at each traffic percentage (Unit 6 covers exactly this). Blue-green just needs a second full environment and a way to flip routing instantly. A team without mature monitoring often reaches for blue-green first, since "the bug either exists or it doesn't" is much simpler to detect than "the bug appears in one thin slice of the traffic and needs to be measured." Neither strategy is strictly better — canary limits blast radius at the cost of needing better monitoring to actually use that advantage.

Check your recall

No peeking back up — answer from memory first, then check.

1. In a blue-green deployment, what makes rolling back so fast if the new version has a problem?

Keeping the old environment alive is exactly what makes an instant switch back possible.

2. How does a canary release limit the impact of a bad deployment, compared to switching all traffic at once?

Limiting exposure to a small traffic slice is exactly what bounds a canary's blast radius.

3. Why might a team choose blue-green over canary, even though canary limits blast radius more effectively?

Canary's advantage depends on monitoring good enough to actually detect a problem in a small slice of traffic.

4. Fill in the blank: running two identical, complete environments and switching all traffic between them instantly is called a ___ deployment.

Blue-green keeps the old environment ready as an instant fallback.

5. Fill in the blank: gradually sending an increasing percentage of real traffic to a new version, starting small, is called a ___ release.

A canary release exposes only a slice of users first, expanding only once that slice looks healthy.
