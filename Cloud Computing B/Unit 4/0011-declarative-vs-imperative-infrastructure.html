Declarative vs. Imperative Infrastructure

Lesson 10 established that infrastructure should live in a file. It didn't say what that file actually contains — and the two possible answers behave very differently the second time you run them.

← Lesson 10 Lesson 12 → Contents Glossary →

Two IaC files can both provision three servers, and behave completely differently if run twice. The difference isn't the tool — it's whether the file describes a sequence of steps to take, or a final state to reach.

Two ways to write the same instruction

Definition An imperative approach lists the exact steps to take, in order: "create a server, then create another server, then create a third." Running that script twice creates six servers, not three — the script has no idea three already exist, it just executes its steps again. A declarative approach instead states the desired end state: "there should be three servers." A declarative tool compares that desired state against what currently exists and only makes the changes needed to close the gap — running it against three already-existing servers does nothing at all, because nothing needs to change.
Definition An operation is idempotent if running it once has the same effect as running it many times. Declarative infrastructure tools are built to be idempotent by design — reapplying the same configuration file is always safe, because the tool only ever acts on the difference between desired and actual state. Most modern IaC tools default to declarative for exactly this reason.

Worked example An engineer accidentally runs the same apply command twice — a genuinely common mistake, especially in an automated pipeline that retries on a network blip. With an imperative "create 3 servers" script, that mistake now means 6 servers are running, quietly doubling the bill until someone notices. With a declarative "desired count: 3" configuration, the second run compares against the 3 servers that already exist, sees no gap, and changes nothing — the exact same mistake has zero effect.
Why declarative became the industry default for IaC specifically Imperative scripts aren't wrong — they're just harder to reason about at scale, because understanding the current state means mentally replaying every script ever run against it, in order. Declarative configuration collapses that history into one readable file: the current desired state, in full, independent of how many times it's been applied or in what order. That property — safety under repetition, and a single source of truth for "what should exist" — is also exactly what Lesson 12's config drift problem needs, which is why almost every major IaC tool is declarative first.

1. What is the key difference between an imperative and a declarative approach to infrastructure?

Steps-to-execute vs. desired-state-to-reach is the defining difference.

2. Why does running an imperative "create 3 servers" script twice typically create 6 servers instead of 3?

Imperative scripts have no concept of current state — they just execute steps.

3. Why do most modern IaC tools default to declarative configuration?

Safety under repeated application is exactly the property declarative tools are built around.

4. Fill in the blank: an operation where running it once has the same effect as running it many times is called ___.

Idempotency is what makes reapplying a declarative configuration file always safe.

5. Fill in the blank: an infrastructure approach that states the desired end state, and lets a tool determine what changes are needed to reach it, is called ___.

Declarative configuration describes "what should exist," not the sequence of steps to get there.
