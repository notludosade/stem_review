Config Drift and Why IaC Prevents It

Lesson 11's declarative file only guarantees state at the moment it's applied. This lesson is about what happens in between applies, when someone changes something the file doesn't know about.

← Lesson 11 Unit 5, Lesson 13 → Contents Glossary →

A declarative IaC file (Lesson 11) describes the desired state accurately — right up until someone logs into a server directly and changes a setting by hand to fix an urgent problem at 2 a.m. That fix works. It also just made the IaC file wrong, and nothing about the file itself knows it happened.

Drift: when reality quietly stops matching the file

Definition Configuration drift is the gap that opens up between a system's actual, running configuration and what its IaC file says it should be — caused by any manual change made outside the IaC process: a console click, an emergency SSH fix, a setting changed by another tool entirely. The file isn't automatically wrong when this happens; it's just no longer the truth, and nothing alerts anyone to that fact on its own.
Definition Reconciliation is the process — run manually or on a schedule — of comparing actual state against the declared desired state and correcting any difference found, exactly the way Lesson 11's declarative tool behaves on every apply. Running reconciliation regularly is what actually catches drift: without it, a manual fix from months ago can sit silently until it causes a much more confusing problem down the line.

Worked example A server's firewall rule is manually opened on a Friday night to unblock an urgent partner integration, with a mental note to "add it to the IaC file on Monday." Monday gets busy. Three months later, a security audit finds a firewall rule nobody can explain, on a server whose IaC file says it shouldn't exist — because it doesn't, in the file. Regular reconciliation would have either caught and reverted the rule the following week (forcing someone to actually add it to the file if it was meant to stay), or confirmed it was deliberate and current, instead of leaving a three-month-old mystery for an audit to find.
Why IaC's real promise isn't "no manual changes ever" — it's "no manual changes survive silently" Emergency fixes will keep happening; no policy stops a 2 a.m. incident from needing an immediate, undocumented change. IaC's actual value is what happens next: a scheduled reconciliation run will either revert that unplanned change back to the file's declared state, or — if the change should stick around — force it to become a reviewed, version-controlled update to the file itself, closing the loop instead of leaving it open. Some teams take this further with immutable infrastructure: instead of patching a running server at all, any change replaces it with a freshly-provisioned one built from the current IaC file, making drift structurally impossible rather than just detectable.

1. What is configuration drift?

Drift is specifically caused by changes the IaC file doesn't know about, not by the tool itself.

2. What does reconciliation actually do?

Reconciliation is what actually catches and corrects drift once it exists.

3. Why does this lesson describe immutable infrastructure as making drift "structurally impossible" rather than just detectable?

Replacing rather than patching removes the very possibility of an untracked manual change persisting.
