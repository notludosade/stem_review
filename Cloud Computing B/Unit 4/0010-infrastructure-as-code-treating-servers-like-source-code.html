Infrastructure as Code: Treating Servers Like Source Code

Unit 3 deployed application code carefully — tested, versioned, reversible. This unit asks why the environment underneath that code usually didn't get the same treatment, and what changes when it does.

← Unit 3, Lesson 9 Lesson 11 → Contents Glossary →

Cloud Computing A covered VPCs, load balancers, and managed databases as things you configure. It didn't say how. The traditional answer — an engineer clicking through a provider's web console, one setting at a time — works fine once. It falls apart the second time someone needs to reproduce that exact environment, and it falls apart completely the tenth time.

Infrastructure, defined the same way as an application

Definition Infrastructure as Code (IaC) means defining servers, networking, and every other piece of infrastructure in version-controlled configuration files, then having a tool read those files and provision the actual resources — instead of an engineer manually clicking through a console or running one-off commands. The infrastructure a system runs on gets treated exactly like the application code running on it: reviewed, versioned, and reproducible from the same file every time.

Worked example A team needs identical staging and production environments. Provisioned manually, an engineer clicks through a console twice, and inevitably picks a slightly different disk size, forgets one security rule, or names a resource differently — the two environments quietly diverge from day one. Provisioned with IaC, the same configuration file is applied twice, once per environment: the tool reads the exact same definition both times, so staging and production start out — and stay — structurally identical, differing only in the values (like environment name) the file was deliberately parameterized to change.
Why "it's version-controlled" is the part that matters most A console click leaves no history — no record of who changed a setting, when, or why, and no way to review a change before it takes effect. An IaC configuration file lives in the same kind of repository as application code: every change is a diff, reviewable before merging (Unit 2's CI can even validate it automatically), and revertible with the same rollback tools Unit 3 covered for application deployments. The infrastructure stops being something only one specific engineer remembers how to rebuild, and becomes something the whole team can read, review, and trust.

1. What does Infrastructure as Code mean?

IaC treats infrastructure definitions like source code, provisioned by a tool rather than clicked by hand.

2. Why do two environments provisioned manually through a console tend to diverge over time, even when the intent was identical?

Human repetition introduces small, easy-to-miss inconsistencies that a configuration file doesn't.

3. Why does putting infrastructure configuration under version control matter, beyond just automating the clicks?

Review history and revertibility are exactly what a console click can never provide on its own.
