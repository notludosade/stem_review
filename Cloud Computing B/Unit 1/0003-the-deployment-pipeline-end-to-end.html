The Deployment Pipeline, End to End

Lessons 1 and 2 argued that DevOps is culture first. Culture still needs a concrete path for code to travel — from a developer's keyboard to a user's screen. This lesson maps that whole path once, so every later unit has a place to slot into.

Every practice this course covers — automated builds, deployment strategies, infrastructure as code, orchestration, observability — exists somewhere along one continuous path from a developer committing a change to a user actually experiencing it. Seeing that whole path once, before zooming into any one stage of it, makes every later unit easier to place: each one is really just a deep dive on a single stop along this map.

The deployment pipeline, defined

Definition A deployment pipeline (often called a CI/CD pipeline) is the automated sequence of stages a code change passes through between being committed and running in production — typically build, test, package, deploy, and release, with monitoring wrapped around the whole thing. "Automated" is the key word: the same sequence runs the same way every time, without a human manually repeating each step by hand.
Definition A build artifact is the packaged, runnable output of the build stage — a compiled binary, a bundled application, or (as Unit 5 covers) a container image — versioned and stored so that the exact same artifact that passed every test is the one that actually gets deployed, instead of rebuilding from source at each stage and risking something changing in between.

Why mapping the whole pipeline first is worth doing It's tempting to treat "CI," "CD," "IaC," and "orchestration" as a pile of unrelated buzzwords to memorize separately. They're not — they're consecutive stops on one path, each one solving the problem the previous stage hands off. CI (Unit 2) exists because merging code without automated checks is risky. Deployment strategies (Unit 3) exist because even correctly-tested code can still fail in production. Infrastructure as code (Unit 4) exists because the environment that code deploys into needs to be as reliable and reviewable as the code itself. Orchestration (Unit 5) exists because a fleet of containers needs to be run, not just built. Observability (Unit 6) exists because "it deployed successfully" and "it's working correctly for users right now" are two different claims. Nothing in this course is a detour — it's all one pipeline, examined one stage at a time.
