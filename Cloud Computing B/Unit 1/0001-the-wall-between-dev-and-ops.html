The Wall Between Dev and Ops, and Why It Broke Down

Cloud Computing A gave you the building blocks — containers, elastic fleets, redundant regions. This course is about the humans who decide when new code actually lands on top of them, and the wall that used to make that painfully slow.

Lesson 2 → Contents Glossary →

Cloud Computing A answered "where does code run" — a container, sized by an auto scaling group, spread across availability zones for redundancy. It never answered "how does new code actually get there." For a long time, most organizations answered that question with two separate teams, two separate goals, and a slow, painful handoff between them. This course starts with why that arrangement existed, and why it stopped working.

Two teams, one application, opposite incentives

Definition Development ("Dev") is the team that writes application code and wants to ship changes — new features, fixes — as fast as possible. Operations ("Ops") is the team that keeps that code running reliably in production, and is judged on uptime, not feature velocity. Historically these were separate teams with separate managers, separate tools, and separate definitions of success: Dev's incentive was change; Ops's incentive was stability. Every deploy sits exactly on top of that conflict, since every change is also a risk.
Definition The wall (sometimes "throwing it over the wall") is the informal handoff boundary in that arrangement: Dev finishes code and hands it off — often as a ticket, a build artifact, or a deployment request — to Ops, who then has to deploy code they didn't write, understand only from documentation, and be the one paged at 3 a.m. if it breaks. Neither side has full context on the other's half of the job, and neither side is rewarded for making the handoff smoother.

Why elastic infrastructure made the wall unbearable An auto scaling group from Cloud Computing A, Unit 6 can add ten servers in minutes with nobody manually provisioning anything. That speed is wasted if the code meant to run on those servers still has to cross a multi-day ticket queue between the person who wrote it and the person allowed to deploy it. As infrastructure got faster and cheaper to change, the wall didn't move with it — it became the single slowest, most error-prone step in the entire path from "code written" to "code running," which is exactly the gap DevOps set out to close.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does "the wall" refer to, in the traditional Dev/Ops split?

The wall is an organizational handoff, not a technical or network boundary.

2. Why were Dev and Ops's incentives historically in conflict?

Change (Dev's goal) and stability (Ops's goal) pull in opposite directions on every single deploy.

3. Why did the wall become a bigger problem as cloud infrastructure got more elastic and automated?

As every other step got faster, the human handoff at the wall increasingly stood out as the bottleneck.

4. Fill in the blank: the informal handoff boundary where responsibility for deploying code passes from Dev to a separate Ops team is often called ___.

"The wall" (or "throwing it over the wall") names exactly this handoff.

5. Fill in the blank: the team historically judged on uptime and reliability, rather than feature velocity, is called ___.

Operations (Ops) owns production stability, in contrast to Dev's focus on shipping change.
