Model Drift and Monitoring in Production

AI Developer's Unit 8 covered drift from the outside — logging an API's inputs and outputs over time. This closing lesson covers it from the inside: a model whose weights you trained yourself, whose accuracy you can no longer just re-measure the way Lesson 19 did, because the labels stopped arriving the moment it shipped.

← Lesson 19 Contents Glossary →

Every metric Lesson 19 computed needed one thing this lesson has to reckon with directly: true labels. A test set has them. Production traffic, the moment a model actually ships, usually doesn't — nobody is manually confirming whether each new prediction was correct, in real time, forever. Drift has to be caught largely without that ground truth, which is why it splits into two genuinely different things to watch for.

Python — the two kinds of drift, and how each shows up without labels 
import numpy as np

def input_distribution_shift(training_features, live_features):
    # Data drift: the *inputs* look different than what the model trained on --
    # detectable without any labels at all, just by comparing distributions.
    return abs(training_features.mean() - live_features.mean())

def prediction_distribution_shift(training_predictions, live_predictions):
    # A proxy for concept drift: the relationship between input and correct
    # output may have changed, even if inputs still look familiar. Without
    # labels, a shifting prediction distribution is often the first hint.
    return abs(training_predictions.mean() - live_predictions.mean())

Data drift is a change in the input distribution itself — a fraud model trained mostly on desktop transactions suddenly seeing a surge of mobile ones, or a vision model trained on daytime photos starting to see far more low-light images. This is detectable without any new labels: just compare the statistical distribution of live inputs against training-time inputs. Concept drift is subtler and more dangerous — the actual relationship between input and correct output changes, even though the inputs still look statistically familiar. A spam model trained before a new scam template became popular can face emails that look structurally ordinary yet are now, in reality, spam; the mapping from features to true label shifted, not the features themselves.

Definition Data drift is a change in the distribution of input features compared to training time, detectable by comparing input statistics alone. Concept drift is a change in the true relationship between input and correct output, often invisible until new labels eventually arrive. A retraining trigger is a defined threshold — a metric crossing a set value, or a fixed time interval — that starts a new training run automatically, rather than leaving the decision to whenever someone happens to notice.

1. What is the key difference between data drift and concept drift?

Data drift is about the inputs themselves; concept drift is about the mapping from input to correct output changing.

2. Why is concept drift harder to detect than data drift?

Unlike data drift, concept drift can hide behind inputs that still look perfectly ordinary.

3. Why can't Lesson 19's evaluation metrics simply be recomputed continuously in production the way they were during development?

The lack of continuously arriving ground truth is exactly why monitoring has to rely on proxies like distribution shifts.
