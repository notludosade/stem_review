The Compilation Pipeline: Preprocessor, Compiler, Assembler, Linker

Lesson 1 called compiling "one step." It's actually four separate programs running in sequence, each handing its output to the next — and knowing which one is which is exactly what turns a cryptic build error into an obvious one.

← Lesson 1 Lesson 3 → Contents Glossary →

When you type gcc hello.c -o hello, it looks like one command does everything. Underneath, four distinct tools run one after another, each doing one specific job and passing a transformed file to the next. Understanding these four stages is the difference between staring blankly at "undefined reference" and knowing immediately which tool complained and why.

Stage 1: the preprocessor

Definition The preprocessor runs first and performs purely textual substitution on the source code, before any real compiling happens. It expands #include directives by literally pasting in the contents of the named file, expands #define macros by substituting their text everywhere they're used, and resolves #if/#ifdef conditional blocks. Its output is still plain C source code — just a much larger, fully expanded version of it.

Stage 2: the compiler proper

Definition The compiler (in this narrower, stage-specific sense) takes the preprocessed C source and translates it into assembly language — a human-readable text format that maps closely, roughly one line per instruction, to the processor's actual machine instructions (Unit 7 covers assembly in depth). This is where syntax errors, type errors, and most of what programmers casually call "compiler errors" actually get caught.

Stage 3: the assembler

Definition The assembler takes that human-readable assembly and translates it into an object file — actual binary machine code, but not yet a complete, runnable program. An object file's machine code may still reference functions or variables defined somewhere else entirely, like printf, which lives in the C standard library, not in your own source file.

Stage 4: the linker

Definition The linker takes one or more object files, plus any libraries they depend on, and stitches them together into one final, complete executable — resolving every reference to an outside function or variable by finding where it's actually defined and patching in its real address. A static library gets copied directly into the executable at link time; a dynamic library stays a separate file on disk, loaded and linked in only when the program actually runs.

Interactive: the four-stage compilation pipeline

Worked example: hello.c through all four stages hello.c (your source) → preprocessor → hello.i (fully expanded C source, every #include pasted in) → compiler → hello.s (assembly text) → assembler → hello.o (an object file — real machine code, but with an unresolved reference to printf) → linker → hello (a complete executable, with printf's address patched in from the C standard library). Only the very last file is something you can actually run.
Why knowing the stages turns a confusing error into an obvious one A misspelled variable name fails at the compiler stage, with a message pointing at your exact source line. Calling a function that's declared but never actually defined anywhere fails at the linker stage instead, with a very different-looking message: undefined reference to 'my_function' — no source line, no syntax complaint, because syntactically nothing is wrong; the linker simply never found where that symbol's actual machine code lives. Without knowing these are two different tools doing two different jobs, both errors just look like "the compiler is broken." Knowing the pipeline turns "undefined reference" into an immediate, specific diagnosis: something is missing at link time, so go check whether that function was actually implemented or the right library was included.

Check your recall

No peeking back up — answer from memory first, then check.

1. What does the preprocessor stage actually do?

The preprocessor only manipulates text — its output is still C source code, just fully expanded.

2. Why does an object file (.o) still fail to run on its own?

An object file is real machine code, but it isn't complete until the linker resolves every outside reference and combines everything into one executable.

3. Which stage is responsible for turning assembly language into an object file's binary machine code?

The assembler sits between the compiler (which produces assembly) and the linker (which combines object files).

4. Fill in the blank: an "undefined reference" error, with no specific source line and no syntax complaint, comes from the ___ stage.

The linker complains this way when it can't find where a referenced symbol is actually defined.

5. Fill in the blank: a ___ library gets copied directly into the final executable at link time, unlike a dynamic library, which stays a separate file loaded at run time.

Static linking bakes the library's code into the executable itself; dynamic linking keeps it external.
