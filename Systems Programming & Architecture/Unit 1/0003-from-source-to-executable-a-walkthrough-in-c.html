From Source to Executable: A Walkthrough in C

Lesson 2 named the four stages. This lesson runs them, one real gcc command at a time, on one real C program — and uses the pipeline to figure out which stage would catch which kind of mistake.

← Lesson 2 Unit 2, Lesson 4 → Contents Glossary →

Start with the smallest real C program that does something:

// hello.c
#include <stdio.h>

int main(void) {
    printf("Hello, world!\n");
    return 0;
}

Compare this to Computer Programming 1's Python or JavaScript "hello world" — no #include, no type on main, no semicolons. C requires more upfront ceremony because, unlike Python, nothing about C assumes an interpreter is standing by to figure things out at run time. Every type, every included capability, has to be nailed down before the pipeline can even start.

Running each stage by hand

Worked example: four commands, four outputs gcc -E hello.c -o hello.i stops after the preprocessor — open hello.i and you'll find hundreds of lines from stdio.h pasted in above your two-line main. gcc -S hello.c -o hello.s stops after the compiler — hello.s is short, readable assembly with instructions like call printf. gcc -c hello.c -o hello.o stops after the assembler — hello.o is binary and unreadable as text, containing real machine code with an unresolved reference to printf. Finally, gcc hello.c -o hello, with no stage-stopping flag, runs the whole pipeline through the linker and produces hello — an executable you run with ./hello.

Which stage catches which mistake?

Every one of the four tools only looks for its own category of problem. A mistake that's invisible to one stage might sail right through it and get caught — or missed entirely — by the next.

Interactive: which stage would catch this?

Why "it compiled" doesn't mean "it will run" In Python, a typo in a function name you never call is invisible until that line actually executes — the interpreter never looks ahead. In C, gcc hello.c -o hello either succeeds all the way through the linker, producing a runnable file, or it doesn't produce anything runnable at all. But "it compiled" still isn't the same guarantee as "it's correct": the pipeline only checks that your code is well-formed and every reference resolves — it says nothing about whether the logic is right. A program with a serious logic bug can sail through all four stages without a single complaint, then produce the wrong answer instantly, or crash on some input the pipeline had no way to anticipate. Later units — especially Unit 8 — are about exactly that gap between "compiles cleanly" and "behaves correctly."

Check your recall

No peeking back up — answer from memory first, then check.

1. What does the gcc flag -c actually do?

-c means "compile and assemble only" — stop right before linking.

2. Why does C's "hello world" require #include <stdio.h> while Python's doesn't need an equivalent import for print()?

C's ahead-of-time pipeline needs every function's signature known before compiling, unlike an interpreter that resolves names as it goes.

3. A C program compiles and links with zero errors, but produces the wrong output when run. What does this tell you?

A clean build guarantees structural correctness, not logical correctness — those are separate concerns entirely.

4. Fill in the blank: the gcc flag that stops the pipeline after only the preprocessor stage is ___ (lowercase is fine).

-E stops right after preprocessing, outputting expanded C source rather than assembly, an object file, or an executable.

5. Fill in the blank: after running gcc hello.c -o hello successfully, the command used to actually run the resulting program on the same machine is ___.

The leading ./ tells the shell to run the executable sitting right here, rather than searching for a system-wide command of the same name.
