What Actually Happens When You Run a Program

Computer Programming 1 and 2 taught you to write correct programs. This course is about what happens the instant after you hit "run" — the machinery underneath every language you already know, starting with the split between two fundamentally different ways a program can execute at all.

Lesson 2 → Contents Glossary →

Every program you've written so far — in Python, JavaScript, Java, or C++ — you ran the same way: save the file, run a command, watch it work. What that command actually did underneath was completely different depending on the language, and this course exists because that difference matters a great deal once you start asking why programs crash, why some run a hundred times faster than others, and what a computer is actually doing between "run" and "output."

Two ways to turn source code into a running program

Definition Source code is the human-readable text you write in a programming language. A computer's processor cannot execute source code directly — it only executes machine code, raw binary instructions specific to that processor's design. Something has to bridge that gap, and there are two fundamentally different ways to do it: compiling the whole program into machine code ahead of time, or interpreting it line by line as it runs.
Definition A compiler translates an entire program's source code into machine code once, producing a standalone executable file. Running the program later means the processor runs that machine code directly — no translation happens at run time. An interpreter, by contrast, reads and executes source code (or a lightweight intermediate form of it) one piece at a time, translating as it goes, every single time the program runs.

Where Python and JavaScript actually sit

"Compiled vs. interpreted" is usually taught as a clean split between languages, but the honest picture is a little messier — and worth being precise about now, since the rest of this course lives on the compiled side of that line.

Worked example: three languages, three strategies C is compiled ahead of time by a program like gcc: source code goes in, a standalone executable full of machine code comes out, and that executable runs directly on the processor with no C toolchain present at all. Python is interpreted: the python program reads your .py file and executes it on the spot, translating as it goes — nothing you can hand someone else and run without Python installed. JavaScript, run by V8 (the engine inside Chrome and Node), is more subtle still: V8 starts by interpreting, then compiles the "hot" parts of your code into machine code on the fly, while the program is already running — a strategy called just-in-time (JIT) compilation, blurring the line between the two categories.

Why this course lives on the compiled side An interpreter is itself a program — one that has already been compiled, usually written in C. Every time you run a Python script, you're running a compiled C program (the Python interpreter) that reads and executes your source code for you. That means there is always a bottom layer where translation happens once, ahead of time, into raw machine code with no further translation layer underneath — and understanding that bottom layer is what this entire course is about. C sits at that bottom layer directly, which is why it's this course's language for looking at what a computer is actually doing.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the core difference between how a compiler and an interpreter turn source code into something a processor can run?

Ahead-of-time, one-time translation into a standalone executable is what defines compiling; repeated, on-the-fly translation is what defines interpreting.

2. Why can a compiled C executable run on a machine with no C compiler installed, while a Python script cannot run without Python installed?

Compiling removes the need for the original toolchain at run time; interpreting requires the interpreter every single time.

3. What does it mean that V8's JIT compilation "blurs the line" between compiled and interpreted execution?

JIT compilation mixes both strategies: interpret first, then compile the hot paths on the fly, during execution rather than strictly before or instead of it.

4. Fill in the blank: the raw binary instructions a processor executes directly, specific to that processor's design, are called ___.

Machine code is the only thing a processor can actually run — every language ultimately has to become this.

5. Fill in the blank: a Python script is executed by a program, itself already compiled into machine code, called an ___.

The interpreter itself has to be a compiled program somewhere at the bottom, which is exactly why this course studies that bottom layer directly.
