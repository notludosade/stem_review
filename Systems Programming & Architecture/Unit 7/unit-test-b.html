1. What does the ALU actually do?

The ALU is the component that actually carries out an instruction's arithmetic or logic operation.

2. Fill in the blank: the CPU's continuously repeating cycle of reading an instruction, figuring out what it means, and carrying it out is the ___ cycle.

Fetch, decode, execute, repeat — this cycle is every running program at the hardware level.

3. Why does a CPU have only a few dozen registers instead of millions?

The physical cost of on-die register circuitry is exactly why registers stay few and RAM stays enormous by comparison.

4. Why doesn't a C function's source code need to explicitly state which registers its arguments arrive in?

The calling convention is an agreed contract the compiler follows automatically, with no explicit statement needed in C source.

5. Why does reading compiled assembly output stay useful, even though almost no one writes assembly by hand anymore?

Assembly is the stripped-down ground truth of a program's actual behavior, useful well beyond the rare case of writing it by hand.

6. Fill in the blank: the small, very fast layer of memory sitting between registers and RAM, automatically keeping recently and nearby-used data close to the CPU, is called the ___.

The cache exists specifically to soften the speed gap between registers and RAM.

7. What is spatial locality?

Spatial locality is about nearby addresses; temporal locality (a separate idea) is about reusing the same address soon.

8. Requesting one byte of an array pulls in its entire 64-byte cache line. Why does this generally pay off rather than waste bandwidth?

Spatial locality is exactly why fetching a whole line ahead of need so often pays off.

9. Why does minimizing struct padding (Unit 4) directly help performance when looping over a large array of struct instances?

Fitting more struct instances per cache line reduces how often the array needs a fresh trip to RAM.

10. A loop's Big-O complexity looks identical whether it accesses memory sequentially or in a scattered order. Answer both parts:

(a) Does identical Big-O complexity guarantee identical real-world wall-clock speed?

(b) What is the standard way to actually detect this kind of gap, since it doesn't show up on paper?

Cache effects live outside Big-O analysis entirely — measuring real behavior is the only way to see them.
