From C to Assembly: Reading Compiled Output

Lesson 2 named "the compiler" as the stage that turns C into assembly, and put off actually looking at it. Lesson 19 gave the vocabulary — registers, the ALU. This lesson finally reads real compiler output, one instruction at a time.

← Lesson 19 Lesson 21 → Contents Glossary →

Take the smallest possible C function and compile it with gcc -S — stopping the pipeline right after the compiler stage, exactly like Lesson 3 did. What comes out is real, readable assembly, and every line of it maps to something Lesson 19 already gave you the words for.

// add.c
int add(int a, int b) {
    return a + b;
}

Reading the output, line by line

Definition Each line of assembly is one mnemonic — a short, human-readable name standing in for a single machine instruction — followed by its operands, the registers or values it acts on. On x86-64, a widely used calling convention (a fixed agreement compilers follow, from Lesson 5's ABI link) says the first two integer arguments to a function arrive in specific registers, and the return value goes out in another specific register — no C code has to say this explicitly, the compiler just follows the convention. 
; add.s  (gcc -S add.c -o add.s, simplified)
add:
    mov  eax, edi     ; edi holds argument a — copy it into eax
    add  eax, esi     ; esi holds argument b — ALU adds it into eax
    ret               ; return: eax already holds a + b
Worked example: three lines, three ideas already in your vocabulary mov eax, edi is a fetch-decode-execute cycle on its own (Lesson 19): fetch this instruction, decode it as "copy edi into eax," execute the copy. add eax, esi is another full cycle — this time decode routes it to the ALU, which adds esi into eax and writes the result back into eax. ret returns to the caller, with eax — by calling-convention agreement — already holding the answer the caller expects. No stack frame, no memory access anywhere in this function: every operand this entire function ever touches is a register.

Try it: the same function, two optimization levels

Compilers don't produce one fixed translation — how hard they optimize changes the output dramatically, even though both versions compute the exact same thing. Compare gcc -O0 (no optimization, close to a literal translation) against gcc -O2 (aggressively optimized) for a slightly bigger function.

Interactive: -O0 vs. -O2 for int compute(int x) { return x * 2 + 1; }

Why reading assembly matters even if you never write it by hand Almost no one writes assembly for a living anymore, but reading it stays genuinely useful: it's the ground truth for what your program actually does, stripped of every abstraction the C source itself provides. It's how you confirm a compiler actually optimized away a bounds check or a redundant computation, how you diagnose a crash a debugger's backtrace (Lesson 22) leaves ambiguous, and how you understand a compiler's optimization decisions instead of just trusting them blindly. Tools like Compiler Explorer exist specifically because working systems programmers check this output routinely, not as a rare last resort.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is a mnemonic, in the context of assembly language?

A mnemonic like mov or add is the readable stand-in for the actual binary opcode the assembler produces.

2. In the add function's assembly, why don't edi and esi need to be explicitly declared anywhere in the C source?

The calling convention is an agreed contract the compiler follows automatically, invisible at the C source level.

3. Why might -O0 and -O2 assembly output for the exact same C function look substantially different?

Optimization changes how the same logical computation gets translated into instructions, not what it computes.

4. Fill in the blank: a short, readable name like mov or add, standing in for a single machine instruction, is called a ___.

Mnemonics are what make assembly readable at all, compared to raw binary opcodes.

5. Fill in the blank: the fixed, agreed-upon rule for which registers hold a function's arguments and return value is called the ___.

The calling convention is why compiled functions can call each other correctly without ever agreeing on register use case by case.
