Caches and Why Memory Access Patterns Matter for Speed

Unit 4's struct lesson promised this: "fewer struct instances fit in a CPU cache line at once — Unit 7 covers exactly why that hurts performance." This is that lesson — the layer of memory between fast registers and slow RAM, and why the order you access memory in can matter more than what you're computing.

← Lesson 20 Unit 8, Lesson 22 → Contents Glossary →

Lesson 19 showed registers are tiny and blazing fast, while RAM (Unit 2's stack and heap) is enormous but comparatively slow to reach. Real processors don't leave that gap unaddressed — they insert a small amount of much faster memory in between, and how your program accesses memory determines how often it actually benefits from it.

The memory hierarchy

Definition The memory hierarchy is the layered set of storage a CPU can reach, trading size for speed at every step: registers (fastest, smallest) → cache (small, very fast, built into or right next to the CPU) → RAM (large, much slower) → disk (enormous, far slower still). A cache automatically keeps a copy of recently and nearby-used data close to the CPU, so a repeated or predictable access can be served without ever reaching all the way out to RAM.
Definition Memory isn't fetched into the cache one byte at a time — it moves in fixed-size chunks called cache lines (commonly 64 bytes). Requesting a single byte pulls its entire surrounding cache line in at once. This pays off because of locality: spatial locality is the tendency for a program to access nearby memory addresses close together in time (like walking an array); temporal locality is the tendency to reuse the exact same address again soon (like a loop counter). Programs that exhibit either kind benefit enormously from caching; programs that jump around unpredictably barely benefit at all.

Worked example: closing Unit 4's loop Lesson 12's struct example compared {char, int, double} at 16 bytes to a tighter reordering — here's why that mattered beyond raw memory use: a 64-byte cache line holds 4 instances of a 16-byte struct, but only 3 of a 20-byte one (with 4 bytes wasted per line). Looping over a large array of these structs, the smaller version needs 25% fewer cache-line fetches from RAM to visit the same number of instances — the exact performance cost Lesson 12 promised this unit would explain, now made concrete.
Why the same algorithm can run dramatically slower with no change in complexity Two loops with identical Big-O complexity — say, visiting every element of a 2D array once — can differ by ten times or more in actual wall-clock time, purely based on whether they walk memory in the order it's physically laid out (row-major, sequential, cache-friendly) or jump across it (column-major on a row-major array, mostly cache misses). Nothing about this shows up in the assembly from Lesson 20, and nothing about it shows up in a Big-O analysis — it only shows up as measured, real speed, which is exactly why profiling a program's actual behavior matters as much as reasoning about it on paper.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the memory hierarchy, from fastest/smallest to slowest/largest?

Each layer trades size for speed, with registers fastest/smallest and disk slowest/largest.

2. Why does requesting a single byte pull in an entire 64-byte cache line, not just that one byte?

Fetching a whole cache line pays off precisely when nearby memory gets accessed soon after — spatial locality.

3. Why can two loops with identical Big-O complexity run at very different real speeds?

Cache-friendly vs. cache-hostile access patterns can separate two same-complexity loops by a large real speed gap.

4. Fill in the blank: the fixed-size chunk of memory (commonly 64 bytes) moved between RAM and cache at once is called a ___.

Cache lines are the unit caching actually operates in, not individual bytes.

5. Fill in the blank: the tendency for a program to access nearby memory addresses close together in time, like walking an array in order, is called ___.

Spatial locality is exactly what makes sequential access patterns so much more cache-friendly than scattered ones.
