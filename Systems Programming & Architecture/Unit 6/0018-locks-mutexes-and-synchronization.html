Locks, Mutexes, and Synchronization

Lesson 17 showed exactly how a shared counter loses updates. This lesson shows the standard fix: force the three-step read-add-write sequence to run as one uninterruptible unit, by making every other thread wait its turn.

← Lesson 17 Unit 7, Lesson 19 → Contents Glossary →

The lost-update bug happened because two threads' read-add-write sequences interleaved. The fix isn't to make increment faster — it's to guarantee that once one thread starts its read-add-write, no other thread can touch the counter until it finishes.

Mutex: mutual exclusion, enforced

Definition A mutex (mutual exclusion lock) is an object one thread can lock before touching shared data, and must unlock afterward. If a thread tries to lock a mutex another thread currently holds, it blocks — pauses and waits — until the mutex is unlocked. The block of code between lock and unlock is called a critical section: the shared-data operation that needs to run as one uninterrupted unit, exactly like the increment from Lesson 17.

Worked example Thread A calls lock(&m), succeeds immediately since the mutex is free, and begins its read-add-write. Thread B calls lock(&m) right in the middle of A's work — but the mutex is already held, so B blocks, doing nothing until A finishes. A completes its full read-add-write and calls unlock(&m). Only now does B's blocked lock call succeed, and B performs its own complete read-add-write from the now-correct, updated value. Both increments count — the counter correctly ends at 2, because the two critical sections were forced to run one at a time instead of interleaving.

Deadlock: the cost of getting locking wrong

Why more locking isn't automatically safer A deadlock happens when two or more threads are each waiting on a lock the other one holds, and neither can ever proceed — the classic case is Thread A holding lock 1 and waiting for lock 2, while Thread B holds lock 2 and waits for lock 1, forever. Locks solve race conditions, but they introduce a brand-new failure mode that didn't exist before: a program can be perfectly race-free and still hang permanently, frozen at exactly the moment two threads locked in the wrong order. The standard defense is simple to state and easy to violate under pressure: always acquire multiple locks in the same, agreed-upon order, everywhere in the codebase, with no exceptions.
