Race Conditions and Why Shared State Is Dangerous

Lesson 16 said two threads can read and write the same variable with no coordination required. This lesson shows exactly why that "no coordination required" is also the problem — using the simplest possible example: two threads, one shared counter, and a bug you can't see by reading the code alone.

← Lesson 16 Lesson 18 → Contents Glossary →

"Increment a shared counter" sounds like the simplest possible operation. It's actually three separate steps at the machine level — read the current value, add one, write the new value back — and if two threads interleave those three steps badly, one entire increment can vanish without a trace.

An increment is not one step

Definition A race condition is a bug where a program's correctness depends on the precise timing or interleaving of operations across multiple threads, so the outcome differs depending on execution order that isn't controlled or guaranteed. counter++ looks atomic (indivisible) in source code, but compiles down to three separate machine steps: read counter into a register, add 1 to the register, write the register back to counter. Any of those three steps can be interrupted by the other thread doing its own read/add/write in between.

Worked example: the exact interleaving that loses an update Counter starts at 0. Thread A reads counter (gets 0). Before A writes anything back, Thread B also reads counter (also gets 0 — A hasn't written yet). Thread A adds 1 to its register (1) and writes it back — counter is now 1. Thread B, working from the stale value it already read, adds 1 to its own register (also 1) and writes that back — counter is still 1. Two threads each incremented once, but the counter only went up by 1 instead of 2 — Thread A's update was completely overwritten, with no error, no crash, and nothing in the source code that looks wrong.
Why race conditions are uniquely hard to debug A race condition often doesn't show up every run — most of the time, threads happen to interleave in a way that produces the right answer, and the bad interleaving only strikes occasionally, under specific timing that's hard to reproduce on purpose. A test suite can pass a thousand times in a row and still contain a race condition that shows up once in ten thousand runs in production, often under heavier load, where more threads are competing and interleavings become more varied. This is exactly what makes concurrency bugs feel different from every other bug category in this course — the code can look completely correct, read top to bottom, and still be wrong.

1. Why is counter++ not actually a single atomic step at the machine level?

Read-add-write is the hidden three-step sequence that a race condition can interleave badly.

2. In the lost-update example, why did the counter only end up at 1 instead of 2 after two increments?

Both threads read the same stale value, and the second write simply clobbered the first.

3. Why can a race condition pass a test suite a thousand times and still be a real bug?

Timing-dependent bugs can hide behind mostly-correct interleavings for a long time before surfacing.

Race conditions depend on the exact order in which threads' steps happen to interleave.
