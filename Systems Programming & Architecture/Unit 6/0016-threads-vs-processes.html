Threads vs. Processes

Unit 5 covered many processes sharing one machine, fully isolated from each other. This unit is about a different kind of "many things at once" — many threads sharing one process's own memory, on purpose, and everything that makes possible and dangerous.

← Unit 5, Lesson 15 Lesson 17 → Contents Glossary →

A process's isolation, from Unit 5, is a feature when you want two unrelated programs to never interfere with each other. But it's a real cost when a single program wants to do several things at once and needs them to cooperate closely — say, a web browser rendering a page while still responding to clicks. Threads are the answer.

A thread: an independent path of execution inside one process

Definition A thread is an independent sequence of instructions the CPU can schedule and run, existing inside a process. Every process has at least one thread (the "main" thread); a multithreaded process has several, each with its own stack (Lesson 5) and its own set of CPU register values, but — critically — all threads within the same process share that process's heap, its global/data segment, and its open files. Two threads in the same process can both read and write the exact same heap-allocated variable directly, with no special mechanism required to do so — unlike two separate processes, which cannot see each other's memory at all.

Worked example A video game runs rendering on one thread and physics calculations on another, both threads within the same process. They share the same heap-allocated game-world data directly — the physics thread updates a character's position, and the rendering thread reads that exact same memory to draw it, with no copying or message-passing needed. Compare that to running rendering and physics as two separate processes: they'd need some explicit inter-process communication mechanism just to share a single position value, since separate processes cannot see each other's memory at all.
Why threads are lighter weight than processes, and why that's also the danger Creating a new thread is cheaper than creating a new process — no new address space to set up, no memory isolation to establish, just a new stack and a new path of execution inside memory that already exists. That's exactly why threads are the standard tool for a program that wants to do several things concurrently without the overhead of full process isolation. But sharing memory directly cuts both ways: nothing stops two threads from reading and writing the exact same variable at the exact same moment, with no coordination at all — and unlike a normal single-threaded bug, the result depends on split-second timing that can differ from run to run. That's the entire subject of the next lesson.

1. What do multiple threads within the same process share, that separate processes do not?

Shared heap and data-segment access is exactly what distinguishes threads from separate, isolated processes.

2. What does each individual thread still keep private to itself?

Each thread still needs its own stack to track its own local variables and call history independently.

3. Why is creating a new thread generally cheaper than creating a new process?

Skipping full address-space isolation is exactly what makes thread creation lighter weight.

4. Fill in the blank: an independent sequence of instructions the CPU can schedule, existing inside a process and sharing that process's heap with any other threads in it, is called a ___.

A thread is the unit of independent execution within a shared-memory process.

5. Fill in the blank: a process with more than one thread running inside it is described as ___.

Every process starts with one main thread; a multithreaded process has added more.
