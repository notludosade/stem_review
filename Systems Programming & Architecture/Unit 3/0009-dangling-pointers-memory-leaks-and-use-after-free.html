Dangling Pointers, Memory Leaks, and Use-After-Free

This unit ends by naming precisely the family of bugs that pointers make possible — the ones garbage-collected languages simply cannot produce, and that a segfault (Unit 8) is often the visible symptom of.

← Lesson 8 Unit 4, Lesson 10 → Contents Glossary →

Lesson 5 introduced returning a stack address as a mistake. Lesson 6 introduced memory leaks. Both are specific cases of a more general problem: a pointer's value is just an address, and C has no built-in way to know whether the memory at that address is still valid. This lesson names the full family and ties it together.

A dangling pointer: an address that's no longer good

Definition A dangling pointer is a pointer that still holds an address, but the memory at that address is no longer valid to use — either because it belonged to a stack frame that has since been popped (Lesson 5), or because it was heap memory that has already been freed. Critically, C does not clear a pointer's value when the memory it points to becomes invalid — the pointer still looks exactly like a normal, valid pointer, holding the exact same address it always held.
Worked example: use-after-free int *p = malloc(sizeof(int)); *p = 42; free(p); — at this point, p is now a dangling pointer: it still holds the same address, but that memory has been returned to the allocator and may already be handed out again to the next malloc call anywhere else in the program. printf("%d", *p); written right after is a use-after-free — dereferencing a dangling pointer. It might print 42 if nothing has reused that memory yet, print something completely different if something has, or crash — and which of those happens can change from run to run.

Double free: freeing the same block twice

Definition A double free happens when free is called twice on the same pointer. The allocator's internal bookkeeping generally isn't designed to be told "this block is free" a second time, and the result is corrupted allocator state — which can crash immediately, or silently corrupt an unrelated future allocation, depending on the allocator and the moment it happens.
Why "set it to NULL after freeing" is the standard defense, not a full fix A common, genuinely useful habit is free(p); p = NULL; — dereferencing a null pointer crashes immediately and obviously (a segfault, Unit 8), instead of silently reading or corrupting reused memory. That turns an unpredictable, hard-to-reproduce bug into a loud, easy-to-find one, which is a real improvement. But it only protects the one variable that got set to NULL — if a second pointer variable also held that same address, and nobody set that one to NULL too, it's still a fully live dangling pointer. There is no feature of C that automatically tracks every pointer that happens to hold a given address; that discipline is entirely on the programmer, every single time.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is a dangling pointer?

The defining trait is holding a now-invalid address, indistinguishable in appearance from a valid pointer.

2. Why is a use-after-free bug's behavior unpredictable from run to run?

Whatever else has claimed that freed memory in the meantime determines the outcome, and that's not guaranteed to be consistent.

3. Why does setting a pointer to NULL right after freeing it only partially protect against use-after-free?

NULL-after-free is a real, useful habit, but it's per-variable, not a program-wide guarantee.

4. Fill in the blank: dereferencing a dangling pointer — one that points to memory already freed — is called a ___ bug.

Use-after-free names the exact act of dereferencing memory after it has already been freed.

5. Fill in the blank: calling free() twice on the exact same pointer, corrupting the allocator's internal bookkeeping, is called a ___.

A double free confuses the allocator about which blocks are actually free, with unpredictable results.
