Pointer Arithmetic and Arrays

In Python, indexing a list and following a linked reference are unrelated ideas. In C, arr[i] and pointer arithmetic are not just related — they're literally the same operation, and seeing why explains a lot about how C actually runs.

← Lesson 7 Lesson 9 → Contents Glossary →

A C array is really just a single block of contiguous memory, and a pointer to its first element is enough information to reach every other element in it — as long as you know how big each element is. That's what pointer arithmetic is for.

Adding to a pointer moves it by whole elements

Definition Pointer arithmetic lets you add or subtract an integer from a pointer, and the result moves by that many elements, not bytes — the compiler automatically multiplies by sizeof the pointer's type. If p is an int * pointing at address 1000 on a system where an int is 4 bytes, then p + 1 points at address 1004, not 1001 — one whole int further along, exactly where the next int in an array would sit.
Worked example: arr[i] is *(arr + i) Given int arr[5] = {10, 20, 30, 40, 50};, the name arr decays into a pointer to its first element whenever it's used in an expression. arr[2] and *(arr + 2) are not just equivalent — they compile to the identical machine code: take arr's address, move forward by 2 elements, and dereference. This is why C array indexing never checks whether the index is in bounds: arr[2] is really just "some arithmetic, then a dereference," and the compiler has no idea whether 2 is a valid index for this particular array or not.

Out-of-bounds arithmetic is undefined, not blocked

Why arr[10] on a 5-element array doesn't crash immediately, and why that's worse, not better Nothing about C's array indexing checks bounds at run time — arr[10] on a 5-element array is legal syntax that computes an address 10 elements past arr's start and dereferences whatever happens to be there. Sometimes that's unused memory and nothing visibly bad happens. Sometimes it's another variable, and you silently corrupt it. Sometimes it crashes. The genuinely dangerous part is that all three outcomes are possible from the exact same buggy line, which is why an out-of-bounds C bug can pass every test on your machine and still corrupt memory on someone else's.
