Processes vs. Programs

Unit 2 already used the word "process" a lot, on the assumption you'd pick up the idea by context. This lesson makes it exact — a program is a static file on disk; a process is that program brought to life, with its own state, and the OS is what juggles many of them on one CPU.

You can double-click the same game's icon five times and get five separate windows, each with its own score, its own state, all able to crash independently without taking the others down. That's the program/process distinction in one example: one file on disk, five completely separate running instances.

A program is a file; a process is that file, running

Definition A program is a static executable file sitting on disk — the compiled output from Unit 1's pipeline, doing nothing until something runs it. A process is a running instance of that program: its own address space (Lesson 4), its own set of open files, its own CPU register values, all tracked by the OS. Running the same program's executable twice creates two entirely independent processes, exactly like the game example above — neither can see or touch the other's memory.

The process lifecycle

A process moves through a small set of states as the OS manages it, never running continuously from start to finish on a single-core machine sharing time among many processes.

Interactive: a process's life

Worked example You launch a program: the OS creates a process for it in the new state, loading its executable and setting up its address space. It moves to ready — fully able to run, just waiting for CPU time. The OS's scheduler gives it the CPU, and it becomes running — actually executing instructions right now. If it needs to read a file, it moves to waiting, giving up the CPU entirely until that slow disk operation finishes, rather than sitting idle on a CPU another process could be using. Once the file read completes it goes back to ready, waits its turn again, and eventually finishes and becomes terminated.
Why "waiting" exists as its own state, instead of just staying "running" until I/O finishes A disk read can take a million times longer than a single CPU instruction. If a process just sat on the CPU doing nothing while waiting for that read, the CPU itself would sit idle for that entire, comparatively enormous stretch of time — a massive waste, since dozens of other processes on the machine may have real work ready to do right now. Moving a waiting process off the CPU entirely, and letting the scheduler hand that time to something ready to actually use it, is exactly why a machine running one CPU-heavy game and twenty background processes still feels responsive: those twenty processes spend almost all their time in the waiting state, barely touching the CPU at all.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the difference between a program and a process?

Running the same executable twice creates two separate, independent processes from the one program file.

2. What happens to a process's state when it needs to wait for a slow disk read to complete?

Giving up the CPU during slow I/O lets other ready processes actually use it instead of sitting idle.

3. Why does a machine running many background processes at once still feel responsive to the one program you're actively using?

The waiting state is what frees up the CPU for whatever actually has ready work to do.

4. Fill in the blank: a running instance of a program, with its own address space, open files, and register values, is called a ___.

A process is a program brought to life, tracked and managed by the OS.

5. Fill in the blank: the process state entered while it's blocked on something slow, like a disk read, having given up the CPU entirely until that operation completes, is called ___.

The waiting (or blocked) state frees the CPU for other ready processes during slow I/O.
