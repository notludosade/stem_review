System Calls: Asking the Kernel for Help

Lesson 13 said ordinary programs can't touch hardware directly, and Lesson 14 mentioned processes waiting on a disk read without ever explaining how a process actually asks for one. This lesson closes that gap: the single narrow doorway every program uses to ask the kernel to do something on its behalf.

Calling printf in C looks like an ordinary function call. Underneath, at some point, that call has to actually write bytes to a terminal or a file — and writing to hardware is exactly the kind of thing Lesson 13 said ordinary programs aren't allowed to do directly. The mechanism that bridges that gap is the system call.

Two privilege levels: user mode and kernel mode

Definition A processor generally runs in one of two privilege levels: user mode, where ordinary program code runs with restricted access — it cannot directly touch hardware devices or another process's memory — and kernel mode, where the OS kernel runs with full, unrestricted hardware access. A system call is a controlled, deliberate request that switches the CPU from user mode into kernel mode for a moment, lets trusted kernel code perform the privileged operation on the program's behalf, and then switches back.
Worked example A C program calls printf("hi\n"). printf itself is ordinary user-mode library code that formats the string, but eventually it calls write() — a system call. That triggers a switch into kernel mode; the kernel, with full hardware access, actually sends those bytes to the terminal device; then control switches back to user mode, and the program's own code resumes right where it left off. From the program's point of view, it looks like one function call. Underneath, it's a full privilege-level round trip.

System call categories worth knowing by name

Definition Common system call categories include: file I/O (open, read, write, close), process control (fork to create a new process, exit to terminate one), and memory management (requesting more address space from the OS — what malloc ultimately relies on when the heap needs to grow). Every one of these does something that requires touching real hardware or another process's data — exactly the category of operation user mode alone cannot perform.
Why this narrow doorway matters more than it looks like it should System calls are the only way in or out of kernel mode, and that narrowness is deliberate: every single privileged operation any program on the machine ever performs passes through a small, well-defined, checkable set of entry points, instead of arbitrary code reaching out and touching hardware however it wants. That's what makes it possible for the kernel to enforce every guarantee earlier lessons took for granted — that one process can't read another's memory, that a file's permissions are actually checked before it's opened, that a device isn't accessed by two programs in a way that corrupts it. Remove system calls, and there would be no single place left to enforce any of that.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is a system call?

System calls are the controlled bridge between restricted user-mode code and privileged kernel-mode operations.

2. Why can't a program running in user mode write directly to a disk device?

Direct hardware access is exactly the privilege user mode withholds, by design.

3. Why does funneling every privileged operation through a small set of system calls matter for security and isolation?

A single, narrow, checkable doorway is what makes process isolation and permission checks enforceable at all.

4. Fill in the blank: the privilege level in which the OS kernel runs with full, unrestricted hardware access is called ___.

Kernel mode is reached only through a controlled system call from user mode.

5. Fill in the blank: printf ultimately relies on a lower-level ___ named write to actually send bytes to a terminal or file.

write() is a system call — the actual mechanism behind printf's user-mode-looking function call.
