Floating Point and Why 0.1 + 0.2 Isn't Exactly 0.3

Type 0.1 + 0.2 into Python, JavaScript, Java, or C, and every one of them prints something like 0.30000000000000004. This isn't a bug in any of those languages — it's a direct, unavoidable consequence of how floating-point numbers are represented in binary.

Lesson 10 showed integers use every bit for exact whole-number precision, at the cost of a hard range limit. Floating-point numbers make the opposite trade: an enormous range, from tiny fractions to astronomically large values, at the cost of exactness for most fractional values — including some that look perfectly simple in decimal.

Scientific notation, in binary

Definition A floating-point number is stored as three parts, mirroring scientific notation: a sign bit, a mantissa (also called the significand — the significant digits), and an exponent (how far to shift the binary point). The IEEE 754 standard, which essentially every modern language and processor uses, defines float (32 bits: 1 sign, 8 exponent, 23 mantissa) and double (64 bits: 1 sign, 11 exponent, 52 mantissa) precisely this way. The exponent is what buys floating point its huge range — the same handful of mantissa bits can represent a value near 0.0000001 or a value near 10,000,000,000, just shifted by a different exponent.
Worked example: why 0.1 has no exact binary representation In decimal, 1/3 has no finite decimal representation — it's 0.3333... forever, because 3 doesn't divide evenly into any power of 10. The exact same thing happens to 0.1 in binary, because 0.1 is 1/10, and 10 doesn't divide evenly into any power of 2. Written in binary, 0.1 is the repeating fraction 0.0001100110011... forever — and a mantissa only has a finite number of bits, so it gets cut off and rounded. 0.2 rounds similarly. Add the two already-rounded values together, and the tiny rounding errors compound into a result that's extremely close to, but not exactly, 0.3 — hence 0.30000000000000004.

Why this matters far beyond a curious print statement Comparing floating-point values with == is a common, serious bug — two calculations that are mathematically supposed to produce the same result can differ in their last few bits due to rounding along different paths, making == unreliable for anything computed rather than literally assigned. The standard fix is comparing whether two values are within a small tolerance of each other (fabs(a - b) < 0.0001) instead of checking exact equality. This isn't specific to C — it's true in every language that uses IEEE 754 floating point, which is effectively all of them. It's also why financial software almost never uses floating point for money at all, instead representing cents as exact integers precisely to sidestep this entire category of rounding error.
