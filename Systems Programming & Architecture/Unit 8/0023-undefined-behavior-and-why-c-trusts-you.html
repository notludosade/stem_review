Undefined Behavior and Why C Trusts You

Lesson 10 called signed integer overflow "technically undefined behavior" and moved on. Lesson 8's out-of-bounds array write and Lesson 9's dangling-pointer dereference are the same category of problem: C's specification simply does not say what happens, and the compiler is free to assume it never will. This lesson names that category and shows exactly how much it costs to ignore.

Every previous unit has quietly used the phrase "this is a bug" for things C's compiler will happily accept and compile without complaint. That's not an oversight — it's a defining design choice of the language, and this lesson makes it explicit before Lesson 24 asks whether that choice is worth it.

Undefined behavior: the promise C doesn't keep

Definition Undefined behavior (UB) is any operation the C standard places absolutely no requirement on — not "results in an error," not "produces some unspecified but harmless value," but genuinely anything at all is a conforming result, including a crash, a wrong answer, or a program that appears to work perfectly. Signed integer overflow (Lesson 10), dereferencing a dangling or null pointer (Lesson 9), and writing past the end of an array (Lesson 8) are all undefined behavior. Critically, the compiler is allowed to assume a program never triggers UB — and real compilers use that assumption aggressively when optimizing.
Worked example: the check that vanishes A programmer writes if (x + 1 < x) { /* handle overflow */ } to detect whether x + 1 overflowed a signed int. This looks reasonable, but signed overflow is undefined behavior — so the compiler is entitled to assume it never happens, which means it's entitled to assume x + 1 is always greater than x, which means the entire if branch can never run, which means an optimizing compiler can legally delete it outright. The overflow check that was supposed to catch the bug is exactly the code that disappears — not because the compiler is broken, but because it's trusting the programmer never to have written overflowing code in the first place.

Implementation-defined behavior: still loose, but not chaos

Definition Implementation-defined behavior is different from UB in one crucial way: the standard requires each compiler to pick a specific, consistent, documented behavior, even though the standard itself doesn't dictate which one. Whether char is signed or unsigned by default, and exactly how many bytes an int occupies, are both implementation-defined — a given compiler on a given platform always answers the same way, and documents that answer, but a different compiler is free to answer differently. Undefined behavior has no such floor: nothing is required, documented, or consistent.
Why C trusts you instead of checking Python raises IndexError on an out-of-bounds list access; Java throws on integer overflow in checked contexts far more often than C ever complains. C could have specified all of this — bounds-checked arrays, overflow traps, guaranteed-null-safe dereferences — and simply chose not to, because every one of those checks costs a runtime instruction, every single time, on every single operation, even in code that's already correct. C's governing philosophy is that the programmer, not the language, is responsible for maintaining the invariants the language assumes — Unit 8's whole story, from segfaults to this lesson, is what happens when that trust turns out to be misplaced. Tools like AddressSanitizer and UBSan (mentioned back in Lesson 9's source link) exist precisely to catch these violations during testing, in a build that's allowed to be slower, so the version that ships doesn't have to pay for the check at all.
