Engine vs. Game: Where the Line Is

Lesson 1 established that an engine is "the reusable part." In practice that line isn't always obvious — and drawing it in the wrong place is one of the most common architecture mistakes a team makes early in a project.

← Lesson 1 Lesson 3 → Contents Glossary →

"Draw a triangle" is obviously engine. "The boss has 500 hit points" is obviously game. Most real decisions live between those two extremes: is "health" itself an engine concept, or something the game defines? Is "damage" a built-in idea, or just a number some game code decided to subtract?

The line: does it know what a "game" even is?

Definition A piece of code belongs to the engine if it has no knowledge of any particular game's rules — it manipulates generic concepts like meshes, transforms, and numeric values. It belongs to the game if it encodes a rule specific to that game — what damage means, what happens when the player dies, what a "win" is. An engine that starts hard-coding rule words like "health" or "ammo" into its core has quietly started becoming a specific game.

This is why serious engines expose generic building blocks — an entity can hold arbitrary named numeric or data fields — rather than a built-in "health" field. The engine doesn't know or care that one of those fields happens to represent hit points; that meaning lives entirely in the game's code, sitting on top.

Worked example Unreal Engine's core has no idea what "mana" is. A game built on Unreal defines a "mana" value as game-specific data attached to a character, written by that game's own gameplay code, and drawn on screen using the engine's completely generic UI and rendering tools. If Unreal's core team hard-coded "mana" as a built-in concept, every unrelated game built on the engine — a racing game, a farming sim — would be carrying dead weight for a concept that only makes sense in one genre.
Why blurring this line causes real damage later A team that writes game-specific logic directly into what should be reusable, generic engine code doesn't feel the cost immediately — it's faster to hard-code "if enemy touches player, subtract 10 health" straight into the collision system than to build a generic event system first. The cost shows up later: that collision code can no longer be reused for the next game, or even the next feature in the same game, without being rewritten. Keeping the line clean is what makes an engine actually reusable, instead of reusable in name only.
