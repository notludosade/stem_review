What a Game Engine Actually Provides

Software Engineering covered how teams build and structure large codebases. A game engine is one of the largest, most demanding kinds of software there is — and almost none of what makes a game run is actually "game logic." This course is about the rest of it.

← STEM+ Home Lesson 2 → Contents Glossary →

Picture a simple game: a character walks around a room, picks up a key, and opens a door. Writing "if the player has the key, unlock the door" is a few lines of code. But before that line can even run, something has to be drawing the room on screen sixty times a second, tracking where every object is in space, reading the keyboard or controller, deciding whether the character can walk through a wall, and playing a footstep sound at the right moment. None of that is the game's actual logic — and all of it has to exist before the logic can matter at all.

The engine is everything below the game

Definition A game engine is the reusable software layer that provides the general-purpose systems every game needs — rendering, physics, audio, input handling, asset loading, and a way to organize game objects — so that a team building a specific game can write the logic that makes their game unique, instead of re-solving problems every other game already solved.

That word "reusable" is the whole point. A racing game and a puzzle game have almost nothing in common at the level of rules — but both need to get pixels on screen, load a texture from disk, respond to a button press, and keep track of where things are in space. An engine is the part of the codebase built to not care which game is using it.

Worked example A three-person student team wants to make a small 3D platformer. Without an engine, "rendering a textured triangle on screen" alone is weeks of graphics-API work before a single platform exists to jump on. With an engine (even a small, open-source one), that same team spends their first day placing platforms and writing jump physics, because the engine already turned "draw this mesh with this texture" into a single function call. The engine doesn't make their game good — it makes it possible to spend their limited time on the 5% that's actually theirs.
Why almost nobody writes a AAA game "from scratch" anymore In the 1990s, most studios wrote a new engine for every game, because no general-purpose one existed yet that fit their needs. Today, building a full custom engine is usually a bad bet: the rendering, physics, and audio problems an engine solves are largely the same across genres, they're extremely hard to get right, and every hour spent reinventing them is an hour not spent on the game that's supposed to be unique. Studios that do write custom engines (id Software, for instance) do it because their game's technical needs are the product — for most teams, that tradeoff doesn't pay off.

Check your recall

No peeking back up — answer from memory first, then check.

1. What makes a system part of a "game engine" rather than part of "the game"?

Reusability across different, unrelated games is the defining property of engine code.

2. Why do a racing game and a puzzle game both benefit from the same engine?

The shared need is at the systems level (drawing, sound, input), not the rules level.

3. Why do most studios today build on an existing engine rather than writing one from scratch?

It's a time-and-risk tradeoff, not a legal or technical impossibility.

4. Fill in the blank: the reusable software layer providing rendering, physics, audio, input, and asset systems so a team can focus on what's unique to their game is called a ___.

A game engine is exactly this general-purpose, reusable layer.

5. Fill in the blank: the property that separates engine code from game code is that engine code is ___ across different, unrelated games.

Reusability across unrelated games is the defining line this lesson draws.
