The Problem with Deep Inheritance Hierarchies

Software Engineering's Unit 4 covered design patterns and the idea of "favor composition over inheritance." Game object modeling is the single clearest, most-cited case where inheritance actively fights back against a growing codebase.

← Unit 2, Lesson 6 Lesson 8 → Contents Glossary →

A natural first instinct: every game object is a class. A GameObject base class, then Character extends it, then Enemy extends Character, then FlyingEnemy extends Enemy. It works, right up until a designer asks for a flying enemy that's also a boss that also swims sometimes.

The diamond problem, in a game's own terms

Definition A deep inheritance hierarchy models game object types as classes that extend other classes, layer after layer, to reuse behavior. It breaks down at multiple inheritance — needing a single object type to combine behaviors from two branches of the tree that don't share a common, sensible ancestor (a flying enemy and a swimming enemy that also needs to fly), which most languages either forbid outright or make dangerously ambiguous through the diamond problem: if two parent classes both define a method, which one does the child actually inherit?

Try it: grow a hierarchy and watch it strain

Add new game object types one at a time. Watch how quickly the tree needs a type that doesn't fit cleanly anywhere.

Interactive: growing a class hierarchy

Worked example Enemy splits cleanly into FlyingEnemy and SwimmingEnemy — so far, so good. Then design asks for a boss that flies and swims. It can't extend both FlyingEnemy and SwimmingEnemy cleanly in most languages, so a team is stuck picking one of several bad options: duplicate the flying or swimming code into a new one-off class, restructure the whole hierarchy around this one new requirement, or bolt on a special case that breaks the "is-a" assumption the tree was built on. None of these get easier as the hierarchy grows deeper.
Why this specific problem hits games so hard Every domain has some inheritance trees, but games are unusually bad for it: game designers constantly ask for new combinations of existing behaviors — a fast enemy that's also invisible, a slow enemy that's also explosive — because novel combinations are often exactly what makes a game interesting. A hierarchy designed around "is-a" relationships assumes those relationships are mostly stable and tree-shaped. Game design assumes the opposite: behaviors need to mix and match freely, which is precisely what a rigid tree structure resists.
