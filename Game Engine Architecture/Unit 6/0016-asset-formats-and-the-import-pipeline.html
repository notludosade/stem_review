Asset Formats and the Import Pipeline

Every texture, 3D model, and sound in a game started life as a file an artist exported from their own tool — Photoshop, Blender, a DAW. None of those files are in a format the engine can use directly at runtime. Something in between has to bridge that gap.

← Unit 5, Lesson 15 Lesson 17 → Contents Glossary →

A .png is great for editing in an image tool and terrible for a GPU to read directly at full speed — it's compressed in a way built for file size, not fast random access to any pixel. A .blend file stores an artist's entire editable scene, layers and all, when the engine only needs the final baked-down mesh and materials. Every asset needs translating before it's actually useful at runtime.

Two formats for two different jobs

Definition A source asset is the file an artist actually edits — a .png, .blend, .wav — optimized for editing convenience and tool compatibility. The import pipeline is the automated process that converts a source asset into a runtime asset: a format optimized for fast loading and direct use by the engine's own subsystems (a GPU-ready compressed texture format, a pre-baked mesh with precomputed data, an audio format decoded for low-latency playback). This conversion typically happens once, ahead of time — not every time the game loads that asset.

Worked example An artist exports a 4096×4096 .png character texture — great for editing, but the wrong shape for a GPU to sample efficiently at runtime. The import pipeline compresses it into a GPU-native format (roughly a quarter the file size, decodable directly by the graphics hardware), generates smaller pre-shrunk copies called mipmaps for when the character is far away on screen, and writes the result to disk as a runtime asset the engine loads directly — no conversion work left to do the moment the game actually launches.
Why this conversion happens ahead of time, not at game launch Converting a large model or texture is relatively slow work — the kind of one-time cost nobody wants paying every single time the game boots. Baking it into a fast-loading runtime format once, during development, means the actual game only ever does the cheap part: reading an already-optimized file straight into memory. This is the same "do the expensive part once, reuse the result" idea Software Engineering's build pipeline unit covered for compiled code, applied here to art and audio instead of source files.
