Capstone — Designing a Small Engine's Architecture

Twenty lessons, seven subsystems, one question left: how does it all actually fit together, in one running program? This capstone pulls every unit into a single architecture diagram and traces one frame end to end.

← Lesson 20 Course Contents → Contents Glossary →

Every piece has been introduced in isolation: the loop, the ECS, the pipeline, the physics step, the asset budget, the scripting layer, the state machine. None of them actually do anything alone. This lesson is about the wiring — which subsystem calls which, in what order, every single frame.

One frame, every subsystem, in order

Definition A minimal but complete engine's per-frame architecture is: the state machine (Unit 7) determines which scene is active; the game loop (Unit 2), using a fixed timestep, drives that scene's ECS (Unit 3) — process input, then run each system in a defined order (typically scripting logic, then physics integration and collision, then animation), then the scene graph (Unit 4) resolves world transforms, then the render pipeline culls, batches, and draws. Underneath all of it, the asset manager (Unit 6) streams what's needed into the fixed memory budget and evicts what isn't.

Worked example Trace a single frame of a platformer: the state machine confirms the game is in Playing. The loop's fixed timestep fires. Input is read: right arrow held. The scripting system reads that input and sets the player entity's velocity component. The physics system integrates every entity with Position + Velocity, then checks AABBs for collisions — the player's feet AABB overlaps a platform, so collision response zeroes vertical velocity. The scene graph recomputes world transforms for the player and anything parented to it. The renderer culls anything outside the frustum, batches draw calls, and pushes pixels to the framebuffer. Meanwhile, the asset manager has already streamed in the next screen's tileset, just in case the player walks that far. All twenty prior lessons, one frame.
Why this ordering isn't arbitrary Scripting runs before physics because gameplay logic (a jump button press) needs to set intent — a velocity, a force — before physics integrates it that same frame, not one frame late. Physics runs before the scene graph resolves transforms because collision response can change an object's position, and the render pipeline must draw where things ended up after physics, not before. Every ordering decision in this diagram traces back to a single rule from Lesson 4: each stage must see the freshest correct input from the stage before it, or the whole frame is one step behind itself.

Check your recall

No peeking back up — answer from memory first, then check.

1. Why does the scripting system typically run before the physics system in a single frame?

Physics needs fresh intent from scripting before it integrates that frame.

2. Why must the scene graph resolve world transforms after physics runs, not before?

Rendering needs post-physics positions, so scene graph resolution must follow physics.

3. What single rule from Lesson 4 explains nearly every subsystem ordering decision in this capstone?

Freshness of input to each stage is the underlying reason for the whole frame's ordering.

4. Fill in the blank: the piece that streams needed assets into a fixed memory budget and evicts what isn't needed, running underneath every other subsystem, is the ___.

The asset manager operates continuously alongside every other per-frame subsystem.

5. Fill in the blank: the system that determines which scene is currently active — menu, playing, paused — is the ___.

The state machine gates which scene the rest of the frame's work applies to.
