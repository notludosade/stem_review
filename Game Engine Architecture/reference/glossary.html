Unit 1 — The Anatomy of a Game Engine

Game engine

The reusable software layer providing the general-purpose systems every game needs — rendering, physics, audio, input, asset loading, and object organization — so a team can write the logic unique to their game instead of re-solving already-solved problems.

Engine code vs. game code

Code belongs to the engine if it has no knowledge of any particular game's rules, manipulating only generic concepts; it belongs to the game if it encodes a rule specific to that title, like what "damage" or "winning" means.

Subsystem

A self-contained part of an engine responsible for one category of work — rendering, physics, audio, input, or scripting — with its own internal data and logic, exposed through a defined interface rather than internals other code reaches into directly.

Unit 2 — The Game Loop & Timing

Game loop

The top-level loop that runs for the entire life of a game, repeatedly executing process input, update, and render, in that order, until the player quits.

Fixed timestep / Variable timestep

A fixed timestep always advances the simulation by the same constant amount, running update() multiple times per rendered frame if needed; a variable timestep passes the actual, measured duration of the previous frame — accurate, but never the same number twice.

Frame rate (FPS)

How many times per second the game loop completes.

Delta time (dt)

The amount of real time, in seconds, that elapsed since the last frame — multiplied into any per-second rate (movement, rotation, a timer) so it stays consistent regardless of frame rate.

Unit 3 — Entity-Component Systems

Diamond problem / Multiple inheritance

Multiple inheritance is needing a class to inherit from two unrelated parent classes at once; the diamond problem is the resulting ambiguity over which parent's method a child inherits when both define it.

Entity

An identifier — often just an integer ID — with no behavior and no data of its own; its effective "type" is whichever components happen to be attached to it right now.

Component

A plain bundle of data (Position, Health, Velocity) with no logic attached, stored in a component store keyed by entity ID.

System

A function, run every frame, that queries for every entity with a specific combination of components and operates on their data — where all ECS logic lives.

Query

The operation a system performs to find every entity ID present in all of its required component stores at once.

Component store

A map from entity ID to that component type's data, one per component type — often stored contiguously for fast, cache-friendly iteration at scale.

Unit 4 — Rendering Basics

Render pipeline (graphics pipeline)

The fixed sequence of GPU stages every triangle passes through: vertex processing, rasterization, fragment/pixel processing, then writing the result to the framebuffer.

Rasterization / Framebuffer

Rasterization determines exactly which screen pixels a triangle covers; the framebuffer is the block of memory holding the final pixel colors that get displayed.

Scene graph

A tree arranging every object in a scene, where each node's transform is stored relative to its parent rather than as an absolute world position.

World-space transform

An object's true position in the scene, computed by combining its local transform with every parent's transform up to the root.

View frustum / Frustum culling

The frustum is the pyramid-shaped region of space a camera can see; frustum culling discards objects entirely outside it before the render pipeline processes them.

Draw call

An instruction telling the GPU to render one object, typically issued once per visible object, carrying its own fixed overhead regardless of triangle count.

Unit 5 — Physics Integration

AABB (Axis-Aligned Bounding Box)

The smallest non-rotated rectangle (or box, in 3D) fully containing an object, used for cheap overlap checks at broad phase.

Broad phase / Narrow phase

Broad phase uses cheap AABB checks to rule out most object pairs quickly; narrow phase then runs the expensive, exact collision test on the small handful of pairs broad phase couldn't rule out.

Rigid body

An object treated as a solid, non-deformable shape with mass, position, and velocity, that forces like gravity or a collision can act on.

Numerical integration (Euler integration)

Updating a rigid body's velocity and position each small timestep by accumulating forces — velocity first, then position, using that new velocity.

Physics engine

The subsystem handling collision detection, collision response, integration, and constraints as one complete simulation loop — usually an existing library (Box2D, Bullet, PhysX) rather than a custom one.

Collision response / Constraint

Collision response resolves overlap and updates velocities so bodies push apart realistically; a constraint is a rule, like a joint, that must keep holding true as the simulation runs.

Unit 6 — Asset Pipelines & Resource Management

Source asset / Runtime asset

A source asset is the file an artist edits, optimized for editing convenience; a runtime asset is the converted, engine-native format optimized for fast loading and direct use.

Import pipeline

The automated process that converts a source asset into its runtime form, typically once, ahead of time, rather than on every game launch.

Mipmap

A smaller, pre-shrunk copy of a texture, generated during import, used when an object is far enough away that full resolution would be wasted detail.

Memory budget

The fixed amount of fast memory a game may use for assets at any one time, set by the target hardware, not the developer.

Eviction

Unloading an already-loaded asset from memory to make room for a newly-needed one, usually the asset judged least likely to be needed again soon.

Streaming / Level of detail (LOD)

Streaming loads and unloads assets in the background based on player position, bounding memory usage; LOD swaps in a lower-triangle-count version of a model as it gets farther from the camera, bounding rendering cost.

Unit 7 — Scripting, Scenes & Putting It Together

Scripting layer

A separate, usually interpreted language embedded in an engine, used to write game-specific logic that can iterate faster than the compiled engine core.

Hot-reloading

Editing a script's logic and seeing the change take effect immediately in a running game, with no recompile and no restart.

Scene

A distinct, loadable collection of game state — a menu, a level, a loading screen — usually with its own scene graph.

State machine / Transition

A state machine is always in exactly one of a fixed set of named states, moving between them only along explicitly defined transitions — used to manage which scene is active without ever running two incompatible modes at once.
