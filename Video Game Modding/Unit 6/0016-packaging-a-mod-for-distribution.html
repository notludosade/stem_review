Packaging a Mod for Distribution

A working mod on your own machine and a mod someone else can actually install are two different things. This lesson is about the gap between them.

← Unit 5, Lesson 15 Lesson 17 → Contents Glossary →

Every earlier unit assumed you already had access to an unpacked, modified copy of a game to test against. Sharing that work with someone else means packaging only the changed files — never the original game's own files — into a clean, self-contained bundle, typically a single .zip archive, matching the same folder structure the game expects so a user can drop it in and have it work.

The manifest

Most modding frameworks (Unit 3) expect a mod manifest — a small metadata file, often named something like mod.json or manifest.txt, declaring the mod's name, author, version number, and any dependencies (Lesson 9) it requires. This is what lets a mod loader find, identify, and correctly order the mod without a human having to read a readme first — the same load-order and dependency machinery from Unit 3 depends on this metadata actually being present and accurate.

Definition A mod manifest is a metadata file — name, author, version, dependencies — that a mod loader reads to identify and correctly manage a mod, distinct from the mod's actual asset or script files.

Version numbers that mean something

Semantic versioning (semver) is a widely-used convention for version numbers in the form MAJOR.MINOR.PATCH — incrementing PATCH for a small bug fix, MINOR for a new feature that doesn't break existing users, and MAJOR for a change that does break compatibility with what came before. A mod that follows this convention gives other modders' dependency declarations (Lesson 9) something reliable to check against: "requires version 2.x or higher" means something concrete only if version numbers are actually incremented meaningfully.

The readme

A readme — a plain-text file included with the package, meant to be the very first thing a user opens — should cover installation steps, requirements (which game version, which framework, which dependencies), and known issues. This isn't optional polish; it's the difference between a mod someone can actually use and a folder of files nobody can figure out how to install.

Why it matters here Lesson 17's compatibility testing and Lesson 18's responsible publishing both assume the package itself is already clean, versioned, and documented. Skipping this step doesn't just create a bad user experience — it makes every later step in Unit 6 harder to do well.
