Embedded Scripting Languages in Games (Lua and Similar)

Config files (Unit 2) can only change numbers that already exist. To add real new behavior without recompiling the game, a modder needs a scripting language the game itself already knows how to run.

← Unit 2, Lesson 6 Lesson 8 → Contents Glossary →

A great many games ship with an embedded scripting language built directly into the engine — a small programming language interpreter the game runs internally, exposed so that some (or all) of the game's own logic is written in it, not just its compiled core. Lua is by far the most common choice across the industry — it's small, fast, and designed from the start to be embedded inside a larger host application. World of Warcraft's entire user-interface system runs on Lua. Garry's Mod and Roblox build nearly their whole player-facing experience around it. Other games use Python, JavaScript, or a fully custom, game-specific scripting language instead, but the underlying idea is identical across all of them.

Definition An embedded scripting language is a lightweight programming language interpreter built into a game engine, letting some of the game's logic — and, when exposed to players, a mod's logic — run as script rather than as compiled engine code.

Why studios expose this to players at all

Scripting sits in a genuinely different category from the earlier units' techniques. Unpacking (Unit 2) reveals what already exists; config edits change values that already exist. A script can add logic that never existed in the base game at all — a new ability, a new game mode, an entirely new system — all without touching a single line of the compiled engine. Studios that expose a scripting API (application programming interface — the specific set of functions and data a script is allowed to call) are making a deliberate choice to let modders build real new functionality, safely contained within limits the studio still controls.

Sandboxing

That containment matters because a script isn't given free rein over the player's computer. Games run mod scripts inside a sandbox — a restricted execution environment that only exposes the specific functions the API deliberately provides (spawn an item, deal damage, display a message) and blocks everything else (reading arbitrary files, making network requests, touching other running programs). A well-designed sandbox is what makes it safe for a studio to let untrusted, community-written scripts run inside its game at all.

Why it matters here Lesson 8's event hooks and Lesson 9's modding frameworks are both built entirely on top of what this lesson introduces: a scripting language the game already runs, and an API surface the studio has chosen to expose through it.
