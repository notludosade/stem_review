Choosing a Cloud Architecture for a Real App

Every lesson so far taught one decision in isolation: which compute model, which storage model, whether to use a queue. A real architecture is all of those decisions made together, for one actual workload — and the right combination changes completely depending on what that workload actually looks like.

← Unit 6, Lesson 18 Lesson 20 → Contents Glossary →

There is no single "correct" cloud architecture — only an architecture that fits a specific workload's traffic pattern, data shape, and reliability needs, or one that doesn't. This lesson doesn't introduce new services; it's about the judgment call of combining everything from Units 2 through 6 into one coherent design, and recognizing that the same set of building blocks produces a genuinely different architecture for a genuinely different workload.

The questions, in the order they matter

A working checklist Compute (Unit 2): Is the workload constant, spiky, or mostly idle? Storage (Unit 3): Whole files, database rows, or a shared filesystem — and how often is it actually touched? Networking (Unit 4): Does it serve the public internet, and does distance to users matter? Managed services (Unit 5): Is there a well-understood piece of infrastructure (a database, a queue) worth not building by hand? Scale and reliability (Unit 6): What does downtime actually cost, and does load change predictably or unpredictably? Answering these, in order, for a real workload turns "design an architecture" from a guess into a series of small, defensible decisions.

See how the answer changes with the workload

The same toolbox — compute, storage, networking, managed services, elasticity — produces three very different architectures below, depending only on what's actually being built.

Interactive: matching architecture to workload

Shape: unpredictable public uploads, global users, media files, read far more than written.

  • Compute: containers in an auto scaling group for the API tier; a serverless function to generate thumbnails on upload.
  • Storage: object storage for photos, with a lifecycle policy moving rarely-viewed ones to a cold tier.
  • Networking: a CDN in front of the photo storage for fast delivery worldwide; a load balancer in front of the API tier.
  • Reliability: multi-AZ deployment for the API tier; object storage's built-in high durability covers the photos themselves.

Shape: internal-only, bursts of activity a few times a day, long idle stretches in between.

  • Compute: a serverless function — scale-to-zero is close to free during the long idle stretches, and cold starts are an acceptable tradeoff for internal, non-latency-critical traffic.
  • Storage: minimal; a managed queue buffers each burst so downstream systems process it at their own pace.
  • Networking: stays inside a private subnet — it's internal-only, so no public route or CDN is needed.
  • Reliability: the queue itself is the resilience story here — a burst just makes the queue longer, not a crashed system.

Shape: constant, moderate, predictable transactional load; correctness and durability matter enormously.

  • Compute: a modestly sized, steady fleet — elasticity's aggressive scaling matters less when load barely changes hour to hour.
  • Storage: a managed database on block storage, chosen specifically for low-latency, small, transactional reads and writes.
  • Networking: the database sits in a private subnet, reachable only from the app tier in a public subnet behind a load balancer.
  • Reliability: the managed database's automatic failover to a standby, plus a multi-AZ app tier — downtime here has a real business cost.
Why copying another company's architecture is a common mistake A widely publicized architecture diagram from a huge streaming company solves problems that huge streaming company actually has — massive global scale, extreme personalization, a specific cost structure. Copying it wholesale for a five-person startup's internal tool imports all of that complexity without any of the reasons for it: more services to operate, more failure modes to design around, and often a larger bill for capacity nobody needs yet. The right process is always the checklist above, applied honestly to the actual workload in front of you — not a template borrowed from a company solving a different problem at a different scale.

Matching compute model to traffic pattern — spiky and idle vs. steady and predictable — is exactly the judgment call this lesson is about.

2. In the photo-sharing app scenario, why does a CDN make sense in front of the photo storage, but not in front of the internal API scenario's traffic?

A CDN earns its keep on public, cacheable, globally-distributed content — not on private, internal-only traffic.

3. Why is copying a huge streaming company's public architecture diagram risky for a five-person startup's internal tool?

An architecture should fit the actual workload's needs — borrowing one built for a different scale and problem imports cost and complexity without the matching benefit.
