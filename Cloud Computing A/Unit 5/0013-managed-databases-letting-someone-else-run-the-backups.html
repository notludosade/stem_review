Managed Databases — Letting Someone Else Run the Backups

You could install a database on a VM yourself and manage every part of it. Almost nobody chooses to anymore — and this unit is about why "managed" versions of common software became the default.

← Unit 4, Lesson 12 Lesson 14 → Contents Glossary →

Nothing in Units 2 through 4 stops you from renting a plain VM (Lesson 4), installing a database engine on it yourself, and managing it exactly the way you would on-prem. Plenty of teams do. But a database has an unusually long list of ongoing chores — patching, backups, replication, failover — and most of that list has nothing to do with the actual business problem a team is trying to solve. Managed services exist to take that list away.

What a managed database actually changes

Definition A managed database (sometimes called Database as a Service, or DBaaS — Amazon RDS, Google Cloud SQL, Azure Database are examples) is a database engine the provider installs, patches, backs up, and monitors on your behalf, on infrastructure you never directly touch. You still design your schema, write your queries, and tune performance — the database itself works exactly like the one you'd run yourself — but the operational upkeep around it is the provider's job, not yours.
Worked example: self-managed vs. managed, side by side Running a database on a self-managed VM means personally scheduling nightly backups (and testing that they actually restore correctly), watching for the database engine's next security patch and applying it without breaking anything in production, and building your own failover plan for when the VM crashes at 3 a.m. Running the same database as a managed service means the provider takes automatic backups on a schedule you configure, applies patches during a maintenance window you choose, and — depending on the tier — automatically fails over to a standby copy if the primary crashes, often within seconds, with no engineer paged at all.
Why this is the shared responsibility model, applied to one specific piece of software This is the exact same line Lesson 2 drew for IaaS vs. PaaS vs. SaaS, just applied to a database specifically instead of the whole stack. A self-managed database on a VM is closer to IaaS: you own everything above the hypervisor, including the database engine's patches and backups. A managed database moves the operating system, the database engine's installation, and its operational upkeep onto the provider's side of the line — much closer to PaaS — while your schema design, queries, and data remain entirely yours, the same way they would under any service model.
The tradeoff, honestly stated A managed database is usually more expensive per hour than the equivalent raw VM, and it takes away some low-level control — you typically can't SSH into the machine running it, install arbitrary extensions, or tune every obscure configuration flag. For most teams, the operational time saved is worth the premium and the reduced control. For a small number of highly specialized, unusual, or extremely cost-sensitive workloads, self-managing is still the right call — this is a real tradeoff, not a strictly dominant choice.
