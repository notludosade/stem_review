Choosing the Right Storage for the Job

Lessons 7 and 8 gave you the vocabulary — storage model, durability, availability. This lesson puts it together into an actual decision, plus one more variable: how often the data even gets touched.

← Lesson 8 Unit 4, Lesson 10 → Contents Glossary →

Real storage decisions aren't made in a vacuum — they're made against an actual workload, with a real access pattern and a real budget. This lesson walks through the questions worth asking, in order, and introduces the last major lever: how frequently data is actually accessed, which turns out to be one of the biggest cost knobs in all of cloud storage.

Question 1: what's the access pattern?

This is Lesson 7's question, and it comes first because it usually narrows the choice down immediately. Is the data read/written as whole files by many clients over the internet (object)? Does it need low-latency, small, random reads and writes from one machine (block)? Does it need to be a shared filesystem mounted by many machines at once (file)?

Question 2: how much durability and availability does it actually need?

This is Lesson 8's question. Not every dataset deserves eleven 9s of durability or five-nines availability — those guarantees cost real engineering effort and money. A cache that can be rebuilt from a database in seconds doesn't need the same durability guarantee as the only copy of a company's financial records.

Question 3: how often is the data actually accessed?

Definition Cloud storage services commonly offer multiple storage tiers (or storage classes) for the same underlying model — trading retrieval speed for cost. A "hot" tier keeps data instantly accessible at a higher price per gigabyte; a "cold" or "archive" tier costs a small fraction as much per gigabyte, but retrieving a file can take from minutes to hours instead of milliseconds. The data doesn't change model (it might stay in object storage the whole time) — only which tier of that model it lives in.
Worked example: a video streaming service A newly uploaded video gets watched heavily in its first week, so it sits in object storage's standard, instantly-retrievable tier. Six months later, almost nobody watches it — but deleting it isn't an option, since a handful of viewers still might. Moving it to a cold archive tier cuts its storage cost dramatically, at the price of a multi-minute delay the rare viewer experiences before the video plays. A lifecycle policy — a rule the storage service enforces automatically, like "move any object untouched for 90 days to the archive tier" — makes this transition happen without an engineer manually tracking every file's access pattern by hand.

Putting it together

ScenarioModelTier
User profile photos, viewed constantlyObjectHot / standard
Seven-year-old compliance backups, almost never openedObjectCold / archive
A production database's live data filesBlockN/A — always hot by nature
A shared media library read by 30 render serversFileHot / standard
Why this three-question framework beats guessing Skipping straight to "which service has the cheapest price per gigabyte" without asking these three questions in order is how teams end up with a slow database on the wrong storage model, or a storage bill three times higher than necessary because nothing ever gets moved to a cheaper tier. Access pattern narrows the model; required durability and availability narrow the guarantee level; access frequency narrows the tier and the price. Answer all three, in that order, and the right choice is usually obvious rather than a guess.

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the purpose of a storage tier (like "hot" vs. "cold" or "archive")?

Tiers trade access speed for price within one storage model — they don't change the underlying model or automatically delete anything.

2. In the video streaming example, why does moving an old, rarely-watched video to a cold archive tier make sense instead of deleting it?

Archiving keeps rarely-needed data available at much lower cost, accepting slower retrieval as the tradeoff — a middle ground between paying full price and deleting it outright.

3. Why is a lifecycle policy useful for managing storage tiers?

Lifecycle policies automate tier transitions based on rules like "untouched for 90 days," removing the need for manual tracking.

4. Fill in the blank: within the same storage model, a "hot" or "cold" option trading retrieval speed for cost per gigabyte is called a storage ___.

Storage tiers let the same model (like object storage) offer different price/speed tradeoffs for the same data.

5. Fill in the blank: an automated rule, such as "move any object untouched for 90 days to the archive tier," is called a ___ policy.

Lifecycle policies automate the tier-migration decision instead of requiring manual tracking of every object's access pattern.
