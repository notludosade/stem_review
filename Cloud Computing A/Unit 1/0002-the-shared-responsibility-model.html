The Shared Responsibility Model

Moving to the cloud doesn't mean the provider handles everything. It means you and the provider draw a line, and everything on your side of it is still entirely your problem.

← Lesson 1 Lesson 3 → Contents Glossary →

A dangerously common misconception among people new to the cloud is that "the cloud" means security and reliability become someone else's job entirely. They don't. What changes is which layers are someone else's job. Get this wrong and you'll ship a database with no password, assume "the cloud" backed it up for you, and find out otherwise during an outage.

The line: security "of" the cloud vs. security "in" the cloud

Definition The shared responsibility model splits every task involved in running a system into two buckets: the provider is responsible for the security and reliability of the cloud — the physical data centers, the underlying hardware, the network backbone, and (depending on the service) the virtualization layer. The customer is responsible for security and correctness in the cloud — everything they configure, deploy, and run on top of that foundation: their operating system patches, their application code, their access permissions, and their own data.
Worked example A provider's data center burns down — that's the provider's problem; they've already built redundant facilities elsewhere and your workload keeps running (Unit 6 covers exactly how). A developer leaves a database open to the entire internet with no password — that's entirely the customer's problem; the provider correctly gave them a fully configurable database and the customer configured it insecurely. Both are "cloud" failures in a loose sense, but only one of them is the provider's fault.

Where the line falls depends on the service model

The shared responsibility line isn't fixed — it slides depending on how much of the stack the provider manages for you. The more the provider manages, the less you have to, but the less control you have. Try the tabs below to see how the split changes.

Definitions IaaS (Infrastructure as a Service) rents you raw virtual machines and networking — you still install and patch the operating system yourself (Lesson 4 covers this in depth). PaaS (Platform as a Service) additionally manages the operating system and runtime for you — you just deploy your application code. SaaS (Software as a Service) is a complete, ready-to-use application — you only manage your own data and account configuration inside it. Gmail is SaaS; a virtual machine you rent and configure yourself is IaaS; a platform where you push code and it runs without you touching a server is PaaS.
Why this matters more than it looks like it should Every real security incident involving "the cloud" that makes the news is almost always a shared responsibility failure on the customer's side of the line — an exposed storage bucket, an unpatched application dependency, an overly broad access permission — not a failure of the provider's physical data center. Understanding exactly where the line sits for whatever service you're using is the single most important habit this unit can give you, because assuming the provider handles something it doesn't is how real breaches happen.

Check your recall

No peeking back up — answer from memory first, then check.

1. Under the shared responsibility model, who is responsible for the physical security of a cloud provider's data center building?

Physical facilities and hardware are always the provider's responsibility, regardless of service model.

2. A developer using an IaaS virtual machine forgets to install a critical operating system security patch, and the machine is compromised. Whose failure is this under the shared responsibility model?

IaaS leaves OS management, including patching, on the customer's side of the line.

3. Moving from IaaS to PaaS to SaaS generally does what to the customer's share of responsibility?

The customer's slice shrinks moving from IaaS to SaaS, but some responsibility — at minimum for their own data and account access — always remains.

4. Fill in the blank: the service model where the provider manages the operating system and runtime, and the customer just deploys application code, is called ___.

PaaS sits between IaaS (customer manages the OS) and SaaS (customer manages neither OS nor application) on the shared responsibility spectrum.

5. Fill in the blank: the framework that splits every task into "the provider's job" and "the customer's job," with the exact split depending on the service model in use, is called the ___.

This is the exact term providers themselves use to describe the split.
