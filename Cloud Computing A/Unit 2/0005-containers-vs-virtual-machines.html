Containers vs. Virtual Machines

A VM gives an application its own entire operating system. A container gives it almost as much isolation for a fraction of the overhead — by sharing the one thing a VM insists on duplicating.

← Lesson 4 Lesson 6 → Contents Glossary →

Lesson 4's VM gives an application a completely isolated, full operating system to run in — which is powerful, but expensive: every single VM boots and runs its own copy of a guest operating system, with all the memory and startup time that implies, even if ten VMs on the same host are all running the exact same Linux distribution. Containers ask a pointed question: if every workload is already running the same OS anyway, why duplicate it?

What a container actually is

Definition A container is an isolated, packaged unit containing an application and everything it needs to run (code, libraries, dependencies) — but, unlike a VM, it shares the host machine's operating system kernel instead of running its own. A container engine (Docker is the best-known) enforces isolation between containers at the process level: each container sees only its own filesystem and processes, even though they're all ultimately processes running on one shared OS kernel underneath.

Each workload you add gives the VM host a full new guest OS to boot and hold in memory. The container host just adds one more process sharing the OS it already has running.

Worked example A host runs four small workloads. As four VMs, that's four separate guest operating systems booted, patched, and held in memory — commonly hundreds of megabytes to a few gigabytes of pure OS overhead each, before the application itself uses a single byte. As four containers on one shared host OS, there's exactly one operating system running, and each workload adds only its own application process and files — typically megabytes, not gigabytes, of added overhead per workload.
Why containers start in milliseconds and VMs start in tens of seconds Starting a VM means booting an entire operating system from scratch — the same slow process as turning on a physical computer, just virtualized. Starting a container means asking an OS that's already running to start one more isolated process, which is a fast, lightweight operation the OS was already built to do quickly. That startup-time gap — tens of seconds versus tens or hundreds of milliseconds — is the single biggest reason containers, not VMs, became the default packaging format for modern application deployment, and it's the gap Lesson 6's serverless computing pushes to its logical extreme.
The tradeoff, honestly stated Containers aren't strictly better — they're a different isolation boundary. A VM's isolation is enforced by the hypervisor at the hardware level, which is a stronger, harder-to-breach boundary; a container's isolation is enforced by the shared OS kernel at the process level, which is lighter-weight but depends on that one kernel being correctly secured for every container running on it. Sensitive multi-tenant workloads sometimes still run inside a VM specifically for that stronger boundary — often with containers running inside that VM, combining both. (Deploying and orchestrating containers at scale — the tools and practices for running many containers together in production — is a deliberately deeper topic than this course covers; it's exactly what a follow-on DevOps course would pick up from here.)

Check your recall

No peeking back up — answer from memory first, then check.

1. What is the key architectural difference between a container and a virtual machine?

Sharing (container) versus duplicating (VM) the operating system is the defining architectural difference.

2. Why do containers typically start in milliseconds while VMs take tens of seconds?

Booting a full OS is inherently slower than starting one more process on an OS that's already booted.

3. Why might a sensitive multi-tenant workload still run inside a VM, even with containers being lighter-weight?

Stronger isolation is the specific tradeoff a VM offers in exchange for its heavier overhead.

4. Fill in the blank: what containers on the same host share, instead of each running their own copy, is the operating system ___.

The shared kernel is exactly what lets containers skip the overhead of a full duplicated OS.

5. Fill in the blank: the software (Docker being the best-known example) that enforces isolation between containers at the process level on a shared OS is called a ___.

The container engine is the software layer that manages and isolates containers, analogous to the hypervisor's role for VMs.
