Serverless — Paying Only for the Milliseconds You Use

A VM runs whether or not anyone's using it. A container is faster to start but still something you keep running. Serverless asks: what if nothing runs at all until the exact moment it's needed?

← Lesson 5 Unit 3, Lesson 7 → Contents Glossary →

Every VM in Lesson 4 and every container in Lesson 5 shares one trait: once started, it keeps running — and costing money — whether or not it's doing anything useful at that exact second. A web server handling one request a minute still occupies its full VM or container the other 59 seconds. Serverless computing removes that idle time from the bill entirely, by removing the always-on server from the picture altogether.

What "serverless" actually means (there are still servers)

Definition Serverless computing — most concretely, Function as a Service (FaaS), like AWS Lambda, Azure Functions, or Google Cloud Functions — lets a developer upload a single function's worth of code, without provisioning or managing any server, VM, or container themselves. The provider runs that code only when a triggering event happens (an API request, a file upload, a scheduled time), spins up just enough capacity to execute it, and then shuts it back down. There genuinely are servers running the code underneath — "serverless" describes the developer's experience of never having to think about them, not the actual absence of hardware.
Worked example A photo-sharing app needs to generate a thumbnail every time a user uploads a photo. As a serverless function, that resizing code sits completely dormant — and free — until an upload event triggers it. The provider spins up an execution environment, runs the function for the roughly 200 milliseconds it takes to resize the image, returns the result, and shuts the environment down. If uploads happen once a minute or a thousand times a second, the same code handles both cases automatically, and the bill is proportional to the actual milliseconds of execution — not to any server sitting idle between uploads.

Scale-to-zero and billing by the millisecond

Definition Scale-to-zero means capacity drops all the way to nothing — and costs nothing — when there's no work to do, in contrast to a VM or container that keeps running (and billing) at some baseline even at zero traffic. Serverless billing follows directly from this: instead of paying per hour a machine exists, you pay per invocation plus the actual execution time consumed, typically metered in milliseconds.
Why this is a fundamentally different economic bet, not just a smaller VM A workload that runs constantly at high, predictable volume is often cheaper on a VM or container you provision once and keep busy, because serverless's per-invocation pricing carries a premium for that on-demand convenience. But a workload that's spiky, unpredictable, or mostly idle — like the thumbnail generator, which might sit dormant for hours between uploads — is often dramatically cheaper serverless, because there's no idle VM burning money the other 23 hours and 59 minutes of the day it isn't needed. Choosing serverless is a bet about your workload's traffic shape, not a universal upgrade over Lessons 4 and 5.

The tradeoffs: cold starts and short-lived execution

Definition A cold start is the delay — often a few hundred milliseconds to a few seconds — a serverless function incurs the first time it runs after being idle, while the provider spins up a fresh execution environment for it. A function invoked constantly stays "warm" and skips this delay; one invoked rarely pays it on nearly every call. Serverless functions are also typically limited to short maximum execution times (commonly minutes, not hours) and don't preserve memory or state between separate invocations, which makes them a poor fit for long-running processes or workloads that need to hold large amounts of data in memory across requests.

These constraints are exactly why serverless doesn't replace VMs and containers outright — it's a third option, best suited to short, event-triggered, spiky workloads, sitting alongside the always-on flexibility of a VM and the lighter-weight-but-still-running nature of a container.

No peeking back up — answer from memory first, then check.

1. What does "serverless" actually mean, given that servers are still physically involved?

Servers still run the code — "serverless" describes not having to manage them, not their literal absence.

2. In the thumbnail-generator example, why is serverless likely cheaper than an always-on VM for this specific workload?

Serverless's economic advantage is specific to idle, spiky workloads — not a universal rule.

3. Why might a constantly busy, high-volume workload actually be cheaper on a provisioned VM than as a serverless function?

At high, constant utilization, a VM you're already paying for around the clock can beat serverless's per-invocation premium.

4. Fill in the blank: the extra delay a serverless function experiences the first time it runs after being idle, while a fresh execution environment spins up, is called a ___.

A cold start is avoided only when a function has been invoked recently enough to still have a warm environment ready.

5. Fill in the blank: capacity (and cost) dropping all the way to nothing when there's no work to do, rather than maintaining some baseline like an idle VM, is called ___.

Scale-to-zero is the property that makes serverless billing proportional to actual usage rather than uptime.
