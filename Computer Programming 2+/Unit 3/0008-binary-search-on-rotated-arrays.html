Binary Search Revisited on Rotated Arrays

CP2's binary search assumed a fully sorted array. This unit is about spotting when binary search still applies once that assumption gets bent.

← Lesson 7 Lesson 9 → Contents Glossary →

A rotated sorted array — like [4, 5, 6, 7, 0, 1, 2] — was sorted once, then some prefix was moved to the end. It's no longer sorted overall, so binary search's usual guarantee (everything left of the midpoint is smaller, everything right is larger) seems to break. The key realization: at least one half of the array, split at any midpoint, is still fully sorted — and that's enough information to decide which half to search.

The idea At each step, check which half — [left, mid] or [mid, right] — is sorted (compare its endpoints). Then check whether the target falls inside that sorted half's range. If it does, search there; if it doesn't, the target must be in the other half.
Python 
def search(nums, target):
    left, right = 0, len(nums) - 1
    while left <= right:
        mid = (left + right) // 2
        if nums[mid] == target:
            return mid
        if nums[left] <= nums[mid]:      # left half is sorted
            if nums[left] <= target < nums[mid]:
                right = mid - 1
            else:
                left = mid + 1
        else:                              # right half is sorted
            if nums[mid] < target <= nums[right]:
                left = mid + 1
            else:
                right = mid - 1
    return -1
Java 
int search(int[] nums, int target) {
    int left = 0, right = nums.length - 1;
    while (left <= right) {
        int mid = (left + right) / 2;
        if (nums[mid] == target) return mid;
        if (nums[left] <= nums[mid]) {          // left half is sorted
            if (nums[left] <= target && target < nums[mid]) right = mid - 1;
            else left = mid + 1;
        } else {                                  // right half is sorted
            if (nums[mid] < target && target <= nums[right]) left = mid + 1;
            else right = mid - 1;
        }
    }
    return -1;
}

Still O(log n) — the array size is still halved every step, just with one extra check per step to figure out which half is trustworthy. This is the pattern for the rest of the unit: binary search doesn't actually require a sorted array. It requires being able to eliminate half the remaining possibilities at every step, using whatever structure the problem provides.

Why it matters here Rotated-array search is the standard example interviewers use to test whether binary search is understood as an idea (repeatedly halving a search space using a decidable rule) rather than memorized as a formula for sorted arrays. Lessons 9 and 10 push that same idea further: onto answer spaces that were never an array at all, and onto arrays with duplicate values where a single target has multiple valid positions.

Check your recall

1. What key fact about a rotated sorted array makes binary search still applicable?

That guaranteed sorted half is exactly what makes it possible to decide which side to search next.

2. Once you know which half is sorted, how do you decide which half to search next?

If the target is within the sorted half's range, it must be there; otherwise it must be in the other half.

3. What is the time complexity of searching a rotated sorted array with this approach?

One extra comparison per step to identify the sorted half doesn't change the halving — still logarithmic.
