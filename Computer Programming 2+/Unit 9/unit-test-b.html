1. A closely related problem, Merge Intervals, sorts by start time instead of end time. Why doesn't this contradict the "sort by end time" rule used for interval scheduling?

Both problems reduce to "sort, then a single greedy pass" — they just sort by whichever endpoint their own correctness argument depends on.

2. Fill in the blank: proving a greedy choice is always safe often uses an ___ argument — showing swapping it for any other choice never does better.

This is the standard way to justify that a greedy algorithm is actually correct, not just fast.

3. Why doesn't the order in which numbers are XOR-ed together matter in the Single Number solution?

These two properties are what let a single running accumulator replace tracking every number's pair explicitly.

4. Fill in the blank: n & (n - 1) clears the lowest set bit of n — if the result is 0, n was a power of two; this expression uses the bitwise AND and subtraction operators together, a common ___ trick for working directly with a number's binary representation.

These tricks trade a data structure for a mathematical property of an operator.

5. A problem states n ≤ 15–20. What does that constraint most strongly suggest as a candidate approach?

A tiny n like this is often a deliberate hint that an exponential brute force over all subsets is fine.

6. For intervals = [[1,100],[11,22],[1,11],[2,12]], sorted by end time this becomes [[1,11],[2,12],[11,22],[1,100]]. Answer both parts:

(a) After keeping [1,11] (prev_end=11), what happens when [2,12] is checked?

(b) Fill in the blank: after also removing [1,100] (start 1 < prev_end 22), the total number of intervals removed is ___.

(a) [2,12] starts at 2, which is before prev_end=11 (the end of the last kept interval, [1,11]), so it overlaps and must be removed. (b) [11,22] is then kept (start 11 ≥ prev_end 11, prev_end becomes 22), but [1,100] starts at 1, well before prev_end=22, so it's also removed — for a total of 2 intervals removed.

7. Trace result = 0; for each num in [7, 3, 5, 3, 7]: result ^= num. Answer both parts:

(a) What is the value of result immediately after processing the third element (5)?

(b) Fill in the blank: continuing through the remaining elements (3 and 7), the final value of result — the single non-duplicated number — is ___.

(a) 0^7=7, 7^3=4, 4^5=1 — after three elements, result is 1. (b) Continuing: 1^3=2, then 2^7=5; the two 7's and two 3's each fully cancel via a^a=0, leaving only 5, the number with no pair.

8. A problem gives a large set of servers connected by cables, and repeatedly asks "are server X and server Y on the same network?" as cables are added one at a time. Answer both parts:

(a) Which pattern applies, and why not a fresh BFS/DFS on every query?

(b) Fill in the blank: this lesson organizes every pattern in the course by the ___ in a problem's description that points to it.

(a) "Are these already connected?" asked repeatedly is Lesson 21's exact signal for Union-Find — each query becomes a near-constant-time root comparison instead of a fresh traversal. (b) Lesson 33 organizes its entire table around this same idea: recognizing the signal, not memorizing individual problems, is the transferable skill.

9. For nums = [1, 2, 1, 2], k = 3, trace the prefix-sum algorithm. sumCounts starts as {0: 1}. Answer both parts:

(a) After processing the second element (2, prefix sum = 3), what is count, and what does sumCounts contain?

(b) Fill in the blank: after processing the remaining two elements, the final count of subarrays summing to 3 is ___.

(a) At the second element, prefix sum is 1+2=3; looking up prefix−k = 3−3 = 0 finds the initial {0: 1} entry once, so count becomes 1, and sumCounts is updated to {0: 1, 1: 1, 3: 1}. (b) The third element (prefix sum 4) finds one more match, and the fourth element (prefix sum 6) finds another, bringing the final count to 3 — matching the three length-2 subarrays that each sum to 3.

10. Applying the five-step framework's "brute force" step to Subarray Sum Equals K, answer both parts:

(a) What is the complexity of the direct nested-loop approach that checks every pair of start and end indices, extending each subarray sum from the previous end index rather than recomputing it from scratch?

(b) Fill in the blank: the initial sumCounts entry, {0: ___}, represents the empty prefix and is what lets a subarray starting at index 0 that already equals k be counted correctly.

(a) Checking every (start, end) pair is O(n²) once each subarray sum is extended incrementally from the previous end index rather than resummed from scratch (which would cost O(n³) instead). (b) Without this initial {0: 1} entry for the empty prefix, a match found immediately at index 0 would have nothing to pair against, undercounting the result.
