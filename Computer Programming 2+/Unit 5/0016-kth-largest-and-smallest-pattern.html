The Kth Largest / Smallest Pattern

Sorting the whole array to find one value is doing far more work than the question actually asked for.

← Lesson 15 Lesson 17 → Contents Glossary →

Problem: find the kth largest element in an unsorted array. Sorting the whole array first solves it in O(n log n), but that computes the full order of every element when only one position actually matters. A heap gets there in O(n log k) — and when k is small relative to n, that's a real, measurable improvement, not just a constant-factor tweak.

The idea Maintain a min-heap capped at size k. Push every element in; whenever the heap grows past size k, pop the smallest — discarding it, since it can't possibly be among the k largest once k larger elements are already being tracked. After processing everything, the heap's minimum (its top) is exactly the kth largest element overall.
Python 
import heapq

def find_kth_largest(nums, k):
    heap = []
    for num in nums:
        heapq.heappush(heap, num)
        if len(heap) > k:
            heapq.heappop(heap)     # discard the smallest tracked value
    return heap[0]                   # the minimum of the k largest is the kth largest
Java 
int findKthLargest(int[] nums, int k) {
    PriorityQueue<Integer> heap = new PriorityQueue<>();   // min-heap
    for (int num : nums) {
        heap.offer(num);
        if (heap.size() > k) heap.poll();   // discard the smallest tracked value
    }
    return heap.peek();
}
JavaScript 
// Reuses the MinHeap class introduced in Lesson 15
function findKthLargest(nums, k) {
  const heap = new MinHeap();
  for (const num of nums) {
    heap.push(num);
    if (heap.data.length > k) heap.pop();   // discard the smallest tracked value
  }
  return heap.data[0];
}
C++ 
int findKthLargest(std::vector<int>& nums, int k) {
    std::priority_queue<int, std::vector<int>, std::greater<int>> heap;
    for (int num : nums) {
        heap.push(num);
        if (heap.size() > k) heap.pop();   // discard the smallest tracked value
    }
    return heap.top();
}

Each of the n elements triggers at most one push and one pop, and because the heap never holds more than k + 1 elements, every one of those operations costs O(log k) instead of O(log n). Total: O(n log k). When k is a small constant (find the 3rd largest, say) this is effectively O(n) — dramatically better than sorting everything just to read off one position.

Why it matters here "Find the kth largest/smallest" and its close cousins — "find the k closest points," "find the k most frequent elements" (Lesson 17) — are among the most frequently asked interview questions specifically because they test whether a heap is reached for automatically instead of a full sort. There's also a quickselect approach that averages O(n) time by partitioning like quicksort, at the cost of worse worst-case behavior and no ability to process the array as a stream — worth knowing exists, but the heap approach here is the more broadly reusable skill.

Check your recall

1. Why is a min-heap used to find the kth largest element, rather than a max-heap?

Once the heap holds exactly the k largest values seen so far, its smallest member is the kth largest overall.

2. What is the overall time complexity of the heap-based approach?

All n elements are processed, but each push/pop costs only O(log k) since the heap is capped at size k.

3. Why does capping the heap at size k make each individual push or pop cheaper?

Heap push/pop cost is O(height), and a heap capped at size k has height O(log k) rather than O(log n).

4. Fill in the blank: whenever the heap grows past size k, the ___ value currently in the heap is popped and discarded.

It's safe to discard, since k values known to be larger are already being tracked.

5. Fill in the blank: an alternative approach that averages O(n) time by partitioning the array like quicksort is called ___.

It trades a better average case for a worse worst case and the inability to handle a data stream, unlike the heap approach.
