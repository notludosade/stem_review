Big-O in Practice: Time and Space Together

Computer Programming 2 introduced Big-O in isolation. Interviews and contests both expect you to read it off unfamiliar code on sight — and to weigh it against memory, not just speed.

← Lesson 1 Lesson 3 → Contents Glossary →

Reading complexity by inspection comes down to a small number of rules, applied consistently.

Rule 1 — sequential loops add, nested loops multiply Two separate loops over n items, one after the other, cost O(n) + O(n) = O(n). A loop inside another loop, each running n times, costs O(n) × O(n) = O(n²).
Rule 2 — only the fastest-growing term survives O(n² + n) is written as O(n²) — as n grows large, the n² term dominates so completely that the n term becomes irrelevant. Constants drop too: O(2n) is just O(n).

Recursive calls follow the same logic, just less visibly. A recursive function that makes one call per level, doing O(1) work besides the call, costs O(depth) — same as a loop. But naive recursive Fibonacci (from CP2's Unit 4) makes two calls per level, and those branches don't share work: that's roughly O(2ⁿ), which is why memoizing it mattered.

Space complexity uses the identical rules, but counts memory instead of steps — including memory a recursive call stack quietly uses. A recursive function with no extra data structures can still be O(n) in space, because each pending call sits on the call stack until it returns.

Python · O(n) time, O(n) space 
def sum_to(n):
    if n == 0:
        return 0
    return n + sum_to(n - 1)  # n pending calls sit on the stack
Java · O(n) time, O(n) space 
int sumTo(int n) {
    if (n == 0) return 0;
    return n + sumTo(n - 1); // n pending calls sit on the stack
}
JavaScript · O(n) time, O(n) space 
function sumTo(n) {
  if (n === 0) return 0;
  return n + sumTo(n - 1); // n pending calls sit on the stack
}
C++ · O(n) time, O(n) space 
int sumTo(int n) {
    if (n == 0) return 0;
    return n + sumTo(n - 1); // n pending calls sit on the stack
}

Rewriting the same function as a loop keeps O(n) time but drops space to O(1) — no call stack growth, just one running total. That's the space-time relationship this whole course leans on constantly: the same problem often has more than one correct complexity profile, and the right one depends on which resource is actually scarce. Lesson 1's hash map is the mirror image — it spent O(n) space to buy back time.

The competitive-programming reflex Contest problems publish constraints for exactly this reason: if n ≤ 20, an O(2ⁿ) brute force is expected to pass. If n ≤ 10⁵, only roughly O(n log n) or better will finish in time. If n ≤ 10⁹, even O(n) is too slow — the intended solution is O(log n) or O(1). Reading the constraint line first, before writing any code, tells you what complexity you're being asked to hit.

One more idea worth knowing by name: amortized complexity. Appending to a dynamic array (Python's list, Java's ArrayList, C++'s vector) is usually O(1), but occasionally the array is full and has to be resized and copied — O(n) for that one call. Averaged over many appends, the cost still works out to O(1) per append; that average is what "amortized O(1)" means, and it's why these structures are treated as constant-time in practice.

Check your recall

1. What is the combined time complexity of two separate, sequential loops over n items each?

O(n) + O(n) simplifies to O(n) — only nested loops multiply.

2. Why can a recursive function with no extra arrays still use O(n) space?

The call stack itself is memory — n pending calls means O(n) stack space, even with no other data structure in sight.

3. If a contest problem states n can be as large as 10⁹, what does that constraint signal about the required time complexity?

At n = 10⁹, even a single O(n) pass can be too slow within typical time limits — the constraint is a direct hint about intended complexity.

4. Fill in the blank: the technique of averaging an occasional expensive operation (like a dynamic array resize) over many cheap ones is called ___ analysis.

It's why dynamic-array append is treated as O(1) even though any single call might occasionally be O(n).

5. Fill in the blank: the input-size limits stated in a problem, which hint at the time complexity a correct solution needs, are called the problem's ___.
