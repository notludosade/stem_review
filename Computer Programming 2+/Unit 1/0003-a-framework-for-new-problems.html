A Repeatable Framework for New Problems

Every pattern in this course plugs into the same five-step process. Learn the process now, and every later unit is "which tool goes in step four."

← Lesson 2 Contents Glossary →

Whether the setting is an interview or a timed contest, the same five moves apply, in the same order, every time:

The framework 1. Clarify. Restate the problem, check the input range and constraints, ask about edge cases (empty input, duplicates, negative numbers).
2. Brute force. State the naive solution out loud, even if you won't fully write it — it proves you understand the problem and gives a correctness baseline.
3. Find the bottleneck. Name the specific repeated or wasted work the brute force does.
4. Pattern-match. Ask: does removing that bottleneck look like a two-pointer problem? A sliding window? A graph traversal? DP? (This is what the rest of the course builds — a library of answers to this exact question.)
5. Verify. Trace the optimized solution against the original example, then against edge cases from step 1, before considering it done.

Applied to Lesson 1's Two Sum: Clarify — exactly one answer exists, array isn't sorted. Brute force — check every pair, O(n²). Bottleneck — repeatedly re-scanning for a needed value. Pattern-match — "have I seen X?" is a hash-map lookup question. Verify — trace it against [2, 7, 11, 15], then against a two-element array and an array with a negative number.

Step 4 is where constraints from Lesson 2 pay off directly. If n is small (say, ≤ 20), an exponential brute force — trying every subset or every ordering — might genuinely be the intended solution, and reaching for something more complex would be wasted effort. If n is up to 10⁵ or more, the constraint is actively ruling out O(n²) and pointing toward O(n) or O(n log n).

Why it matters here An interviewer is grading the process as much as the final code — stating the brute force out loud before optimizing shows you understand the problem, rather than guessing at a clever trick. A contest judge only grades the final submission, but skipping straight to a "clever" idea without checking it against the brute force on a small example is exactly how subtle bugs slip through under time pressure. The five steps serve both audiences for the same reason: they force verification before commitment.

From here, every unit in this course adds entries to step 4's pattern library: two pointers and sliding windows (Unit 2), binary search on unsorted-looking problems (Unit 3), trees and graphs (Units 4 and 6), heaps (Unit 5), backtracking (Unit 7), dynamic programming (Unit 8), and greedy and bit tricks (Unit 9). Unit 9 closes by assembling all of them into a single reference — a cheat sheet for step 4 itself.

Check your recall

1. Why state the brute-force solution out loud in step 2, even when it clearly won't be fast enough?

A stated brute force is both a proof of understanding and something to check the optimized version against later.

2. If a problem states n can be as large as 20, what does that suggest?

A very small n is often a deliberate signal that an exponential-time approach is expected to pass.

3. What is the purpose of step 5, verifying against edge cases, in a contest setting where only the final answer is graded?

Without an interviewer to catch a misunderstanding, tracing against edge cases is the only safety net before submission.

4. Fill in the blank: step 3 of the framework asks you to name the specific repeated or wasted work the brute force does — its ___.

Naming it precisely is what makes step 4's pattern-matching possible.

5. Fill in the blank: the first step of the framework — restating the problem and checking constraints and edge cases before writing anything — is to ___.

Skipping this step is one of the most common causes of solving the wrong version of a problem.
