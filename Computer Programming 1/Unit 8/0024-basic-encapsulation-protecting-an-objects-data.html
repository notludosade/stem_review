Basic Encapsulation — Protecting an Object's Data

If any outside code can set a bank balance to whatever it wants, no method's rules can ever be trusted.

Contents Glossary →

Nothing so far has stopped outside code from reaching directly into an instance's data and changing it — buddy.name = "anything" works fine after Lesson 22. Encapsulation is the practice of restricting that direct access, forcing changes to go through methods that can enforce rules.

Python 
class BankAccount:
    def __init__(self, balance):
        self._balance = balance  # leading underscore: internal use only, by convention

    def deposit(self, amount):
        if amount > 0:
            self._balance += amount

    def get_balance(self):
        return self._balance
Java 
class BankAccount {
    private double balance; // enforced by the compiler

    BankAccount(double balance) { this.balance = balance; }

    void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    double getBalance() {
        return balance;
    }
}
JavaScript 
class BankAccount {
    #balance; // enforced private field (ES2022+)

    constructor(balance) { this.#balance = balance; }

    deposit(amount) {
        if (amount > 0) this.#balance += amount;
    }

    getBalance() {
        return this.#balance;
    }
}
C++ 
class BankAccount {
private:
    double balance; // enforced by the compiler — this is C++'s default anyway

public:
    BankAccount(double balance) : balance(balance) {}

    void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    double getBalance() {
        return balance;
    }
};

Java's private and C++'s private: (recall from Lesson 22 that this is actually C++'s default) are enforced by the compiler — code outside the class simply cannot reach balance at all, only through deposit() and getBalance(). JavaScript's #balance syntax is genuinely enforced too, a newer addition to the language. Python is the odd one out: the leading underscore in _balance is a convention signaling "internal, don't touch" — nothing in the language actually stops account._balance = -1000000 from outside. Python trusts the programmer to respect the underscore rather than enforcing it.

Because every change to balance is forced through deposit() in the three enforcing languages, that method can guarantee the balance never goes negative through a bad deposit, by checking amount > 0 before applying it. Bypass that method, and the guarantee is gone — which is exactly what encapsulation is designed to prevent.

Definition Encapsulation is bundling an object's data together with the methods that operate on it, and restricting direct outside access to that data. A member marked private is accessible only from within its own class — enforced by the compiler in Java and C++, enforced by the language in modern JavaScript's #fields, and only a naming convention in Python.
Why it matters here Encapsulation is what lets an object make guarantees about itself. A BankAccount whose balance can only change through deposit() can promise it will never go negative from a bad deposit — a promise that direct, unrestricted access would make impossible to keep.
